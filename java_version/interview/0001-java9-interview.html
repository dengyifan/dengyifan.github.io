面试官角度

JPMS 模块系统

Q1: 什么是 JPMS？它要解决什么问题？

参考答案：JPMS（Java Platform Module System）是 Java 9 引入的模块化系统，核心目标是解决类路径时代的三个根本问题：

  1. 可靠配置：类路径是扁平列表，无法在编译期或启动时验证依赖完整性。JPMS 用模块图在启动时解析依赖，缺失模块直接启动失败。
  2. 强封装：类路径时代 public 类只要在路径上就可访问。JPMS 中未 exports 的包即使类是 public 也无法跨模块访问。
  3. 可定制运行时：JDK 拆分为 90+ 模块，用 jlink 可以只打包应用需要的模块。
关键点：JPMS 不是语法糖，是平台级的依赖契约重构。回答时要强调“运行期契约”而非“构建期依赖”——这是和 Maven/Gradle 的本质区别。
Q2: 追问：exports 和 opens 有什么区别？为什么需要两个指令？

参考答案：exports 和 opens 控制两个不同生命周期的可见性：

指令控制什么生效时机典型场景
exports编译期访问（import / 引用）编译+运行公开 API 包
opens运行期反射访问（setAccessible）仅运行框架反射（Spring/Hibernate）

为什么需要两个：编译期可见不等于反射可达。一个包可以 exports 但不 opens——编译器允许你 import 类，但反射调用 setAccessible(true) 会抛 InaccessibleObjectException。这给了模块作者精细控制：公开 API 可以编译访问但禁止框架深度反射。

关键点：能说出“exports 控制编译期，opens 控制运行期反射”就抓住了本质。如果只说“都是开放包”则不得分。
Q3: 追问：写出模块图解析的伪代码，核心判断条件是什么？

参考答案：

// 伪代码：模块图解析
function resolveModules(rootModules, modulePath) {
    graph = new ModuleGraph();

    // 1. BFS 从根模块开始
    queue = new Queue(rootModules);
    while (!queue.isEmpty()) {
        module = queue.dequeue();
        if (graph.contains(module)) continue;
        graph.add(module);

        // 2. 遍历 module-info 中的 requires
        for (req in module.requires) {
            // 核心判断条件：目标模块是否在模块路径上？
            target = findModule(modulePath, req.name);
            if (target == null) {
                // 可靠配置：立即失败
                throw new FindException("Module not found: " + req.name);
            }
            // 核心判断条件：传递依赖
            if (req.isTransitive) {
                graph.addEdge(module, target, TRANSITIVE);
            } else {
                graph.addEdge(module, target, NORMAL);
            }
            queue.enqueue(target);
        }
    }

    // 3. 一致性检查
    checkCycles(graph);      // 循环依赖
    checkConflicts(graph);   // 版本冲突

    return graph;
}

核心判断条件：

  • findModule(path, name) == null → 立即抛 FindException（可靠配置）
  • req.isTransitive → 决定是否传递给依赖本模块的模块
  • graph.contains(module) → 去重，避免重复解析
关键点：能写出「依赖缺失时立即失败」和「transitive 的传递语义」就是掌握的核心。

Compact Strings

Q4: Compact Strings 是什么？为什么 Java 9 要引入它？

参考答案：Compact Strings 是 JEP 254 引入的优化，把 String 内部存储从 char[]（每字符 2 字节）改为 byte[] + coder：

  • 如果字符串全是 Latin-1 字符（0-255），用 1 字节/字符，coder = LATIN1(0)
  • 如果含非 Latin-1 字符，用 2 字节/字符，coder = UTF16(1)

引入原因：绝大多数实际字符串只包含 Latin-1 字符（URL、JSON key、日志、配置文件），但 Java 8 之前一律用 2 字节存储，一半内存被浪费。JDK 6 曾尝试 -XX:+UseCompressedStrings，但因每次操作需要解包导致性能下降，JDK 7 被移除。Java 9 的方案用 coder 分发到 StringLatin1/StringUTF16 静态方法，避免运行时转换。

关键点：必须提到「JDK 6 失败的历史」——这说明为什么 Java 9 的方案不同（coder 分发，无解包）。
Q5: 追问：length() 方法怎么实现的？为什么用位移而不是 if-else？

参考答案：

public int length() {
    return value.length >> coder;
}

coder 取值 0（LATIN1）或 1（UTF16）：

  • LATIN1：value.length >> 0 = 字节数 = 字符数
  • UTF16：value.length >> 1 = 字节数 / 2 = 字符数

用位移而非 if-else 的原因：length() 是极高频方法（字符串遍历、循环边界都用），if-else 会有分支预测开销。位移在 JIT 编译后通常是 2-3 条机器指令，无分支。这是用数据表示替代控制流的经典优化。

关键点：能说出「coder 只有 0/1，正好对应右移 0/1 位」和「避免分支预测」是关键。

G1 GC

Q6: 为什么 Java 9 用 G1 替代 CMS 作为默认 GC？

参考答案：CMS 有两个结构性缺陷，无法通过调参解决：

  1. 碎片化：CMS 用标记-清除，不移动对象。长时间运行后堆碎片化，大对象分配失败 → Concurrent Mode Failure → Full GC。
  2. 暂停不可预测：CMS 的暂停随堆大小和碎片程度波动，无法设定 -XX:MaxGCPauseMillis 目标。

G1 的设计优势：

  • Region 化堆布局，可动态调整各代大小
  • 标记-复制/整理，消除碎片
  • Mixed GC 优先回收垃圾最多的 Region（Garbage First），配合暂停目标动态决定回收量
  • 可设定 -XX:MaxGCPauseMillis 暂停目标
关键点：必须提到「碎片」和「暂停不可预测」两个词。只说「G1 更新更快」不得分。
Q7: 追问：G1 的 "Garbage First" 具体指什么？写出 Region 选择的伪代码。

参考答案："Garbage First" 指 Mixed GC 时优先回收垃圾比例最高的 Region。

// 伪代码：Mixed GC 的 Region 选择
function selectRegionsForMixedGC() {
    // 1. 并发标记阶段已标记哪些 Region 有活跃对象
    candidates = oldRegions.filter(r -> r.hasMarkedObjects());

    // 2. 按垃圾比例从高到低排序
    //    垃圾比例 = 已死对象大小 / Region 总大小
    candidates.sortBy(r -> r.deadRatio, DESC);

    // 3. 从垃圾最多的开始，累加暂停时间估计
    selected = [];
    totalPause = 0;
    for (region in candidates) {
        regionPause = estimateCopyTime(region);
        if (totalPause + regionPause > maxGCPauseMillis) {
            break;    // 达到暂停目标，停止
        }
        selected.add(region);
        totalPause += regionPause;
    }
    return selected;
}

核心判断条件：

  • r.deadRatio 排序 → 决定回收顺序
  • totalPause + regionPause > maxGCPauseMillis → 决定停止条件
关键点：能写出「按垃圾比例排序 + 暂停目标约束回收量」就是核心。这说明 G1 的动态权衡机制。

架构师角度

Q8: 一个已有的大型 Spring 应用要迁移到 JPMS，你会怎么规划？

参考答案：迁移决策应基于收益而非技术难度。

第一步：评估收益

  • 是否需要 jlink 定制运行时？（容器化部署时体积收益大）
  • 是否需要强封装保护内部 API？（多团队协作时有价值）
  • 如果都不是，迁移收益有限，建议暂缓。

第二步：分层迁移

  1. 依赖升级：Spring 5+、Hibernate 5.2+ 才支持 JPMS。
  2. 自动模块过渡：把 JAR 放到模块路径但暂不写 module-info。自动模块自动 requires 所有模块，可以让旧代码先跑起来。
  3. 逐模块迁移：从底层库开始，写 module-info.java，用 jdeps 分析依赖。
  4. 反射开放：为框架需要的包加 opens，或启动参数加 --add-opens。

第三步：回归验证

  • 用 jdeps --jdk-internals 检查是否用了 JDK 内部 API
  • 集成测试必须覆盖反射场景（Spring 依赖注入、Jackson 序列化）
关键点：能说出「自动模块过渡」和「反射 opens」两个关键点。直接说「全部重写 module-info」是错误答案。
Q9: 你的应用堆大小 2GB，延迟敏感，选 G1 还是 Parallel GC？为什么？

参考答案：需要看具体延迟目标。

场景推荐理由
延迟目标 100-200ms，可接受G1G1 在此区间表现好，Region 化管理降低碎片
延迟目标 <50msZGC（Java 11+）G1 无法稳定达到 <50ms，尤其堆 2GB 以上
吞吐优先，延迟不敏感Parallel GC2GB 小堆上 Parallel 吞吐更高，无 G1 的 RSet/写屏障开销
容器化，CPU 有限Parallel 或 SerialG1 的并发线程需要多核

关键分析：G1 在小堆（<4GB）上有额外开销：

  • RSet（记忆集）占堆约 5-10%
  • 写屏障每次引用赋值额外检查
  • 并发标记线程占用 CPU

如果应用吞吐优先且延迟不敏感，Parallel GC 在 2GB 堆上可能比 G1 快 10-20%。

关键点：不能简单说「G1 更好」，要说出「G1 在小堆上有额外开销，需权衡延迟目标和吞吐」。这是架构师的判断标准。
Q10: 用 jlink 能把运行时从 200MB 降到多少？有什么限制？

参考答案：典型应用可以降到 40-60MB（减少 70-80%）。

完整流程：

# 分析依赖
jdeps --module-path mods --module com.example.app

# 创建自定义运行时
jlink --module-path mods:$JAVA_HOME/jmods \
      --add-modules com.example.app \
      --output my-runtime \
      --strip-debug --compress 2 \
      --no-header-files --no-man-pages

# 结果：约 40-60MB（取决于应用模块复杂度）

限制：

  1. 依赖必须模块化：jlink 只处理模块路径上的模块。自动模块和未命名模块无法参与链接（自动模块可以，但有限制）。
  2. 动态加载限制：运行时无法加载链接时未包含的模块。用反射加载模块会失败。
  3. Java Agent 兼容性：某些 agent（如字节码增强）可能不兼容链接后的运行时。
  4. 库生态限制：依赖的第三方库如果没有 module-info，可能无法完全 jlink。
关键点：能说出「依赖必须模块化」和「运行时无法加载未链接的模块」两个限制。

代码审查者角度

Q11: 以下 module-info.java 有什么问题？
module com.example.app {
    requires java.base;
    requires java.sql;
    exports com.example.internal;
    opens com.example.api;
}

参考答案：

问题 1：exports 和 opens 用反了

  • exports com.example.internal：导出内部包，破坏了封装目的。内部包不应该 exports。
  • opens com.example.api：API 包不应该 opens，因为 API 通过编译期引用访问，不需要反射。
  • 正确写法：exports com.example.api; opens com.example.internal to framework.module;

问题 2：requires java.base 是冗余的

  • 所有模块隐式 requires java.base，显式声明是多余但无害。
  • 如果代码审查要求简洁，可以删除。

问题 3：缺少 transitive 声明

  • 如果 com.example.api 中暴露了 java.sql 的类型（如 public Connection getConnection()），则 java.sql 应该 requires transitive。否则调用方必须自己也 requires java.sql。
// 正确写法
module com.example.app {
    requires transitive java.sql;   // API 暴露 java.sql 类型时
    exports com.example.api;
    opens com.example.internal to com.fasterxml.jackson.databind;
}
关键点：能指出「exports 和 opens 用反」是核心。很多开发者以为「opens 就是更彻底的 exports」。
Q12: 以下代码在 Java 9 + JPMS 下有什么问题？
// 假设 com.example.framework 是命名模块
// com.example.app 也是命名模块
public class MyService {
    public void process() throws Exception {
        Class clazz = Class.forName("com.example.internal.SecretImpl");
        Object instance = clazz.getDeclaredConstructor().newInstance();
        Field field = clazz.getDeclaredField("secret");
        field.setAccessible(true);       // 问题在这里
        Object value = field.get(instance);
        System.out.println(value);
    }
}

参考答案：

问题 1：跨模块反射访问未 opens 的包

  • com.example.internal 如果不是 opens 状态，setAccessible(true) 会抛 InaccessibleObjectException。
  • 即使 com.example.internal 被 exports，也不足以支持反射——exports 只管编译期，opens 才管反射。

问题 2：Class.forName 的模块归属

  • 命名模块中 Class.forName("com.example.internal.SecretImpl") 会从当前模块的 ClassLoader 查找。如果 com.example.framework 是不同模块，可能找不到。
  • 正确写法：Class.forName(module, "com.example.internal.SecretImpl")

问题 3：应该通过 SPI 或公开 API 访问

  • 跨模块用反射访问内部实现违反了模块化设计的初衷。正确做法是通过 exports 的公开 API 或 uses/provides SPI 机制。
// 正确做法 1：通过公开 API
// module-info: exports com.example.api;
import com.example.api.SecretService;
SecretService service = new SecretServiceImpl();

// 正确做法 2：通过 SPI
// module-info: uses com.example.api.SecretService;
ServiceLoader<SecretService> loader = ServiceLoader.load(SecretService.class);
关键点：能指出「setAccessible 需要 opens 而非 exports」是关键。同时能建议「改用 SPI 或公开 API」体现架构意识。
Q13: 以下 G1 GC 配置有什么问题？
java -XX:+UseG1GC \
     -Xms512m -Xmx512m \
     -XX:MaxGCPauseMillis=20 \
     -XX:G1HeapRegionSize=1m \
     -XX:InitiatingHeapOccupancyPercent=80 \
     -jar app.jar

参考答案：

问题 1：MaxGCPauseMillis=20 过于激进

  • 20ms 暂停目标对 G1 来说很难稳定达到，尤其堆 512MB 有并发标记开销。
  • 目标设太小会导致每次 Mixed GC 只回收很少 Region，回收跟不上分配，最终触发 Full GC（长暂停）。
  • 建议：≥50ms，通常 100-200ms。

问题 2：G1HeapRegionSize=1m 太小

  • 512MB 堆 / 1MB Region = 512 个 Region，Region 数量太多，管理开销上升。
  • 更大问题是 Humongous 判定阈值 = Region 大小 / 2 = 512KB。任何 ≥512KB 的对象都变成 Humongous，碎片风险高。
  • 建议：让 G1 自动计算（512MB 堆通常 1-2MB Region），或明确设置为 2-4MB。

问题 3：InitiatingHeapOccupancyPercent=80 太高

  • 默认 45%。设 80% 意味着堆占用 80% 才启动并发标记。但并发标记需要时间，标记完成时堆可能已满，触发 Full GC。
  • 建议：保持默认 45%，或根据实际调整到 40-50%。
// 推荐配置
java -XX:+UseG1GC \
     -Xms512m -Xmx512m \
     -XX:MaxGCPauseMillis=100 \
     -XX:InitiatingHeapOccupancyPercent=45 \
     -jar app.jar
关键点：能指出「MaxGCPauseMillis 过小反而导致 Full GC」是核心。这是 G1 调优最常见的反直觉点。

故障排查者角度

Q14: 生产环境：G1 频繁 Full GC，暂停长达 3 秒。怎么排查？

参考答案：

第一步：开启详细 GC 日志

java -Xlog:gc*:file=gc.log:time,uptime,level,tags \
     -XX:+UseG1GC -jar app.jar

第二步：看日志找根因

日志关键词根因优化方向
Humongous大对象频繁分配增大 Region / 减少大对象
Concurrent Mode Failure并发标记未完成堆就满了降低 IHOP
Evacuation FailureYoung GC 时 Survivor 不足增大 Young 区 / 降低晋升阈值
To-space Exhausted复制目标 Region 不足增大堆 / 降低 Mixed GC 目标

第三步：针对性诊断

  • -Xlog:gc+heap=debug 看 Humongous 分配频率
  • -Xlog:gc+ergo=debug 看 G1 的启发式决策
  • jmap -histo:live <pid> 看大对象类型分布

第四步：降级与优化

  1. 短期：增大堆（-Xmx）缓解压力
  2. 中期：调整 -XX:InitiatingHeapOccupancyPercent=35 提前触发并发标记
  3. 中期：增大 -XX:G1HeapRegionSize=4m 降低 Humongous 概率
  4. 长期：代码层面减少大对象分配（分页、流式处理）
关键点：能说出「先看 gc.log 找根因」而不是「直接调参数」。诊断路径比答案更重要。
Q15: 生产环境：Spring 应用升级到 Java 9 后启动失败，报 InaccessibleObjectException。怎么排查？

参考答案：

第一步：看异常信息

java.lang.reflect.InaccessibleObjectException:
Unable to make field private final java.lang.String
java.lang.String.value accessible:
module java.base does not "opens java.lang" to unnamed module @1234abcd

异常信息告诉你三件事：

  • 访问的字段：java.lang.String.value
  • 被访问模块：java.base
  • 调用方模块：unnamed module（类路径代码）

第二步：判断问题类型

异常信息问题类型解决方案
module X does not "opens pkg"反射访问未 opens 的包加 --add-opens X/pkg=ALL-UNNAMED
module X does not "exports pkg"编译期访问未 exports 的包改用公开 API 或加 --add-exports
package X is not visible依赖缺失检查 module-info 的 requires

第三步：定位是哪个框架在反射

  • 异常栈会显示调用方类。常见：Spring、Hibernate、Jackson、CGLIB。
  • 如果是 Spring，检查 Spring 版本（需要 5+ 才支持 Java 9）。

第四步：修复

  1. 首选：升级框架版本，让框架自己声明 opens。
  2. 次选：在自己模块的 module-info 加 opens。
  3. 兜底：启动参数加 --add-opens java.base/java.lang=ALL-UNNAMED。
# 兜底启动参数示例
java --add-opens java.base/java.lang=ALL-UNNAMED \
     --add-opens java.base/java.util=ALL-UNNAMED \
     --add-opens java.base/java.lang.reflect=ALL-UNNAMED \
     -jar app.jar
关键点：能读懂异常信息中「which module / which package / which target」三要素，并选择正确的解决方案（opens vs exports vs add-opens）。
