var 类型推断（4 题）

面试官角度

Q1: var 是关键字吗？它改变了 Java 的静态类型系统吗？

var 是保留类型名（reserved type name），不是关键字。它没有改变 Java 的静态类型本质——变量在编译后仍有确定的静态类型。var 是 100% 的编译期语法糖，字节码中不存在 var。

区分「保留类型名」与「关键字」：var 不能用作类名，但可以用作变量名和方法名。
Q2: 追问 — var 为什么不能用于方法参数和字段？

方法参数和字段是接口契约的一部分。调用方和子类需要看到稳定的类型声明，而 var 的推断结果是编译器内部决定的，对调用方不可见。JEP 286 的设计原则是「局部性」——var 只影响变量声明所在的局部作用域。

「局部性」是 var 设计的第一原则。
Q3: 追问 — 写出 var 推断的核心伪代码，什么情况下会编译失败？
function processVarDeclaration(node):
    if node.vartype != null: return  // 显式类型
    if node.init == null:
        error("var requires initializer"); return
    inferredType = attribExpr(node.init, Type.noType)
    if inferredType.isErroneous():
        error("cannot infer type"); return
    node.vartype = inferredType

编译失败的情况：(1) 无初始化表达式；(2) 初始化表达式是 poly expression（数组初始化器、lambda），无法独立推导类型。

poly expression 是 var 拒绝的核心场景。
Q4: 代码审查 — 以下代码有什么问题？
var result = service.process(input);
// ... 50 行之后 ...
return result.getData();

问题：result 的类型对读者不可见。50 行之后，读者无法通过类型声明判断 result 是什么，只能回溯到第 1 行去查看 service.process 的返回类型。建议：当变量跨越多行使用时，显式声明类型。

var 的可读性风险：跨行使用时应显式声明。

不可变集合 API（4 题）

面试官角度

Q1: List.copyOf() 和 Collections.unmodifiableList() 有什么区别？

三个核心区别：(1) 副本 vs 视图——copyOf 创建独立副本，原列表修改不影响；unmodifiableList 是视图，原列表修改会影响。(2) null 处理——copyOf 拒绝 null，unmodifiableList 允许。(3) 幂等性——copyOf 传入不可变集合时直接返回原引用。

防御性编程用 copyOf，只读视图用 unmodifiableList。
Q2: 追问 — copyOf 为什么设计成幂等的？

幂等性避免多次防御性拷贝的开销。在方法链中每层都调用 copyOf() 时，传入的如果是不可变集合，后续调用零成本。这是「零成本防御」设计哲学——鼓励开发者在不牺牲性能的前提下防御性编程。

幂等性是防御性编程性能友好的关键。
Q3: 追问 — Collectors.toUnmodifiableList() 的累加器类型是什么？为什么？

累加器是 ArrayList（可变），最终通过 listFromTrustedArray 转为不可变列表。如果累加器本身是不可变类型，每次 add 都要创建新对象，导致 O(n²) 复杂度。

Stream Collector 的通用模式：收集用可变，结果用不可变。
Q4: 故障排查 — 生产环境出现 List.copyOf 抛 NullPointerException，怎么排查？

排查步骤：(1) 确认入参集合是否包含 null 元素——copyOf 拒绝 null，unmodifiableList 不拒绝；(2) 检查数据来源——上游是否有 null 值注入；(3) 如果确实需要允许 null，改用 Collections.unmodifiableList(new ArrayList<>(input))。

copyOf 的 null 拒绝是设计选择，不是 bug。排查时首先检查数据源。

AppCDS（3 题）

Q1: AppCDS 为什么能减少内存占用？

归档文件被 mmap 为只读映射。操作系统对同一文件的只读 mmap 在不同进程间共享物理页——多个 JVM 进程看到的归档内容映射到同一块物理内存。类元数据只在内存中保留一份。

共享的是物理内存页，不是虚拟地址空间。
Q2: 追问 — JDK 升级后 AppCDS 归档会怎样？

JVM 启动时检查归档的 JDK 版本。不匹配时静默忽略，回退到文件系统加载。不报错，但加速效果消失。这是生产环境最易踩的坑——升级 JDK 后必须重新生成归档。

静默回退保证兼容性，但需要监控启动时间来发现。
Q3: 架构师角度 — 在 K8s 中如何设计 AppCDS 方案？

(1) 在 Docker 镜像构建阶段生成 AppCDS 归档（与运行时 JDK 版本一致）；(2) 归档文件作为只读层放入镜像；(3) 多个 Pod 的 JVM 进程 mmap 同一归档，共享物理内存；(4) 在 CI/CD 中验证归档版本匹配，避免静默失效。

AppCDS 在容器化场景的收益最大：启动时间 + 内存双优化。

G1 并行 Full GC（4 题）

Q1: Java 10 之前 G1 的 Full GC 为什么是单线程的？

历史原因。G1 从 CMS/Parallel GC 代码基础演进而来，Full GC 选择了更简单的串行算法——设计假设是「尽量避免 Full GC」。但实际生产中 Full GC 仍会发生，单线程成为严重瓶颈。Bazel 曾报告 JDK 9 下 G1 导致构建性能回退 30%。

不是设计失误，是优先级权衡。
Q2: 追问 — 并行化的核心改动是什么？

引入 G1FullCollector 替代 G1SerialFullCollector。四个阶段（标记、准备压缩、调整指针、压缩）全部通过 WorkGang 并行执行。关键入参：mark_bitmap 和 active_workers。

不是简单循环改并行，而是重新设计了任务划分和数据共享。
Q3: 追问 — 画出并行 Full GC 的阶段伪代码。
function fullGC():
    collector = new G1FullCollector(active_workers)
    collector.prepare_collection()
    workers.runTask(G1FullGCMarkTask)       // Phase 1
    workers.runTask(G1FullGCPrepareTask)    // Phase 2
    workers.runTask(G1FullGCAdjustTask)     // Phase 3
    workers.runTask(G1FullGCCompactTask)    // Phase 4
    collector.complete_collection()

四个阶段串行，每个阶段内部并行。

分阶段并行：阶段间串行，阶段内并行。
Q4: 故障排查 — Full GC 频繁触发，暂停时间仍然很长，怎么排查？

(1) 检查 GC 日志确认 Full GC 的触发原因（并发模式失败/晋升失败/疏散失败）；(2) 如果暂停时间仍长，检查引用处理阶段——该阶段可能仍是单线程；(3) 检查堆大小和 Region 大小配置；(4) 如果对象分配速率过高，考虑增大堆或优化对象生命周期。

并行 Full GC 优化了标记-压缩阶段，但引用处理仍是潜在瓶颈。

Thread-Local Handshakes 与 GC 接口（5 题）

Q1: Thread-Local Handshakes 解决了 Safepoint 的什么问题？

传统 Safepoint 需要所有线程停止。但偏向锁撤销、stack trace 获取等操作只需单个线程暂停。Thread-Local Handshakes 将全局轮询页改为每线程独立轮询页，VM Thread 只修改目标线程的标志，其他线程不受影响。

从「全体暂停」到「按需暂停」。
Q2: 追问 — HandshakeState 如何保证操作的唯一性？

通过信号量（Semaphore）序列化。VM Thread 和 JavaThread 通过 claim_handshake_for_vmthread() 和 process_self_inner() 竞争信号量，确保操作只被一方执行。

信号量确保「恰好一次」语义。
Q3: 追问 — 画出 Thread-Local Handshake 的执行伪代码。
function requestHandshake(targetThread, callback):
    op = new HandshakeOperation(callback)
    targetThread.handshake_state.set_operation(op)
    // 在 targetThread 的轮询页设置标志
    SafepointMechanism.arm_local_poll(targetThread)

// 目标线程在执行过程中轮询到标志
function targetThread.poll():
    if localPollArmed():
        if handshake_state.has_operation():
            // 尝试自己执行
            if handshake_state.process_self_inner():
                return  // 自己执行成功
            // 否则由 VM Thread 代为执行
轮询页是每线程独立的——这是「本地」握手的核心。
Q4: GC 接口（JEP 304）实际做了什么？

表面是代码整理，实质是架构解耦。将 GC 特定的屏障实现、诊断代码收敛到 CollectedHeap 接口和 GC 各自目录中。这直接使得 ZGC 和 Epsilon 能以较小侵入性落地。

JEP 304 是「基础设施投资」——为后续 GC 创新铺路。
Q5: 讲师角度 — 用大白话解释 Thread-Local Handshake 和全局 Safepoint 的区别。

想象一个教室。全局 Safepoint 是「全班同学起立」——老师要发通知，所有人都要站起来。Thread-Local Handshake 是「老师走到某个同学桌前单独说话」——其他同学继续做题，不受影响。很多操作其实只需要找一个人，却让全班起立，太浪费了。Handshake 就是「走过去悄悄说」。

类比记忆：「全班起立」vs「走到桌前单独说」。
