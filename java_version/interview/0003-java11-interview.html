语言与语法特性（4 题）

面试官角度

Q1: java HelloWorld.java 背后发生了什么？

JEP 330 为启动器新增第四种模式（source-file mode）。判定进入后，命令等价于 java -m jdk.compiler/<SourceLauncher> HelloWorld.java。SourceLauncher 读源文件 → 按白名单过滤编译选项 → 通过 MemoryFileManager 把 .class 写进内存 Map（不落盘）→ 用委托给 application class loader 的自定义 loader 加载首个顶层类 → 反射调用 main。全程在未命名模块中运行，等效 --add-modules=ALL-DEFAULT。

类文件不落盘；classpath 上的类看不到源文件里声明的类。
Q2: 追问 — 什么情况下必须显式写 --source？
  1. 文件名不以 .java 结尾——典型是 shebang 脚本（文件叫 hello、factorial）；
  2. 使用 --enable-preview 时；
  3. 想指定源码语言级别（同时作为 --release 生效）。

反过来，遵循 .java 命名规范的文件禁止用 #! 首行。shebang 要求 --source 紧跟在可执行文件名之后。

核心判定条件：是否出现 --source；「类名」位置是否命中一个存在的 .java 文件。
Q3: 代码审查 — 这段 Lambda 有什么问题？
(var x, y) -> x.process(y)
(var x, int y) -> x.process(y)
var x -> x.foo()

三个全部编译失败。JEP 323 规定：隐式类型的 Lambda 必须要么全 var、要么全不写；显式类型的 Lambda 必须全给类型，不能插 var；也不允许 var x -> expr 这种写法。允许的只有 (var x, var y) -> ...、(x, y) -> ...、(int x, int y) -> ... 和 (@Nonnull var x) -> ...。

「全有或全无」的动机：避免半显式类型冲击类型推断与重载决议。

故障排查者角度

Q4: 线上脚本 java worker 报「找不到主类」，但 java worker.java 正常，为什么？

因为没有 .java 后缀时不会进入 source-file 模式——启动器把它当 class 名解析，于是去找 worker.class（不存在）或 classpath 上的 worker 类。修复：要么写全 worker.java，要么显式 --source 11 强制 source 模式；若是 shebang 脚本，首行必须是 #!/path/to/java --source 11。

模式判定只看两件事：--source 是否出现、参数是否命中存在的 .java 文件。

HTTP Client（4 题）

面试官角度

Q5: JEP 321 做了什么？核心抽象是什么？

把 jdk.incubator.http（JDK 9 的 JEP 110、JDK 10 的 JEP 162）转正为标准模块 java.net.http。核心抽象：HttpClient（线程安全、可复用）、HttpRequest（不可变）、HttpResponse<T>，以及基于 java.util.concurrent.Flow 的 BodyHandler / BodyPublisher / BodySubscriber 三件套。同时提供同步 send、异步 sendAsync（返回 CompletableFuture）与 WebSocket API。

从 incubator 转正意味着包名稳定、可长期依赖。
Q6: 追问 — 说出必须背下来的四个默认值。
  1. followRedirects 默认 Redirect.NEVER，3xx 直接返回；
  2. version 默认 HTTP_2（HTTPS 走 ALPN，失败降级 1.1）；
  3. connectTimeout 默认无；
  4. HttpRequest.timeout() 默认无。

另外 executor 默认是内部执行器——回调里做重活会占用 client 的事件循环。

默认全部「关到位」是 JDK API 的一贯风格：最小惊讶，能力自己开。

架构师角度

Q7: java.net.http 和 OkHttp / Apache HttpClient 怎么选？

java.net.http 是标准的传输层 + 协议层实现：零依赖、HTTP/2 多路复用、WebSocket、TLS 1.3、Flow 背压。它不提供应用层能力：连接池精细调优、自动重试与熔断、拦截器链、Cookie 持久化。因此：只做标准 HTTP 调用 → JDK 实现；需要治理能力（重试/熔断/拦截器/会话）→ Apache HttpClient 5 / OkHttp；gRPC / QUIC → 两者都不行，另选栈。

选型的分界线是「协议实现」还是「应用治理」。

代码审查者角度

Q8: 审查以下代码，指出至少三个问题。
HttpResponse<String> call(String url) throws Exception {
    HttpClient c = HttpClient.newHttpClient();          // 1
    HttpRequest r = HttpRequest.newBuilder(URI.create(url)).GET().build();
    return c.send(r, BodyHandlers.ofString());          // 2 3
}
  1. 每次新建 client：连接池无法复用，TCP/TLS 握手开销翻倍，应全局单例复用；
  2. 没有请求超时与连接超时：慢接口会长期占住调用线程；
  3. 没有处理状态码：4xx/5xx 不抛异常，会被当成功返回；
  4. 隐式依赖 ofString() 的字符集解析——响应头没写 charset 就落 UTF-8，GBK 接口会乱码；
  5. 大响应体整包进堆，可能 OOM。
「HTTP 状态码不是异常」是最常被漏掉的一条。

String / Files / Collection API（4 题）

面试官角度

Q9: trim() 与 strip() 的区别？strip() 就一定更强吗？

判据不同：trim() 剥离所有 c <= ' ' 的字符（ASCII 空白）；strip() 以 Character.isWhitespace(int) 为准，能处理全角空格 \u3000、EM 空格 \u2003。不是「更强」而是「换判据」：两者都剥不掉不换行空格 \u00A0——isWhitespace 明确把非断行的 SPACE_SEPARATOR 排除在外。实测 "\u00A0x\u00A0".strip().length() == 3，"\u00A0".isBlank() == false。

网页抓取的文本常用 NBSP 排版，清洗时要先 replace('\u00A0',' ')。
Q10: 追问 — 写出 strip() 的边界扫描伪代码。
lo = 0; hi = len - 1
while lo <= hi && isWhitespace(codePointAt(lo)): lo++
while hi >= lo && isWhitespace(codePointAt(hi)): hi--
if lo == 0 && hi == len - 1: return this   # 无分配
if lo > hi: return ""
return substring(lo, hi + 1)

核心判断条件：Character.isWhitespace(codePoint)。三个细节：用 codePointAt 而非 charAt（代理对安全）；无可剥时返回原对象（不分配）；isBlank() 就是 indexOfNonWhitespace() == length()。另外，因为 Java 9 Compact Strings，方法体必须按 coder 分派到 StringLatin1 / StringUTF16 两套实现。

逐字符扫描的 String 方法都要双实现，否则会踩错字节边界。

代码审查者角度

Q11: 审查 Files.readString(path) 的使用。

源码只有两行：readAllBytes(path) + new String(ba, cs)。审查要点：

  1. 整文件进堆，大文件会 OOM——日志/CSV/大 JSON 必须改 Files.lines() 或 BufferedReader（且要关流）；
  2. 默认 UTF-8，非 UTF-8 文件直接抛 IOException（不是替换成 ?）；
  3. 同目录 writeString 不是原子写，中途失败会留下截断文件，关键数据要先写临时文件再 ATOMIC_MOVE；
  4. writeString 默认截断已有内容。
readString 是「便捷」不是「流式」。
Q12: toArray(new String[0]) 和 toArray(String[]::new) 差别在哪？

语义等价，但 IntFunction 版本（JDK 11 新增，Collection 默认方法）把「创建数组」的意图表达清楚了。接口的 @implSpec 规定默认实现是先用 0 调用生成器，再把结果交给 toArray(T[])。真正的价值是杜绝两类手写错误：new String[10] 这种定长数组（返回的往往不是你传的那个，且长度错时会 ArrayStoreException）；new String[c.size()] 在并发修改下的 ArrayStoreException。

生成器解决「数组怎么造」，不解决「快照语义」——并发修改仍会抛 CME。

ZGC 与 Epsilon GC（5 题）

面试官角度

Q13: ZGC 的停顿为什么与堆大小无关？

JEP 333 规定 STW 只限于根扫描，标记、重定位、重映射全部并发；根扫描规模只取决于线程栈与静态根，与堆中对象数量无关。改指针的工作不由 GC 统一做，而是由加载屏障在应用线程读到旧指针时当场修正，成本被摊到整个并发周期。核心机制是着色指针（4 bit 元数据：Marked0/Marked1/Remapped/Finalizable）+ 加载屏障。

目标：停顿 < 10ms（实测 avg 1.09ms vs G1 的 156ms），吞吐降幅 ≤ 15%。
Q14: 追问 — 写出加载屏障的伪代码，核心判断条件是什么？
function loadReferenceBarrier(ptr):
    if (ptr & ZAddressBadMask) == 0:   # 核心条件
        return ptr                     # 好指针，零成本放行
    newPtr = forward(ptr)              # 查转发表 / 取新地址
    store_back(newPtr)                 # heal：写回引用
    return newPtr

GoodMask/BadMask 是全局变量，每完成一个相位就整体翻转（ZGC 用 Marked0/Marked1 双缓冲标记位）。相位一变，全堆旧指针自动落进 BadMask——不需要任何全局扫描就能「标出」待处理引用，这是着色指针最精妙的地方。出处：src/hotspot/share/gc/z/zGlobals.hpp（openjdk/jdk11u）。

着色指针表达的是「指针的时效性」，不是「对象在哪」。
Q15: 追问 — Java 11 的 ZGC 有哪些实验性代价？
  1. 必须 -XX:+UnlockExperimentalVMOptions -XX:+UseZGC；
  2. 仅 Linux/x64；
  3. 不支持类卸载——ClassUnloading 被禁用且开启无效，动态生成类的场景会堆涨；
  4. 不支持 JVMCI/Graal，开 EnableJVMCI 直接报错；
  5. 单代实现（分代 ZGC 到 JDK 21 / JEP 439）；
  6. 着色指针需要预留大虚拟地址空间。
JDK 15（JEP 377）才转正 production，JDK 11 只适合灰度评估。

架构师角度

Q16: 为什么不给 G1 加并发压缩，而要另造 ZGC？

JEP 333 的 Alternatives 章节记录了这个决策：G1 的并发压缩原型经过大量验证后放弃，理由是「把从未为此目的设计的功能塞进 G1、同时还要保住其稳定性与其它优点，不可行」。CMS 路线也否决（不压缩、remark 阶段无界、代码复杂、已被 JEP 291 弃用）。剩下的并行方案是 Shenandoah 的 Brooks 指针（JEP 189）。架构原则：当核心机制与现有设计前提冲突时，新建成本低于改造成本。

ZGC 与 Shenandoah 是同一问题的两种解法：着色指针+加载屏障 vs Brooks 指针。

故障排查者角度

Q17: -XX:+UseEpsilonGC 开在生产上会发生什么？怎么发现？

Epsilon 只分配不回收，堆满即抛 OutOfMemoryError 并按配置 dump / 执行 -XX:OnOutOfMemoryError，没有任何降级路径，服务必然反复重启。发现手段：启动日志 [gc] Using Epsilon GC；jcmd <pid> GC.heap_info 显示堆只增不减；System.gc() 完全无反应（Epsilon 下它是 no-op，可能打印「徒劳」警告）。修复：换回 G1/ZGC，并检查是谁把 UseEpsilonGC 写进了启动脚本——它属于 experimental，必须同时有 UnlockExperimentalVMOptions。

Epsilon 是测试工具（基准测试/内存压力测试/短任务），不是生产 GC。
Q18: 代码审查 — 为什么这里的 repeat 要那样写？
if (Integer.MAX_VALUE / count < len) {
    throw new OutOfMemoryError("Required length exceeds implementation limit");
}

这是整数溢出的乘法前预检：如果写成 len * count > Integer.MAX_VALUE，乘法会先溢出成负数，判定失效。用除法判断是标准做法。JDK 源码同样有三道防线：负数抛 IllegalArgumentException、count == 1 返回 this、长度溢出抛 OutOfMemoryError。审查点：repeat 抛的是 OutOfMemoryError 而非 IllegalArgumentException，调用方的 catch 要接得住。

溢出预检必须发生在运算之前。

模块移除 · TLS 1.3 · Nashorn（4 题）

面试官角度

Q19: Java 11 删了哪些模块？为什么要删？

9 个：平台模块 java.xml.ws、java.xml.bind、java.activation、java.xml.ws.annotation、java.corba、java.transaction，聚合模块 java.se.ee，工具模块 jdk.xml.ws、jdk.xml.bind。同时删除工具：wsgen、wsimport、schemagen、xjc、idlj、orbd、servertool、tnamesrv，rmic 移除 -idl/-iiop。理由（JEP 320 原文）：Java SE 里是 EE 上游的快照+子集、裁剪成本高；Endorsed Standards Override 无人使用；Maven Central 有独立版本；CORBA 在现代 Java 中没有需求。例外：javax.transaction.xa 留在 java.sql，不受影响。

这些模块在 Java SE 9 已标记 forRemoval，11 是执行删除。

故障排查者角度

Q20: 升 11 后报 ClassNotFoundException: javax.xml.bind.JAXBContext，为什么 --add-modules 没用？

因为 JDK 9/10 是「模块存在但默认不解析」，可用 --add-modules java.xml.bind 激活；而 JDK 11 是「模块的类根本不在运行时镜像里」，JEP 320 明确写「没有任何命令行开关能启用它们」。--add-modules 只能解析已存在的模块。正确做法：把 javax.xml.bind:jaxb-api（API）+ com.sun.xml.bind:jaxb-ri（实现）作为普通依赖加到 classpath（不是 module path）。

9/10 是不解析，11 是不存在——量变到质变。
Q21: 追问 — 写出 JDK 11 升级编译失败的分类诊断伪代码。
if 类型 ∈ {javax.xml.bind, javax.xml.ws, javax.activation,
            javax.annotation, javax.transaction, javax.rmi, org.omg}:
    → JEP 320：加 Maven 依赖到 classpath
elif 类型 以 "sun.misc" / "jdk.internal" 开头:
    → jdeps --jdk-internals 定位；改公开 API 或 --add-exports
elif InaccessibleObjectException on setAccessible:
    → JDK 16+ 强封装：--add-opens 模块/包=ALL-UNNAMED
elif ScriptEngineManager.getEngineByName("js") == null:
    → Nashorn 已移除（JDK 15 / JEP 372）：换 GraalJS

核心判断条件是「报错包名属于哪一类」，它决定走「加依赖」「改代码」还是「改启动参数」三条完全不同的路。常见隐蔽迁移点：javax.xml.bind.DatatypeConverter 做 Base64 → 改用 java.util.Base64；javax.annotation.Generated → javax.annotation.processing.Generated。

先分类再修复，否则问题会反复横跳。

技术讲师角度

Q22: 用大白话解释 TLS 1.3 和 Nashorn 弃用分别意味着什么？

TLS 1.3：可以理解成「握手从两趟减到一趟」——以前建安全连接要来回两次，现在一次，恢复连接还能更快（0-RTT，但因为有重放攻击风险默认不开）；同时把一批老的不安全加密算法直接踢出默认配置。对我们的影响是要复查协议白名单，否则会出现 SSLHandshakeException。
Nashorn：JDK 自带的 JavaScript 引擎。JDK 11 只是贴了「即将删除」的标签并打印警告，真正拔掉是 JDK 15——之后 JDK 里没有任何 JS 引擎，用 ScriptEngineManager 取 "js" 会得到 null，要换 GraalJS。

弃用（11）≠ 移除（15）；「11 上能跑」不代表「以后能跑」。
