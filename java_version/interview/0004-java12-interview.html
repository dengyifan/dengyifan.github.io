Switch 表达式与预览特性（JEP 325）（5 题）

面试官角度

Q1: JEP 325 在 Java 12 里交付了什么？用一句话说清它「不是」什么。

交付的是 switch 作为表达式的预览形态：新增 case L -> 箭头标签（无 fall-through）、逗号多标签、用 break <value>; 从块中产出值。它「不是」正式特性——需要 javac --enable-preview --release 12 编译、java --enable-preview 运行，语义在 13（JEP 354，break → yield）还改过一次，14（JEP 361）才转正。

12 = break 值，13 = yield，14 = 正式——这条时间线是最高频考点。
Q2: 追问 — switch 表达式的两条硬规则是什么？违反了分别报什么？
  1. 穷尽性（exhaustive）：必须覆盖所有可能输入。enum 全覆盖时编译器可自动补 default，否则报 the switch expression does not cover all possible input values（javac compiler.properties not.exhaustive）。
  2. 完整性（每个分支给出值或抛异常）：箭头规则走完没给值报 switch rule completes without providing a value；break 缺值报 missing break value；整个 switch 正常落空报 switch expression completes normally；空体报 switch expression does not have any case clauses。

编译期还强制：禁止 return/continue/带标签 break 穿越表达式（illegal jump through a switch expression 相关错误）。

「穷尽性」管输入覆盖，「完整性」管每个分支的产出——两条都要背。

代码审查者角度

Q3: 审查 — 这段「Java 12 预览」代码为什么编译不过？
// javac --enable-preview --release 12
String r = switch (day) {
    case MONDAY, FRIDAY, SUNDAY -> {
        log(day);
        break day.name();          // 期望产出名字
    }
    case TUESDAY -> "T";
    default -> "other";
};

问题：break day.name() 违反 「value break 必须是紧邻的、未被嵌套结构切断的直接产物」——javac 对此的报错是 value break not supported in '{0}' / unexpected value break（Attr.java 的 BreakExprNotImmediate、BreakComplexValueNoSwitchExpression）。12 的规矩是：值 break 只能出现在箭头块的直接语句序列里，且该块不能把控制流「绕道」出去；块内局部变量也不会泄漏到其他分支（传统 : 形式会泄漏）。写成 break day.name().toUpperCase(); 这种表达式本身没问题，但把 log(day) 之后的值产出与跨块跳转混在一起就越界了。

审查清单：值 break 的位置、default 是否存在（enum 全覆盖除外）、有没有 return/continue 穿越。

故障排查者角度

Q4: 本地编译通过，部署后报 UnsupportedClassVersionError / preview 特性被拒，怎么排查？

九成是预览特性的版本锁定：预览 class 文件带有 preview 标记，运行 JVM 必须是编译时同一个启用了 preview 的版本。排查三步：

  1. 编译命令是否带 --enable-preview 且 --release 与运行 JDK 完全一致（--release 12 ↔ 运行 12）；
  2. 启动命令是否漏了 java --enable-preview（或容器里跑的是 11/13 的 JRE）；
  3. CI 是否用多版本矩阵——12 编译的 preview 类混进 11 的运行时一定炸。

修复：三处（编译、运行、镜像 JDK）锁成同一版本；治本是把开关收敛到构建脚本一处，业务代码干脆不进预览特性。

预览特性的故障几乎总是「版本三角」不一致：javac 版本 / --release / 运行 JVM。

架构师角度

Q5: 团队能不能在生产项目里用 switch 表达式？给决策框架。

分三档：① 主干/框架库——不用（语义无承诺，12 与 13 的产值语法不同，升级即改码）；② 锁定 JDK 12 的实验分支——可以，满足四个条件：开关只在构建脚本一处、编译运行同版本、CR 加「预览特性清单」项、升级时跑迁移检查（break 值 → yield）；③ 以 14+/17 为目标——先写成传统形式，等切到 14 再一次性转正语法。判断锚点：「预览特性是租来的，不是买到的」——任何用法都要保证一个版本内能整体回退。

决策看的不是语法好不好，而是「回退成本」与「版本停留时长」。

类库 API：teeing · 紧凑数字 · String（5 题）

面试官角度

Q6: Java 12 新增了哪些类库 API？挑三个讲原理。
  1. Collectors.teeing(other, merger)：把两条收集流水线的结果交给 merger 合并——内部用局部类 PairBox 同时持有两个下游的容器，每个元素喂两个 accumulator，并行时 combine 合并两对容器，最后 merger(finisher1(left), finisher2(right))。
  2. 紧凑数字：NumberFormat.getCompactNumberInstance(locale, Style.SHORT|LONG)，把 1234567 格式化为 123万 / 123 万（依 locale），实现类是 java.text.CompactNumberFormat。
  3. String.indent(n) / String.transform(f)：按行缩进（n>0 加前缀、n<0 去前缀、MIN_VALUE 相当于 stripLeading）与整串函数变换（就是 f.apply(this)）。

另有 Unicode 11.0 支持与日本新年号「令和」（java.time 新增 JapaneseEra.HEISEI 之外的令和识别）。

teeing 是「收集器的二元组合子」，与 reduce 的区别在保持两条独立下游的特性信息。
Q7: 追问 — 用伪代码写出 teeing0 的核心逻辑。
teeing0(c1, c2, merger):
    requireNonNull(c1); requireNonNull(c2); requireNonNull(merger)
    对 c1/c2 的 supplier/accumulator/combiner/finisher 逐个 requireNonNull（共 11 处）
    if CH_ID ⊆ chars(c1) or CH_ID ⊆ chars(c2):
        characteristics = {}                     # 任一侧无 identity finish → 整体去掉
    else:
        characteristics = chars(c1) ∩ chars(c2) - {IDENTITY_FINISH}

    class PairBox:
        left  = c1.supplier.get()
        right = c2.supplier.get()
        add(t):      c1.acc(left, t); c2.acc(right, t)     # 同一元素喂两个下游
        combine(o):  left = c1.comb(left, o.left); right = c2.comb(right, o.right)
        get():       return merger(c1.finish(left), c2.finish(right))
    return Collector(PairBox::new, PairBox::add, PairBox::combine, PairBox::get, characteristics)
去掉 IDENTITY_FINISH 是因为最终结果经过 merger，不再是下游容器本身。

故障排查者角度

Q8: 并行流下 teeing 的结果与串行不一致，为什么？

两点：① merger 必须满足交换律与结合律——并行时 PairBox 分片合并的顺序不确定，merger 若依赖顺序（如字符串拼接、减法）结果就会漂移；② 下游 1/2 各自的 accumulator/combiner 也要线程安全语义正确（JMH 容器本身按标准收集器约定分片）。排查方法：同数据集串/并行各跑 N 次对比；检查 merger 里有没有「减法、除法、依赖首次出现顺序的取舍」。修复：换成交换律安全的合并（加法、max/min、拼接改为先收集再排序）。

收集器契约（无序时交换律 + 结合律）在 teeing 里被「放大」到 merger 上。

代码审查者角度

Q9: 审查 — String.indent 的这三个用法对不对？
"a\nb".indent(2)             // → "  a\n  b\n"  尾部多一个 \n
"text".indent(0)             // → "text\n"     不是原样返回！
"  x".indent(Integer.MIN_VALUE)  // → 相当于 stripLeading()

三处坑：① indent 强制保证输出以换行结尾（内部用 joining("\n","","\n")），空串除外——拿它做「原样缩进」会平白多个换行；② indent(0) 不是 no-op，也会补尾换行；③ n == Integer.MIN_VALUE 因为取负会溢出，被特判为去前导空白。审查建议：对换行敏感的场景（拼 JSON、协议帧）改用手工逐行处理，或 indent 后 stripTrailing()。

「缩进 0 也加换行」是最反直觉的一条，来自实现的统一收尾逻辑。

技术讲师角度

Q10: 大白话解释 teeing 和紧凑数字分别解决什么问题？

teeing：以前想在一次遍历里既算总分又算平均分，要么遍历两遍、要么手写一个容器收集器。teeing 就是「一根水管分两头接，最后拿个三通把两股水合起来」——两个收集器各干各的，merger 负责合流，而且只遍历一次。
紧凑数字：报表里 1,234,567 要读半天，123万 一眼就懂——getCompactNumberInstance 按 locale 套用「万/亿」或「K/M/B」的单位规则，比自己除以 10000 再拼字符串省事，还能随 NumberFormat 体系换 locale。

teeing 省一次遍历，紧凑数字省一套手写单位换算。

JVM 常量 API 与常量池（JEP 334 / 309）（4 题）

面试官角度

Q11: JEP 334 交付了什么包？和 JEP 309 什么关系？

JDK 12 新增 java.lang.constant 包（注意：JEP 文本写的是 java.lang.invoke.constant，但 JDK 12 实际交付与 Oracle 12 API 文档均为 java.lang.constant），提供 ConstantDesc、Constable 双接口与 ClassDesc/MethodTypeDesc/MethodHandleDesc/DynamicConstantDesc 等描述符类。与 JEP 309 的关系：JEP 309（CONSTANT_Dynamic）随 JDK 11 交付了字节码层面的 CONSTANT_Dynamic 常量池项；JEP 334 交付的是它的 Java 语言 API 层——DynamicConstantDesc 让库代码能以类型安全方式描述并解析 CONDY，两层合起来才是「常量池可被 Java 程序读写」。

309 = 字节码（JDK 11），334 = API（JDK 12）；包名是 java.lang.constant，不是 …invoke.constant。
Q12: 追问 — 写出 ConstantDesc 的两段协议伪代码。
# 协议一：把运行时对象降维成"池里的描述"
obj.describeConstable() -> Optional<ConstantDesc>
    Class   → ClassDesc.ofDescriptor("Ljava/lang/String;")
    String/Integer/MethodHandle/MethodType/Enum → 各自的常量描述
    动态句柄/调用点/常量 → DynamicConstantDesc（含 bootstrap 方法 + 参数）

# 协议二：把描述还原成运行时值（逆向）
ConstantDesc.resolveConstantDesc(Lookup lookup) -> Object
    普通常量 → 直接返回字面值
    DynamicConstantDesc →
        校验 bsm：参数数 ≥ 2 且第 1 参是 MethodHandles.Lookup，否则 BootstrapMethodError
        args = [lookup, constantName, constantType] + [arg.resolveConstantDesc(lookup)...]
        bsm.invokeWithArguments(args)          # 即常量池 BSM 的 Java 版
        catch Throwable → 包成 BootstrapMethodError 抛出
describeConstable 是「写」，resolveConstantDesc 是「读+执行 BSM」——两者对称。

代码审查者角度

Q13: 审查 — 有人写 import java.lang.invoke.constant.ClassDesc;，对吗？

错。JDK 12 实际交付的包是 java.lang.constant（源码 src/java.base/share/classes/java/lang/constant/、Oracle 12 API 文档均可证），JEP 334 正文里的 java.lang.invoke.constant 是提案阶段的措辞。审查时还要注意两点：① 别把后续 JDK 的成员安到 12 头上——ModuleDesc/PackageDesc 在 jdk12u 该包不存在；② @since 12 的类型（ConstantDesc、ClassDesc、DynamicConstantDesc、VarHandleDesc、Style…）可以用，标注了更晚版本的成员不行——用本机 JDK 25 的 src.zip 对照行号时尤其要小心。

以「JDK 12 API 文档 + jdk12u 源码」为准，不以 JEP 草案措辞为准。

架构师角度

Q14: 常量 API 对框架作者有什么实际价值？

三类场景：① 字节码生成类库（ASM 替代品、序列化框架、LambdaMetafactory 周边）——以前拼常量池要手写字节数组/依赖内部 API，现在用 ClassDesc.ofDescriptor、MethodHandleDesc.ofStatic 这类类型安全的工厂；② 跨语言/跨类加载器的常量共享——CONDY 让「一次计算、按名字复用」的惰性常量可以被描述并传递；③ 可移植的元数据——Constable 让 Enum、String 等类型能自描述为池常量，利于模块化/镜像化场景下的元信息交换。本质价值：把常量池从「.class 文件的私有格式」升格为「公开的 Java API 模型」。

对普通业务代码无感，对「生成/操纵字节码」的框架是刚需。

GC 与运行时：Shenandoah · G1 · CDS（6 题）

面试官角度

Q15: JEP 189 Shenandoah 的核心机制是什么？怎么启用？

核心是并发疏散（concurrent evacuation）：移动对象不再占满 STW 暂停——给每个对象配一个间接指针（Brooks 指针，源码 shenandoahBrooksPointer.hpp，位移量为负的 HeapWord），应用线程在写屏障里完成对象疏散，标记与压缩全并发，STW 只扫描线程栈根。卖点：暂停时间与堆大小无关——200MB 与 200GB 的堆暂停量级一致，代价是吞吐与空间（间接指针 + 并发复制的临时双份）。启用：

java -XX:+UnlockExperimentalVMOptions -XX:+UseShenandoahGC ...   # 实验性，默认关

平台 aarch64 + amd64；JDK 15（JEP 379）才转正。

Brooks 指针（Shenandoah）vs 着色指针（ZGC）——同一问题（并发移动）的两种解。
Q16: 追问 — JEP 344 与 JEP 346 分别改了 G1 的什么？

JEP 344（可中断的混合回收）：把每次混合回收的 collection set 拆成 mandatory（不可增量，含 young 与部分 old，约 80%）与 optional（纯 old，约 20%）两段；optional 段按剩余时间余量增量推进，最细可到一次一个 region，启发式发现「预测总出错」才进入增量模式。只有额外 CPU 开销（称 <1%）与少量指针跟踪内存，无用户可见开关。

JEP 346（及时归还空闲内存）：空闲期周期性 GC 后按 Min/MaxHeapFreeRatio 与 Xms/Xmx uncommit 内存。触发需同时满足：距上次暂停超过 G1PeriodicGCInterval 毫秒（默认 0 = 关闭，JDK 12 默认不生效）且 1 分钟平均负载 < G1PeriodicGCSystemLoadThreshold（默认 0.0 = 不检查）；G1PeriodicGCInvokesConcurrent 默认 true（走并发 cycle 而非 Full GC），日志 cause 为 G1 Periodic Collection。

344 管「单次暂停太长」，346 管「内存占着不还」——方向相反，配合理解。

故障排查者角度

Q17: 需求是「空闲时把内存还给系统」，加上 -XX:G1PeriodicGCInterval=5000 后没效果，排查路径？

按触发链逐项核对：

  1. 负载条件：G1PeriodicGCSystemLoadThreshold 默认 0.0 即不检查，但若有人配了阈值而机器 1 分钟均值更高，周期 GC 永不触发（日志里看不到 [gc,periodic] Checking for periodic GC.）；
  2. 并发周期占用：距上次 GC 暂停不足 5000ms 或有进行中的 concurrent cycle 时被跳过；
  3. GC 类型：默认走并发 cycle（G1PeriodicGCInvokesConcurrent=true），结束才按空闲比例 uncommit——检查 MinHeapFreeRatio/MaxHeapFreeRatio 与 -Xms 是否等于 -Xmx（Xms=Xmx 时堆固定，无内存可还）；
  4. 延迟因素：uncommit 后是否立刻又被分配吃掉——看 -XX:G1UncommitDelay（存在该 flag，默认值建议用 PrintFlagsFinal 现查，勿凭记忆）。

验证：开 -Xlog:gc,periodic 观察触发日志与 uncommit 记录。

「没效果」先分清是没触发 GC，还是 GC 了但没 uncommit（Xms=Xmx 是经典答案）。
Q18: 混合回收后老年代还是涨，怀疑 344 没生效——344 有开关可开吗？

没有。JEP 344 未提供任何用户可见 flag，它是 G1 内部行为：只有当启发式反复预测不准时才进入 optional 段的增量模式，预测准确时 optional 段会缩小甚至为零。因此「看不到效果」是正常设计（它不是永远可中断，Non-goal 也明确不承诺所有 G1 暂停可中断）。排查老年代增长要看别的：分配速率、InitiatingHeapOccupancyPercent、大对象、是否有内存泄漏。源码侧确认点：g1CollectionSet.hpp 的 _optional_regions、g1CollectedHeap.cpp 的 G1EvacuateOptionalRegionTask（:3772）与 evacuate_optional_collection_set（:3870）。

344 是「按需触发的自保机制」，不是「长效可中断开关」。

架构师角度

Q19: JEP 341 默认 CDS 归档改变了什么？怎么开/关？

以前要手动 -Xshare:dump 生成 classes.jsa；JEP 341 起 JDK 构建期（link image 后）自动生成默认归档放进 lib/server/，随发行版分发。开关三态（arguments.cpp）：-Xshare:auto（server VM 默认：尝试用、失败继续）、-Xshare:off（禁用）、-Xshare:on（强制，归档不可用即失败）；dump 用 -Xshare:dump。限制：仅 64 位、仅 native 构建（非交叉编译）。收益：JDK 11 EA 的 HelloWorld 实测启动提速 32%。自定义 class list / GC 配置仍可自建归档，默认归档只是「零配置的下限」。

默认归档 = 构建期产物，不是运行期首次生成；-Xshare:off 是诊断兜底。
Q20: 讲师角度 — 给业务团队一句话讲清「12 的 GC 选项」。

「G1 照常用；Shenandoah 想试低暂停就加两行实验性开关（15 才转正）；两件新东西 344/346 是 G1 自动优化——344 让混合回收的尾巴更碎、更好掐断，346 能在你空闲时把内存还给机器，但后者默认关着（要配 G1PeriodicGCInterval）；CDS 不用管，JDK 自带默认归档，启动自动快 30% 左右。」一句话里四个 JEP 全部对应到默认行为与动作项。

工具链与升级策略（JEP 230 / 340 / 非 LTS）（4 题）

面试官角度

Q21: JEP 230 是什么？怎么构建、怎么运行？

把基于 JMH 的微基准正式纳入 JDK 仓库：test/micro/org/openjdk/bench/{java,javax,vm}，初始约 100 个。流程：

configure --with-jmh=<JMH 目录>        # JMH 是外部二进制依赖，缺失会报错
make build-microbenchmark               # Main.gmk:551 独立目标，不进常规构建
make test TEST="micro:regexp"           # 按名称运行

产物为 test/micro/benchmarks.jar，且脚本注释明确「for both the old and new JDK」——支持 JDK(N) 与 JDK(N-1) 对比。Non-goal：不为新特性自动配基准、不覆盖全部 JDK。

三个关键词：--with-jmh 依赖、独立 make target、双版本对比。
Q22: 追问 — JEP 340 到底删了什么？

OpenJDK 曾有两套 64 位 ARM 实现：寄生在 src/hotspot/cpu/arm 里的 arm64 变体（大量 64/32 位 #ifdef）和独立的 src/hotspot/cpu/aarch64。JEP 340：删除 arm64 相关源码与 #ifdef → 全仓扫描残留 → 删除对应构建选项，aarch64 端口成为 64 位 ARM 默认 → 验证 32 位 ARM 端口无回归。结果：src/hotspot/cpu/ 只剩 arm（32 位）+ aarch64（64 位）两条 ARM 路径，外加 x86/ppc/s390/sparc/zero。

合并的是「64 位实现」，不是砍掉 ARM 支持——32 位端口仍在。

架构师角度

Q23: JDK 12 是非 LTS，你们的版本策略怎么定？

三档：① 生产只上 LTS（11 → 17/21），非 LTS 不进生产，规避支持窗口短与特性摇摆；② 预发每个版本都跟——12 的价值是提前暴露 11→17 中间的变化（switch 预览语法、CDS 默认归档、G1 行为、AArch64 构建选项消失）；③ 库与公共 API 以 LTS 为最低基线编译，禁止把非 LTS 专属 API 暴露进公共签名。12 的定位一句话：LTS 之间的排练场，用它验证、不用它托底。

非 LTS = 雷达，LTS = 地基；排练成本远低于在生产里第一次踩坑。

技术讲师角度

Q24: 用大白话给新人讲「预览特性」和「正式特性」的区别，以及 Java 12 的位置。

把它想成餐厅的新菜试吃：正式特性是「已上菜单的菜」——配方锁死、随便点；预览特性是「主厨今天请你试吃的新菜」——味道可以下次改（Java 12 的 switch 用 break 端出结果，13 就改成 yield 了），而且只在指定档口供应：必须用 --enable-preview 明说，编译和吃的时候（运行）都要同一家店（同一个 JDK 版本）。Java 12 的位置：非 LTS、只卖一季——switch 预览首发、Shenandoah 首发、JMH 体检入库、G1 修修补补、CDS 白送启动提速。学它是为了看懂 11→17 之间发生了什么，不是把它当成长期饭票。

试吃（预览）≠ 上菜单（正式）；一季店（非 LTS）≠ 长期基线（LTS）。

  • 能用「试吃/一季店」类比向新人讲清预览与非 LTS（instructor 角度）
