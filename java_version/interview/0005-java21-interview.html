本题库怎么读

围绕 JDK 21 的三条并发主线：虚拟线程（JEP 444）、结构化并发（JEP 453 预览）、ThreadLocal 与其继任者 ScopedValue（JEP 446 预览）。沿用五角度：面试官 / 架构师 / 代码审查者 / 故障排查者 / 技术讲师。答案中标注「JDK 21 口径」的内容忠于 Oracle Java 21 文档；本机代码实测环境为 openjdk-25.0.1（版本差异处单独说明）。

虚拟线程（7 题）

面试官角度

Q1: 虚拟线程是什么？它和平台线程的本质区别？

虚拟线程是 JDK 21（JEP 444）引入的轻量级 java.lang.Thread，由 Java 运行时而非 OS 实现。平台线程 1:1 封装 OS 线程、整个生命周期独占、数量受限；虚拟线程是 M:N，不绑定特定 OS 线程，阻塞 I/O 时挂起并释放载体线程，同一 JVM 可承载百万级。

本质区别：谁实现线程（OS vs 运行时）与阻塞时是否释放 OS 线程。
Q2: 追问 — 虚拟线程能让接口变快（降低延迟）吗？什么条件下才提升吞吐？

不能。虚拟线程不是更快的线程，不降低延迟，只提供规模。提升吞吐需同时满足：① 并发任务数很高（几千以上）；② 工作负载不是 CPU 密集型——线程数远超核数对计算任务无收益。典型服务端大量任务阻塞等 I/O，正符合。

提供 scale（吞吐）而非 speed（延迟）；CPU 密集任务用 Stream 并行。

架构师角度

Q3: 什么场景该用、什么场景不该用虚拟线程？现有异步/响应式服务要不要迁？

该用：高吞吐、任务大部分时间阻塞等 I/O（HTTP / JDBC / 消息）。不该用：长时间 CPU 密集计算。迁移：异步管道若已稳定且团队能承受其调试成本，不急于迁；虚拟线程最大价值是保留 thread-per-request 风格——把业务代码写回简单同步阻塞式，由框架为每请求启动虚拟线程；旧的 CompletableFuture 回调链不会从虚拟线程获益多少。

迁移核心是「回到同步代码」，不是给旧回调链套虚拟线程。

代码审查者角度

Q4: 审查这段「用固定大小线程池给虚拟线程限流」的代码，有什么问题？
var pool = Executors.newFixedThreadPool(200);
pool.submit(() -> query());
  1. newFixedThreadPool 建的是平台线程，不是虚拟线程——既无规模、又把 200 条重线程变成瓶颈；
  2. 虚拟线程永远不该池化：每任务 Thread.ofVirtual() 新建或走 newVirtualThreadPerTaskExecutor()；
  3. 限流应表达为对下游资源的许可：用 Semaphore（如 DB 连接数），acquire 后调用。
池化是应对平台线程昂贵的旧习惯；限流用 Semaphore，不用线程池。
Q5: JDK 21 口径 — 下面这段在虚拟线程里为什么损害吞吐？怎么改？
synchronized (guard) {
    socket.read(buf);          // 阻塞 I/O
}

JDK 21 上虚拟线程在 synchronized 块内阻塞会被钉住 carrier、无法卸载，carrier 被阻塞操作占住不能服务其他虚拟线程，吞吐退回平台线程水平。改写为 ReentrantLock（其阻塞在虚拟线程上不钉住）：

guardLock.lock();
try { socket.read(buf); } finally { guardLock.unlock(); }
注意版本：JDK 24 的 JEP 491 已让 synchronized 不再钉住——21 上需改写，25 上已免；native/FFI 至今仍钉住。

故障排查者角度

Q6: 上线虚拟线程后吞吐没提升、CPU 也不高，按什么顺序排查？
  1. jcmd <pid> Thread.dump_to_file -format=text：确认请求真跑在虚拟线程（标签 virtual），看是否大量卡在同一阻塞点；
  2. JFR 看 jdk.VirtualThreadPinned（默认阈值 20ms）：21 上常因 synchronized 守护 I/O（老连接池/老 JDBC），改 ReentrantLock、升级驱动或 JDK；
  3. 查下游：DB 连接池打满会让虚拟线程全部 park 等连接，此时加 Semaphore 限并发而非加线程；
  4. 确认不是 CPU 密集负载。
顺序：thread dump 定性 → JFR pinning → 下游资源 → CPU 密集度。

技术讲师角度

Q7: 用通俗的话讲清虚拟线程原理，它和 Java 早期的绿色线程有何不同？

类比虚拟内存：OS 把大虚拟地址空间映射到有限 RAM 来模拟「很多内存」；Java 运行时把大量虚拟线程映射到少量 OS 线程来模拟「很多线程」。运行时把虚拟线程 mount 到 carrier（平台线程）上执行，遇到阻塞 I/O 就 unmount 让出 carrier。调度模型是 M:N。Java 早期绿色线程是 M:1（全共享一条 OS 线程），无法利用多核、后被 1:1 平台线程淘汰；虚拟线程是 M:N，既能海量并发又能利用多核，且阻塞由运行时透明挂起。

M:1（绿色线程，不能并行）→ 1:1（平台线程，昂贵）→ M:N（虚拟线程，海量且并行）。

结构化并发（6 题）

面试官角度

Q8: 什么是结构化并发？它解决 ExecutorService + Future 的什么痛点？

结构化并发（JDK 21 JEP 453 预览，核心 StructuredTaskScope）把在不同线程运行的一组相关任务当作单一工作单元。解决：① 线程泄漏——一个子任务失败后其余仍在跑、结果已无人需要；② 取消传播困难——超时/中断要逐个处理；③ 无可观测结构——thread dump 看不出子任务属于谁。try-with-resources 保证 scope 关闭时子任务必然已结束。

不变式：父任务结束前所有子任务必已结束——由语法结构保证。
Q9: 追问 — fork / join / shutdown / close 各自的语义？
操作语义
fork(callable)在独立线程启动子任务，返回 Subtask 句柄
join()把所有子任务作为整体等待完成（或等策略短路）
shutdown()停止接新任务，中断取消未完成子任务（子类用来短路）
close()关闭 scope 并等待未完成子任务结束——保证无孤儿线程
join 是「等」，shutdown 是「取消」，close 是「收尾并保证寿命嵌套」。

架构师角度

Q10: ShutdownOnFailure 和 ShutdownOnSuccess 怎么选？各给一个场景。

ShutdownOnFailure：捕获第一个异常并取消其余——用于「聚合多个必需下游」，任一失败请求即失败，join().throwIfFailed()。ShutdownOnSuccess：捕获第一个成功结果——用于「多个等价来源取最快」，scope.result()。两者都是短路模式。

一个对首个失败短路，一个对首个成功短路。

代码审查者角度

Q11: 审查这段非结构化代码，指出风险并用结构化并发改写。
Response handle() throws Exception {
  Future<String> user  = exec.submit(this::findUser);
  Future<Integer> order = exec.submit(this::fetchOrder);
  return new Response(user.get(), order.get());   // user 失败后 order 仍在跑 → 泄漏
}

风险：findUser 失败后 fetchOrder 仍占用线程、结果无人需要，需手动取消，忘了就是孤儿线程；取消/超时传播也分散。改写：

Response handle() throws ExecutionException, InterruptedException {
  try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<String> user  = scope.fork(this::findUser);
    Subtask<Integer> order = scope.fork(this::fetchOrder);
    scope.join().throwIfFailed();                  // 任一失败 → 取消其余并抛出
    return new Response(user.get(), order.get());
  }
}
改写后「失败即取消其余」与「close 必等待结束」都由 scope 保证。

故障排查者角度

Q12: 怎么从 jcmd JSON 转储重建一个卡住请求的父子任务结构？

① 在 threadContainers 找到 container 名为 StructuredTaskScope$... 的容器；② 看 owner（父任务 tid）和 parent 确定归属；③ 容器内 threads 数组即该 scope fork 的全部子任务，逐个看 stack 找卡点（如全 park 在等下游）；④ 父线程栈通常停在 ThreadFlock.awaitAll / StructuredTaskScope.join。

container + owner + parent 是重建结构的三个钥匙字段。

技术讲师角度

Q13: 讲清「结构化」的含义，并说明预览特性与 21→25 的 API 差异。

「结构化」类比 { } 代码块：控制流嵌套、寿命有界；结构化并发让线程寿命也嵌套在语法结构里——子任务在 scope 内 fork，scope 关闭时必结束。JDK 21 是第一次预览，需 javac --enable-preview --release 21、java --enable-preview，API 未来可能变、不宜暴露到长期 API。演进：21（JEP 453）→ 22（462）→ 23（480）→ 24（499）→ 25（505）。JDK 25 已重设计：StructuredTaskScope<T,R> 变接口，用 open(Joiner) 创建，两个 ShutdownOnXxx 子类被移除，join() 直接返回结果。

21 记 ShutdownOnXxx，25 记 open(Joiner)；两版均为预览，勿混用。

ThreadLocal 与 ScopedValue（5 题）

面试官角度

Q14: ThreadLocal 的每线程副本是怎么实现的？为什么通常声明为 static？

值不存在 ThreadLocal 对象上，而在每个 Thread 内部的映射（Thread.threadLocals）里，ThreadLocal 只是键；set/get 操作当前线程的映射，get 未命中走 initialValue()。声明 static 是因为 ThreadLocal 无状态只作键，static 保证全应用用同一个键，避免每实例一个键导致映射膨胀。

每线程一张 Map，ThreadLocal 当 key；成本 N 线程 × M 个 ThreadLocal。

架构师角度

Q15: ThreadLocal 在线程池里最危险的事故是什么？定什么纪律？

任务间值泄漏：线程被复用，上一个任务 set 的上下文（用户身份/租户/事务）被下一个任务意外读到且无报错。纪律：任务体 try/finally，finally 必须 remove()，不能依赖线程结束清理（池化线程不结束）；虚拟线程海量时，还应优先评估 ScopedValue。

ThreadLocal + 线程池：每任务 finally remove，是不可省略的契约。

代码审查者角度

Q16: 审查下面代码，为什么子线程拿 TLADMIN 正常、拿期望的新值却失败？
Thread child = new Thread(() -> System.out.println(TLADMIN.get()));
TLADMIN.set(new User("Admin"));   // 在构造之后才 set
child.start();

因为 InheritableThreadLocal 的继承快照发生在 new Thread(...) 构造时，不是 start() 时——构造之后才 set 的值不在快照里。必须「先 set、再构造子线程」。另外它是浅拷贝、传同一引用，父子修改互相可见。

构造时拷贝 + 引用共享：顺序与别名两个陷阱都源于实现。

故障排查者角度

Q17: 怀疑 ThreadLocal 导致内存泄漏，怎么定位与处置？
  1. 堆直方图/堆转储里观察大量 Thread 实例与 ThreadLocalMap 条目 retained，或被线程局部引用住的大对象（如 ClassLoader 无法卸载）；
  2. 确认是否线程池 + 任务未 remove()：值随池化线程长期保留；
  3. 处置：在任务 finally 补 remove；多次 set 处明确最终清理点；必要时缩小线程池寿命；
  4. 新代码的上下文传递改用 ScopedValue，作用域结束自动失效。
泄漏根因是「无界寿命 + 忘记 remove」；ScopedValue 从机制上消除它。

技术讲师角度

Q18: ThreadLocal 的三大设计缺陷是什么？ScopedValue 如何一一对应解决？JDK 21 能用吗？

三大缺陷：① 无约束可变性——任何代码可 set、难追踪；② 无界生命周期——保留到线程结束或手动 remove，线程池中任务间泄漏；③ 昂贵继承——每生一个子线程都复制父映射，百万虚拟线程放大成本。ScopedValue 对应：① 不可变（绑定时写一次、之后只读）；② 有界作用域（where 结束即失效）；③ 无继承复制（配合 StructuredTaskScope，fork 子任务共享绑定）。JDK 21 上为预览 JEP 446（需开关），JDK 25 由 JEP 506 转正免开关。

ThreadLocal 可变/无界/靠继承复制；ScopedValue 不可变/有界/结构化共享。
