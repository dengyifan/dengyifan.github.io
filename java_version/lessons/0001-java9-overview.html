L1 · Java 9 全景：模块化与工程化的起点

📚 层模型 L1 概念层 🔬 OpenJDK jdk9 ⏱ 预计 25 分钟

一句话定位

Java 9 是 Java 平台从「语言演进」转向「平台工程化」的分水岭。它引入的 JPMS 不是又一个语法糖，而是重新定义了 JAR 之间的边界、JDK 的部署形态和整个生态的依赖契约。

Java 8 给了你 Lambda 和 Stream，让代码更优雅；Java 9 给了你 JPMS 和 jlink，让系统更可控。

为什么是 Java 9：三个根本问题

问题一：类路径的“JAR 地狱”

Java 从 1.0 起使用类路径（Classpath） 来定位类。类路径是一个扁平的 JAR 列表，JVM 按顺序扫描，加载第一个匹配的类。这个机制有三个致命缺陷：

缺陷具体表现后果
隐式依赖类路径上看不到 A 依赖 B 的哪个版本版本冲突难以诊断
无封装边界只要类在类路径上，任何 JAR 都能访问 public 类内部实现被外部依赖，无法演进
运行时臃肿整个 rt.jar 约 60MB+ 全部部署容器镜像大、攻击面大
常见误区
很多开发者以为「用了 Maven/Gradle 就不会有 JAR 地狱」。事实上构建工具只解决编译期的依赖解析，运行时的类加载仍然是扁平类路径——这正是 JPMS 要解决的核心问题。

问题二：JDK 自身的巨型单体

Java 8 的 JDK 是一个约 60MB 的单体 rt.jar。无论你的应用只用 java.util.List 还是用了全套 Swing/JavaFX，部署时都要带上整个 JDK。这在容器化时代是巨大的浪费。

问题三：没有官方的依赖契约

在 Java 9 之前，一个 JAR 能声明“我依赖什么”“我导出什么”的唯一方式是 Maven POM——但这是构建期的元数据，运行期 JVM 完全看不见。JVM 只知道“这些类在类路径上”，不知道“谁依赖谁、谁该被暴露”。

JPMS 用三个机制回应上述三个问题：

  1. 可靠配置（Reliable Configuration）：用模块图在启动时就检查依赖完整性。缺模块直接启动失败，而不是运行时抛 NoClassDefFoundError。
  2. 模块化 JDK：JDK 拆成 90+ 模块，java.base 是根。应用可以只依赖需要的模块。
  3. 强封装（Strong Encapsulation）：未 exports 的包，即使类是 public 也无法从其他模块访问。JAR 之间终于有了真正的边界。

Java 8 vs Java 9：思维方式的转变

维度Java 8 之前Java 9 之后
依赖单位JAR / 类路径模块 / 模块路径
依赖声明构建工具 POM（运行期不可见）module-info.java（编译期+运行期）
封装边界package + public（可被绕过）module + exports（强封装）
JDK 部署整个 rt.jarjlink 定制运行时
启动检查运行时懒加载启动时解析模块图
反射访问setAccessible(true) 即可需要 opens 或 --add-opens
生产环境视角：JPMS 迁移的真实成本
企业级应用（Spring、Hibernate、Dubbo）大量依赖反射访问内部 API。迁移到 JPMS 时，这些框架需要：
  • 在 module-info.java 中声明 opens 开放被反射访问的包
  • 或在启动参数加 --add-opens java.base/java.lang=ALL-UNNAMED
  • 升级到支持 JPMS 的框架版本（Spring 5+、Hibernate 5.2+）
结论：JPMS 迁移不是“加个 module-info.java”，而是整个依赖契约的重新梳理。中小项目可以先用自动模块（Automatic Module）平滑过渡。

关键判断逻辑：模块化迁移的决策树

面对一个现有项目，决定是否需要/如何迁移到 JPMS 时，可以参考以下伪代码逻辑：

// 伪代码：JPMS 迁移决策
function decideJPMSMigration(project) {
    if (project.hasReflectionHeavyFrameworks()) {
        // Spring/Hibernate 等：优先用自动模块过渡
        return useAutomaticModules(project);
    }

    if (project.isLibrary() && project.targetsMultipleJDKVersions()) {
        // 库开发者：考虑多版本 JAR
        return useMultiReleaseJAR(project);
    }

    if (project.isApplication() && project.wantsJlinkRuntime()) {
        // 应用开发者：完整迁移以使用 jlink
        return fullJPMSMigration(project);
    }

    // 默认：保持类路径，按需渐进
    return keepClasspath(project);
}
判断要点
JPMS 迁移的核心决策因素不是“技术难度”，而是收益：如果不需要 jlink 定制运行时、不需要强封装保护内部 API，那么完整迁移的收益有限。自动模块（把 JAR 放到模块路径但不写 module-info）是绝大多数项目的合理起点。
