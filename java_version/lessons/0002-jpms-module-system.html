模块描述符：module-info.java 全解

module-info.java 是 JPMS 的核心——一个编译期描述文件，编译后生成 module-info.class，被 JVM 在启动时读取。

module com.example.myapp {
    requires java.base;                       // 依赖模块
    requires transitive java.sql;             // 传递依赖
    requires static java.compiler;            // 编译期依赖，运行期可选

    exports com.example.api;                  // 导出包
    exports com.example.spi to com.example.plugin;  // 限定导出

    opens com.example.internal;               // 运行期反射开放
    opens com.example.model to com.fasterxml.jackson.databind;

    uses com.example.spi.Service;             // 声明服务消费者
    provides com.example.spi.Service
        with com.example.impl.ServiceImpl;    // 声明服务实现
}

指令语义对照表

指令作用生命周期典型场景
requires声明编译期+运行期依赖编译+运行依赖另一个模块
requires transitive传递依赖：依赖本模块的模块自动获得此依赖编译+运行API 中暴露的类型来自此模块
requires static编译期必须，运行期可选编译期注解处理器
exports导出包，编译期可见编译+运行公开 API 包
exports ... to限定导出，只对指定模块编译+运行内部 API 给特定合作方
opens运行期反射开放仅运行框架反射访问
opens ... to限定反射开放仅运行给特定框架开放
uses声明服务消费者运行SPI 消费
provides...with声明服务实现运行SPI 提供
常见误区
exports 和 opens 不是一回事。一个包可以 exports 但不开 opens——编译期可见但反射不可达。Spring 需要在启动时反射注入字段，所以你必须在 module-info 里 opens 相关包，否则会抛 InaccessibleObjectException。

模块图的解析流程

JVM 启动时，模块系统按以下步骤构建模块图：

sequenceDiagram participant JVM as JVM 启动 participant Finder as ModuleFinder participant Resolver as Resolver participant Graph as Module Graph participant Loader as ModuleLayer JVM->>Finder: 扫描模块路径
(--module-path) Finder-->>JVM: 发现所有模块 JVM->>Resolver: resolve(rootModules) Resolver->>Resolver: 从根模块开始
BFS 解析 requires Resolver->>Graph: 构建依赖图 Graph->>Graph: 检查一致性
(缺失/冲突/循环) Graph-->>Resolver: 解析完成 Resolver-->>JVM: 模块图就绪 JVM->>Loader: 创建 ModuleLayer Loader-->>JVM: 开始加载类

关键点：模块图在启动时完整解析。如果某个 requires 的模块缺失，JVM 在启动时抛 FindException，而不是等到运行时。这就是“可靠配置”的含义。

模块图的三类节点

类型来源能力
命名模块有 module-info.class 的 JAR完整 JPMS 能力
自动模块放在模块路径但无 module-info 的 JAR自动 requires 所有模块，自动 exports 所有包
未命名模块类路径上的所有代码可读所有模块，但只能被自动模块读取
自动模块的命名规则
自动模块名由 JAR 文件名推导：去掉版本号、把 - 换成 .。例如 commons-lang3-3.12.0.jar → 模块名 commons.lang3。这个规则不稳定，因此生产环境建议库作者显式提供 Automatic-Module-Name 清单条目。

实现位置：OpenJDK 中的 jdk.internal.module.Modules 和 java.lang.Module 负责此检查。Module 类维护三个关键集合：

反射访问的检查链

当代码调用 setAccessible(true) 时，JDK 内部会走以下检查链（简化版）：

// 伪代码：setAccessible 的模块检查
function checkReflectiveAccess(Class target, Class caller) {
    Module targetModule = target.getModule();
    Module callerModule = caller.getModule();

    // 1. 同一个模块，直接通过
    if (targetModule == callerModule) return ALLOW;

    // 2. 目标模块是否 opens 了目标包给 caller?
    if (targetModule.isOpen(target.getPackageName(), callerModule)) {
        return ALLOW;
    }

    // 3. 目标模块是否无条件 opens 了目标包?
    if (targetModule.isOpen(target.getPackageName())) {
        return ALLOW;
    }

    // 4. 检查启动参数 --add-opens
    if (isAddOpens(targetModule, target.getPackageName(), callerModule)) {
        return ALLOW;
    }

    // 5. 未命名模块且目标是 JDK 内部 API
    if (callerModule.isNamed() == false && isJdkInternal(target)) {
        throw new InaccessibleObjectException(...);
    }

    throw new InaccessibleObjectException(...);
}
生产环境：--add-opens 是常见逃生舱
大型框架（Spring 5.x 早期版本、Hibernate 5.x、Jackson）在 JPMS 下需要 opens 才能反射。当无法修改第三方库的 module-info 时，启动参数 --add-opens java.base/java.lang=ALL-UNNAMED 是标准做法。Java 17 起对 JDK 内部 API 的反射访问进一步收紧，--add-opens 使用会更普遍。

jlink：模块化的直接产物

jlink 是 JDK 9 随模块化一起提供的工具，它把应用模块 + JDK 模块打包成一个自定义运行时镜像。

工作流程

(JDK_HOME/jmods)"] --> B B --> D["模块图
(传递闭包)"] D --> E["jlink 链接器"] E --> F["优化与压缩"] F --> G["自定义运行时镜像

完整可执行示例

# 1. 目录结构
# src/
#   com.example.app/
#     module-info.java
#     com/example/app/Main.java

# 2. module-info.java
cat > src/com.example.app/module-info.java << 'EOF'
module com.example.app {
    requires java.base;
    requires java.logging;
}
EOF

# 3. Main.java
mkdir -p src/com.example.app/com/example/app
cat > src/com.example.app/com/example/app/Main.java << 'EOF'
package com.example.app;

import java.util.logging.Logger;

public class Main {
    private static final Logger LOG = Logger.getLogger(Main.class.getName());

    public static void main(String[] args) {
        LOG.info("Hello from custom runtime!");
        System.out.println("Runtime: " + Runtime.version());
        System.out.println("Modules: " + ModuleLayer.boot().modules().size());
    }
}
EOF

# 4. 编译
javac -d mods/com.example.app \
      src/com.example.app/module-info.java \
      src/com.example.app/com/example/app/Main.java

# 5. 运行（模块路径）
java --module-path mods --module com.example.app/com.example.app.Main

# 6. 分析依赖
jdeps --module-path mods --module com.example.app

# 7. 用 jlink 创建自定义运行时
jlink --module-path mods:$JAVA_HOME/jmods \
      --add-modules com.example.app \
      --output my-runtime \
      --strip-debug \
      --compress 2 \
      --no-header-files \
      --no-man-pages

# 8. 使用自定义运行时（体积约为完整 JDK 的 1/4）
du -sh my-runtime
./my-runtime/bin/java --module com.example.app/com.example.app.Main

jlink 的优化选项

选项作用收益
--strip-debug移除调试信息减少约 20%
--compress 2压缩资源（0/1/2，2最激进）减少约 30%
--no-header-files移除 C 头文件减少少量
--no-man-pages移除 man 手册减少少量
--bind-services自动绑定 uses/provides方便但增大体积

并发语义与异常容错（L2 必查维度）

并发语义

场景行为
模块图解析单线程启动阶段完成，无并发问题
类加载每个模块由独立的 ClassLoader 加载（或共享 bootstrap）
jlink 链接单线程，但可对多个模块并行处理
服务加载ServiceLoader.load() 是线程安全的

异常容错

异常触发场景处理方式
FindException模块路径上找不到某模块检查 --module-path 和 module-info
ResolutionException依赖冲突或循环依赖用 jdeps 分析依赖树
IllegalAccessError访问未 exports 的包添加 exports 或改用公开 API
InaccessibleObjectException反射访问未 opens 的包添加 opens 或 --add-opens
LayerInstantiationException模块层创建失败检查模块图一致性

性能开销

维度开销优化
启动时模块解析O(模块数)，通常 <10msjlink 预解析
类加载检查每次加载做 exports 检查JIT 内联后影响可忽略
