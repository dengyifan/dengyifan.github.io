为什么 Java 9 换成 G1：CMS 的结构性缺陷

Java 8 的默认 GC 是 CMS（Concurrent Mark Sweep）。CMS 有两个无法通过调参解决的结构性缺陷：

缺陷根因后果
碎片化标记-清除算法不移动对象长时间运行后无法分配大对象 → Full GC / Concurrent Mode Failure
暂停不可预测暂停时间随堆大小和碎片程度波动无法设定 -XX:MaxGCPauseMillis 目标
并发失败惩罚重并发收集期间应用分配过快 → 退化到单线程 Full GC可能停顿数秒
常见误区
“G1 一定比 CMS 快”是错的。G1 的目标不是最大化吞吐量，而是在可控暂停下尽量高吞吐。对于小堆（<4GB）且追求最大吞吐的场景，Parallel GC 可能更合适。G1 的价值在于可预测的暂停和可调的目标。

Region 大小：-XX:G1HeapRegionSize，默认 1-32MB，根据堆大小自动计算，目标是 2048 个 Region 左右。

核心设计：物理上堆是连续的，逻辑上被划分为等大小的 Region。每个 Region 可以在不同时刻扮演 Eden / Survivor / Old / Humongous 角色。这打破了传统分代的物理隔离。

Humongous 对象的特殊处理

大小 ≥ Region 一半的对象被标记为 Humongous，分配在连续的 Region 中。这类对象直接进入 Old 区，且在 Region 回收时粒度更粗，容易造成碎片。

生产环境：Humongous 是 G1 性能杀手
如果应用频繁分配接近 Region 一半的大对象（如大数组、大字符串），会频繁触发 Humongous 分配。诊断方法：-Xlog:gc+heap=debug 输出中搜索 "Humongous"。优化方向：增大 Region 大小（-XX:G1HeapRegionSize=32m）或减少大对象分配。

Mixed GC 的 Region 选择策略

Mixed GC 是 G1 的核心创新。它每次回收时：

// 伪代码：Mixed GC 的 Region 选择
function selectRegionsForMixedGC() {
    // 1. 收集所有候选 Old Region（并发标记阶段已标记）
    candidates = getOldRegionsWithMarkedObjects();

    // 2. 按垃圾比例从高到低排序
    //    垃圾比例 = 已死对象大小 / Region 总大小
    candidates.sortBy(region -> region.deadRatio, DESC);

    // 3. 从垃圾最多的开始，累加回收时间估计
    selected = [];
    totalPauseEstimate = 0;
    for (region in candidates) {
        regionPause = estimateCopyTime(region);
        if (totalPauseEstimate + regionPause > maxGCPauseMillis) {
            break;  // 达到暂停目标，停止
        }
        selected.add(region);
        totalPauseEstimate += regionPause;
    }
    return selected;   // 这就是 "Garbage First" 的含义
}

关键：Mixed GC 每次回收的 Old Region 数量由 -XX:MaxGCPauseMillis 和实际垃圾比例动态决定。这让 G1 能够在暂停时间和回收效率之间动态权衡。

什么时候不该用 G1

场景推荐 GC原因
堆 < 4GB，追求最大吞吐Parallel GCG1 的分区管理和并发标记有开销，小堆上不如 Parallel 直接
单核 CPU 或小容器Serial GCG1 的并发线程需要多核才能发挥作用
极端低延迟（<10ms）ZGC / ShenandoahG1 的暂停通常在 10-200ms，无法达到亚毫秒级
超大堆（>64GB）ZGCG1 在超大堆上 Region 数量多，管理开销上升
大量 Humongous 对象Parallel / ZGCG1 的 Humongous 碎片问题严重
批量计算，暂停不敏感Parallel GCG1 的并发开销换来的低暂停没有价值
Java 9 时代的现实
Java 9 时 ZGC（Java 11 引入）和 Shenandoah 尚未可用。因此 Java 9 的 G1 默认化是在 CMS 和 Parallel 之间的折中。如果你在 Java 11+ 环境，超低延迟场景应该考虑 ZGC。

G1 调优参数

参数默认作用建议
-XX:MaxGCPauseMillis200ms目标暂停时间不要设太小（<50ms 会导致 Region 回收不足，退化到 Full GC）
-XX:G1HeapRegionSize自动Region 大小Humongous 多时增大
-XX:InitiatingHeapOccupancyPercent45%触发并发标记的堆占用率频繁 Mixed GC 时降低
-XX:G1MixedGCLiveThresholdPercent85%Old Region 存活对象超过此比例则不回收降低可回收更多 Region，但成本上升
-XX:G1MixedGCCountTarget8Mixed GC 分几次完成增大可降低单次暂停
-XX:G1NewSizePercent5%Young 区最小占比Young GC 频繁时增大
-XX:G1MaxNewSizePercent60%Young 区最大占比控制 Young GC 频率

并发语义与异常容错（L4 必查维度）

并发语义

阶段与应用线程的关系是否 STW
Young GC并行（多 GC 线程）是（短暂停）
并发标记并发（与用户线程同时运行）否（仅初始标记和最终标记 STW）
Mixed GC并行（多 GC 线程）是（可控暂停）
Full GC单线程或并行是（长暂停）
Refinement（卡表更新）并发（写屏障）否

异常容错

问题触发条件G1 的行为
Concurrent Mode Failure并发标记期间应用分配过快，Old 区满退化到 Full GC（单线程整理，长暂停）
Evacuation FailureYoung GC 时 Survivor 空间不足对象晋升到 Old 区，可能触发 Full GC
Humongous 分配失败连续 Region 不足触发 Full GC 释放空间
To-space Exhausted复制目标 Region 不足回退：保留原对象，标记待下次处理

边界判断

边界阈值影响
Humongous 判定对象 ≥ Region 大小 / 2直接进入 Old 区，碎片风险
Region 大小1-32MB，2048 个为目标太小 → Humongous 多；太大 → 回收粒度粗
并发标记触发堆占用 45%太高 → 来不及标记就满；太低 → 频繁标记
Mixed GC 触发并发标记完成后标记周期长度影响回收及时性

性能开销

维度开销对比 CMS
写屏障每次引用赋值额外检查类似
卡表（Card Table）每 Region 一张卡表更细粒度
记忆集（RSet）每个 Region 维护跨 Region 引用CMS 无此开销
并发标记线程占用 CPU（约 1/4 核心数）类似
Young GC并行复制类似
内存占用RSet 约占堆 5-10%CMS 约 1%

完整可执行示例：观察 G1 行为

/**
 * G1 GC 行为观察示例
 *
 * 运行方式：
 *   javac G1Demo.java
 *   java -XX:+UseG1GC \
 *        -Xms512m -Xmx512m \
 *        -XX:MaxGCPauseMillis=100 \
 *        -Xlog:gc*:file=gc.log:time,uptime,level,tags \
 *        G1Demo
 *
 * 观察 gc.log 中的：
 *   - Pause Young (G1 Evacuation Pause)
 *   - Pause Concurrent Mark (CMS-like)
 *   - Pause Remark
 *   - Pause Cleanup
 *   - Pause Mixed (G1 Evacuation Pause)
 *   - Pause Full (G1 Compaction Pause)
 */
public class G1Demo {

    static final int OBJECT_SIZE = 1024;         // 1KB
    static final int ALLOC_RATE = 5000;          // 每次循环分配5000个对象
    static final int ITERATIONS = 200;

    public static void main(String[] args) throws Exception {
        System.out.println("=== G1 GC 行为观察 ===");
        System.out.println("Max heap: " + Runtime.getRuntime().maxMemory()
            / 1024 / 1024 + " MB");
        System.out.println("GC: " + java.lang.management.ManagementFactory
            .getGarbageCollectorMXBeans());

        // 保留一些长期存活对象，制造 Old 区压力
        java.util.List<byte[]> longLived = new java.util.ArrayList<>();

        for (int iter = 0; iter < ITERATIONS; iter++) {
            // 短命对象：大部分会被 Young GC 回收
            for (int i = 0; i < ALLOC_RATE; i++) {
                byte[] temp = new byte[OBJECT_SIZE];
                temp[0] = (byte) i;
            }

            // 每 10 轮保留一批对象，制造 Old 区增长
            if (iter % 10 == 0) {
                for (int i = 0; i < 100; i++) {
                    byte[] survivor = new byte[OBJECT_SIZE * 10];
                    longLived.add(survivor);
                }
                System.out.println("Iter " + iter
                    + " | heap used: "
                    + (Runtime.getRuntime().totalMemory()
                       - Runtime.getRuntime().freeMemory())
                    / 1024 / 1024 + " MB"
                    + " | retained: " + longLived.size());
            }

            Thread.sleep(50);
        }

        System.out.println("\n=== 完成 ===");
        System.out.println("Final retained objects: " + longLived.size());
        System.out.println("Check gc.log for G1 behavior");
    }
}

关键观察点：

  • Pause Young：短暂停，回收 Young 区。
  • Pause Concurrent Mark：全局标记，与应用并发。
  • Pause Remark：标记收尾，STW 短暂停。
  • Pause Mixed：回收 Young + 部分 Old，暂停时间可控。
  • 如果看到 Pause Full，说明退化到 Full GC，需要调优。

关键设计决策

决策为什么代价
Region 化替代物理分代可灵活调整各代大小，适应不同负载需要记忆集维护跨 Region 引用
优先回收垃圾最多的 Region最大化单次回收收益回收顺序依赖并发标记准确性
用暂停目标驱动回收量可预测暂停目标过严导致回收不足，退化 Full GC
Humongous 直接进 Old避免大对象复制成本碎片化风险，连续 Region 不足
Full GC 作为兜底保证最终能回收单线程长暂停，是 G1 最差场景
并发标记 + 写屏障减少 STW 时间写屏障开销，记忆集内存
