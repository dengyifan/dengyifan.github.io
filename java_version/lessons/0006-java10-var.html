L1 · 概念层：var 是什么，不是什么

Java 10 引入 var 作为局部变量类型推断的保留类型名（reserved type name），不是关键字。它在编译期根据初始化表达式的类型来推断变量的静态类型，字节码层面与显式声明完全一致[reference:0]。

// Java 10 之前
List<String> list = new ArrayList<String>();
// Java 10
var list = new ArrayList<String>();  // 推断为 ArrayList<String>

// 增强 for 循环
for (var entry : map.entrySet()) { ... }

// 传统 for 循环
for (var i = 0; i < 10; i++) { ... }

// try-with-resources
try (var reader = new BufferedReader(...)) { ... }
常见误区：var 不是动态类型

var 不会改变 Java 的静态类型本质。变量在编译后仍然有确定的静态类型，只是声明时省略了。一旦推断完成，赋值给其他类型会编译报错——与显式声明完全一致[reference:1]。

L2 · 原理层：编译器如何推断

推断算法

var 的推断规则非常直接：将初始化表达式视为独立表达式，推导其类型，然后把这个类型作为变量的静态类型[reference:2]。

flowchart LR A[var x = expr] --> B[将 expr 作为独立表达式
进行类型检查] B --> C{expr 是 poly expression?} C -->|否| D[推导出具体类型 T] C -->|是| E[编译错误
缺少目标类型] D --> F[变量 x 的类型 = T] E --> G[如数组初始化器
lambda 表达式]

这意味着：

var list = new ArrayList<String>();
// 推断为 ArrayList<String>，不是 List<String>

// 如果初始化表达式是 poly expression
var ints = {1, 2, 3};  // 编译错误：数组初始化器需要目标类型
var f = () -> "hello";  // 编译错误：lambda 需要目标类型
为什么推断为 ArrayList 而不是 List？

JEP 286 FAQ 中明确回应：「That would be confusing type inference with mind reading.」编译器只做它能看到的事——初始化表达式是什么类型，变量就是什么类型[reference:3]。开发者如果想要 List 接口类型，需要显式声明。

关键限制背后的设计逻辑

限制设计理由
不能用于方法参数方法签名是接口契约，必须稳定可读。调用方看不到方法体，无法理解 var 推断的结果
不能用于字段字段是对象状态的一部分，其类型影响序列化、反射和子类设计
不能用于返回类型返回类型是方法的 API 边界
必须初始化没有初始化表达式就无法推断——这不是限制，而是逻辑必然

源码片段：Infer.java 中的推断入口

// OpenJDK jdk10 · Infer.java
// 版本：metropolis/dev 48ec75306997
// 路径：src/jdk.compiler/share/classes/com/sun/tools/javac/comp/Infer.java

// var 的推断复用了 Java 8 引入的泛型推断引擎。
// 核心逻辑在 Attr.java 的 visitVarDef 中：
// 1. 检测到变量声明没有显式类型（vartype == null）
// 2. 将初始化表达式交给 Infer 推导类型
// 3. 将推导结果设置为变量的类型

// Infer 中的推断方法（简化示意）：
Type inferVarType(JCTree init) {
    // 将 init 视为独立表达式进行类型检查
    // 不提供任何目标类型约束
    Type inferredType = attribExpr(init, env, Type.noType);
    // 检查推断结果的有效性
    if (inferredType.isErroneous()) {
        log.error(pos, "cannot.infer.type");
    }
    return inferredType;
}

关键设计点：var 的推断不引入新的类型系统机制，而是复用已有的泛型推断引擎。这意味着 Java 8 中对泛型推断的改进（如嵌套调用链推断）直接让 var 受益。

Lambda 参数的扩展（JEP 323，Java 11）

// Java 11 允许：
(var x, var y) -> x.process(y)

// 等价于：
(x, y) -> x.process(y)

// 但要求：隐式类型 Lambda 的参数要么全部用 var，要么全部不用
// 非法：
(var x, y) -> x.process(y)   // 不能混用
(var x, int y) -> ...          // 不能混用 var 和显式类型

JEP 323 的核心动机是语法一致性：让局部变量和 Lambda 参数的声明语法对齐，使得注解（如 @Nonnull）可以同时应用于两者[reference:4]。

从 Java 视角看：与 C# 的 var 对比

C# 从 3.0 起就有 var，但其推断规则更激进——C# 的 var 可以推断数组初始化器 var a = new[] {1,2,3}。Java 选择更保守的策略：只接受独立表达式，拒绝需要目标类型的 poly expression。这体现了 Java 对「可预测性」的偏好——编译器不会猜测开发者的意图。

L4 · 边界层：局限、坑与最佳实践

var 不能做什么

场景问题替代方案
推断出具体类而非接口var list = new ArrayList<String>() 推断为 ArrayList，无法赋值给 List 变量显式声明 List<String> list = new ArrayList<>()
可读性下降var result = process() 看不出返回类型方法名要足够自描述，或显式声明类型
与 Lombok var 冲突Lombok 的 var 在 Java 10 后无法使用升级 Lombok 版本或改用 Java var
var 作为类名Java 10 之前可以定义名为 var 的类，之后不再允许重命名类（违反命名规范，实际很少见）
生产环境建议

var 的使用应遵循「局部性原则」：

  • ✅ 适合：循环变量、try-with-resources、方法调用链的中间变量——类型从上下文容易看出
  • ❌ 不适合：API 边界、字段、方法签名——这些地方类型是契约的一部分
  • ⚠️ 建议：单行 var 使用比例不超过 30%，可读性优先于简洁性[reference:5]

与 Java 8 的兼容性

var 带来的唯一源不兼容：不能再定义名为 var 的类。JEP 286 将此视为可接受的兼容性代价，因为类名应大写开头[reference:6]。

L5 · 面试层：追问链

Q1: var 是什么？它改变了 Java 的静态类型吗？

var 是 Java 10 引入的局部变量类型推断语法。它不改变 Java 的静态类型本质——变量在编译后仍有确定的静态类型，只是声明时由编译器自动推断。字节码层面 var 不存在，与显式声明生成的字节码完全一致。

关键点：var 是编译期语法糖，不是运行时特性。
Q2: 追问 — var 为什么不能用于方法参数和字段？

方法参数和字段是接口契约的一部分。调用方或子类需要看到稳定的类型声明，而 var 的推断结果是编译器内部决定的，对调用方不可见。如果允许，会导致 API 语义不可预测——同一段代码在不同编译器版本下可能推断出不同的类型。

关键点：var 的设计原则是「局部性」——只影响变量声明所在的局部作用域。
Q3: 追问 — 写出 var 推断的伪代码，核心判断条件是什么？
// javac 中 var 推断的核心逻辑（伪代码）
function processVarDeclaration(JCVariableDecl node):
    if node.vartype != null:
        return  // 显式类型，不处理

    if node.init == null:
        error("cannot use 'var' without initializer")
        return

    // 将初始化表达式作为独立表达式进行类型检查
    // 不提供目标类型（Type.noType）
    inferredType = attribExpr(node.init, env, Type.noType)

    if inferredType == null or inferredType.isErroneous():
        error("cannot infer type")
        return

    node.vartype = inferredType  // 设置推断出的类型

核心判断条件：(1) 是否有初始化表达式；(2) 初始化表达式是否能独立推导出类型（即不是 poly expression）。

关键点：poly expression（需要目标类型的表达式，如数组初始化器、lambda）会被拒绝。
