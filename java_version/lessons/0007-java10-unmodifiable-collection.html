L1 · 概念层：三类不可变集合工厂

Java 9 引入了 List.of() / Set.of() / Map.of() 来创建小规模不可变集合。Java 10 补充了两个关键缺口：

  1. copyOf()：从已有集合创建不可变副本
  2. Collectors.toUnmodifiableList/Set/Map()：Stream 终端操作直接收集为不可变集合
  3. Optional.orElseThrow()：无参版本，作为 get() 的语义化替代
// copyOf — 从已有集合创建不可变副本
List<String> mutable = new ArrayList<>();
mutable.add("a");
List<String> immutable = List.copyOf(mutable);  // 不可变

// toUnmodifiableList — Stream 终端操作
List<Integer> result = Stream.of(1, 2, 3)
    .collect(Collectors.toUnmodifiableList());

// Optional.orElseThrow — 语义化替代 get()
Optional<String> opt = Optional.of("hello");
String value = opt.orElseThrow();  // 缺失时抛 NoSuchElementException

L2 · 原理层：不可变性与幂等性设计

copyOf 的幂等性

copyOf() 的关键设计是幂等性：如果入参已经是不可变集合（ImmutableCollections.AbstractImmutableList 类型），直接返回原引用，不创建新对象。

// 源码实现（简化）
static <E> List<E> copyOf(Collection<? extends E> coll) {
    if (coll instanceof ImmutableCollections.AbstractImmutableList) {
        return (List<E>) coll;  // 幂等：已是不可变，直接返回
    }
    return (List<E>) List.of(coll.toArray());  // 创建不可变副本
}
幂等性的意义

在防御性编程中，开发者经常需要在方法入口处 List.copyOf(input) 来防止外部修改。幂等性保证了：如果调用方传入的已经是不可变集合，不会产生不必要的拷贝开销。这在链式调用和多次防御时非常关键。

Collectors.toUnmodifiableList 的实现

// OpenJDK · Collectors.java
// 版本：jdk-10+35 · 路径：java.base/java/util/stream/Collectors.java

public static <T>
Collector<T, ?, List<T>> toUnmodifiableList() {
    return new CollectorImpl<>(ArrayList::new, List::add,
        (left, right) -> { left.addAll(right); return left; },
        list -> {
            if (list.getClass() == ArrayList.class) { // 确保可信
                return SharedSecrets.getJavaUtilCollectionAccess()
                    .listFromTrustedArray(list.toArray());
            } else {
                throw new IllegalArgumentException();
            }
        },
        CH_NOID);
}

关键设计点：收集过程使用可变的 ArrayList 作为累加器，在最后一步通过 listFromTrustedArray 转换为不可变列表。这避免了在收集过程中反复创建不可变对象的开销。

常见误区：Collectors.toList() 返回的是可变列表

Collectors.toList() 返回的 ArrayList 是可变的。Java 10 之前，开发者需要 collectingAndThen(toList(), Collections::unmodifiableList) 来获得不可变列表。Java 10 的 toUnmodifiableList() 是原生支持，性能更优（不需要包装器）。

Optional.orElseThrow() 的设计

// OpenJDK · Optional.java
// 版本：jdk10 · rev 48328 · JDK-8140281
// 四个 Optional 变体（Optional / OptionalInt / OptionalLong / OptionalDouble）同步添加

public T orElseThrow() {
    if (value == null) {
        throw new NoSuchElementException("No value present");
    }
    return value;
}

实现与 get() 完全一致，区别仅在方法名——orElseThrow 明确表达了「如果缺失则抛出异常」的语义，比 get 更符合 Optional 的设计哲学[reference:8]。

L4 · 边界层：不可变不等于不可修改内容

边界条件：不可变集合的「浅不可变性」

List.copyOf() 拒绝 null 元素——传入包含 null 的集合会抛 NullPointerException。这是与 Collections.unmodifiableList() 的关键区别：后者允许 null，前者不允许。

此外，不可变集合只保证集合结构不可修改，如果元素本身可变，集合的「内容」仍然会变化。

L5 · 面试层：追问链

Q1: List.copyOf() 和 Collections.unmodifiableList() 有什么区别？

三个核心区别：(1) 副本 vs 视图——copyOf 创建独立副本，unmodifiableList 创建包装视图，原列表修改会影响视图；(2) null 处理——copyOf 拒绝 null，unmodifiableList 允许；(3) 幂等性——copyOf 传入不可变集合时直接返回原引用。

关键点：防御性编程应用 copyOf（副本独立），只读视图用 unmodifiableList（零拷贝）。
Q2: 追问 — 为什么 copyOf 要设计成幂等的？

幂等性避免了多次防御性拷贝的开销。在方法链中，每一层都调用 copyOf() 时，如果传入的已经是不可变集合，后续的调用都是零成本的。这鼓励开发者在不牺牲性能的前提下进行防御性编程。

关键点：幂等性是「零成本防御」设计哲学的体现。
Q3: 追问 — Collectors.toUnmodifiableList() 的累加器类型是什么？为什么？

累加器是 ArrayList（可变），在收集结束时转换为不可变列表。原因是：如果累加器本身就是不可变类型，每次 add 操作都需要创建新对象，导致 O(n²) 复杂度。使用可变累加器 + 最终转换，复杂度为 O(n)。

关键点：收集过程用可变，最终结果用不可变——这是 Stream Collector 的通用模式。
