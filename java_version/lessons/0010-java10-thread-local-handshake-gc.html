L1 · 概念层：两个底层机制

Thread-Local Handshakes（JEP 312）

传统的 Safepoint 机制要求所有线程停下来才能执行某些全局操作。但很多场景其实只需要操作单个线程——比如撤销某个线程的偏向锁、获取某个线程的 stack trace、执行栈采样[reference:17]。让所有线程停下来做这些事，代价太高。

Thread-Local Handshakes 允许 JVM 在不执行全局 Safepoint 的情况下，对单个线程执行回调。

GC 接口（JEP 304）

在 Java 10 之前，GC 实现代码散落在 HotSpot 各处——屏障代码在解释器/C1/C2 中，诊断代码在 MemoryMXBeans 中，大量 if-else 分支区分不同 GC。JEP 304 引入干净的 GC 接口（CollectedHeap 抽象），使每个 GC 的实现尽可能收敛到自己的目录中[reference:18]。

L2 · 原理层

Safepoint 机制回顾

flowchart TD A[JVM 需要执行全局安全操作] --> B[设置全局 Safepoint 标志] B --> C[所有应用线程轮询检查标志] C --> D[线程在最近的 Safepoint 点停下] D --> E[VM Thread 执行操作] E --> F[恢复所有线程] style A fill:#fef0f0 style F fill:#e8f5e9

问题：线程轮询和停止的过程需要时间，且让所有线程都停下做单个线程的操作是资源浪费[reference:19]。

Thread-Local Handshake 机制

flowchart LR A[VM Thread 需要操作
单个线程 X] --> B[在线程 X 的
Safepoint 轮询页设置标志] B --> C[线程 X 执行回调] C --> D[其他线程不受影响] style A fill:#fef0f0 style D fill:#e8f5e9

核心变化：从全局轮询页改为每线程独立的轮询页。VM Thread 只修改目标线程的轮询页标志，该线程在下次轮询时执行回调，其他线程继续运行[reference:20]。

HandshakeState 的源码结构

// OpenJDK · runtime/handshake.hpp
// A handshake operation is a callback that is executed for each JavaThread
// while that thread is in a safepoint safe state.

class HandshakeState {
    HandshakeOperation* volatile _operation;
    Semaphore _semaphore;
    bool _vmthread_holds_semaphore;
    bool _thread_in_process_handshake;

    bool claim_handshake_for_vmthread();
    bool vmthread_can_process_handshake(JavaThread* target);
    void clear_handshake(JavaThread* thread);
    void process_self_inner(JavaThread* thread);
public:
    void set_operation(JavaThread* thread, HandshakeOperation* op);
    bool has_operation() const { return _operation != NULL; }
    void cancel(JavaThread* thread);
};

关键设计：HandshakeState 使用信号量（Semaphore）来序列化 VM Thread 和目标 JavaThread 之间的握手操作——确保操作只被其中一方执行，不会重复[reference:21]。

GC 接口的 CollectedHeap 抽象

// OpenJDK · gc/shared/collectedHeap.hpp
// The GC interface would be defined by the existing class CollectedHeap
// which every garbage collector needs to implement.

class CollectedHeap : public CHeapObj<mtInternal> {
public:
    // 所有 GC 必须实现的纯虚函数
    virtual Name kind() const = 0;
    virtual bool is_maximal_no_gc() const = 0;
    virtual size_t capacity() const = 0;
    virtual size_t used() const = 0;

    // 垃圾回收入口
    virtual void collect(GCCause::Cause cause) = 0;
    virtual void do_full_collection(bool clear_all_soft_refs) = 0;

    // 屏障相关（由 GC 特定的 BarrierSet 提供）
    virtual BarrierSet* barrier_set() const = 0;
};

JEP 304 的目标不是添加或移除 GC，而是整理代码结构，使 GC 实现尽可能隔离在自己的目录中，减少跨模块的耦合[reference:22]。

从 Java 视角看：与 .NET GC 的对比

.NET 的 GC 是单体式的——Workstation GC 和 Server GC 在同一套代码中，通过配置切换。HotSpot 选择了多实现路线：Serial、Parallel、CMS、G1、ZGC、Shenandoah 各自独立。JEP 304 的 GC 接口正是这条路线的基础设施——让新增 GC 的实现者只需关注自己的接口实现，不需要理解整个 HotSpot 代码库。

L4 · 边界层

机制局限后续演进
Thread-Local Handshakes仅支持 x64 和 SPARC 架构；偏向锁撤销等场景受益，但 GC 的 STW 阶段仍需全局 Safepoint成为 Loom 虚拟线程调度的基础机制
GC 接口只是代码整理，不提供运行时插件能力（不能在不重新编译 JVM 的情况下插入新 GC）为 ZGC (JEP 333) 和 Epsilon (JEP 318) 的实现铺路
JVM 调优参数

Thread-Local Handshakes 默认开启（在支持的架构上）。可通过 -XX:+ThreadLocalHandshakes 显式启用，-XX:-ThreadLocalHandshakes 禁用。GC 接口无运行时参数，它是 HotSpot 的内部重构。

L5 · 面试层

Q1: Thread-Local Handshakes 解决了 Safepoint 的什么问题？

传统 Safepoint 需要所有线程停止才能执行操作。但偏向锁撤销、stack trace 获取等操作只需要单个线程暂停。Thread-Local Handshakes 将全局轮询页改为每线程独立的轮询页，VM Thread 只修改目标线程的轮询标志，其他线程不受影响。

关键点：从「全体暂停」到「按需暂停」，减少不必要的 STW。
Q2: 追问 — HandshakeState 如何保证操作的唯一性？

通过信号量（Semaphore）序列化。VM Thread 和 JavaThread 通过 claim_handshake_for_vmthread() 和 process_self_inner() 竞争信号量，确保握手操作只被其中一方执行。如果 VM Thread 先获取信号量，它代表 JavaThread 执行回调；否则 JavaThread 自己执行[reference:23]。

关键点：信号量确保「恰好一次」语义，不会重复执行也不会遗漏。
Q3: 追问 — GC 接口（JEP 304）实际做了什么？只是整理代码吗？

表面上是代码整理，实质是架构解耦。在 JEP 304 之前，添加新 GC 需要修改解释器、C1、C2、MemoryMXBeans 等多处代码。JEP 304 将 GC 特定的屏障实现、诊断代码等收敛到 CollectedHeap 接口和 GC 各自的目录中。这直接使得 Java 11 的 ZGC 和 Epsilon 能够以较小的代码侵入性落地。

关键点：JEP 304 是「基础设施投资」——本身不提供用户可见的新功能，但为后续 GC 创新铺平了道路。
