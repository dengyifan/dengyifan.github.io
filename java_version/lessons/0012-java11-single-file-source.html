L1 · 概念层：Java 11 只动了两处语法

Java 11（2018-09，LTS）在语言层面非常克制：没有引入新的类型系统特性，只做了两件「减少仪式感」的事——一个是让 java 启动器能直接吃源文件，一个是让 Lambda 参数能写 var 并挂注解。

先跑一个：从写到执行，中间没有 javac，也没有 .class
$ cat Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, " + String.join(" ", args));
    }
}

$ java Hello.java Java 11
Hello, Java 11

$ ls Hello*.class
ls: Hello*.class: No such file or directory

两条命令走完全程：cat 写文件、java 跑文件。程序参数跟在文件名之后原样传给 main，编译在内存里完成、进程退出即消失，目录里一个 .class 都不会多。

JEP 330：java 启动器的第四种模式

在此之前，java 启动器只有三种模式。JEP 330 加了第四种：

模式命令JDK
启动 class 文件java HelloWorld1.0
启动 JAR 主类java -jar app.jar1.2
启动模块主类java -m com.app/com.app.Main9
启动源文件中的类java HelloWorld.java11

语义上它等价于（JEP 330 原文用词是 informally equivalent to）：

java HelloWorld.java
// 等价于
javac -d <memory> HelloWorld.java
java -cp <memory> HelloWorld

// 带程序参数
java Factorial.java 3 4 5
// 等价于
javac -d <memory> Factorial.java
java -cp <memory> Factorial 3 4 5
与 jshell 的分工

JEP 330 的 Alternatives 一节明确写了：为什么不交给 jshell？因为 jshell 的设计目标是交互式体验，把「批处理跑一次」的任务塞进去会损害交互设计。所以：jshell 管 REPL，java Foo.java 管一次性脚本，两者不重叠。

JEP 323：Lambda 参数的 var

Java 10 的 var 只能用于局部变量，Lambda 参数不行。JEP 323 补上了这个语法缺口：

// Java 11 允许
(var x, var y) -> x.process(y)
// 与下面完全等价（推断出的类型一模一样）
(x, y) -> x.process(y)

它的真正价值不是省字，而是让注解能挂上去——这是 JEP 323 的 Motivation 原文给出的唯一示例：

// Java 10：注解无法应用于隐式类型的 Lambda 参数
@Nonnull var x = new Foo();            // ✅ 局部变量可以挂注解
(x, y) -> x.process(y)                 // ❌ 参数上没地方挂注解

// Java 11：语法对齐后
(@Nonnull var x, @Nullable var y) -> x.process(y)   // ✅
常见误区：不存在「@Var 注解」

学习者容易把这条特性记成「Lambda 参数可以加 @Var 注解」。正确理解：var 是 Java 10 引入的保留类型名（reserved type name，不是关键字），JEP 323 只是允许它出现在 Lambda 形参位置；可选的是 var 关键字本身，而由此解锁的才是任意注解（如 @Nonnull、@Nullable）。没有名为 @Var 的注解。

L2 · 原理层：模式判定与编译执行

关键判断逻辑伪代码：source-file 模式怎么被选中

function selectMode(argv):
    # 第一个「既不是选项、也不是某个选项的参数」的元素
    item = firstNonOptionArgument(argv)

    # 规则 1：显式 --source 强制 source 模式
    if "--source" 存在于 argv:
        return SOURCE_MODE

    # 规则 2：item 指向一个存在的 .java 文件
    if item 以 ".java" 结尾 and Files.exists(item):
        return SOURCE_MODE

    # 规则 3：按 class / jar / module 老规则解析
    return resolveLegacyMode(item)

两个推论必须记住：

  • 文件名不是 .java 结尾时，必须显式 --source N 才进 source 模式——这正是 shebang 脚本（文件名常叫 hello、factorial）的场景。
  • 使用 --enable-preview 时也必须给 --source。

编译期与执行期的硬约束（JEP 330 原文条款）

阶段约束等效于
编译不搜索其他源文件source path 为空
编译注解处理被关闭-proc:none
编译--source N 作为 --release N 生效同时约束语言级别与可用 API
编译在未命名模块（unnamed module）上下文中编译—
编译源文件中第一个顶层类即为执行目标不要求文件名 == 类名（放宽了 JLS §7.6 的可选限制）

执行在未命名模块中运行，等效 --add-modules=ALL-DEFAULT—
执行classpath 上存在同名类 → 报错避免「以为跑的是源码，实际跑的是 jar」

可传给编译环境的启动器选项（白名单）

JEP 330 规定只有一组选项会被识别并传给编译器：--class-path、--module-path、--add-exports、--add-modules、--limit-modules、--patch-module、--upgrade-module-path 及其变体形式，外加 --enable-preview。没有任何通道把 -processor、-Werror 这类 javac 选项透传进去。

四维度生产检查

维度本特性的情况
并发语义单次运行、单 main 线程；编译在启动线程内同步完成，编译产物只存于内存 Map<String,byte[]>，无跨进程共享，不存在并发写入问题。
异常容错编译报错 → 错误信息写 stderr、非零退出码；main 抛异常 → 启动器会剥掉到 main 为止的 launcher 栈帧，让堆栈看起来像直接执行；System.exit 正常传播。
边界判断classpath 同名类冲突；文件不存在 / 非 .java 且无 --source；第一个顶层类没有 public static void main。
性能开销每次运行都从零编译，无任何缓存（这正是 JEP 458「多文件模式」仍未解决的痛点）。启动开销 ≈ 一次 javac + 一次 JVM 起动。

Lambda var 的全有或全无：判定伪代码

function checkLambdaFormals(params):
    hasVar    = params 中存在参数声明为 var
    hasPlain  = params 中存在参数既无 var 也无显式类型
    hasTyped  = params 中存在显式类型（如 int y）

    # 规则 1：隐式类型 Lambda 要么全 var，要么全不写
    if hasVar and hasPlain:
        error("不能混用 var 与不写 var")

    # 规则 2：显式类型 Lambda 必须全显式，不能插 var
    if hasVar and hasTyped:
        error("不能混用 var 与显式类型")

    # 规则 3：禁止 var x -> ... 这种「参数列表带 var 的箭头简写」
    if 形如 "var x -> expr":
        error("不允许")
设计原理追问：为什么不允许「半显式」(var x, int y) -> ...？

JEP 323 给了三层理由：

  1. 它会深度影响类型推断与重载决议，超出本 JEP 范围；
  2. 必须保证带不带 var 推断出的类型完全一致（否则会破坏向后兼容）；
  3. 部分推断属于更复杂的问题，留给后续 JEP。

代价是语法不够灵活，收益是零源码不兼容——JEP 323 的 Risks 一节直接声明「本特性没有源不兼容风险」。

L3 · 源码层：SourceLauncher 走读

源码片段一：编译 + 执行的主流程

// OpenJDK 25 · jdk.compiler/com/sun/tools/javac/launcher/SourceLauncher.java
public Result run(String[] runtimeArgs, String[] args) throws Fault, InvocationTargetException {
    Path file = getFile(args);                                        // 1. 取源文件

    ProgramDescriptor program = ProgramDescriptor.of(ProgramFileObject.of(file));
    RelevantJavacOptions options = RelevantJavacOptions.of(program, runtimeArgs); // 2. 过滤白名单选项
    MemoryContext context = new MemoryContext(out, program, options);
    context.compileProgram();                                         // 3. 编译进内存

    String[] mainArgs = Arrays.copyOfRange(args, 1, args.length);     // 4. 文件名之后的都是程序参数
    var appClass = execute(context, mainArgs);                        // 5. 反射调 main
    return new Result(appClass, context.getNamesOfCompiledClasses());
}

源码片段二：字节码如何「不落盘」

// OpenJDK 25 · jdk.compiler/com/sun/tools/javac/launcher/MemoryFileManager.java
final class MemoryFileManager extends ForwardingJavaFileManager<JavaFileManager> {
    private final Map<String, byte[]> map;   // className → 字节码

    @Override
    public JavaFileObject getJavaFileForOutput(Location location, String className,
                                               JavaFileObject.Kind kind, FileObject sibling) {
        if (location == StandardLocation.CLASS_OUTPUT && kind == JavaFileObject.Kind.CLASS) {
            return createInMemoryClassFile(className);   // ← 关键：拦截 CLASS_OUTPUT
        }
        return super.getJavaFileForOutput(location, className, kind, sibling);
    }

    private JavaFileObject createInMemoryClassFile(String className) {
        URI uri = URI.create("memory:///" + className.replace('.', '/') + ".class");
        return new SimpleJavaFileObject(uri, JavaFileObject.Kind.CLASS) {
            @Override
            public OutputStream openOutputStream() {
                return new ByteArrayOutputStream() {
                    @Override
                    public void close() throws IOException {
                        super.close();
                        map.put(className, toByteArray());  // close 时才落进内存 Map
                    }
                };
            }
        };
    }
}

设计要点：只拦截 CLASS_OUTPUT + KIND.CLASS 两种情况，其他全部委托给真正的文件管理器——所以源文件读取、类路径查找照常走磁盘，只有产物被截胡。这就是 ForwardingJavaFileManager 装饰器模式的标准用法。

源码片段三：main 方法查找的兜底顺序

// 1) 先在「第一个顶层类」上找 public static void main
firstClass = Class.forName(firstClassName, false, loader);
mainMethod = MethodFinder.findMainMethod(firstClass);

// 2) 找不到 → 回退到「与文件同名的那个类」
if (mainMethod == null) {
    expectedName = (packageName.isEmpty() ? "" : packageName + ".") + 文件名去掉 .java;
    actualName   = program.qualifiedTypeNames().stream()
                         .filter(n -> n.equals(expectedName)).findFirst()

    mainMethod   = MethodFinder.findMainMethod(Class.forName(actualName, false, loader));
}

L4 · 边界层：限制、坑与最佳实践

source-file 模式不能做什么

限制原因绕法
只能单文件JEP 330 标题即 Single-File；源文件里声明的类对 classpath 不可见多文件场景等 JEP 458（Java 24 起的 multi-file source-code mode），或回退到 javac + java
不能传 -processor / -Werror没有 javac 选项透传通道用 javac 单独编译
注解处理被强制关闭-proc:noneLombok / MapStruct 等不可用
classpath 同名类冲突 → 直接报错防止「跑错版本」改名或清理 classpath
每次运行都重新编译无编译缓存高频执行请先编译成 class
文件名非 .java 时必须 --source模式判定规则shebang 首行写 #!/path/to/java --source 17
.java 文件禁止用 shebang 首行JEP 330 明确：遵循命名规范的源文件不接受 shebangshebang 脚本请去掉 .java 后缀
生产环境建议
  • ✅ 适合：一次性运维脚本、教学演示、CI 里的健康检查、快速复现 bug
  • ❌ 不适合：有依赖的项目（依赖管理不在 JEP 330 范围内）、需要注解处理的代码、高频调度的短任务
  • ⚠️ shebang 脚本记得 chmod +x，并且首行第一个参数必须是 --source（JEP 330 规定：若要带 VM 选项，--source 必须紧跟在可执行文件名之后）
  • ⚠️ --source N 会作为 --release N 生效：同时限制语言版本和可调用的 JDK API。写 --source 8 就不能用 List.of()

Lambda var 的边界清单

写法合法性说明
(var x, var y) -> ...✅隐式类型，全 var
(x, y) -> ...✅隐式类型，全不写
(var x, y) -> ...❌混用 var 与不写
(var x, int y) -> ...❌混用 var 与显式类型
(int x, int y) -> ...✅全显式（Java 8 就有）
var x -> x.foo()❌JEP 323 明确禁止

(@Nonnull x) -> ...❌不写 var 就没有挂注解的位置

L5 · 面试层：追问链

Q1: java HelloWorld.java 背后发生了什么？

启动器判定进入 source-file 模式后，实际执行的是 java -m jdk.compiler/<SourceLauncher> HelloWorld.java。SourceLauncher 读取源文件 → 过滤出白名单编译选项 → 通过 MemoryFileManager 把 .class 写进内存 Map（不落盘）→ 创建委托给 application class loader 的自定义类加载器 → Class.forName 加载首个顶层类 → 反射定位并调用 main。整个过程在未命名模块中进行，等效 --add-modules=ALL-DEFAULT。

关键点：类文件从不写到磁盘，classpath 上的类也看不到源文件里声明的类。
Q2: 追问 — JEP 330 有哪些编译期「默认收紧」的设定？为什么这样设计？

三条：

  1. -proc:none 关闭注解处理；
  2. source path 视为空，不牵扯其他源文件；
  3. 只接受固定白名单选项，不透传 javac 参数。

设计动机是把 source-file 模式定位成「一次性的、无构建配置的小程序」——凡是需要构建配置的场景都应该用构建工具 + javac。代价是 Lombok 这类注解处理器无法使用。

关键点：这是 trade-off——用「配置能力」换「零配置的开箱即用」。
Q3: 追问 — 写出 source-file 模式的判定伪代码，核心判断条件是什么？
item = argv 中第一个既非选项也非选项参数的元素
if argv 含 "--source":            → SOURCE 模式
else if item 以 ".java" 结尾 且文件存在: → SOURCE 模式
else:                              → 按 class/jar/module 老规则

核心判断条件只有两个：是否显式出现 --source；「类名」位置上的参数是否命中一个存在的 .java 文件。注意它带出的副作用：java HelloWorld.java 原本会被解析成「包 HelloWorld 里的类 java」，现在只要文件存在就优先按文件处理——JEP 330 承认这是可接受的歧义。

关键点：非 .java 文件名（如 shebang 脚本）必须靠 --source 才能进入该模式。
Q4: 追问 — 为什么 JEP 323 要求 Lambda 参数「全 var 或全不 var」？

三点：

  1. 混写会产生「半显式类型」的 Lambda，会深度影响类型推断与重载决议；
  2. 必须保证带 var 与不带 var 推断出的类型完全一致，否则引入源不兼容；
  3. 部分推断是更复杂的问题，留给后续 JEP。

收益是 JEP 323 声明「零源码不兼容风险」，同时让注解有了落点。

关键点：var 在这里是纯语法糖，不改变任何推断结果，只改变「能不能挂注解」。
