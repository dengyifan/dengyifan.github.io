L1 · 概念层：从孵化模块到正式 API

Java 里长期只有 HttpURLConnection（1.0 时代的产物，API 设计停留在同步 + 手动管理连接的阶段）。HTTP Client 走了三步才转正：

JDKJEP包名状态
9JEP 110jdk.incubator.http孵化
10JEP 162jdk.incubator.http孵化（打磨 API）
11JEP 321java.net.http正式标准 API

正式版的 API 由四个核心抽象构成：

HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(5))
        .followRedirects(HttpClient.Redirect.NORMAL)   // 默认 NEVER
        .build();

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/v1/users"))
        .header("Accept", "application/json")
        .timeout(Duration.ofSeconds(3))
        .GET()
        .build();

// 同步：阻塞当前线程
HttpResponse<String> resp = client.send(request, BodyHandlers.ofString());
System.out.println(resp.statusCode() + " " + resp.body());

// 异步：返回 CompletableFuture，不阻塞
CompletableFuture<HttpResponse<String>> future =
        client.sendAsync(request, BodyHandlers.ofString())
              .thenApply(r -> r);
三个泛型角色（Flow API 的化身）

BodyPublisher（请求体 → 订阅者）、BodySubscriber<T>（响应字节 → T）、BodyHandler<T>（根据响应头「造一个 Subscriber」）。它们直接复用了 java.util.concurrent.Flow（JDK 9 引入的 Reactive Streams 规范接口），所以背压是一等公民，而不是事后补的。

四个上手示例：POST JSON / 上传 / 下载 / 三件套落地

下面四段都能直接跑（示例 1 需要 Jackson，JDK 11+ 通用）。分工：Publisher 管「怎么发出去」、Handler 管「按响应头选 Subscriber」、Subscriber 管「字节怎么变成 T」。

示例 1 · POST JSON 并解析响应 JSON 报文

// ---- 发：BodyPublisher（请求体 → 对端）----
String payload = "{\"name\":\"dengyifan\",\"tags\":[\"java\",\"jvm\"]}";
HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.example.com/v1/users"))
        .header("Content-Type", "application/json; charset=UTF-8")   // charset 必须显式写
        .timeout(Duration.ofSeconds(3))
        .POST(BodyPublishers.ofString(payload, StandardCharsets.UTF_8))  // 长度已知 → Content-Length
        .build();

// ---- 收：BodyHandler 按响应头造 Subscriber；ofString() 按头里的 charset 解码，拿不到一律 UTF-8 ----
HttpResponse<String> resp = client.send(req, BodyHandlers.ofString());
if (resp.statusCode() / 100 != 2) {
    throw new IllegalStateException("HTTP " + resp.statusCode());    // 4xx/5xx 不是异常，要自己判
}

// ---- 解析：JDK 11 标准库没有 JSON API（ javax.json 属 Java EE，Java 11 已移除），必须用三方库 ----
ObjectMapper mapper = new ObjectMapper();                 // Jackson（Gson / fastjson 同理）
JsonNode node = mapper.readTree(resp.body());             // 或直接给类型：mapper.readValue(body, User.class)
long   id   = node.at("/data/id").asLong();
String name = node.path("data").path("name").asText();
System.out.println(id + " " + name);
字符集与「JSON 解析」的两个坑
  • ofString() 解码规则：先看响应头 Content-Type 里的 charset，拿不到或解不出一律落 UTF-8（不按 RFC 的 text/* 默认 ISO-8859-1）。老接口正文是 GBK 而头里没写 → 乱码，此时必须 BodyHandlers.ofString(Charset.forName("GBK"))。
  • 发送方向不自动：请求头里的 application/json 不会帮你编码，BodyPublishers.ofString(json) 默认 UTF-8，要明确就用 ofString(json, UTF_8)，同时把 charset 写进 Content-Type。
  • JSON 解析永远是业务层的事：JDK 11 没有内置 JSON API，别去找 Json.parse(...)。

示例 2 · POST 上传文件

// A. 整个文件就是请求体：最省事，ofFile 边读边发，不整包进堆（长度 = Files.size）
HttpRequest raw = HttpRequest.newBuilder(URI.create(url))
        .header("Content-Type", "application/octet-stream")
        .POST(BodyPublishers.ofFile(Path.of("/data/report.pdf")))
        .build();

// B. multipart/form-data（浏览器风格表单）：JDK 没有现成 builder，boundary 自己拼；
//    注意 JDK 11 的 BodyPublishers 没有 concat(...)，只能靠 ofByteArrays / ofInputStream 组合
String b = "----Java11" + UUID.randomUUID();
byte[] head = ("--" + b + "\r\n"
        + "Content-Disposition: form-data; name=\"file\"; filename=\"report.pdf\"\r\n"
        + "Content-Type: application/octet-stream\r\n\r\n").getBytes(StandardCharsets.UTF_8);
byte[] file = Files.readAllBytes(Path.of("/data/report.pdf"));
byte[] tail = ("\r\n--" + b + "--\r\n").getBytes(StandardCharsets.UTF_8);

HttpRequest form = HttpRequest.newBuilder(URI.create(url))
        .header("Content-Type", "multipart/form-data; boundary=" + b)
        .POST(BodyPublishers.ofByteArrays(List.of(head, file, tail)))   // 三段拼接，长度已知
        .build();
HttpResponse<String> resp = client.send(form, BodyHandlers.ofString());
文件大了怎么办
  • ofByteArrays 仍要把整个文件读进堆。改成流式：BodyPublishers.ofInputStream(() -> new SequenceInputStream(new ByteArrayInputStream(head), new SequenceInputStream(Files.newInputStream(path), new ByteArrayInputStream(tail))))——长度变未知 → HTTP/1.1 走 Transfer-Encoding: chunked，部分网关/WAF 对 chunked 的 POST 不友好，需要 Content-Length 就只能预读或用已知长度的 ofFile 单独发。
  • Content-Type 不会自动补：multipart 的 boundary 必须与 header 里的一致，否则服务端解析出空 part。

示例 3 · POST 下载文件

// A. 最省事：Handler 直接落盘，边收边写不进堆，返回 HttpResponse<Path>
HttpRequest dl = HttpRequest.newBuilder(URI.create(url)).GET().build();
HttpResponse<Path> saved = client.send(dl, BodyHandlers.ofFile(Path.of("/tmp/pkg.tar.gz")));
System.out.println(saved.body());                       // 落盘路径

// B. 流式：拿 InputStream 自己控制（进度条 / 限速 / 校验和）
HttpResponse<InputStream> st = client.send(dl, BodyHandlers.ofInputStream());
try (InputStream in = st.body()) {                      // apiNote：必须读到 EOF 或显式 close
    Files.copy(in, Path.of("/tmp/pkg.tar.gz"), StandardCopyOption.REPLACE_EXISTING);
}
// 提前 close（没读完）可能连底层 HTTP 连接一起关掉 → Keep-Alive 连接无法复用
下载三件配套齐
  • BodyHandlers.ofFile(path[, openOptions])：返回 HttpResponse<Path>，字节到达即写文件；文件在 handler 创建时就做安全检查。
  • BodyHandlers.ofInputStream()：返回时header 已读完、body 可能没到齐，body() 是边收边读的流；读到 EOF 或 close 必须二选一。
  • BodyHandlers.ofFileDownload(dir, openOptions...)：按响应头里的文件名下载到目录（带目录穿越保护），不想自己解析 filename 时用它。

示例 4 · 三件套自定义（Handler 选型 / Subscriber 背压限流 / Publisher 分片）

// import java.net.http.HttpResponse.ResponseInfo; import java.util.concurrent.Flow;
// ① BodyHandler：读完响应头、还没读正文时被调用（@FunctionalInterface），职责只有一个——选 Subscriber
static BodyHandler<String> pick(ResponseInfo info) {
    if (info.statusCode() == 204) return BodySubscribers.replacing("");   // 无正文 → 直接给占位值
    String ct = info.headers().firstValue("Content-Type").orElse("");
    Charset cs = ct.toUpperCase(Locale.ROOT).contains("GBK")
              ? Charset.forName("GBK") : StandardCharsets.UTF_8;
    return BodySubscribers.mapping(                    // 组合用法：byte[] 先收齐，再映射成 String
            BodySubscribers.ofByteArray(), ba -> new String(ba, cs));
}
// 用法：HttpResponse<String> r = client.send(req, Info -> pick(Info));  或直接 client.send(req, this::pick)

// ② BodySubscriber：自己实现背压 + 体积上限——三件套里最硬核的一环
static BodySubscriber<byte[]> capped(int limit) {
    return new BodySubscriber<>() {                   // 即 Flow.Subscriber<List<ByteBuffer>>
        private final CompletableFuture<byte[]> future = new CompletableFuture<>();
        private final ByteArrayOutputStream out = new ByteArrayOutputStream();
        private Subscription sub;
        private long got;

        @Override public void onSubscribe(Subscription s) { sub = s; s.request(1); }   // 先要 1 批
        @Override public void onNext(List<ByteBuffer> bufs) {
            for (ByteBuffer b : bufs) {
                byte[] a = new byte[b.remaining()]; b.get(a); out.writeBytes(a);
                if ((got += a.length) > limit) {
                    future.completeExceptionally(new IOException("响应体超过 " + limit + " 字节"));
                    sub.cancel(); return;             // 主动掐断——限流的落点就在 cancel()
                }
            }
            sub.request(1);                           // 处理完再要下一批 → 拉式驱动，这就是背压
        }
        @Override public void onError(Throwable t)   { future.completeExceptionally(t); }
        @Override public void onComplete()           { future.complete(out.toByteArray()); }
        @Override public CompletionStage<byte[]> getBody() { return future; }
    };
}
// 用法：client.send(req, info -> capped(1 << 20));      // 1 MB 上限，超了就 cancel

// ③ BodyPublisher：自己实现只要两件事——contentLength() + subscribe()
static BodyPublisher chunks(Path f, int chunk) {
    long total;
    try   { total = Files.size(f); }
    catch (IOException e) { throw new UncheckedIOException(e); }
    return new BodyPublisher() {
        @Override public long contentLength() { return total; }   // -1 表示未知 → chunked
        @Override public void subscribe(Flow.Subscriber<? super ByteBuffer> out) {
            out.onSubscribe(new Subscription() {
                long pos = 0; volatile boolean cancelled;
                @Override public void request(long n) {          // 拉式：订阅者要 n 个，我才读 n 段
                    for (long i = 0; i < n && !cancelled && pos < total; i++) {
                        ByteBuffer b = readChunk(f, pos, (int) Math.min(chunk, total - pos));
                        pos += b.remaining();
                        out.onNext(b);                           // 一次只吐一块，读盘被对方速度牵引
                    }
                    if (pos >= total && !cancelled) out.onComplete();
                }
                @Override public void cancel() { cancelled = true; }
            });
        }
    };
}
// readChunk(p, off, n)：FileChannel 定位到 off 读 n 字节 → ByteBuffer（略）
// 不想手写就用现成的：BodyPublishers.fromPublisher(flowPub) / fromPublisher(flowPub, knownLen)，
// 以及流式现成品 ofInputStream(supplier)、ofByteArrays(iterable)、ofFile(path)
追问：三个泛型怎么串起来的？
  1. BodyHandler<T>.apply(ResponseInfo) 在读响应体字节之前被调用，产出 BodySubscriber<T>；
  2. BodySubscriber<T> extends Flow.Subscriber<List<ByteBuffer>>，靠 request(n) 拉字节，结果通过 CompletionStage<T> getBody() 交回；
  3. BodyPublisher extends Flow.Publisher<ByteBuffer>，多一个 long contentLength()（未知填 -1 → chunked）；
  4. 三者的泛型 T 必须一致，这就是为什么 discarding()（Void）不能塞进 BodyHandler<String>——要用 replacing("")。
关键点：Handler 决定「怎么收」，Subscriber 决定「收成什么、何时要更多」，Publisher 决定「怎么发、要不要 Content-Length」。

Java 视角对照：它替代了谁

与 HttpURLConnection / OkHttp / Apache HttpClient 的关系
  • vs HttpURLConnection：后者不支持 HTTP/2、无 WebSocket、异步要靠线程池硬扛、Keep-Alive 细节暴露给用户。JEP 321 之后官方推荐新代码用 java.net.http。
  • vs OkHttp / Apache HttpClient：第三方库仍有价值——连接池策略、重试/熔断、拦截器、cookie 自动管理等应用层能力 JDK 并不提供。java.net.http 的定位是「标准的传输层 + 协议层实现」，不是全家桶框架。

四维度生产检查

维度本特性的覆盖情况
并发语义HttpClient 实例线程安全、可复用，内部是共享的 Selector 事件循环 + ConnectionPool；HTTP/2 在单连接上多路复用，多个并发请求可共享一条 TCP 连接。是否复用同一 client 决定了连接池能否收敛——不要每次请求 HttpClient.newHttpClient()。
异常容错传输层：IOException / ConnectTimeoutException / HttpTimeoutException（请求超时）/ HttpConnectTimeoutException；中断：InterruptedException。HTTP 状态码 4xx/5xx 不是异常，只体现在 statusCode()——这是最常见的误用点。
边界判断重定向默认关；请求超时默认无；连接超时默认无；ofString() 的字符集由响应头决定（无 charset 时落 UTF-8，而非 RFC 的 ISO-8859-1）；HTTP/2 明文需 h2c 升级。
性能开销共享 client + Keep-Alive 池摊薄握手成本；HTTP/2 多路复用减少连接数；ofString() / ofByteArray() 会把整个响应体缓存在内存——大响应体必须改用 ofInputStream() 或自定义 BodySubscriber 流式消费。

源码片段：ofString 的字符集到底怎么定的

// OpenJDK 25 · java.net.http/java/net/http/HttpResponse.java
public static BodyHandler<String> ofString() {
    // 注意：不是无脑 UTF-8，而是「从响应头解析 charset」
    return (responseInfo) -> BodySubscribers.ofString(charsetFrom(responseInfo.headers()));
}

// OpenJDK 25 · java.net.http/jdk/internal/net/http/common/Utils.java
public static Charset charsetFrom(HttpHeaders headers) {
    String type = headers.firstValue("Content-type")
                         .orElse("text/html; charset=utf-8");   // 完全没有 Content-Type 时的兜底
    int i = type.indexOf(";");
    if (i >= 0) type = type.substring(i + 1);                   // 取 ; 之后的参数部分
    try {
        HeaderParser parser = new HeaderParser(type);
        String value = parser.findValue("charset");
        if (value == null) return StandardCharsets.UTF_8;       // 有 Content-Type 但没 charset
        return Charset.forName(value);
    } catch (Throwable x) {
        return StandardCharsets.UTF_8;                          // charset 写错 → 静默回退 UTF-8
    }
}
常见误区：ofString() 默认 ISO-8859-1？

不是。BodyHandlers.ofString() 从不按 RFC 2616 的 text/* 默认 ISO-8859-1 解码：拿不到 charset 一律落 UTF-8，连 Charset.forName 抛异常都静默回退 UTF-8。这意味着响应头没写 charset 但正文是 GBK 的老接口会拿到乱码，必须显式 BodyHandlers.ofString(GBK)。

// 全局唯一，随应用生命周期创建 —— executor 用显式 ThreadPoolExecutor，不用 Executors.newFixedThreadPool
private static final ExecutorService CALLBACKS = new ThreadPoolExecutor(
        16, 16, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(512),                  // 有界队列：宁可显式拒绝，也不静默堆积
        r -> { Thread t = new Thread(r, "http-cb"); t.setDaemon(true); return t; },
        new ThreadPoolExecutor.AbortPolicy());          // 明确的拒绝策略（见下方说明）

private static final HttpClient HTTP = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(3))
        .followRedirects(HttpClient.Redirect.NORMAL)
        .executor(CALLBACKS)                            // 不设则 JDK 用 newCachedThreadPool（线程数无界）
        .build();

public String getJson(String url) throws Exception {
    HttpRequest req = HttpRequest.newBuilder(URI.create(url))
            .header("Accept", "application/json")
            .timeout(Duration.ofSeconds(2))      // 请求级超时，必须设
            .GET().build();
    HttpResponse<String> resp = HTTP.send(req, BodyHandlers.ofString());
    if (resp.statusCode() / 100 != 2) {
        throw new IllegalStateException("HTTP " + resp.statusCode());  // 状态码不是异常
    }
    return resp.body();
}
追问：生产里到底能不能用 Executors.newFixedThreadPool？

能用，但不该当默认——问题不在「fixed」三个字，在 Executors.* 工厂方法把有界性藏了起来：

  • Executors.newFixedThreadPool(n, tf) 内部是 ThreadPoolExecutor(n, n, 0, ms, LinkedBlockingQueue)：队列无界、没有拒绝策略。下游变慢时任务在队列里无限堆积，症状是延迟爬升直到堆耗尽，而 CPU 看着很闲——没有背压、没有告警。这正是 Effective Java / JCiP 反复强调的「显式 ThreadPoolExecutor + 有界队列 + 明确 RejectedExecutionHandler」。
  • Executors.newCachedThreadPool 反过来是线程数无界：回调一旦阻塞，线程会一路涨。而 JDK 给 HttpClient 的默认 executor 恰恰就是 newCachedThreadPool（jdk.internal.net.http.HttpClientImpl，未调用 .executor(...) 时创建），所以不设池时的风险是「回调阻塞 → 线程暴涨」，设成 fixed 的风险是「回调堆积 → 队列膨胀」。
  • 这个 executor 到底跑什么：看 HttpClientImpl.DelegatingExecutor.execute——当前在 selector 线程上 → 转交你设的 executor；在其它线程 → 直接 command.run() 内联执行。它只负责异步任务/回调派发，连接 I/O 仍在 selector 线程。
  1. 回调里不许阻塞：不做同步 send、不解析大 JSON、不查库——重活提交到业务线程池，回调只做转发。
  2. 池要有界且可诊断：有界队列 + 具名线程（上面代码的 http-cb），容量按峰值回调并发量估。
  3. 别用 CallerRunsPolicy：拒绝若发生在 selector 线程提交路径上，回调会被直接跑在 selector 线程里，卡住整个 client 的 I/O 循环（所有连接一起变慢）。Java 11 的实现没有「拒绝后回退到内部池」的兜底（JDK 25 才加），异常会抛回提交处——所以宁可 AbortPolicy + 埋点报警，或把队列调大。
  4. newFixedThreadPool 并非禁用项：内部小工具、回调确定极短且量可控时完全够用。被否的是「拿它当 HTTP 回调池的默认答案」。
关键点：问「能不能用 Executors」之前先问「队列有没有界、拒绝了怎么办、回调会不会阻塞」——这三个问题答不上来，换成显式 ThreadPoolExecutor 也不会自动变好。

选型：什么时候不该用 java.net.http

  • 需要连接池精细调优、自动重试、熔断、拦截器链 → Apache HttpClient 5 / OkHttp
  • 需要Cookie 自动持久化、会话保持的浏览器级行为 → 用 CookieFilter 要自己搭，不如库
  • 需要零依赖的极简同步调用且只支持 HTTP/1.1 → HttpURLConnection 仍可用（但没有理由再选它）
  • 需要 gRPC / QUIC → 都不在 JDK 范围内

L5 · 面试层：追问链

Q1: HTTP Client 在 Java 11 中的变化是什么？核心抽象有哪些？

JEP 321 把 jdk.incubator.http 从孵化模块转正为 java.net.http 标准模块。核心抽象四个：HttpClient（客户端，线程安全可复用）、HttpRequest（不可变请求）、HttpResponse<T>（响应）、以及基于 Flow 的 BodyHandler / BodyPublisher / BodySubscriber 三件套。同时提供同步 send、异步 sendAsync（返回 CompletableFuture）和 WebSocket API。

关键点：正式版的包名没有 incubator，意味着 ABI 稳定、可长期依赖。
Q2: 追问 — send 和 sendAsync 是两套实现吗？

不是。底层都是同一条由 Selector 驱动的异步管线，send 只是在其上做同步等待，因此需要响应 InterruptedException。这带来一个并发语义要点：HttpClient 实例本身线程安全、内部共享连接池与事件循环，并发请求应该复用同一实例，而不是每次新建。

关键点：同步 API 是异步 API 的封装，不是另一条代码路径。
Q3: 追问 — 写出请求分发的伪代码，重定向与超时的默认判断条件是什么？
version       = req.version()      默认 HTTP_2（明文无 h2c 则降级 1.1）
connectTO     = client.connectTimeout()   默认 null = 无限
requestTO     = req.timeout()              默认 null = 无限
redirectPolicy= client.followRedirects()   默认 NEVER = 不跟随
exchange      = MultiExchange + Filter 链(Redirect/Auth/Cookie)
              → ConnectionPool 取/建连接 → Http1Exchange 或 Http2 Stream

核心判断条件：是否显式配置。所有「像框架一样好用」的行为（重定向、超时、重试）在 JDK 里全部默认关闭——这是 JDK API 的一贯风格：默认最小惊讶，能力自己开。

关键点：默认不跟随重定向 + 默认无超时，是线上最容易踩的两个坑。
Q4: 追问 — BodyHandlers.ofString() 用什么字符集解码？

由 Utils.charsetFrom(headers) 决定：从 Content-Type 的 charset= 参数解析；没有 Content-Type、没有 charset、或 Charset.forName 失败，一律回退 UTF-8（实现里连默认兜底值都是 text/html; charset=utf-8）。它不遵循 HTTP/1.1 对 text/* 默认 ISO-8859-1 的规定。

关键点：老接口返回 GBK 却不写 charset，必然乱码，必须显式传 Charset。
