L1 · 概念层：一批「早就该有」的方法

Java 11 的类库增强没有新框架，全是把社区写了十年的工具方法收编进 JDK。五组：

组新增解决的老问题
StringisBlank()isEmpty() 只判空串，不认空白
strip() / stripLeading() / stripTrailing()trim() 只按 ' ' 截断，处理不了全角空格与 NBSP
lines()拆行要写 split("\r?\n")
repeat(int)拼分隔符/边框要写循环或 Collections.nCopies
（Java 11 的 String 到此为止只有这 6 个；indent / transform 是 Java 12 才加的）
FilesreadString(Path)、writeString(Path, CharSequence, OpenOption...)读小文件要 new String(Files.readAllBytes(p), UTF_8)
CollectiontoArray(IntFunction<T[]>)toArray(new String[0]) 的堆污染与误写 new String[size]
其他Optional.isEmpty()、Path.of(...)与 optional.isPresent() 对称；Paths.get 的静态工厂写法
流式读InputStream.readNBytes(int)、readNBytes(int,int)分块读要手写 while ((n = in.read(buf)) != -1)；readAllBytes() 只有「一次全量」一档

用法速览

"  \u3000\u3000 ".isBlank();                 // true —— 全角空格也算空白
"\u3000x\u3000".strip().length();            // 1 —— 全角空格被剥掉
"a\r\nb\nc".lines().collect(Collectors.toList()); // ["a", "b", "c"]，不含换行符（.toList() 要 Java 16）
"-".repeat(20);                              // "--------------------"

// Files —— UTF-8 默认
Files.writeString(Path.of("a.txt"), "hello");
String s = Files.readString(Path.of("a.txt"));

// Collection —— 数组生成器，杜绝 new String[10] 这种错法
String[] arr = list.toArray(String[]::new);

// 其他
Optional.ofNullable(x).isEmpty();
Path p = Path.of("conf", "app.yaml");        // Java 11 起可替代 Paths.get

// 流式读 —— Java 11 新增的「按块」读法（readAllBytes/transferTo 是 9，这个是 11）
try (InputStream in = Files.newInputStream(path)) {
    byte[] head = in.readNBytes(8192);        // 最多读 8192 字节，到 EOF 提前返回
    int skip = 0;                             // 两参版本：偏移量 + 最大长度
    byte[] buf = in.readNBytes(skip, 4096);
}
toArray(IntFunction) 到底改了什么

老写法 toArray(new String[10]) 有个隐蔽陷阱：如果集合元素少于 10，JDK 会新建一个恰好大小的新数组返回，你拿到的不是你传进去的那个——「传数组能复用」的前提是数组够长且所有元素都能存入。而 new String[size] 更糟：size 是集合当时的长度，并发修改下可能 ArrayStoreException。toArray(String[]::new) 把「创建数组」这件事交回集合自己按需执行，语义干净。

L2 · 原理层：几个方法的语义细节

strip / isBlank 的空白定义：跟随 Character.isWhitespace

strip() 和 trim() 的区别不是「更强」，而是「判据不同」：

方法空白判据能剥掉剥不掉
trim()单字节 c <= ' '（'\u0020' = 32）空格、Tab、LF、CR（均 ≤ 32）全角空格 \u3000、EM 空格 \u2003、不换行空格 \u00A0（均 > 32）
strip()Character.isWhitespace(int)Tab、LF、CR、全角空格 \u3000、EM 空格 \u2003\u00A0 不换行空格（NBSP）
isBlank()同上，空串或全为 isWhitespace 码点即 true—"\u00A0" 返回 false
实测确认的坑：strip() 剥不掉 NBSP

在 OpenJDK 25 上实测："\u00A0x\u00A0".strip().length() == 3（首尾 NBSP 原样保留），"\u00A0".isBlank() == false。原因在 Character.isWhitespace 的规范：类别为 SPACE_SEPARATOR 但非 break 的字符（如 NBSP）不算空白。网页抓来的文本常用 NBSP 做排版，用 strip() 清洗会残留——这类数据应先 replace('\u00A0', ' ')。

lines() 的拆行规则

行终止符只认三种：\n、\r、\r\n。返回的行不含终止符。javadoc 的 @apiNote（这批方法没有独立 JEP）明确了两个边界：

"".lines().count()      // 0 —— 空串没有行
"a\n\n".lines().count() // 2 —— 末尾换行之后不再产生空行（["a", ""]）
"a\nb".lines().count()  // 2
"a\r\nb".lines().count()// 2，\r\n 被视为一个终止符

// implNote：比 split("\R") 更快 —— 惰性供给元素 + 更快的终止符搜索

关键判断逻辑伪代码：strip 的边界扫描

function strip(s):
    lo = 0
    hi = s.length - 1
    # 核心判断条件：Character.isWhitespace(codePointAt(i))
    while lo <= hi && isWhitespace(s.codePointAt(lo)): lo += 1
    while hi >= lo && isWhitespace(s.codePointAt(hi)): hi -= 1
    if lo == 0 && hi == s.length - 1: return s     # 无可剥，返回原对象（不分配）
    if lo > hi: return ""                          # 全是空白
    return s.substring(lo, hi + 1)

function isBlank(s): return indexOfNonWhitespace(s) == s.length
实现注：这份伪代码是「契约」，真实实现藏在 StringLatin1 / StringUTF16

契约层就是 Character.isWhitespace(int)（javadoc 的 @see Character.isWhitespace(int) 已经写死）。真实扫描在 StringLatin1.indexOfNonWhitespace(byte[] value)：先短路 ch != ' ' && ch != '\t'（ASCII 高频快速通过），不命中再走 CharacterDataLatin1.instance.isWhitespace(ch)。外层 strip() 用 ret == null ? this : ret 兜住「一个都没剥掉」的返回，伪代码里那句 return s 就对应它。

为什么 Java 9 引入 compact strings 后，这些方法都走双实现？

看 String.strip() 的方法体：isLatin1() ? StringLatin1.strip(value) : StringUTF16.strip(value)。因为 Java 9 起 String 内部是 byte[] + coder（Latin-1 或 UTF-16 两种紧凑表示），所有逐字符扫描的方法都必须按 coder 分派，否则按 char 步长遍历会踩错字节边界。这正是 Compact Strings 源码走读 那一课的直接后果——新增 String 方法的实现成本因此翻倍。

Files.readString / writeString 的实现

// OpenJDK 25 · java.base/java/nio/file/Files.java
public static String readString(Path path) throws IOException {
    return readString(path, UTF_8.INSTANCE);          // 无 Charset 重载 = UTF-8
}

public static String readString(Path path, Charset cs) throws IOException {
    Objects.requireNonNull(path);
    Objects.requireNonNull(cs);
    byte[] ba = readAllBytes(path);                   // ← 一次性全量读进 byte[]
    if (path.getClass().getModule() != Object.class.getModule())
        ba = ba.clone();
    return JLA.uncheckedNewStringNoRepl(ba, cs);      // 解码成 String
}

public static Path writeString(Path path, CharSequence csq, OpenOption... options)
        throws IOException {
    return writeString(path, csq, UTF_8.INSTANCE, options);  // 无 Charset 重载 = UTF-8
}

四维度生产检查

维度本组 API 的情况
并发语义全部是无状态静态方法或不可变对象操作，线程安全。但 toArray(IntFunction) 与 toArray(T[]) 一样，遍历时集合被并发修改仍会抛 ConcurrentModificationException——生成器只解决「数组怎么造」，不解决「快照语义」。
异常容错readString：文件不存在 → NoSuchFileException；字节序列不是合法字符集 → 直接抛 MalformedInputException（它本身就是 IOException 的子类，不是被「包装」进 IOException 的）；repeat：负数 → IllegalArgumentException，长度溢出 → OutOfMemoryError；writeString 参数为 null → NullPointerException（在打开文件之前就校验）。
边界判断NBSP 不被 strip/isBlank 认作空白；lines() 末尾换行不产生空行；repeat(0) 或空串 → ""；repeat(1) 返回 this（零拷贝）；writeString 不是原子写。
性能开销readString = readAllBytes + 解码，整个文件进堆，大文件会 OOM；repeat 用2 的幂倍增拷贝（25 抽成 repeatCopyRest，jdk11u 是同构的内联循环），复杂度 O(n) 而非 O(n²)；strip 无可剥时返回原对象，不分配。

下文片段取自本地 OpenJDK 25 的 lib/src.zip，方法行号按 25 计；与 Java 11 的 jdk11u 差异已逐条回查：

  • strip / isBlank / lines 的方法体与 jdk11u 逐字一致，行号表里只有行号会漂。
  • repeat(int)：25 把倍增循环抽成私有工具 repeatCopyRest(multiple, 0, limit, len)；jdk11u 没有这个方法，循环是内联的（for (; copied < limit - copied; copied <<= 1) System.arraycopy(multiple, 0, multiple, copied, copied);），且溢出判断排在单字符快路径之后（25 把它提到了快路径之前）。语义与复杂度不变。
  • Files.readString：25 用 JLA.uncheckedNewStringNoRepl(ba, cs)，jdk11u 用的是同族的 JLA.newStringNoRepl；两步骨架与「UTF-8 默认」在 11 就已定型。
  • Files.writeString：jdk11u 源码里那句 // ensure the text is not null before opening file 证实了「null 校验发生在打开文件之前」——L4 坑清单里的结论以此为据。

源码片段：repeat 的三道防线

// OpenJDK 25 · java.base/java/lang/String.java :: repeat(int count)
public String repeat(int count) {
    if (count < 0) {
        throw new IllegalArgumentException("count is negative: " + count);   // 防线 1：负数
    }
    if (count == 1) {
        return this;                                                          // 防线 2：零成本返回
    }
    final int len = value.length;
    if (len == 0 || count == 0) {
        return "";                                                            // 空串
    }
    if (Integer.MAX_VALUE / count < len) {
        throw new OutOfMemoryError(
            "Required length exceeds implementation limit");                  // 防线 3：溢出预判
    }
    if (len == 1) {
        final byte[] single = new byte[count];                                // 单字符快路径
        Arrays.fill(single, value[0]);
        return new String(single, coder);
    }
    final int limit = len * count;
    final byte[] multiple = new byte[limit];
    System.arraycopy(value, 0, multiple, 0, len);
    repeatCopyRest(multiple, 0, limit, len);                                  // 2 的幂倍增复制
    return new String(multiple, coder);
}
为什么溢出要用 Integer.MAX_VALUE / count < len 而不是 len * count > MAX？

后者会先溢出成负数再比较，判定失效；前者用除法在乘法发生之前判断，是整数溢出预检的标准写法。这类细节是 code reviewer 角度的高频考点。溢出时抛的是 OutOfMemoryError——Java 11 的文案是 Repeating N bytes String M times will produce a String exceeding maximum size.（"ab".repeat(Integer.MAX_VALUE) → N=2, M=2147483647）；Required length exceeds implementation limit 是 JDK 17 之后才改写的同一条消息。

源码片段：isBlank 与 strip 的最小实现

// OpenJDK 25 · java.base/java/lang/String.java
public boolean isBlank() {
    return indexOfNonWhitespace() == length();   // 第一个非空白位置 == 长度 ⇒ 全空白
}

public String strip() {
    String ret = isLatin1() ? StringLatin1.strip(value)
                            : StringUTF16.strip(value);
    return ret == null ? this : ret;             // 返回 null 表示「无可剥离」，复用原对象
}

设计要点：strip 用 null 作为「不用变」的哨兵，避免了无谓的 substring 分配——这在循环里高频调用时是可观测的 GC 收益。

L5 · 面试层：追问链

Q1: trim() 和 strip() 的区别是什么？

判据不同。trim() 剥离所有 c <= ' '（'\u0020'）的字符，只能处理 ASCII 空白；strip() 以 Character.isWhitespace(int) 为准，能处理全角空格 \u3000、EM 空格 \u2003 等 Unicode 空白。两者都剥不掉不换行空格 \u00A0——因为 isWhitespace 明确把非断行的 SPACE_SEPARATOR 排除在外。

关键点：strip() 是「换判据」，不是「加范围」。
Q2: 追问 — 为什么 strip() 的源码要分成 StringLatin1 和 StringUTF16 两套？

因为 Java 9 的 Compact Strings 把 String 内部从 char[] 改成了 byte[] + coder。同一个字符串可能是 Latin-1（1 字节/字符）或 UTF-16（2 字节/字符）编码，按不同步长扫描就必须分派到两套实现，否则会踩错字节边界。String.strip() 的方法体就是一行三元：isLatin1() ? StringLatin1.strip(value) : StringUTF16.strip(value)。

关键点：这是 Java 9 源码层变更对后续所有 String API 的持续性税。
Q3: 追问 — 写出 strip() 的边界扫描伪代码，核心判断条件是什么？
lo = 0; hi = len - 1
while lo <= hi && isWhitespace(codePointAt(lo)): lo++
while hi >= lo && isWhitespace(codePointAt(hi)): hi--
if lo == 0 && hi == len - 1: return this    # 无分配
if lo > hi: return ""
return substring(lo, hi + 1)

核心判断条件：Character.isWhitespace(codePoint)。注意三个细节：用 codePointAt 而非 charAt（代理对安全）；无可剥时返回原对象（省一次分配）；全空白返回 "" 而不是 null。

关键点：isBlank() 就是 indexOfNonWhitespace() == length() 的一句话版本。
Q4: 追问 — Files.readString 的实现是什么？有什么性能风险？

无 Charset 重载委托给 readString(path, UTF_8)；带 Charset 的版本核心只有两步——byte[] ba = readAllBytes(path)，再 JLA.newStringNoRepl(ba, cs) 解码（中间还有 requireNonNull 校验与跨模块的数组 clone()）。所以整个文件会一次性进堆，再解码成 String——存在两份内存峰值。风险是大文件 OOM；另外默认 UTF-8，非 UTF-8 文件直接抛 IOException，且解码失败是异常而不是替换字符。

关键点：它是「便捷」不是「流式」；writeString 也不是原子写。
Q5: 追问 — toArray(String[]::new) 和 toArray(new String[0]) 有什么区别？

语义上等价（都由集合创建正确大小的数组），但 IntFunction 版本把「创建数组」的意图表达得更明确，且 接口文档规定默认实现是「先用 0 调用生成器，再把结果交给 toArray(T[])」（@implSpec 原话 return toArray(generator.apply(0))，@since 11）。真正的收益是杜绝两类手写错误：new String[10] 这种过大数组（返回的往往不是你传的那个），以及 new String[c.size()] 在并发修改下的 ArrayStoreException。

关键点：生成器解决「数组怎么造」，不解决「快照语义」——并发修改仍会 CME。
Q6: 追问 — readNBytes 是 Java 几加的？和 readAllBytes / transferTo 怎么分年份？
  • InputStream.readNBytes(int) 与 readNBytes(int off, int len) → Java 11，本课新增的「按块」读法；返回实际读到的字节数，可能小于请求量（短读是常态，不是错误）。
  • InputStream.readAllBytes()、transferTo(OutputStream) → Java 9，「一次全量 / 一次导完」的一步到位版本。
  • Files.lines(Path) → Java 8，按行流式，和 readNBytes 是两种切分维度（行 vs 字节块）。
  • Stream.toList() → Java 16，所以 L1 速览里写的是 collect(Collectors.toList())。

问年份的本质是问「你要的是一次读完、还是分块读」：readAllBytes 会把整条流吞进堆，readNBytes(8192) 可以在已知头部长度时只取前缀。

关键点：9 给了「全量」，11 补了「按块」；流式（行）比字节块更早，是 8。
Q7: 代码审查 — Files.lines() 和 Files.readString() 该怎么选？
  • 选 readString：KB 级的配置、证书、短消息体。整文件进堆、UTF-8 默认，换取一次调用读完。
  • 选 lines()：日志、CSV、大 JSON 等可能很大的文件——它是惰性 Stream<String>，按行供给，不建中间数组。
  • 用 lines() 必须关流：包成 try-with-resources，或显式 stream.close()——流没关就把文件句柄挂到终止管道上，长跑进程会攒满 fd。
  • 不要拿它当「快」的读法：逐行解码 + Stream 管道开销高于 BufferedReader.readLine() 的裸循环；要极致性能就退回老三样。
关键点：K 是 KB 还是 GB 决定方法；lines() 的 close() 是审查红线。
Q8: 追问 — Path.of("conf", "app.yaml") 和 Paths.get(...) 有什么区别？
  • 实现上等价：两者都是 FileSystems.getDefault().getPath(first, more) 的静态门面，语义、返回对象、抛的异常完全一样。
  • Path.of 是接口上的静态方法（Java 11 新增），Paths.get 是 Paths 工具类的方法——后者只是更早存在的旧写法，没有被废弃。
  • 习惯上的收益：按接口类型建静态工厂，少 import 一个 Paths，且和 List.of / Map.of / Optional.isEmpty 的「工厂方法下沉到类型」风格一致。
  • 没有兼容风险：新代码可以直接用 Path.of；老代码换写法是纯等价重构，不必专门改。
关键点：这是风格统一，不是行为变更——JLS 层面零差异。
