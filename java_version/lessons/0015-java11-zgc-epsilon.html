L1 · 概念层：一个求「最快停顿」，一个求「完全不停顿」

Java 11 同时引入了两个方向相反的实验性 GC，它们共同依赖 Java 10 的 JEP 304（GC 接口） 和 JEP 312（Thread-Local Handshakes）：

ZGC（JEP 333）Epsilon（JEP 318）
一句话可伸缩的低延迟收集器只分配、不回收的 no-op 收集器
回收并发标记 + 并发重定位，全程几乎不 STW永不回收；堆满即 OutOfMemoryError
核心机制着色指针（colored pointers）+ 加载屏障（load barrier）线性分配 + 空屏障集（no-op barrier set）
目标停顿 < 10ms；吞吐相对 G1 降幅 ≤ 15%延迟开销趋近于 0，用内存换
定位生产方向（当时为 experimental）测试/基准/短任务工具
启用-XX:+UnlockExperimentalVMOptions -XX:+UseZGC-XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC
平台JDK 11 仅 Linux/x64跨平台（纯共享代码）
为什么 JDK 11 同时上两个「不像话」的 GC？

它们其实是 JEP 304「Garbage Collector Interface」的验收测试。JEP 304 把 GC 从 HotSpot 里解耦成可插拔组件；Epsilon 的存在意义之一就是证明这个接口足够「空」——一个什么都不做的 GC 只要实现默认屏障就能跑起来，说明接口抽象是对的。ZGC 则反过来证明接口足够「强」，能容纳一个带全新屏障模型的收集器。

L2 · 原理层

ZGC：着色指针 + 加载屏障

JEP 333 的原话：“A core design principle/choice in ZGC is the use of load barriers in combination with colored object pointers.”

着色指针：把 64 位引用拆成三段——低段是对齐偏移（4 字节粒度），中段是 4 bit 元数据（Marked0 / Marked1 / Remapped / Finalizable），高段是真实地址。元数据位不描述「对象在哪」，而描述「这个引用处于哪种视图/状态」。

加载屏障：Java 线程每次读取一个引用字段时都会过一道 LoadReferenceBarrier。屏障检查指针的元数据位，若发现「这是个坏指针（BadMask）」就地修正（heal）——比如把指向已重定位对象的旧地址改写为新地址。这就是 ZGC 能让应用线程和重定位并发跑的原因：不需要 STW 去统一改指针，谁读到旧的谁负责修。

flowchart TB A[并发周期开始] --> B[并发标记 Mark
标记存活对象 + 更新 Marked 位] B --> C[短暂 STW: 根扫描
暂停与堆大小无关] C --> D[并发重定位 Relocate
把存活对象搬到新 Page] D --> E[并发重映射 Remap
把引用改到新地址] E --> F[周期结束
BadMask 随相位切换] C -.->|只此一处 STW| G[停顿 < 10ms 目标]

JEP 333 对 STOP-THE-WORLD 的约束是：STW 阶段只限于根扫描（root scanning），因此停顿时间不随堆大小或存活集增长而增长——这是它与 G1/CMS 最本质的区别。

ZGC 设计目标（JEP 333 原文）数值
GC 停顿不超过 10ms（SPECjbb 2015 实测 avg 1.09ms，max 1.68ms；G1 avg 156.8ms，max 543.8ms）
堆规模几百 MB 到 数 TB
吞吐损失相对 G1 不超过 15%（实测 max-jOPS 100% vs 91.2%，critical-jOPS 76.1% vs 54.7%）
初始平台Linux/x64

Epsilon：把 GC 做到「空」

Epsilon 的实现只有两件正事：在一块连续内存上做线性分配，以及发 TLAB（thread-local allocation buffer）。

机制实现
分配单块连续内存上的线性分配；发 TLAB 是无锁的，TLAB 内分配复用 VM 现有代码
屏障完全为空（BarrierSet 全部 no-op）——因为不做标记、不看对象图
堆满抛带描述信息的 OutOfMemoryError；可配合 -XX:+HeapDumpOnOutOfMemoryError、-XX:OnOutOfMemoryError=...
System.gc()什么都不做，实现可能警告「这次 GC 是徒劳的」

关键判断逻辑伪代码：Epsilon 堆满时的处置

function allocate(size):
    if currentTop + size < heapEnd:
        currentTop += size          # 线性 bump，O(1)，无锁
        return ptr
    # 分配失败 —— 唯一的「回收」路径就是退出
    if -XX:+HeapDumpOnOutOfMemoryError:  dumpHeap()
    if -XX:OnOutOfMemoryError=CMD:       runExternal(CMD)
    throw OutOfMemoryError("Epsilon GC needs X MB more heap")

四维度生产检查（deep-mastery 硬性清单）

维度ZGCEpsilon
并发语义标记/重定位全程并发；只有根扫描 STW。依赖 JEP 312 Thread-Local Handshakes 让单线程握手替代全局 Safepoint。分配是无锁 TLAB + 线性 bump，天然无 GC 线程并发。
异常容错JDK 11 实验版不支持类卸载（ClassUnloading 被禁用，开了也无效）；不支持 JVMCI/Graal（EnableJVMCI 会报错）。堆满 = 进程终止。没有任何降级路径，只能靠预估 -Xmx + OOM 钩子兜底。
边界判断仅 Linux/x64；需 UnlockExperimentalVMOptions；着色指针要预留巨大虚拟地址空间（依赖 64 位平台）。绝对不能开在长期运行的服务上；System.gc() 无效会让依赖 GC 的代码静默失效。
性能开销每读引用过一次屏障（成本被 JEP 312 + 编译器屏障移除优化摊薄）；着色指针带来 multi-mapping 的虚拟内存占用。延迟开销≈0，但空间不释放；非移动式分配还会让对象保持分配顺序，随机分配的负载空间局部性变差。

源码片段：着色指针的位布局（zGlobals.hpp，openjdk/jdk11u）

// src/hotspot/share/gc/z/zGlobals.hpp   (openjdk/jdk11u)

// Global phase state
const uint32_t    ZPhaseMark         = 0;
const uint32_t    ZPhaseMarkCompleted= 1;
const uint32_t    ZPhaseRelocate     = 2;

// Page types
const uint8_t     ZPageTypeSmall     = 0;
const uint8_t     ZPageTypeMedium    = 1;
const uint8_t     ZPageTypeLarge     = 2;

// Pointer part of address（低位：对齐偏移）
const uintptr_t   ZAddressOffsetShift = 0;
const uintptr_t   ZAddressOffsetBits  = ZPlatformAddressOffsetBits;

// Metadata part of address（中段：固定 4 bit）
const uintptr_t   ZAddressMetadataBits = 4;
const uintptr_t   ZAddressMetadataMarked0      = 1 << (Shift + 0);
const uintptr_t   ZAddressMetadataMarked1      = 1 << (Shift + 1);
const uintptr_t   ZAddressMetadataRemapped     = 1 << (Shift + 2);
const uintptr_t   ZAddressMetadataFinalizable  = 1 << (Shift + 3);

//          GoodMask   BadMask   WeakGoodMask  WeakBadMask
// Marked0    001        110        101          010
// Marked1    010        101        110          001
// Remapped   100        011        100          011
extern uintptr_t  ZAddressGoodMask;
extern uintptr_t  ZAddressBadMask;
extern uintptr_t  ZAddressWeakBadMask;

怎么读这张表：ZGC 有两套「标记位」（Marked0 / Marked1），每次周期交替使用（双缓冲），这样上一轮的指针与本轮的指针可以用位模式区分开。GoodMask 是「当前相位下合法的指针位模式」，BadMask 是「需要被屏障修正的模式」——屏障的全部逻辑就是 (ptr & BadMask) != 0 则修正。相位切换时全局翻转 GoodMask/BadMask，旧指针自动变成「坏的」，谁读到谁 heal，无需 STW 扫全堆。

Epsilon 的适用与禁用场景

场景是否可用理由
性能基准测试（要剥离 GC 噪声）✅JEP 318 列的第 1 个用例：得到「无 GC 干扰」的延迟基线

GC 选型决策（Java 11 语境）
  • 默认吞吐优先 → G1（Java 9 起已是默认）
  • 要求 p99 停顿个位数毫秒、堆大、平台是 Linux/x64 → 试 ZGC（先在灰度环境跑 SPECjbb / 业务压测，确认吞吐降幅在 15% 内）
  • 跑一次性批处理、不想等 GC → Epsilon，并把 -Xmx 卡到「预期峰值 + 安全余量」
  • 需要 CMS → 别再用了（JEP 291 已弃用，JDK 14 移除）

为什么不在 G1 上做并发压缩？（ZGC 的 Alternative 分析）

JEP 333 明确记录：给 G1 加并发压缩能力的原型被彻底验证后放弃——「把从没为此设计的功能塞进 G1，同时还要保住它的稳定性与其它优点，是不可行的」。CMS 路线也被否决：不压缩、remark 阶段无界、代码复杂、已被弃用。剩下的并行路线是 Shenandoah 的 Brooks 指针（JEP 189）。这个「为什么另起炉灶而不是改造老 GC」的论证，是架构师角度的经典追问。

L5 · 面试层：追问链

Q1: ZGC 的停顿为什么能做到与堆大小无关？

因为 ZGC 把唯一需要 STW 的阶段限制在根扫描，标记、重定位、重映射全部并发执行；而根扫描的规模只取决于线程栈与静态根的数量，与堆中对象数量无关。真正改指针的工作不是由 GC 统一做的，而是由加载屏障在应用线程读到旧指针时「顺手」修正，把成本分散到了整个并发周期里。

关键点：STW 范围受限 + 屏障摊薄成本，二者缺一不可。
Q2: 追问 — 写出加载屏障的判断逻辑伪代码，核心条件是什么？
function loadReferenceBarrier(ptr):
    if (ptr & ZAddressBadMask) == 0:      # 核心判断：是不是「好指针」
        return ptr                        # 好指针，零开销放行
    # 坏指针 → 查转发表/新地址并写回
    newPtr = (ptr & ~MetadataMask) | GoodMask   # 转成当前相位的好指针
    newPtr = forward(ptr)                       # 必要时查 ForwardingTable
    store_back(newPtr)                          # heal：把引用改写成新的
    return newPtr

核心条件：(ptr & BadMask) != 0。GoodMask/BadMask 是一组全局变量，每完成一个相位就整体翻转——所以相位一变，全堆的旧指针自动落进 BadMask，不需要任何全局扫描就能「标记」出待处理的引用。

关键点：着色指针不是为了「找对象」，是为了「用位模式表达指针的时效性」。
Q3: 追问 — Epsilon 有什么用？一个不回收的 GC 怎么好意思进 JDK？

四个正经用途（JEP 318 原文）：性能测试（剥离 GC 噪声得到延迟基线）、内存压力测试（把 -Xmx 当分配上限断言）、VM 接口测试（验证 JEP 304 接口的最小实现）、极短生命周期任务（退出即释放，跑 GC 循环纯浪费）。它本质上是把「生态里很多人自己魔改 JVM 关掉 GC」这件事标准化、可配置化。

代价是：堆满即崩、System.gc() 失效、非移动式分配让随机分配的负载空间局部性变差。

关键点：它是测试工具，不是生产 GC；误开是高危配置错误。
Q4: 追问 — Java 11 的 ZGC 有哪些「实验性」代价？

(1) 需要 -XX:+UnlockExperimentalVMOptions；(2) 仅 Linux/x64；(3) 不支持类卸载——ClassUnloading / ClassUnloadingWithConcurrentMark 被禁用，打开也无效，动态生成类的场景会堆涨；(4) 不支持 JVMCI/Graal，开 EnableJVMCI 直接报错；(5) 单代（分代 ZGC 要到 JDK 21）。因此 JDK 11 的 ZGC 适合做评估和灰度，不适合做「无条件全量切换」。

关键点：JDK 15 才转正（JEP 377），JDK 11 的定位是 experimental。
Q5: 追问 — 为什么不给 G1 加并发压缩，而要另造 ZGC？

JEP 333 的 Alternatives 章节记录了这个决策：G1 的并发压缩原型被大量验证后放弃，理由是「把从未为此目的设计的功能塞进 G1、同时还要保住其稳定性与其它优点，不可行」。CMS 路线也否决（不压缩、remark 无界、已弃用）。这体现了一个架构原则：当核心机制（并发转移）与现有设计前提（region 回收 + 写屏障模型）冲突时，改造成本高于新建成本。

关键点：ZGC 与 Shenandoah 是同一问题的两种解——着色指针+加载屏障 vs Brooks 指针。
