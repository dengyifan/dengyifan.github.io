L1 · 概念层：三件「减法」的事

Java 11 的工具链主题词是瘦身与止损：把 JDK 里背了二十年的遗留技术删掉、把安全协议补到最新、把注定要删的引擎先标上记号。

JEP 320：删除 Java EE 与 CORBA 模块（9 个）

这 6 个平台模块在 Java SE 9 就已标记 @Deprecated(forRemoval)，Java 11 真正动手删除；另外 3 个相关模块一并处理：

被删模块内容
java.xml.wsJAX-WS + SAAJ + Web Services Metadata
java.xml.bindJAXB
java.activationJAF（JavaBeans Activation Framework）
java.xml.ws.annotationCommon Annotations（JSR 250 子集）
java.corbaCORBA + RMI-IIOP + javax.activity
java.transactionJTA 的 CORBA 互操作部分
java.se.ee上面六个的聚合模块
jdk.xml.wswsgen / wsimport 工具
jdk.xml.bindschemagen / xjc 工具

同时被删除的工具：wsgen、wsimport、schemagen、xjc、idlj、orbd、servertool、tnamesrv；JNDI CosNaming provider 消失；rmic 移除 -idl 与 -iiop 选项。没有任何命令行开关能再打开它们——--add-modules 也不行。

留下的东西

javax.transaction.xa（XA 事务）与 JDBC 一起住在 java.sql 模块里，不受影响。JEP 320 明确说它「将长期留在 Java SE 中」。所以删的是 JTA 的 CORBA 互操作部分，不是 XA。

JEP 332：TLS 1.3

JDK 11 支持 RFC 8446（TLS 1.3），并将其纳入默认启用的协议集。相对 TLS 1.2 的关键差异：握手轮次从 2-RTT 降到 1-RTT、支持 0-RTT 会话恢复（early data）、移除不安全算法（RSA 传输、静态 DH、CBC 模式、RC4 等）。

JEP 335：Nashorn 弃用（为移除做准备）

JDK 11 把内置的 Nashorn JavaScript 引擎标记为 deprecated for removal。jjs 工具与相关 API 从此带删除警告，最终在 JDK 15（JEP 372）被移除——JDK 11 之后没有任何 JDK 版本内置 JS 引擎。

L2 · 原理层：为什么要删，以及迁移怎么走

删除动机（JEP 320 的四条论证）

问题具体表现
版本漂移Java SE 里是 EE 技术的「快照+子集」，而 EE 上游一直在演进（例如 EE 6 的 Common Annotations 加了数据源相关内容），每次都要人工裁剪，既费时又让开发者困惑
维护双轨上游代码在 java.net → GitHub，JDK 里的副本需要人工同步
覆盖机制失效Endorsed Standards Override Mechanism 实际无人使用，大家转而往 bootstrap classpath 塞 jar、或直接放 classpath 赌 split package 不出事
没有存在必要Maven Central 上有完整的独立版本；CORBA 在现代 Java 应用中没有显著需求，Java EE 8 已把 CORBA/RMI-IIOP/JavaIDL 列为「Proposed Optional」

关键判断逻辑伪代码：升级到 11 时的编译失败排查

function diagnoseJdk11Upgrade(compilationError):
    # 1. 报错类是否属于被删模块
    if error.type 在 {javax.xml.bind.* javax.xml.ws.* javax.activation.* javax.annotation.*
                      javax.transaction.* javax.rmi.* org.omg.*}:
        return "JEP 320: 加 Maven 依赖（见迁移表），不要试图开 --add-modules"

    # 2. 是否用了 sun.misc / jdk.internal API
    if error.type 以 "sun.misc" / "jdk.internal" 开头:
        return "JDK 内部 API: 跑 jdeps --jdk-internals 定位，改用公开 API 或 --add-exports"

    # 3. 是否反射访问
    if error 是 InaccessibleObjectException / IllegalAccessException on setAccessible:
        return "JDK 16+ 强封装: 加 --add-opens 模块/包=ALL-UNNAMED"

    # 4. 是否脚本引擎
    if ScriptEngineManager.getEngineByName("js") 返回 null:
        return "JEP 335/372: Nashorn 已移除，换 GraalJS 或去掉 JS 依赖"

迁移对照表（JEP 320 原文给出的 Maven 坐标）

java.xml.ws（JAX-WS/SAAJ/Metadata）API：javax.xml.ws:jaxws-api、javax.xml.soap:javax.soap-api、javax.xml:webservices-api
实现：com.sun.xml.ws:jaxws-ri
java.xml.bind（JAXB）API：javax.xml.bind:jaxb-api

常见误区：Base64 还需要 javax.xml.bind.DatatypeConverter 吗？

JEP 320 特别点名了这个迁移陷阱：很多人用 javax.xml.bind.DatatypeConverter 只是为了做 Base64，删掉后会莫名编译失败。正确做法是用 Java 8 就有的 java.util.Base64。同理，@Generated 注解应从 javax.annotation.Generated 换成 JDK 9 引入的 javax.annotation.processing.Generated——两者都在，只是你原来那个被删了。

四维度生产检查

维度本组特性的情况
并发语义不适用（模块/协议/引擎层面改动，无并发模型变化）。但 TLS 1.3 握手次数减少直接影响连接建立耗时，长连接池收益可测。
异常容错删模块后典型错误：编译期 程序包 javax.xml.bind 不存在、运行期 NoClassDefFoundError / ClassNotFoundException。TLS 层：SSLHandshakeException（对端不支持 1.3 或 cipher 不匹配时的降级失败）、协议版本被禁用时的 handshake_failure。
边界判断迁移依赖必须部署到 classpath（JDK 9 时用 --add-modules 的写法在 11 上直接失效）；javax.transaction.xa 不用迁移；Nashorn 在 11 还能用（只是有警告），JDK 15 起直接没有——别把「11 上能跑」当成「以后都能跑」。
性能开销JDK 体积与启动内存下降（删掉无用类与工具）；TLS 1.3 首次握手 1-RTT、会话恢复可 0-RTT；但 0-RTT early data 默认关闭（有重放攻击面，需显式评估后开启）。

L4 · 边界层：升级 Java 11 的检查清单

必须处理的破坏性变更

类别现象处理
Java EE 模块被删JAXB / JAX-WS / JAF / Common Annotations 编译或运行失败加 Maven 依赖，部署到 classpath
CORBA 被删org.omg.*、RMI-IIOP 无法编译无官方替代，需改架构
工具被删xjc / wsimport / idlj 找不到改用 Maven 插件（jaxb2-maven-plugin 等）
rmic 选项被删-idl / -iiop 不再支持不再生成 IDL/IIOP stub
Nashorn 弃用ScriptEngineManager 取 "js" 出警告JDK 15 起直接为 null，尽早迁 GraalJS
内部 API 使用sun.misc.Unsafe 等jdeps --jdk-internals 全量扫描
升级 Java 11 的操作顺序
  1. 在当前 JDK 上跑 jdeps --jdk-internals，消灭内部 API 依赖
  2. 用 --release 8 编译，再切 --release 11，把报错分类：删模块 / 内部 API / 语言变更
  3. 给 JAXB/JAX-WS 等补齐 Maven 依赖（注意是 classpath，不是 module path）
  4. Base64 换 java.util.Base64，@Generated 换 javax.annotation.processing.Generated
  5. 审计 TLS：jdk.tls.client.protocols、禁用协议与 cipher 白名单是否仍指向 SSLv3/TLSv1.0
  6. 审计脚本引擎：任何 ScriptEngineManager 调用都标记为待迁移
  7. 灰度观察 GC 日志（ZGC/Epsilon 若要试用，记得 UnlockExperimentalVMOptions）

与 Java 9/10 的承接关系

  • Java 9 的 JPMS 强封装是前提：正因为 9 就把 Java EE 模块「从 classpath 编译的默认解析中剔除」，11 才能干净地删掉它们（JEP 320 原文强调了这一点）。
  • Java 10 的 JEP 304 GC 接口 + JEP 312 Handshakes 是 ZGC/Epsilon 的依赖。
  • Java 11 的 HTTP Client 经历了 9（JEP 110）、10（JEP 162）两轮孵化才转正——孵化模块（jdk.incubator.*）随时可能变，这就是 incubator 存在的意义。

L5 · 面试层：追问链

Q1: Java 11 删掉了哪些模块？为什么要删？

9 个：6 个平台模块 java.xml.ws、java.xml.bind、java.activation、java.xml.ws.annotation、java.corba、java.transaction，加聚合模块 java.se.ee，加两个工具模块 jdk.xml.ws、jdk.xml.bind。删除理由：Java SE 里的副本是 EE 上游的「快照+子集」，裁剪成本高且容易与上游漂移；Endorsed Standards Override 机制实际无人使用；Maven Central 有完整独立版本；CORBA 在现代 Java 应用中没有需求（Java EE 8 已将其列为 Proposed Optional）。这些模块在 Java SE 9 就已标记 forRemoval，11 是执行。

关键点：javax.transaction.xa 留在 java.sql，不受影响。
Q2: 追问 — 老项目从 JDK 8 升到 11，报 ClassNotFoundException: javax.xml.bind.JAXBContext，怎么处理？为什么不能用 --add-modules？

处理：把 JAXB 作为普通依赖加到 classpath——API 用 javax.xml.bind:jaxb-api，实现用 com.sun.xml.bind:jaxb-ri。不能用 --add-modules 的原因是 JEP 320 的原文规定：模块的类不再存在于 JDK 运行时镜像中，没有任何命令行开关能启用它们。--add-modules 只能解析「已存在」的模块，解析不了已被删除的模块；它只在 JDK 9/10 对这些模块有效。

关键点：9/10 是「存在但默认不解析」，11 是「根本不存在」——这是量变到质变。
Q3: 追问 — 写出 JDK 11 升级的编译失败诊断伪代码，核心判断条件是什么？
if 报错类型 ∈ {javax.xml.bind, javax.xml.ws, javax.activation,
                javax.annotation, javax.transaction, javax.rmi, org.omg}:
        → JEP 320：加 Maven 依赖到 classpath
elif 报错类型 以 sun.misc / jdk.internal 开头:
        → jdeps --jdk-internals 定位，改公开 API 或 --add-exports
elif InaccessibleObjectException on setAccessible:
        → JDK 16+ 强封装，加 --add-opens
elif ScriptEngineManager 取 "js" 返回 null:
        → Nashorn 已移除，换 GraalJS

核心判断条件是「报错的包名属于哪一类」——它同时决定了修复策略是「加依赖」「改代码」还是「改启动参数」。三者混用会让问题反复横跳，所以要先分类。

关键点：先分类，再修复；--add-exports / --add-modules / 加依赖是三条完全不同的路。
Q4: TLS 1.3 带来什么变化？Nashorn 什么时候彻底没了？

TLS 1.3（JEP 332）：JDK 11 支持 RFC 8446 并默认启用，握手从 2-RTT 降到 1-RTT、支持 0-RTT 会话恢复，同时淘汰大量不安全算法；0-RTT early data 因重放攻击风险默认不启用。升级后要复查老的协议白名单与 cipher 配置，避免出现 SSLHandshakeException。
Nashorn（JEP 335）：JDK 11 标记 deprecated for removal 并输出警告，JDK 15（JEP 372）真正删除，此后 JDK 不再内置任何 JS 引擎，替代方案是 GraalJS/GraalVM 或独立发布的 Nashorn。

关键点：弃用（11）≠ 移除（15）；「11 上能跑」不代表「以后能跑」。
