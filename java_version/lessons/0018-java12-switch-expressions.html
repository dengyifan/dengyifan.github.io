L1 · 概念层：switch 不再只能「做一件事」，还能「算出一个值」

Java 12 的 JEP 325 Switch Expressions（预览特性）让 switch 第一次从「语句（statement）」升级为「表达式（expression）」：它可以从一组标签里算出一个值并参与赋值/返回，而不是只负责跳转到某段代码。

传统形式（Java 12 仍支持）箭头形式（JEP 325 新增）switch 表达式（新增用法）
写法case L: statementscase L -> expression / block / throwint x = switch (v) { case 1 -> 10; ... };
fall-through✅ 有（忘写 break 就掉进下个分支——经典事故源）❌ 无，执行完自然结束❌ 无
多标签✅ case A, B:（Java 12 也支持）✅ case A, B ->✅
产出值只能靠外部变量 + break直接 -> 一个表达式块内用 break 值;（Java 12 写法）
块内局部变量作用域泄漏到整个 switch不泄漏到其他分支同左

Java 12 的写法长什么样

// 1) 箭头形式 + 表达式产出值（最常用）
int numLetters = switch (day) {
    case MONDAY, FRIDAY, SUNDAY -> 6;
    case TUESDAY                -> 7;
    case THURSDAY, SATURDAY     -> 8;
    case WEDNESDAY              -> 9;
};

// 2) 箭头 + 块：Java 12 规定用 break <value> 产出（不是 yield！）
String formatted = switch (kind) {
    case LIGHT -> {
        String result = "L" + lumens;
        break result;          // ← Java 12 预览版的「返回值」写法
    }
    case HEAVY -> {
        if (lumens > 1000) {
            throw new IllegalArgumentException("too bright");
        }
        break "H" + lumens;    // 每条路径要么 break 值、要么 throw
    }
};

// 3) 传统形式也能当表达式用（同样的 break 值规则）
int x = switch (v) {
    case 1: break 10;
    case 2: break 20;
    default: break 0;
};
误区注入：Java 12 里是 break 值;，不是 yield

网上大量教程写 yield，那是 JDK 13（JEP 354） 才改的写法（JDK 13 也是该特性的第二次预览）；JDK 14（JEP 361） 才最终定稿转正。所以：在 Java 12 语境下写 yield x; 是编译不过的——Java 12 只认 break x;。同理，「switch 表达式是什么时候正式（非预览）进 JDK 的」答案是 JDK 14，不是 12 也不是 13。

为什么要消除 fall-through？

fall-through（从一个 case 直接掉进下一个 case）是 Java switch 最著名的事故源：忘写 break 时程序「看起来正常、实际串了分支」，编译期毫无提示。箭头形式从语法层面消灭了这个问题——右侧只能是「表达式 / 语句块 / throw」三者之一，根本没有「掉进下一个分支」的语义。这也是 JEP 325 把两种形式并存而非替换旧形式的原因：旧代码零破坏，新代码默认安全。

预览特性的启用方式

javac --enable-preview --release 12 SwitchDemo.java
java  --enable-preview SwitchDemo

两个开关缺一不可：--release 12 把语言级别钉在 12，--enable-preview 允许使用「12 中尚未定稿」的语法。运行时的 java 版本必须等于编译时的 --release——预览特性禁止「12 编译、13 运行」。

L2 · 原理层

必背规则清单（全部来自 JEP 325 原文）

  1. 箭头右侧只有三种合法形态：表达式、{ ... } 块、throw 语句。没有 ; 之外的「语句序列 + fall-through」。
  2. 多标签：case A, B, C ->（逗号分隔）；传统形式同样支持 case A, B:——这是 Java 12 顺带补上的、对两种形式都生效的能力。
  3. 必须穷尽（exhaustive）：switch 表达式对「所有可能输入」都要有答案。通常意味着要写 default；switch 枚举且覆盖全部常量时，编译器可以自己兜底。
  4. 必须「有值或抛异常」：每个分支要么 break <value>（或 -> 一个表达式），要么 throw；不允许任何路径「直接走完」。
  5. 是 poly expression：目标类型向下推断——Object o = switch (x) { case 1 -> "a"; default -> 1; }; 会按目标类型检查各分支类型。
  6. 禁止跨越它的跳转：在 switch 表达式内部，无标签 break（产出值）是唯一合法跳出方式；return、continue、带标签 break、以及跳出到外层循环的 break 都非法（javac 报 illegal jump through a switch expression 一类错误）。
  7. 作用域更干净：箭头块里声明的局部变量只在本分支可见，不会像传统形式那样污染整个 switch。
  8. JEP 原文留了一句「机会主义」备注：未来可能扩展到 float/double/long 选择器。

    if tree.polyKind == POLY and 目标类型 == void:

    type = STANDALONE ? lub(break 值类型...) : 目标类型

    # ---- Flow.java: 穷尽性 + 完整性（活性分析）----
    constants = selector 是 enum ? 全部枚举常量 : null
    hasDefault = false
    for each case c:
        if c 是 default: hasDefault = true
        else: 从 constants 中扣掉 c 的标签
        alive = 分析 c.body 是否可能「正常走完」
        if alive and c 是箭头规则:
            error "switch rule completes without providing a value"
        elif alive and 是最后一个 case:
            error "switch expression completes without providing a value"
        c.completesNormally = alive
    if (constants == null or constants 还有剩余) and not hasDefault:
        error "the switch expression does not cover all possible input values"   # 穷尽性

    # ---- Lower.java: 降糖成普通字节码 ----
    if 没有 default 分支:
        追加 default: throw new IncompatibleClassChangeError()   # 兜底，绝不让它走飞
    把 case A, B -> 展开成 case A: case B: ...                  # 多标签拆开
    给「正常走完」的箭头规则补一个合成 break;
    selector 是 enum/string: 改写成 hashCode/序号两级 switch（沿用传统降糖）
    返回 一个普通 JCSwitch（语句），结果写入临时变量

四维度生产检查

维度Java 12 switch 表达式的表现
并发语义纯编译期特性，字节码层面与手写 if/switch + 局部变量等价，无任何新增运行时并发行为；selector 只求值一次（比手写重复求值更安全）。
异常容错穷尽性检查缺失时，编译器在降糖阶段插入 default: throw new IncompatibleClassChangeError()——这是「不该发生」的信号，出现即说明类文件与源码不同步（比如有人手工改了 class）。
边界判断预览特性三重边界：① 需要 --enable-preview；② 编译与运行版本必须一致；③ 语义可能在下个版本变（12 的 break 值 就被 13 的 yield 推翻）。跨版本混编 = 直接编译错误或运行期拒绝。
性能开销零额外开销，甚至略有收益：降糖由编译器统一完成，枚举/字符串 switch 仍走与传统形式完全相同的两级降糖（hashCode → 序号）；空分支不会生成多余代码。
两个高频误区

① 「写了 default 就算穷尽」——对 switch 表达式来说还要过第二关：每条路径必须「有值或 throw」。写 default -> {}（空块）依然报 switch rule completes without providing a value。
② 「箭头形式 = 表达式形式」——不是。switch (v) { case 1 -> foo(); } 单独写仍是语句（不产出值）；只有把整个 switch 放在需要值的位置（赋值、return、方法实参……）它才是表达式。判据是有没有目标类型，不是有没有箭头。

怎么读：穷尽性是「枚举还没扣完 或 非枚举选择器」且「没有 default」时触发——所以 非枚举（int/String）的 switch 表达式必须写 default，而枚举全覆盖可以省略。完整性（每条路径有值）则是「活性分析」的结论：alive == ALIVE 意味着控制流能从这个分支底部走出去而没被 break 值/throw 拦住。

设计原理三问

问题答案
为什么这样设计？两层动机：① 表达式化——让「多分支取值」这种占绝对多数的用法不再需要先声明临时变量 + break；② 安全化——用箭头形式在语法上删除 fall-through。而「先以预览发布」是因为语义仍可能被推翻：12 用 break 值、13 改 yield，正是预览机制存在的意义。
代价是什么？① 语言复杂度上升：两套形式、三种错误检查要背；② 预览期代码不能跨版本，团队若混用 JDK 版本会被编译器直接拒绝；③ 面试/培训要额外解释「12 是 break、13 才是 yield」。
如何改进？JDK 13 用 yield 消除「break 既当跳出又当产值」的歧义；JDK 14 转正后预览开关即可摘除；更远期是 JEP 提到的浮点/长整型选择器与 switch 模式匹配（JDK 17 preview、JDK 21 JEP 441 正式）。

L5 · 面试层：追问链

Q1: JEP 325 到底改了什么？

三点：① switch 可以作为表达式产出值（赋值/返回/作实参）；② 引入箭头标签 case L ->，右侧只能是表达式、块或 throw，没有 fall-through；③ 两种形式都支持逗号分隔多标签。同时施加两条硬约束：穷尽性与每条路径有值或抛异常。它是预览特性，JDK 14 才转正。

关键点：表达式化 + 无 fall-through + 多标签，三件事一起发生，但只有前两件是「语义新增」。
Q2: 追问 — break 和 yield 分别是哪个版本的？
  1. Java 12（JEP 325，预览 1）：块内用 break 值; 产出值——这也是「break 一词两义」的来源；
  2. Java 13（JEP 354，预览 2）：改为 yield 值;，与「跳出 switch」的 break 彻底分离；
  3. Java 14（JEP 361）：定稿转正，成为正式语法。

推论题：break;（无值）在 switch 表达式里合法吗？——不合法，javac 报 missing break value（compiler.properties:191），因为裸 break 意味着「不产值地走完」，违反完整性约束。

关键点：12=break 值 / 13=yield / 14=正式，这个三段式是必背时间线。
Q3: 追问 — 写出「switch 表达式合法性的编译期判定」伪代码
# 三阶段：Attr(类型) → Flow(活性/穷尽) → Lower(降糖)

  polyKind = 有目标类型 ? POLY : STANDALONE
  每个 break <value> 按目标类型归因；收集 break 值类型求 lub
  无 case 子句 → "does not have any case clauses"

  enum 选择器 → constants = 全部枚举常量；逐 case 扣减
  每分支做活性分析：
     alive && 箭头规则   → "rule completes without providing a value"
     alive && 最后一个分支 → "switch expression completes without providing a value"
  (constants 有剩余 or 非枚举) && 无 default → "does not cover all possible input values"

  无 default → 追加 default: throw IncompatibleClassChangeError
  多标签展开 + 给可走完的箭头规则补合成 break
  enum/string 选择器 → 两级降糖

两个常被追问的判据：穷尽性看 constants 集合是否扣空；完整性看 alive 活性——不是看语法上有没有 break，而是看控制流会不会「漏出去」。

关键点：Flow.java:635–680 三十余行就是全部判定逻辑，面试可直接背出文件与行号。
Q4: 故障排查 — 编译报「the switch expression does not cover all possible input values」，怎么修？

先判断选择器类型，两条路：

  • 枚举：说明还有枚举常量没被任何 case（和 default）覆盖。补 default，或补上漏掉的常量。常见陷阱：枚举常量在编译期新增（同仓库另一个文件），本地 switch 忘了更新；
  • int / String 等非枚举：必须写 default——因为 constants == null 时恒判为「有剩余」。

注意这与「某分支没产值」是不同错误（后者是 switch rule completes without providing a value），修复方式也不同：前者补覆盖，后者把该分支改成产值表达式或 throw。

关键点：看错误文案的后半句——cover all possible input values 是覆盖问题，without providing a value 是产值问题。
Q5: 追问 — 为什么 switch 表达式里禁止 return / continue？

因为它会破坏「表达式必须有值」的结构保证：return 绕过 breakResult 直接结束整个方法，方法返回类型与 switch 表达式的目标类型之间没有任何检查关系；continue 跳出后，switch 表达式的值同样无人定义。javac 的实现在 Attr.findJumpTarget：在 SWITCH_EXPRESSION 这一环里，只有无标签 break 被接受，continue 记为 ContinueOutsideSwitchExpression；visitReturn 发现 env.info.breakResult != null（正在归因 break 值）就报 ReturnOutsideSwitchExpression。报错文案统一叫「… outside of enclosing switch expression」——语义是「你跳出了它的边界」。

关键点：约束的本源是「表达式必须收敛成一个值」，跳转指令是收敛性的天敌。
Q6: 架构师 — 预览特性该不该进生产代码？怎么给团队定规矩？

分三档：① 工具/一次性脚本——可以试，编译即用，代价可控；② 主干业务代码——不允许，理由不是「有 bug」而是语义无承诺：JEP 预览流程明确「可修改、可撤回、不保证兼容」，12→13 的 break→yield 就是现实案例；③ 框架/库——绝对禁止，因为这会把「预览」传染给所有下游用户。

落地规矩：编译参数集中到构建脚本（一处控制 --enable-preview）、CI 上跑一次「用下一个 JDK 编译」的预警任务、代码评审规则里把 --enable-preview 列为必须标注的改动。

关键点：预览特性 = 「用运行时升级承诺换语法尝鲜」，判断标准是可回退成本，不是功能好不好。
Q7: 讲师角度 — 用大白话解释什么叫「switch 是 poly expression」？

普通表达式「自己知道自己是什么类型」，poly expression（多元表达式）要等目标告诉它是什么类型，Lambda、方法引用、字符串拼接、switch 表达式都属此类。例子：

Object o = switch (x) { case 1 -> "a"; default -> 1; };   // 按 Object 检查
String s = switch (x) { case 1 -> "a"; default -> "b"; }; // 按 String 检查
// 重载决议时也一样：f(switch(x){...}) 会先看 f 的形参类型再检查各分支

它的实际后果是：不能把 switch 表达式单独放在「没有目标类型」的位置（比如作为某些重载场景的裸实参时会出现歧义），并且分支类型不一致时，报错点是「分支 vs 目标类型」而不是「分支之间互相打架」。

关键点：poly = 类型由外向内推；这也是 Attr 里 polyKind = POLY / STANDALONE 分岔的由来。
