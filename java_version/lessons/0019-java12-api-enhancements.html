L1 · 概念层：四组新 API 一句话说清

Java 12（2019-03-19，非 LTS）的库层面改动不大，但四组 API 都很「顺手」——它们解决的是反复出现的样板代码：

API新增位置一句话替代的旧写法
Collectors.teeing(c1, c2, merger)java.util.stream一次遍历喂两个下游，再用合并函数把两份结果合成一个流收集两次 / 手写 reduce / 循环里维护两个累加器
NumberFormat.getCompactNumberInstance(locale, Style)java.text紧凑数字：1234567 → 123万（zh）/ 1M（en SHORT）、1 million（en LONG）自己维护千分位/亿单位映射表

Unicode 11.0 + 日本「令和」年号CLDR / java.time新增字符集支持；JapaneseImperialCalendar 认识 Reiwa手写年号映射

完整使用示例（四组各一份，可直接编译运行）

下面四个程序都是完整可运行的（javac X.java && java X），注释里的运行输出为本机实测——这四组 API 自 JDK 12 引入后语义未变，个别 locale 的显示细节以你本机 CLDR 数据为准。

示例① · Collectors.teeing：一次遍历同时得到和与个数

import java.util.stream.Collectors;
import java.util.stream.Stream;

public class TeeingDemo {
    public static void main(String[] args) {
        // 一次遍历同时算 sum 与 count，再合成平均值
        String stats = Stream.of(3, 1, 4, 1, 5, 9, 2, 6)
            .collect(Collectors.teeing(
                Collectors.summingInt(Integer::intValue),
                Collectors.counting(),
                (sum, cnt) -> "sum=" + sum + ", avg=" + (double) sum / cnt));
        System.out.println(stats);

        // 最小值与最大值——原本要遍历两次才能拿到的结果
        String range = Stream.of(3, 1, 4, 1, 5, 9, 2, 6)
            .collect(Collectors.teeing(
                Collectors.minBy(Integer::compareTo),
                Collectors.maxBy(Integer::compareTo),
                (min, max) -> min.orElseThrow() + ".." + max.orElseThrow()));
        System.out.println(range);
    }
}
// 运行输出：
// sum=31, avg=3.875
// 1..9

import java.text.NumberFormat;
import java.util.Locale;

public class CompactNumberDemo {

        NumberFormat zh = NumberFormat.getCompactNumberInstance(

        System.out.println(enLong.format(1234567));   // en LONG：单词单位
        System.out.println(enShort.format(999000));
    }
}

示例③ · String.indent / String.transform

public class StringIndentDemo {
    public static void main(String[] args) {
        String text = "class Demo {\nint x = 1;\n}";
        String indented = text.indent(4);              // 每行加 4 空格
        System.out.print(indented);
        System.out.println("endsWithNewline=" + indented.endsWith("\n"));
        System.out.print(indented.indent(-4));         // 再减回去（尾换行仍在）

        // transform 返回泛型 R：要先落到具体类型的变量，
        // 直接塞进重载方法（如 println）会让类型推断失败、编译报错
        String wrapped = "  abc  ".transform(String::trim)
                                .transform(s -> "[" + s + "]");
        System.out.println(wrapped);

        System.out.println("empty=[" + "".indent(4) + "]");   // 空串短路
    }
}
// 运行输出：
//     class Demo {
//     int x = 1;
//     }
// endsWithNewline=true
// class Demo {
// int x = 1;
// }
// [abc]
// empty=[]

为什么 teeing 到 Java 12 才有？

它需要把「两个独立 Collector 的容器、累加器、合并器、完结器」组合成一个语义正确的 Collector——并行时还要保证两对容器同步合并。组合子（combinator）写错在并行流下才会暴露，所以这类 API 一旦仓促发布就容易埋雷。JDK 把它留到 12，配上 PairBox 这种「双容器打包」实现，才敢说并发语义是完备的。

L2 · 原理层

teeing 的执行模型

flowchart LR A[流元素 t] --> B{PairBox} B --> C1["left 容器
c1Accumulator"] B --> C2["right 容器
c2Accumulator"] C1 --> D["并行时 c1Combiner
合并两个 left"] C2 --> E["并行时 c2Combiner
合并两个 right"] D --> F["c1Finisher(left)"] E --> G["c2Finisher(right)"] F --> H[merger.apply r1, r2] G --> H H --> I[最终结果]

# ① teeing 的四步（Collectors.teeing0, jdk12u:1927）
function teeing0(downstream1, downstream2, merger):
    对 downstream1/2 的 supplier、accumulator、combiner、finisher
    与 merger 逐一 Objects.requireNonNull(...)      # 8 个函数 + 3 个对象全查

    # characteristics 计算（决定能否走身份优化 / 是否无序）
    if CH_ID ⊇ c1Characteristics or CH_ID ⊇ c2Characteristics:
        characteristics = CH_NOID                  # 有下游是「ID + 无序」→ 结果无 ID
    else:
        characteristics = (c1 ∩ c2) - {IDENTITY_FINISH}   # 交集且永远去掉 ID

    class PairBox:                                  # 一个盒子里装两套容器
        left  = c1Supplier.get()
        right = c2Supplier.get()
        add(t):     c1Accumulator.accept(left, t); c2Accumulator.accept(right, t)
        combine(o): left = c1Combiner(left, o.left); right = c2Combiner(right, o.right)
        get():      merger(c1Finisher(left), c2Finisher(right))
    return Collector(PairBox::new, PairBox::add, PairBox::combine, PairBox::get, characteristics)

# ② String.indent 的分支（String.java:2842, jdk12u）
function indent(s, n):
    if s.isEmpty(): return ""                       # 空串直接返回，不产生 "\n"
    stream = s.lines()                              # 按行切（已丢弃行终止符）
    if n > 0:                每行前加 " ".repeat(n)  # 空格只建一次（O(1) 复用）
    elif n == MIN_VALUE:     每行 stripLeading()     # 特例：完全去掉行首空白
    elif n < 0:              每行去掉 min(-n, 行首已有空白) 个字符
    return stream.join("\n", 前缀"", 后缀"\n")       # ← 必带尾换行

四维度生产检查

维度teeingindent / transform紧凑数字
并发语义并行下两对容器同步累加、同步 combine，最后一次性 merger——语义等价于「两个独立收集的串行结果」；IDENTITY_FINISH 被强制剔除（组合后不再是身份完结）。纯函数，线程安全由不可变 String 保证；lines() 返回流，只能消费一次。NumberFormat 实例非线程安全（JDK 一贯约定），共享需 ThreadLocal 或每次新建。
异常容错下游任何函数为 null → 构造期 NullPointerException（带名字，如 "downstream1 accumulator"）；下游运行期异常原样上抛。transform(null) → NPE（来自 f.apply）；indent 对空串安全。locale/style 为 null → 入口即 NPE；未知 locale 回退默认紧凑样式而非抛错。
边界判断merger 必须处理 null 与顺序无关性：下游可能产出 null（如 minBy/maxBy 空流），并行/串行下 left-right 次序不保证——merger 写成有副作用或依赖顺序就是 bug。indent 结果总以 \n 结尾（非空输入）；负数缩进不会把行变负（有 indexOfNonWhitespace 兜底）；Integer.MIN_VALUE 走完全剥离。紧凑样式依赖 locale 数据：非内置 locale 的样式来自 jdk.localedata，最小化镜像/自定义 jlink 镜像里可能缺失或回退。
性能开销两次累加 + 一个装箱盒对象，仍是单次遍历，比「收集两遍」省一半 I/O/CPU；短流下 PairBox 分配可忽略。indent 每行一次拼接 + joining，O(n) 但会产生新数组；大文本批量调用要留意分配。transform 是单次虚调用，开销≈直接调用。格式化时要查资源模式 + 数量级判定，比 format(long) 贵，别在热点循环里反复 get 实例。
三个高频误区

① 「teeing 就是两次收集」——不是。它是一个 Collector、一次遍历；写成 stream.collect(min); stream.collect(max) 会触发流被消费两次的 IllegalStateException，写成 list.stream()... 两遍则白付两遍遍历。
② 「indent(0) 是无操作」——不是。它仍会按行重拼并补上尾部 \n，还统一了换行符。想要真无操作要自己判空。
③ 「紧凑数字 = String.format("%.1f")」——紧凑数字是 locale 数据驱动的（中文「万」、英文「K」），数量级分组规则与语言绑定，不能靠四舍五入模板复刻。

片段一：teeing 与 PairBox（Collectors.java:1920–1985，openjdk/jdk12u）

// src/java.base/share/classes/java/util/stream/Collectors.java  (openjdk/jdk12u)
public static <T, R1, R2, R>
Collector<T, ?, R> teeing(Collector<? super T, ?, R1> downstream1,   // :1920
                          Collector<? super T, ?, R2> downstream2,
                          BiFunction<? super R1, ? super R2, R> merger) {
    return teeing0(downstream1, downstream2, merger);
}

private static <T, A1, A2, R1, R2, R>
Collector<T, ?, R> teeing0(Collector<? super T, A1, R1> downstream1,  // :1927
                           Collector<? super T, A2, R2> downstream2,
                           BiFunction<? super R1, ? super R2, R> merger) {
    Objects.requireNonNull(downstream1, "downstream1");
    ...  // supplier/accumulator/combiner/finisher 共 8 个函数逐一校验

    Set<Collector.Characteristics> characteristics;
    ...
    if (CH_ID.containsAll(c1Characteristics) || CH_ID.containsAll(c2Characteristics)) {
        characteristics = CH_NOID;                     // 含 IDENTITY_FINISH 的一端
    } else {                                           // 让整体失去身份完结资格
        EnumSet<Collector.Characteristics> c = EnumSet.noneOf(...);
        c.addAll(c1Characteristics);
        c.retainAll(c2Characteristics);                // 取交集
        c.remove(Collector.Characteristics.IDENTITY_FINISH);
        characteristics = Collections.unmodifiableSet(c);
    }

    class PairBox {                                    // 双容器打包，本课关键
        A1 left = c1Supplier.get();
        A2 right = c2Supplier.get();

        void add(T t) {
            c1Accumulator.accept(left, t);             // 同一元素喂两个下游
            c2Accumulator.accept(right, t);
        }

        PairBox combine(PairBox other) {
            left = c1Combiner.apply(left, other.left); // 并行时两对各自合并
            right = c2Combiner.apply(right, other.right);
            return this;
        }

        R get() {
            R1 r1 = c1Finisher.apply(left);
            R2 r2 = c2Finisher.apply(right);
            return merger.apply(r1, r2);               // 最后才合并两份结果
        }
    }

    return new CollectorImpl<>(PairBox::new, PairBox::add, PairBox::combine,
                                PairBox::get, characteristics);
}

怎么读：PairBox 就是「把两个 Collector 的状态绑成一个状态机」的全部秘密——四个函数一一对应 Collector 的四个阶段（supplier→建双容器、accumulator→双收、combiner→双并、finisher→双完结 + merger）。注意 characteristics 那段：只要任一下游是「身份完结」，整体就被降级成 CH_NOID——因为 merger 的存在让「原样返回容器」不再可能。

// src/java.base/share/classes/java/lang/String.java  (openjdk/jdk12u)
public String indent(int n) {                              // :2842  @since 12
    return isEmpty() ? "" : indent(n, false);
}

private String indent(int n, boolean removeBlanks) {
    Stream<String> stream = removeBlanks ? lines(Integer.MAX_VALUE, Integer.MAX_VALUE)
                                         : lines();
    if (n > 0) {
        final String spaces = " ".repeat(n);               // 空格串只构造一次
        stream = stream.map(s -> spaces + s);
    } else if (n == Integer.MIN_VALUE) {                   // 特例：完全去行首空白
        stream = stream.map(s -> s.stripLeading());
    } else if (n < 0) {                                    // 负数：最多剥掉已有缩进
        stream = stream.map(s -> s.substring(Math.min(-n, s.indexOfNonWhitespace())));
    }
    return stream.collect(Collectors.joining("\n", "", "\n"));   // ← 强制尾换行
}

public <R> R transform(Function<? super String, ? extends R> f) {  // :2888  @since 12
    return f.apply(this);                                  // 全部实现就这一行
}

设计原理三问

问题答案
为什么这样设计？teeing：流式 API 的「单遍语义」与「多统计量需求」矛盾，必须由库层提供可并行化的组合子；紧凑数字：显示层需求高度 locale 化，交给 NumberFormat 体系才能复用 CLDR 数据；indent：文本块（JDK 13+ 文本块的前奏）与日志格式化都需要「整体搬运缩进」。
代价是什么？teeing 的 merger 要用户自己保证交换律/结合律，否则并行结果与串行不一致；indent 强制尾换行带来「静默改变字符串」的坑；紧凑数字引入对 jdk.localedata 的隐性依赖。
如何改进？业界常见改进方向：teeing 增加 null-safe 的结果合并变体；indent 提供「不补尾换行」开关（实际未做，只能自己判空）；紧凑数字在 String 侧提供更轻量的格式化入口（至今未提供，仍走 NumberFormat）。

L4 · 边界层：能不能上生产

场景结论要点
Java 12 新 API 在生产（JDK ≥ 12）✅ 可用四组 API 均为正式特性（非预览、非实验）——这是它们与 JEP 325 的本质区别
需要兼容 JDK 11 的项目❌ 不可用Java 12 是非 LTS；要用 teeing 等就得升到 12+ 或找替代写法（reduce / 自定义收集器）
并行流 + teeing⚠️ 有条件merger 必须无序、无副作用；下游之一是 groupingBy 等重量级收集器时，双容器内存翻倍
多线程共享 getCompactNumberInstance 结果❌NumberFormat 非线程安全，共享实例并发格式化会互相污染状态
对超大文本频繁 indent⚠️每行拼接 + joining 产生新数组，热点路径上要评估分配（可自写 char 数组版本）
精简 jlink 镜像⚠️验证目标 locale 的紧凑样式是否随 jdk.localedata 一起被打包
API 选型速查
  • 一个流要算多个统计量 → Collectors.teeing；要 N（>2）个统计量 → 两两嵌套 teeing 或改用 summaryStatistics。
  • 展示大数字 → getCompactNumberInstance；要精确分隔格式 → 传统 DecimalFormat。
  • 整形多行文本 → indent，记得结果尾部有 \n；链式取值 → transform（可读性糖，非必需）。
  • 项目还在 JDK 11 → 用 reduce 组合两个统计量模拟 teeing，语义可完全对齐。

L5 · 面试层：追问链

Q1: Java 12 的 API 层新增了哪些？

四组：① Collectors.teeing——双下游一次遍历合并；② NumberFormat.getCompactNumberInstance(locale, Style) + NumberFormat.Style{SHORT, LONG} + java.text.CompactNumberFormat；③ String.indent(int)、String.transform(Function)；④ 数据层面 Unicode 11.0 支持与日本「令和（Reiwa）」年号支持。全部是正式特性。

关键点：与同版本的 switch 表达式（预览）、Shenandoah（实验）区分开——这四组没有状态标签。
Q2: 追问 — 写出 teeing 的执行模型伪代码，characteristics 怎么算？
PairBox { left = c1Supplier.get(); right = c2Supplier.get() }
add(t):     c1Accumulator(left, t); c2Accumulator(right, t)
combine(o): left = c1Combiner(left, o.left); right = c2Combiner(right, o.right)
get():      merger(c1Finisher(left), c2Finisher(right))

characteristics:
  if 任一下游满足 CH_ID ⊆ characteristics:   → CH_NOID
  else: (c1 ∩ c2) - {IDENTITY_FINISH}

记忆点：「双容器绑定 + 四阶段一一对应 + merger 让身份完结失效」。校验也别忘——merger、两个 downstream 及其各自的四个函数共 11 个 null 检查，全部在构造期完成（错误越早暴露越好）。

关键点：并行正确性靠 combine 同步合并两对容器，而不是合并两份最终结果。
Q3: 代码审查 — String s = text.indent(4) 之后 s.endsWith("\n") 是什么？

只要 text 非空，就是 true——indent 用 Collectors.joining("\n", "", "\n") 收尾，固定追加一个换行。由此派生三个坑：

  • 把 indent 结果直接拼进 JSON/HTML 属性会多一个换行；
  • indent(0) 不是无操作：会去行首统一为 \n + 补尾换行；
  • 负数缩进不会产生「负长度行」：实际剥掉的字符数取 min(-n, 行首空白长度)；Integer.MIN_VALUE 因为取相反数会溢出，被单独处理成 stripLeading()。

空串则短路返回 ""（既不加缩进也不加换行）。

关键点：MIN_VALUE 特判是这道题的「深水区」——-Integer.MIN_VALUE == Integer.MIN_VALUE，不特判会走错分支。
Q4: 故障排查 — teeing(minBy, maxBy, ...) 在并行流下结果偶尔不对，为什么？

先查两点：① merger 有副作用或依赖顺序——并行时 merger(r1, r2) 的两个入参分别来自不同线程合并后的结果，先后顺序不固定，r1 - r2 这类写法会得到负数；② 下游自身不是确定性的——比如下游用了 HashSet 遍历顺序。

其次确认调用形态：如果把同一个流先收集一次再收集一次，第二次会抛 IllegalStateException: stream has already been operated upon or closed——teeing 的意义正是用一次遍历替代两次收集。

关键点：merger 的契约是「纯函数且满足交换律」，这是所有 teeing 并行 bug 的根因。
Q5: 架构师 — 为什么 teeing 不直接做成「把两个统计量塞进一个收集器」？和 reduce 比优势在哪？

因为 Collector 契约（supplier/accumulator/combiner/finisher）是为单结果设计的，两个结果意味着两套容器——只有库层能把这四阶段正确地「叉乘」，用户手写 reduce 很容易漏掉并行分支（combiner）。对比：

  • 手写 reduce：要自己维护二元组容器、处理 combiner、避免装箱开销，还容易把「两次遍历」写进代码；
  • teeing：单遍、可并行、校验齐全、与既有收集器自由组合（甚至可以 teeing(groupingBy, counting, ...)）。

更深一层：teeing 是 Collector 体系成为可组合代数的标志——在此之前收集器只能「嵌套」不能「并联」。

关键点：并联组合子必须由库提供，因为它要同时保证串行/并行两种执行模型的正确性。
Q6: 讲师角度 — transform 存在的意义是什么？不就是 f.apply(s) 吗？

实现上确实是 return f.apply(this)，价值全在调用侧的人体工学：它允许「以字符串为起点」的链式写法，把嵌套调用拉平：

String a = normalize(trim(input));                 // 从内往外读
String b = input.transform(this::trim)             // 从左往右读
                 .transform(this::normalize)
                 .transform(s -> s.toUpperCase(Locale.ROOT));

尤其当处理函数是方法引用、或想在链中插入 peek-式的中间步骤时更顺。缺点也直白：多一层虚调用，以及让「这是一次函数应用」在调试时不如直接调用直观。

关键点：transform 是可读性糖，与 Optional.map 属于同一类「链式上下文」设计。
