L1 · 概念层：常量池（classfile）里的东西，Java 代码终于"说得出口"了

JVM 的常量池（JVMS §4.4）里放着一串可加载常量：整数、字符串、类、方法类型、方法句柄，以及 JDK 11 新增的 CONSTANT_Dynamic。字节码指令 ldc 可以把它们压进操作数栈。但在此之前，Java 层没有任何标准类型能"代表"这些常量——你写 Class 对象代表的是运行时的类本身，不是常量池里那条符号记录；想生成字节码的库（ASM、各类 codegen 框架）只能各自发明一套常量表示，互不相通。

JEP 334 JVM Constants API（Java 12，正式特性）补上的就是这一层：名义描述符（nominal descriptor）——一种纯名字、不含类加载器的 Java 对象，能精确描述任意一种可加载常量；需要时再用一个 MethodHandles.Lookup 把它解析（resolve）回真正的值。

两组核心接口（都是 @since 12）

接口方向一句话
java.lang.constant.ConstantDesc描述符 → 值"我可以被解析成一个常量值"：Object resolveConstantDesc(Lookup)
java.lang.constant.Constable值 → 描述符"我能给出自己的名义描述符"：Optional<? extends ConstantDesc> describeConstable()

两者构成一对可往返的协议：值 describeConstable() → 描述符 resolveConstantDesc(lookup) → 值。描述符是 nominal 的——只记名字（类的二进制名、成员名、类型描述符），不记 ClassLoader，所以同一个描述符在不同类加载器下可能解析出不同的东西。

和 JEP 309 的关系（面试必考的版本题）

JEP 309 CONSTANT_Dynamic 的状态是 Closed / Delivered — Release 11（openjdk.org/jeps/309 实测），即 CONSTANT_Dynamic 这条常量池"能力"是 JDK 11 交付的（JVM/类文件层）。JEP 334 交付的是它的 Java API 层：让 Java 代码能构造、读写这些常量的名义描述符。一句话：11 造好了"货"，12 给了"货单和提货凭证"。

一段最小可用示例

import java.lang.constant.*;
import java.lang.invoke.*;

// 1) 描述一个类 / 一个方法类型（纯名字，不加载任何类）
ClassDesc listDesc = ClassDesc.of("java.util.List");          // 接口 ClassDesc, @since 12
ClassDesc nested   = CD_MethodHandles_Lookup;                  // ConstantDescs 里的现成常量
MethodTypeDesc mtd = MethodTypeDesc.of(ClassDesc.of(int.class.getName()), CD_String);

// 2) 值 → 描述符（Constable）
Optional<ClassDesc> d = String.class.describeConstable();      // Optional.of(ClassDesc.of("java.lang.String"))
Optional<? extends ConstantDesc> sd = "hi".describeConstable();// String 自己就是 ConstantDesc

// 3) 描述符 → 值（ConstantDesc.resolveConstantDesc，模拟 JVMS §5.4.3 解析）
Class<?> c = (Class<?>) ClassDesc.of("java.lang.String")
                   .resolveConstantDesc(MethodHandles.lookup());
包名陷阱：JEP 文本与实际交付不一致

JEP 334 正文写的是「the new package java.lang.invoke.constant」；但 JDK 12 实际交付的包是 java.lang.constant，两处硬证据：① openjdk/jdk12u 源码路径 src/java.base/share/classes/java/lang/constant/；② Oracle JDK 12 API 文档 docs.oracle.com/en/java/javase/12/docs/api/java.base/java/lang/constant/package-summary.html 返回 200、标题为「java.lang.constant (Java SE 12 & JDK 12)」，而 java.lang/invoke/constant 路径不存在。因此不存在"包名后来从 invoke.constant 迁到 constant"这回事——JDK 25 仍在 java.lang.constant（ConstantDesc 至今标注 @since 12）。答题时以源码/API 文档为准，可顺带指出 JEP 文本的滞后。

L2 · 原理层：nominal 描述符为什么"只记名字"，解析时又怎么还原

关键判断逻辑伪代码

# ===== 协议一：值 → 描述符（Constable.describeConstable）=====
class String implements Constable, ConstantDesc:            # String/Integer/... 直接实现两者
    describeConstable() = Optional.of(this)                 # 自己就是描述符，直接返回自己

class Class implements Constable:
    describeConstable() =
        if 是数组/基本类型原始类型: 返回 DynamicConstantDesc(BCI 型 BSM)  # 走特殊引导
        else: return Optional.of(ClassDesc.of(二进制名))     # 纯名字，不触发类加载
class MethodHandle implements Constable:
    describeConstable() =
        if 是直接句柄(REF_getStatic 等): return Optional.of(DirectMethodHandleDesc)
        else: return Optional.empty()                       # 组合子造出来的句柄无法名义描述

# ===== 协议二：描述符 → 值（ConstantDesc.resolveConstantDesc）=====
ConstantDesc.resolveConstantDesc(Lookup lookup):
    # 模拟 JVMS §5.4.3 Resolution + §5.4.4 访问控制；【不缓存】结果
    按 lookup 的类加载器解释描述符里的名字
    抛 ReflectiveOperationException（解析失败）/ LinkageError（链接失败）

四维度生产检查

维度JVM Constants API 的表现
并发语义描述符设计为不可变、且明确"不要依赖对象身份"（比较一律用 equals），可安全跨线程共享；resolveConstantDesc 每次独立执行、不缓存结果，多线程并发解析互不干扰，但也不会互相复用成果。
异常容错解析失败抛 ReflectiveOperationException（名字找不到/无访问权），链接阶段失败抛 LinkageError；DynamicConstantDesc 会把 BSM 抛出的任何非 Error 统一包装成 BootstrapMethodError——与 JVM 真正执行 ldc 时的行为对齐。describeConstable() 用 Optional.empty() 表达"我描述不了我自己"（如方法句柄组合子的产物），不是返回 null。
边界判断描述符不含类加载器：同一个 ClassDesc.of("com.foo.Bar") 在不同 Lookup 下可能解析成两个不同的类；访问控制完全委托给传入的 Lookup（JVMS §5.4.4）——传错 Lookup 是最常见的"解析不到"根因。
性能开销resolveConstantDesc javadoc 明言 No caching of the resulting value is performed：每次解析都走一遍名称解析/反射/可能的类加载。适合冷路径（引导方法、字节码生成、启动期），把它放热路径等于每次重做链接。
三个高频误区

① 「Class 就是 ClassDesc」——不是。Class 是值，ClassDesc 是它的名义描述符；Class 实现的是 Constable（能给出 ClassDesc），而 String/Integer/Long/Double/Float 因为本身就是常量池原生条目，才直接实现 ConstantDesc。
② 「描述符构造完就能用」——不能，必须 resolveConstantDesc(lookup) 之后才是可执行/可加载的值；描述符阶段不加载任何类。
③ 「describeConstable 返回 empty 是 bug」——不是，是契约的一部分：有些实例天然无法名义化（JEP 334 明确 MethodHandle 组合子产物属于此类）。

片段一：resolveConstantDesc —— 用 Java 复刻一次 ldc 引导（DynamicConstantDesc.java:260）

// src/java.base/share/classes/java/lang/constant/DynamicConstantDesc.java (openjdk/jdk12u)
@SuppressWarnings("unchecked")
public T resolveConstantDesc(MethodHandles.Lookup lookup) throws ReflectiveOperationException {
    try {
        MethodHandle bsm = (MethodHandle) bootstrapMethod.resolveConstantDesc(lookup);
        if (bsm.type().parameterCount() < 2 ||
            !MethodHandles.Lookup.class.isAssignableFrom(bsm.type().parameterType(0))) {
            throw new BootstrapMethodError(
                    "Invalid bootstrap method declared for resolving a dynamic constant: " + bootstrapMethod);
        }
        Object[] bsmArgs = new Object[3 + bootstrapArgs.length];
        bsmArgs[0] = lookup;
        bsmArgs[1] = constantName;
        bsmArgs[2] = constantType.resolveConstantDesc(lookup);
        for (int i = 0; i < bootstrapArgs.length; i++)
            bsmArgs[3 + i] = bootstrapArgs[i].resolveConstantDesc(lookup);

        return (T) bsm.invokeWithArguments(bsmArgs);
    } catch (Error e) {
        throw e;
    } catch (Throwable t) {
        throw new BootstrapMethodError(t);
    }
}

怎么读：这段代码逐字对应 JVMS 给 CONSTANT_Dynamic/CONSTANT_InvokeDynamic 定义的引导方法调用协议——(Lookup, String name, ClassDesc type, ...静态实参)。也就是说，JDK 12 让"运行时按 classfile 语义造常量"变成了普通 Java 调用：解析一个动态常量 = 递归解析实参 + 调一次 BSM；异常统一折叠成 BootstrapMethodError，与 JVM 真执行 ldc 的报错口径一致。

设计原理三问

问题答案
为什么这样设计？① 描述与解析分离：常量池本质是"名字 + 上下文"，描述符只有纯名字，解析时才绑定 ClassLoader/Lookup——这正是 classfile 的语义；② 让 ldc 操作数在 Java 里可表达，字节码生成库（以及 javac 自己）不必再用私有协议描述常量；③ 统一 CONSTANT_Dynamic（11 引入）的 Java 侧表示，与 invokedynamic（DynamicCallSiteDesc）形成对称。
代价是什么？① 多一层对象模型（值/描述符/Optional 三种形态），API 面积显著变大；② 解析不缓存，误用在热路径会造成反复名称解析与类加载；③ describeConstable() 的 Optional 让"不能描述"成为常态分支，调用方必须处理 empty。
如何改进？调用方自行缓存解析结果（并按类加载器维度区分）；JDK 后续把 ConstantDesc/ClassDesc 改为 sealed（JDK 25 中已确认），编译期就堵死"第三方直接实现根接口"这条歧路；更远期是让描述符与模式匹配/字符串模板等新特性共享同一套常量表示。

L5 · 面试层：追问链

Q1: JEP 334 是什么？它和 JEP 309 什么关系？

JEP 334（JVM Constants API，Java 12 正式特性）新增 java.lang.constant 包，用名义描述符（ConstantDesc 及其子类型 ClassDesc、MethodTypeDesc、MethodHandleDesc、DynamicConstantDesc，以及配套 Constable 接口）来描述常量池里每一种可加载常量。JEP 309（CONSTANT_Dynamic）状态为 Delivered Release 11——VM/类文件层能力在 11 就绪，334 是它在 Java API 层的"提货单"，两者是底层能力与上层 API 的关系。

关键点：11 = CONDY 进常量池；12 = 描述这些常量的 Java API（JEP 334）。顺序不可颠倒。
Q2: 追问 — ConstantDesc 和 Constable 的分工？为什么 String 直接 implements ConstantDesc 而 Class 不是？
  • ConstantDesc：回答"我能被解析成什么值"（向值方向，resolveConstantDesc）；
  • Constable：回答"我能给出自己的描述符"（向描述符方向，describeConstable）。

因为 String、Integer、Long、Float、Double 本身就是常量池的原生条目（CONSTANT_String/CONSTANT_Integer…），它们的名字即值，"描述符"与"值"是同一个对象，所以干脆自己实现 ConstantDesc。而 Class 的常量池形态是"类的二进制名"，必须多走一步 ClassDesc.of(名字)，所以 Class 只实现 Constable，其 describeConstable() 返回 Optional<ClassDesc>。

关键点：值即描述符 ⇔ 该常量在常量池里"无附加信息"；否则必须套一层 Desc。
Q3: 追问 — 写出 resolveConstantDesc 的协议伪代码，并解释它为何"不缓存"。
DynamicConstantDesc.resolveConstantDesc(lookup):
    bsm = bootstrapMethod.resolveConstantDesc(lookup)        # 先解析引导方法本身
    assert bsm 首参是 MethodHandles.Lookup  否则 BootstrapMethodError
    args = [lookup, constantName, constantType.resolveConstantDesc(lookup)]
         + [每个 bootstrapArg 递归 resolveConstantDesc]
    try:    return bsm.invokeWithArguments(args)
    catch Error: 原样抛
    catch Throwable t: throw new BootstrapMethodError(t)

不缓存的原因有二：① 解析强依赖 Lookup/ClassLoader 上下文——同一个描述符换个 Lookup 结果不同，缓存必须把上下文纳入 key，收益与复杂度都不划算；② 解析本就是冷路径（引导方法、代码生成），正确性优先于速度。需要热路径时由调用方自行缓存，并以 (desc, loader) 为键。

关键点：协议 = 递归解析实参 + 调 BSM；不缓存是语义选择（上下文相关）而非疏忽。
Q4: 故障排查 — 报 BootstrapMethodError: Invalid bootstrap method declared for resolving a dynamic constant，怎么查？

这是 DynamicConstantDesc.resolveConstantDesc 的前置校验失败：BSM 的方法类型不合法（参数个数 < 2，或第一个参数不是 MethodHandles.Lookup）。排查顺序：

  1. 确认 bootstrapMethod 描述符指向的确实是引导方法而不是普通静态方法（自拼 DirectMethodHandleDesc 时最容易错）；
  2. 检查 BSM 签名是否为 (Lookup, String, ClassDesc/Class, ...args)；
  3. 若报的是"被包装过"的 BootstrapMethodError（cause 是业务异常），问题在 BSM 内部——按 cause 栈继续查。

区分点：无 cause 或文案为 "Invalid bootstrap method…" = 签名/描述符错；带 cause = BSM 执行期炸了。

关键点：看到该错误先读 BSM 方法类型，再看 cause——两条路完全不同。
Q5: 架构师 — 为什么需要"名义描述符"这种间接层，反射不够吗？

反射的单位是已加载的类与成员，而常量池/字节码的单位是名字。三个反射做不到的场景：① 生成侧——要写出一个"还不存在的类"的常量（代码生成、代理、lambda 实现类）时，反射没有对应物；② 延迟绑定——描述符可以在完全不触发类加载的前提下随 API 传递、序列化、比较；③ 与 classfile 语义一比一对齐——DynamicConstantDesc 直接复刻 BSM 调用协议，读写类文件的工具不需要两套模型。代价是多一层对象和"解析要显式传 Lookup"的样板。

关键点：反射面向"已存在的东西"，nominal descriptor 面向"类文件里的名字"——一个存在性问题，一个引用性问题。
Q6: 讲师角度 — 用大白话解释 nominal descriptor 和"真正解析"的区别。

把它想成快递单：单子上写着"北京市朝阳区 XX 小区 3 号楼"（纯地址、名字），但单子本身不是房子。收件时（resolveConstantDesc(lookup)）你拿着这张单子，到具体的区县（ClassLoader）去问路——同一个地址，在朝阳和通州找到的可能不是同一栋楼。而且这张单子不记你是哪个快递员（不含 Lookup），所以能随便复制、传给任何人；也因为每次都要重新问路，官方不帮你做地址簿（不缓存）。还有一种情况是"我说不清我家地址"（describeConstable() 返回 empty），比如用句柄组合子拼出来的 MethodHandle。

关键点：nominal = 只有名字；解析 = 名字 + 上下文 + 一次真正的链接动作。
