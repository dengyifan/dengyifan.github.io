L1 · 概念层：四个 JEP，两条主线（新收集器 + 打磨存量 + 起步提速）

Java 12 在运行时上一次交了 4 个 JEP：JEP 189 Shenandoah（新的低暂停收集器，实验性）、JEP 344（G1 混合回收可中断）、JEP 346（G1 空闲期归还内存）、JEP 341（构建期默认生成 CDS 归档）。前三个管"回收得怎么样"，最后一个管"启动得快不快"。

JEP一句话状态（12 时）默认行为
189 Shenandoah把疏散（搬对象）也做成并发——暂停时间与堆大小无关实验性关闭，需 -XX:+UnlockExperimentalVMOptions -XX:+UseShenandoahGC
344 G1 可中断混合回收把混合回收拆成"必须做的"和"来得及才做的"，时间不够就半路停正式始终生效，无开关
346 G1 归还空闲内存应用空闲时周期性 GC，结束后把堆内存还给 OS正式默认关闭（interval = 0）
341 默认 CDS构建 JDK 时自动生成类数据共享归档，开箱即加速正式64 位 server VM：-Xshare:auto 自动使用

关键判断逻辑伪代码（选择与触发）

# ===== 我该用哪个收集器？（Java 12 语境）=====
if 需要 LTS 稳定 + 生产默认:            GC = G1        # JDK 9+ 默认
elif 追求极低暂停且接受实验性:            需要 -XX:+UnlockExperimentalVMOptions
                                        GC = Shenandoah # JDK 12 实验 / JDK 15 起正式
elif JDK 11 且要更低暂停（当时）:         GC = ZGC        # JEP 333，也是实验性
elif 完全不想做回收（测试/工具）:         GC = Epsilon     # JEP 318，JDK 11

# ===== 启动时 CDS 归档用不用？ =====
-Xshare:auto（server VM 默认）:
    if 存在 lib/server/classes.jsa 且校验通过 → mmap 归档，跳过平台类的类加载/验证
    else                                      → 静默回退到普通加载（不报错）
-Xshare:off → 一律不用（诊断"是不是 CDS 引起的问题"的第一步）

# ===== G1 什么时候归还内存给 OS？（JEP 346，JDK 12 默认不还）=====
if G1PeriodicGCInterval > 0                                        # 默认 0 = 关闭
   and 距上次 GC 暂停 > G1PeriodicGCInterval 毫秒
   and 当前没有进行中的 concurrent cycle
   and 1 分钟平均负载 < G1PeriodicGCSystemLoadThreshold             # 默认 0.0 = 不检查负载
then:
    if G1PeriodicGCInvokesConcurrent: 跑一轮并发 cycle（默认 true）
    else:                              跑一次 STW Full GC
    结束后按 MinHeapFreeRatio/MaxHeapFreeRatio/Xms–Xmx 缩堆并 uncommit
    日志 cause: "G1 Periodic Collection"

Shenandoah 凭什么"暂停与堆大小无关"

传统收集器暂停时要把对象从"from 空间"搬到"to 空间"，堆越大、对象越多、暂停越长。Shenandoah 的答案是并发疏散：给每个对象前置一个间接指针（Brooks pointer），应用线程随时读到的都是"当前正确地址"，于是搬对象这件事可以和应用并发做；STW 暂停只负责扫线程栈等少量根，不负责搬数据。因此 200MB 和 200GB 的堆，暂停时长大致一个量级——代价是每个对象多一个字的开销、读写屏障的 CPU 开销。

（Brooks 间接指针保证读者不迷路）"] end C --> B D --> E[下一轮] B --> D
四个必须避开的误区

① 「Shenandoah 暂停 = 0」——不是。STW 仍然存在（标记的 init/final 阶段），只是短到微秒量级且与堆大小无关；JEP 明确 Non-goal：不解决安全点之外的停顿（如 TTSP、monitor inflation）。
② 「JDK 12 的 G1 空闲会自动还内存」——不会。G1PeriodicGCInterval 默认 0 = 功能关闭（JEP 346 风险节原话：default values disable this feature）。
③ 「JEP 344 让 G1 所有暂停都能中断」——只有混合回收里的 optional 部分可分步退出，JEP 的 Non-goal 就是"不承诺全部可中断"。
④ 「默认 CDS = 应用类也共享了」——不是，JEP 341 只生成平台类的默认归档；应用类共享仍要自己 -Xshare:dump 或 AppCDS（12 里叫 CDS for Application Classes）。

L2 · 原理层：三段核心逻辑的伪代码 + 四维度检查

伪代码一：G1 混合回收从"一口气"变成"分步可退"（JEP 344）

# ===== 改造前：一次把整个 collection set 收完 =====
pause:
    for region in collection_set:            # young + 选定的 old，一次做完
        evacuate(region)                     # 时间不可预测 → 停顿尖刺

# ===== 改造后：拆 mandatory + optional（openjdk/jdk12u g1CollectionSet.*）=====
pause:
    # 1) mandatory：不可增量，通常含 young 区（也可能含部分 old），约占预测 CSet 的 80%
    for region in mandatory_regions:          # 必须做完，否则语义不完整
        evacuate(region)

    # 2) optional：纯 old，约 20%，"来得及才做"
    #    进入条件：启发式判定"时间预测反复失败"时才开启增量模式
    for step in steps:                       # 最细可以一步只做 1 个 region
        if 剩余时间预算不够:   break          # ← 本轮到此为止，下次 GC 再说
        evacuate(optional_regions[step])

# 预测重新准确后 → optional 逐渐缩小，最终整个 CSet 都是 mandatory
# 代价：optional 部分 CPU 开销 <1%；额外跟踪"指向 optional 区的指针" → native 内存略增
# 注意：JEP 未提供任何用户可见开关——这是启发式行为，不是配置项

伪代码二：Shenandoah 的一次并发周期

cycle:
    STW: 扫线程栈/根，标记根可达          # init mark，与堆大小无关
    并发: 从根出发做标记                  # 应用照常跑，读写屏障维持三色
    STW: 处理残留根、完成标记             # final mark
    并发: 疏散（搬对象 + 压缩）            # ← JEP 189 的核心：搬移不进 STW
         每个对象前面有 Brooks 间接指针（1 个 HeapWord），
         对象搬到新址后只改指针 → 并发读者永远拿得到正确地址
    STW: 收尾（极短）
    # 若应用线程在写屏障里搬家时遇到 OOM：
    # shenandoahEvacOOMHandler.hpp:31 明确"Java 线程在写屏障中疏散对象"，
    # 失败时进入计数器保护的等待/退化路径，避免 to-space 不变量被破坏

四维度生产检查

维度189 Shenandoah344 G1 可中断混合回收346 G1 归还内存341 默认 CDS
并发语义标记与疏散全并发；靠 Brooks 指针 + 读屏障保证并发读者正确性仍是一次 STW 内的分步执行，不引入新的并发；只是"步与步之间允许退出"默认走并发 cycle（G1PeriodicGCInvokesConcurrent=true），只在显式配置时才用 STW Full GC只读 mmap 共享归档页；类元数据只读共享，不改变类的语义
异常容错写屏障中疏散 OOM 有专门处理（ShenandoahEvacOOMHandler），否则会破坏 to-space 不变量optional 部分退出是正常路径不是错误；下次 GC 继续未完成部分归档不可用时静默回退（-Xshare:auto 不致命）；周期 GC 结束才缩堆，不会抖动式归还归档校验失败 → 打印警告并回退普通加载；-Xshare:on 才会硬失败
边界判断实验性开关 + 平台限制（12 时 aarch64/amd64）；堆极大时仍受限于元数据/根扫描之外的其他停顿没有开关、调不了参数——预测准不准由启发式决定，出问题只能换 GC 或升级 JDK两个默认值卡死功能：Interval=0（关）、SystemLoadThreshold=0.0（不看负载）仅 64 位、仅 native 构建（非交叉编译）；只覆盖平台类
性能开销每对象 1 个 HeapWord 的间接指针 + 读写屏障 CPU（用 CPU/空间换暂停）optional 部分额外 CPU <1%；跟踪指向 optional 区的指针使 native 内存略增空闲期多跑 GC 本身有成本，但换来原型论文实测减少 85% 的已提交内存启动提速明显：JEP 引用 JDK 11 EA 实测 HelloWorld 启动快 32%
为什么 346 的默认值是"关"？

JEP 346 把"归还内存"做成可选优化而非默认行为，风险节明确写了 default values disable this feature：周期 GC 可能在不该跑的时候跑（浪费 CPU）、与应用争抢、在负载阈值判断失误时打扰业务。设计者的思路是先把机制和安全默认值交出去，让有容器/云需求的人显式打开——这也解释了为什么"JDK 12 G1 会自动还内存"是个常见误解。

JEP 341 补充：归档是怎么"默认就有"的

以前要手动敲 -Xshare:dump 才有归档；JDK 12 起 构建 JDK 的最后阶段（link image 之后）会自动跑一次 java -Xshare:dump，把归档放进 lib/server/classes.jsa，所以用户"开箱即用"。限制：仅 64 位、仅本机构建（交叉编译产物不生成）；-Xshare:off 仍可完全关闭；自定义 class list / GC 配置的归档继续自己 dump。

设计原理三问

问题答案
为什么这样设计？三条动机：① 延迟可预测性 > 吞吐成为常态需求（云/容器/交易），所以 Shenandoah 用 Brooks 指针把"搬对象"移出 STW；② G1 的老问题是预测失准——344 承认"预测会错"，给错的时候留了分步退出的活口；③ 内存归还是云场景刚需，但不能默认打扰业务（346 默认关）；④ 启动时间是开发者第一体验，CDS 是最"免费"的加速（341 默认生成）。
代价是什么？Shenandoah：每对象 1 个 HeapWord + 读写屏障 CPU，且 12 时仍是实验性；344：预测不准时混合回收变"分很多轮慢慢收"，老年代回收速度可能下降，额外 tracking 吃 native 内存；346：参数判断失误会在高负载边缘跑多余 GC；341：归档增大安装体积、与特定平台绑定。
如何改进？Shenandoah 在 JDK 15（JEP 379）转正、后续持续优化屏障开销；G1 预测与可中断逻辑在后续版本继续演进（degeneration、更多启发式）；346 类的归还策略被 ZGC/Shenandoah 后来也吸收（并发 + uncommit 常态化）；CDS 之后扩展到 Application CDS、Archiving Containers 镜像等。

调优/落地决策清单（Java 12 语境）
  • 容器里想让 G1 归还内存：显式打开 -XX:+UseG1GC -XX:G1PeriodicGCInterval=<毫秒> -XX:G1PeriodicGCSystemLoadThreshold=<负载>，并确认 MinHeapFreeRatio/MaxHeapFreeRatio 与 -Xms/-Xmx 允许缩堆；另有 -XX:G1UncommitDelay 控制"空闲多久才真正归还"（本课未核实其默认值，先查你所用 JDK 的 -XX:+PrintFlagsFinal）。

  • Shenandoah 上生产：12 只建议压测验证；真正可依赖是 JDK 15+。压测重点是屏障带来的 CPU 上升与暂停稳定性。
  • 怀疑 CDS 出问题：先 -Xshare:off 对比复现，再看启动日志里归档加载/回退提示；不要上来就删归档文件。

L5 · 面试层：追问链

Q1: Java 12 运行时相关有哪几个 JEP？各自状态？

四个：189 Shenandoah（实验性低暂停收集器）、344 G1 可中断混合回收（正式，无开关）、346 G1 空闲归还内存（正式，默认关闭）、341 默认 CDS 归档（正式，64 位 server VM 默认启用 -Xshare:auto）。可选补充：JDK 12 的 8 个 JEP 里其余四个是 230（JMH 微基准）、325（switch 表达式预览）、334（常量 API）、340（单一 AArch64 端口）。

关键点：状态与默认值是这道题的得分点——189 实验、346 默认关、341 默认开。
Q2: 追问 — 为什么 Shenandoah 的暂停时间能与堆大小无关？

因为暂停里不再有"搬数据"这个 O(堆大小) 的动作。传统收集器 STW 时要疏散所有存活对象；Shenandoah 给每个对象前加一个 Brooks 间接指针（源码 shenandoahBrooksPointer.hpp:48：word_offset() = -1，指针就存在对象头前一个字），对象搬家时只更新这层间接，并发的应用线程读到的永远是最新地址——于是标记与压缩（疏散）都能与应用并发执行，STW 只剩扫线程栈等少量根，其耗时由"根的数量"决定，而不是"堆里有多少对象"。

关键点：间接指针 = 把"移动"从 STW 里摘出去的钥匙；对照 ZGC 的着色指针是同一问题的另一种解。
Q3: 追问 — Shenandoah 和 ZGC 怎么比？
Shenandoah（189，12 实验 / 15 转正）ZGC（333，11 实验）
实现移动的机制Brooks 指针（对象前 1 个 HeapWord 的间接指针）着色指针（把元数据藏在指针位里 + load barrier）
空间开销每对象多 1 个字不占对象空间，但要求堆地址空间布局（64 位）
屏障热点读写屏障读屏障为主
共同目标暂停与堆大小无关；用 CPU/内存换可预测延迟

12 的语境里两者都是"实验性低延迟选项"，G1 仍是默认生产选项。

关键点：同一个问题（并发移动对象）的两种指针方案——面试答"Brooks vs colored pointers"即可拉开差距。
Q4: 追问 — JEP 344 的 mandatory / optional 是怎么切的？

把一次混合回收的 collection set 切成两段：mandatory（通常含 young 区，可能带部分 old，约占预测 CSet 的 80%）——必须做完，否则回收语义不完整；optional（纯 old，约 20%）——如果还有时间预算才做，且推进粒度可以细到一次一个 region。进入增量模式的条件是"启发式的时间预测反复失败"；预测恢复准确后 optional 段会缩小直至全为 mandatory。代价：optional 部分 CPU 开销 <1%，加上跟踪指向 optional 区指针的少量 native 内存。JEP 明确 Non-goal：不保证 G1 所有暂停可中断，且没有用户可见开关。

关键点：80/20、一步一 region、"预测连续失败才增量"、无开关——四个关键词答全即满分。
Q5: 故障排查 — 线上 G1 堆一直占着不还给 OS，怎么处理？

先判断是不是本来就默认不还：JDK 12 的 G1PeriodicGCInterval 默认 0（g1_globals.hpp:304），周期 GC 根本没开。处理步骤：

  1. 确认需求：容器限额场景才需要归还，物理机独占通常不必；
  2. 开启：-XX:+UseG1GC -XX:G1PeriodicGCInterval=60000 -XX:G1PeriodicGCSystemLoadThreshold=<按负载调>；
  3. 检查堆缩放前提：-Xms 不能等于 -Xmx（等于就没得缩）、MinHeapFreeRatio/MaxHeapFreeRatio 要允许收缩；
  4. 验证：日志 -Xlog:gc,periodic 应出现 Checking for periodic GC. 与 cause G1 Periodic Collection；
  5. 另有 -XX:G1UncommitDelay 控制空闲多久才 uncommit（本课未核实其默认值，勿凭记忆写数字，用 -XX:+PrintFlagsFinal 现场确认）。
关键点：这类"没生效"问题，第一步永远是查默认值，而不是怀疑 bug。
Q6: 架构师 — 默认 CDS 归档的边界在哪？升级 JDK 12 要注意什么？

边界四条：① 只有平台类进默认归档，应用类仍需自己 -Xshare:dump/AppCDS；② 仅 64 位、仅 native 构建产物（交叉编译的发行包可能没有归档）；③ 归档与具体 JVM 二进制绑定，JVM 变了（不同构建/不同 flags 影响的类元数据）会校验失败并回退；④ -Xshare:off 是官方的"排除变量"。升级收益：JEP 341 实测 HelloWorld 启动快 32%（JDK 11 EA 数据），且不用改任何代码。风险点：极少数依赖"平台类每次都是新加载"的怪异代码（如字节码插桩按 ClassLoader 身份去重）可能行为变化——迁移测试里要覆盖启动与类加载路径。

关键点：CDS 改变的是"类从哪来"，不是"类是什么"——风险集中在类加载/初始化时序与身份假设上。
Q7: 讲师角度 — 用大白话讲"可中断的混合回收"。

想象你答应给整个小区做保洁（一次 GC），最脏的楼道（young/mandatory）必须一次扫完，否则没法交差；但旧货仓库（old/optional）如果时间不够，可以先扫两排，下回接着扫。以前的 G1 是"要么全扫要么不开始"，一旦预测不准就变成超长暂停；现在它承认"预测会错"，给仓库部分装了个进度条 + 可随时按下的暂停键。代价只是进度条本身的一点开销（<1% CPU）。

关键点：mandatory = 不能半途而废的语义；optional = 时间预算内的机会主义回收。
