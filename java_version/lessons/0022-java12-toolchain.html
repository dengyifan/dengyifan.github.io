L1 · 概念层：JDK 自己也要有"体检"和"一张架构地图"

本课覆盖 Java 12 的两个"工程向" JEP——JEP 230 Microbenchmark Suite（把基于 JMH 的微基准正式纳入 JDK 仓库）与 JEP 340 One AArch64 Port, Not Two（清掉重复的 64 位 ARM 端口）——外加预览特性工作流与非 LTS 升级策略两件升级必修的事。

JEP / 主题一句话状态
230 Microbenchmark Suite仓库里有了官方微基准：test/micro/org/openjdk/bench/{java,javax,vm}，初始约 100 个正式（12）
340 One AArch64 Port删掉 cpu/arm 里的 arm64 变体与相关 #ifdef，64 位 ARM 默认只走 cpu/aarch64，保留 32 位 ARM 端口正式（12）
325 switch 表达式（预览）唯一带"开关"的特性，编译运行都要 --enable-preview预览（12/13），14 转正
版本定位JDK 12 是非 LTS（8、11 才是），公开更新窗口短—

关键判断逻辑伪代码

# ===== 微基准怎么构建与运行（JEP 230）=====
configure --with-jmh=<JMH jar 目录>            # JMH 是外部二进制依赖，不配置就用不了
make build-microbenchmark                       # 独立目标：不参与常规 make images
make test TEST="micro:regexp"                   # 运行某个基准（按名称过滤）
# 需要支持 JDK(N) 与 JDK(N-1) 对比编译：同一份基准打两个 jar，切换 JVM 跑同一 jar 对比

# ===== 64 位 ARM 上选哪个端口（JEP 340）=====
if 目标 == 64-bit ARM (aarch64):
    端口 = src/hotspot/cpu/aarch64      # 唯一默认；arm64(arm 目录里的 64 位变体) 已删除
    build 选项里再无"用哪个 64 位 ARM 端口"的选择
elif 目标 == 32-bit ARM:
    端口 = src/hotspot/cpu/arm          # 仍保留，需继续通过一致性测试
else:
    端口 = cpu/{x86,ppc,s390,sparc,zero}

# ===== 该不该在这个 JDK 上用预览特性（325 等）=====
if 模块 == 业务主干/框架:            禁用（语义无承诺）
elif 模块 == 实验分支 且 团队锁定同一 JDK:
    javac --enable-preview --release 12 ...
    java  --enable-preview ...        # 编译与运行版本必须完全一致
else:                                 不用

# ===== 11 → 12 升不升 =====
if 追求稳定生产:  留在 11（LTS），或 直接规划 17/21 等 LTS
elif 要验证新特性/吃性能修复:  升 12 做压测，但把"非 LTS 支持窗口短"算进成本
JDK 12 在版本树里的位置

8（LTS）→ 9 → 10 → 11（LTS） → 12（非 LTS，2019-03-19） → 13 → 14 → 15（Shenandoah 转正）→ … → 17/21（LTS）。JDK 12 的价值在于它是特性节奏里的一站：switch 表达式预览首发、Shenandoah 首发、JMH 基准入库；把它当"生产长期基线"则是错配。

L2 · 原理层：为什么官方要自己养一套微基准

JEP 230 解决了什么

手写微基准的三大坑：死代码消除（结果没人用，JIT 直接把整段计算删掉）、预热不足（测的是解释器/C1 阶段）、常量折叠（循环里全是编译期常量）。JMH 通过生成胶水代码、预热迭代、Blackhole 吞噬结果来逐一化解。JEP 230 做的事是把这套基准放进 JDK 仓库本身，让"JDK 自己的改动有没有让某段代码变慢"成为可复现、可 CI 化的工程动作，而不是散落在各人心血来潮的本地脚本里。

伪代码：一个 JMH 基准从写到出数

# 作者只写"被测逻辑"（test/micro/org/openjdk/bench/java/lang/StringBuilders.java）
@Benchmark @OutputTimeUnit(NANOSECONDS)
public String bench_StringBuilder() {
    StringBuilder sb = new StringBuilder();  sb.append(QUESTION).append(LITERAL);
    return sb.toString();                    // 返回值 = 被 Blackhole 吞掉，防 DCE
}

# JMH 代码生成器（注解处理器）展开成：
#   1) 预热轮（warmup）: 跑 N 轮让 JIT 进入编译后稳态
#   2) 测量轮（measurement）: 跑 M 轮，逐轮采样
#   3) 每轮内: 调用被测方法 + Blackhole.consume 防止消除
#   4) fork 出独立 JVM 进程执行，隔离状态
# JDK 仓库侧（make/test/BuildMicrobenchmark.gmk）:
#   把 test/micro/**.java + JMH 依赖打成 benchmarks.jar
#   并为 JDK(N) 和 JDK(N-1) 各准备一份 → 切换 -java 参数即可做回归对比
flowchart LR A["configure --with-jmh"] --> B["make build-microbenchmark

（含 JDK N / N-1 两套产物）"] C --> D["make test TEST='micro:xxx'"] D --> E["JMH fork + 预热 + 测量"] E --> F["两版 JVM 跑同一 jar
→ 回归对比报告"]

四维度生产检查

维度230 JMH 基准套件340 单一 AArch64 端口预览特性工作流（325）非 LTS 升级策略
并发语义基准内部常带 @Threads/并发场景；JMH 负责正确的分组与协调，但基准不等于业务并发测试纯平台/代码清理，不改语义；AArch64 屏障、内存序代码随之只有一份纯编译期语法，字节码与手写等价（见 0018 课）版本切换会带上一整批 GC/并发改动，升级必须整体回归
异常容错缺 JMH 时构建直接报错：Error: JMH is missing. Please use configure --with-jmh.（BuildMicrobenchmark.gmk:34）删除 arm64 变体后要求 32 位 ARM 端口不出现回归——JEP 明列为验证任务预览 class 文件在非匹配 JVM 上直接拒绝加载非 LTS 停更后无补丁，风险随时间累积
边界判断仅约 100 个基准、不覆盖全部 JDK；不为新特性自动配基准（JEP Non-goal）边界 = 架构目录：cpu/ 下 arm（32 位）与 aarch64（64 位）各司其职，没有第三个 ARM 目录--release 必须等于运行版本；编译运行两侧都要开关12 的目标是"验证与尝鲜"，生产基线应回到 LTS
性能开销构建时间增加（独立 target，不影响常规构建）；仓库体积增加（引入 JMH 依赖）维护成本下降：一份 64 位 ARM 代码路径，编译矩阵更小零运行时开销（编译期特性）升级可能拿到 GC/JIT 修复的性能收益，但要实测
三个高频误区

① 「make build-microbenchmark 是常规构建的一部分」——不是，它在 make/Main.gmk 里是独立目标（常规 make images 不依赖它），只有 test-image 目标会带上它。
② 「仓库里有 cpu/arm 和 cpu/aarch64 说明还留着两套 64 位实现」——不是。arm 目录现在只服务 32 位 ARM；JEP 340 干的正是把该目录里"arm64 变体"及其 64/32 位 #ifdef 全删掉。
③ 「微基准数字能直接当性能结论」——不能：JMH 解决的是测量方法学问题，不解决代表性问题；真实结论要用你的负载压测验证。

设计原理三问

问题答案
为什么这样设计？230：性能回归必须可复现——把基准放进仓库，任何 JDK 改动都能被同一把尺子量；用 JMH 而不是自制框架，是因为方法学问题已被 JMH 解决。340：两套 64 位 ARM 代码意味着双倍维护、双倍测试、#ifdef 泛滥，留强去弱（aarch64 端口更活跃/更现代）能把资源集中到一条路径上。
代价是什么？230：构建依赖外部 JMH jar、仓库变大、构建变慢；基准数量有限（~100）且不自动覆盖新特性。340：失去一个"备选 64 位实现"，某些依赖 arm64 变体行为的平台需要迁移到 aarch64 端口并重新验证；32 位 ARM 端口必须额外做一致性验证。
如何改进？230 后续按需扩充基准（尤其新特性）并让 CI 定期跑对比；340 后续把平台支持进一步收敛/规范化（RISC-V 等新端口以同样方式治理）；对使用者，改进 = 把官方基准当"下限"，自家负载压测当"上限"，两层结合。

L4 · 边界层：能不能上生产

问题结论依据
JDK 12 适合当生产基线吗？一般不建议非 LTS，公开更新窗口短；生产应选 LTS（11/17/21），12 用于验证与迁移预演
官方微基准能当验收标准吗？能做回归哨兵，不能替代压测JEP 230 Non-goal：不覆盖全部 JDK、不为新特性自动提供基准
没有 --with-jmh 能构建吗？能构建 JDK，不能建基准BuildMicrobenchmark.gmk:34 显式报错退出
340 之后还要关心 ARM 构建选项吗？64 位 ARM 默认 aarch64，无选择；32 位 ARM 仍独立JEP 340 任务清单：删除构建选项、aarch64 设为默认
在 12 上用 switch 表达式安全吗？仅限锁定 12 的实验分支预览特性 + 13 改 yield（详见 0018 课）
11 → 12 升级/落地决策清单
  • 先定性质：12 是"过路站"不是"目的地"——把它用于特性验证、性能对比、迁移预演，生产基线仍锚定 LTS。
  • 构建层面：若要跑官方基准，configure 时加 --with-jmh=<path>；CI 里把 make build-microbenchmark 与 make test TEST="micro:…" 放进独立 job（避免拖慢主构建）。
  • 平台层面：ARM 交付链检查是否还依赖"arm64 构建选项"——12 起必须走 aarch64 端口；32 位 ARM 产品线单独验证。
  • 代码层面：预览特性开关集中到构建脚本一处（见 0018 的规矩）；把 Collectors.teeing 等正式 API 的使用点登记为"最低版本 = 12"。
  • 度量层面：升级前后用同一套 JMH 基准（官方 + 自有）跑 JDK 11 vs 12 对比，看的不是单点均值，而是波动区间与趋势。

L5 · 面试层：追问链

Q1: JEP 230 做了什么？怎么用？

把基于 JMH 的微基准正式纳入 JDK 仓库：test/micro/org/openjdk/bench/{java,javax,vm}，初始约 100 个基准。构建与运行：

configure --with-jmh=<JMH 目录>              # JMH 是外部二进制依赖
make build-microbenchmark                     # 独立目标，不参与常规构建
make test TEST="micro:regexp"                 # 按名称过滤运行

构建脚本会为 JDK(N) 与 JDK(N-1) 各准备产物，用同一基准做版本对比。JEP 明确 Non-goal：不为新特性自动提供基准、不覆盖全部 JDK。

关键点：入库的不是"数字"而是"可复现的测量方法"；--with-jmh 与独立 make target 是两个必答细节。
Q2: 追问 — 手写一个计时循环和 JMH 差在哪？

手写循环会被三件事毁掉：① 死代码消除——结果没人消费，JIT 把整段计算删了，你测到的是"什么都不做"的时间；② 预热不足——量到的是解释器/C1 甚至 JIT 编译期的噪声；③ 常量折叠/内联干扰——循环里的值编译期已知，跑的根本不是你要的逻辑。JMH 的解法是：注解处理器生成胶水代码、独立 fork 进程、显式预热/测量轮、返回值喂给 Blackhole。所以官方套件的价值是方法学，不是覆盖度。

关键点：DCE、预热、折叠三宗罪 + Blackhole/fork/warmup 三味药。
Q3: JEP 340 到底删了什么？

背景：OpenJDK 里曾有两份 64 位 ARM 实现——一份是 Oracle 贡献、寄生在 src/hotspot/cpu/arm 目录里的 arm64 变体（带大量"64 位还是 32 位"的 #ifdef），另一份是独立的 src/hotspot/cpu/aarch64。JEP 340 的任务：删除 arm64 相关源码与 #ifdef → 全仓扫描残留 → 删除该构建选项、把 aarch64 端口设为 64 位 ARM 默认 → 验证 32 位 ARM 端口仍能构建并通过一致性测试。结果：现在的 src/hotspot/cpu/ 只有 aarch64（64 位）和 arm（32 位）两条 ARM 路径。

关键点：不是删端口，是合并 64 位实现——保留 32 位 ARM，删掉重复的 64 位变体。
Q4: 故障排查 — configure 后 make build-microbenchmark 报 "JMH is missing"？

原因单一且明确：make/test/BuildMicrobenchmark.gmk:34 检查 JMH_CORE_JAR 为空即报 Error: JMH is missing. Please use configure --with-jmh.。修复：在 configure 阶段（不是 make 阶段）提供 --with-jmh=<含 jmh-core 等 jar 的目录>，重新生成构建目录后再 make。注意它不影响 JDK 本体构建——如果你只是要编译 JDK，可以忽略该错误；只有要跑基准/构建 test-image 才必须配。

关键点：JMH 是外部依赖 → 配置点在 configure；报错只影响基准构建，不阻塞 JDK。
Q5: 架构师 — 非 LTS 版本在你们的升级策略里怎么摆？

三档策略：① 生产只上 LTS（11 → 17/21），非 LTS 不进生产；② 预发/特性验证每个非 LTS 都跟，用于提前暴露 API/行为变化（例如 12 的 teeing、switch 预览、CDS 默认归档对启动路径的影响）；③ 框架与依赖要求以 LTS 为最低基线编译，避免把非 LTS 专属 API 泄漏到公共签名。JDK 12 的具体意义：用它验证"11 → 17"路上会遇到的中间变化（预览语法、GC 开关、CDS 行为），而不是把它当目的地。

关键点：非 LTS = 雷达，LTS = 地基；把 12 当"跳到 17 的排练场"是它的正确用法。
Q6: 讲师角度 — 给团队写一条"JDK 12 预览特性使用规矩"。

可直接落库的四句话：

  1. 仅限实验分支，主干与框架代码禁用 --enable-preview；
  2. 开关只在构建脚本里出现一处，禁止开发者本地随意加；
  3. 编译与运行 JDK 版本必须完全一致（--release 12 配 --enable-preview，运行 JVM 也必须是 12）；
  4. 每次 JDK 升级跑一次预览语法迁移检查（12 的 break 值 → 13 的 yield 是模板案例），并把"预览特性清单"列为 CR 必查项。
关键点：规矩的锚点是"可回退"——一处开关、版本锁定、迁移检查，三件事保证随时能退。
