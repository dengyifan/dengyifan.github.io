本课讲 JDK 21 LTS 转正的虚拟线程（JEP 444）。所有代码示例在本机 openjdk-25.0.1 实测通过（虚拟线程自 21 起为正式特性，免开关）。一处必须提前知道的版本差异：JDK 21 上虚拟线程跑在 synchronized 块里阻塞会被「钉住」（pinning），该行为已被 JDK 24 的 JEP 491 消除——本课在 L4 层给出两个版本的实测对照，别把 25 的行为当成 21 的。

L1 · 概念层：线程的两种实现

线程是可调度的最小处理单元，是 java.lang.Thread 的实例。从 JDK 21 起，Thread 有两种：平台线程（platform thread）与虚拟线程（virtual thread）。

维度平台线程虚拟线程
实现者OS（JDK 只是薄封装）Java 运行时
与 OS 线程的关系1:1，整个生命周期独占一条 OS 线程M:N，不绑定特定 OS 线程，阻塞时让出
数量上限受限于 OS 线程数（几千已吃力）同一 JVM 可达百万级
典型栈深 / 寿命深栈、长寿，故需要池化复用浅栈、短命（一次 HTTP 调用 / 一次 JDBC 查询）
适用任务所有类型，但是稀缺资源大部分时间阻塞等待 I/O 的任务
定位重量级工作线程并发单元，而非更快的线程

平台线程：昂贵的一对一封装

平台线程是 OS 线程的薄封装：它在底层那条 OS 线程上跑 Java 代码，并且整个生命周期都霸占这条 OS 线程。因此平台线程的数量受限于 OS 线程数。平台线程通常带着 OS 维护的大线程栈和其他资源，什么任务都能跑，但可能是稀缺资源——这正是过去必须用线程池的根本原因。

虚拟线程：运行时模拟「很多线程」

虚拟线程同样是 java.lang.Thread 的实例，但不绑定特定 OS 线程。它仍然在某条 OS 线程上执行代码；然而当虚拟线程里的代码调用阻塞 I/O 操作时，Java 运行时会挂起该虚拟线程直到它可以恢复，与之关联的 OS 线程随即被释放出来去服务其他虚拟线程。

虚拟线程的实现思路类似虚拟内存：OS 把很大的虚拟地址空间映射到有限的 RAM，以模拟「很多内存」；Java 运行时则把大量虚拟线程映射到少量 OS 线程，以模拟「很多线程」。

两个适用边界
  • 虚拟线程通常调用栈很浅，只做一次 HTTP 客户端调用或一次 JDBC 查询；单个 JVM 可能承载百万虚拟线程，因此是否使用线程局部变量要仔细权衡（见 0026）。
  • 虚拟线程适合大部分时间阻塞、常等待 I/O 完成的任务；不适合长时间运行的 CPU 密集型操作。

为什么要用：提供规模（吞吐），不是速度（延迟）

高吞吐并发应用——典型是服务端，要处理大量执行阻塞 I/O（如抓取资源）的客户端请求——应使用虚拟线程。但务必记住这句话：

虚拟线程不是更快的线程：它跑代码并不比平台线程快。它的存在是为了规模（更高吞吐），而不是速度（更低延迟）。

L2 · 原理层：M:N 调度与 mount/unmount

谁来调度：carrier 与挂载

平台线程何时运行由 OS 调度；虚拟线程何时运行由 Java 运行时调度。运行时调度一个虚拟线程时，会把它分配/挂载（mount）到一条平台线程上，然后 OS 照常调度那条平台线程——这条平台线程称为载体线程（carrier）。运行一段代码后，虚拟线程可以从载体上卸载（unmount），通常发生在它执行阻塞 I/O 操作时。卸载后载体空闲，调度器就可以把另一个虚拟线程挂上去。

sequenceDiagram participant Sch as 运行时调度器 participant C as Carrier（平台线程） participant VT as 虚拟线程 Sch->>C: mount(VT) C->>VT: 执行 CPU 计算 VT->>VT: 调用阻塞 I/O Note over VT: 发起非阻塞 OS 调用并 park VT-->>C: unmount（VT 挂起） Note over C: 空闲 → 可挂载其他虚拟线程 Sch->>C: mount(VT2) Note over VT: I/O 完成 → unpark，稍后重新挂载

阻塞时底层发生了什么

关键在于 java.* API 里的阻塞操作被运行时「接管」了：虚拟线程遇到阻塞 I/O 时，运行时执行的是非阻塞 OS 调用，然后自动挂起虚拟线程，稍后 I/O 就绪再恢复。于是「阻塞一个虚拟线程」很便宜——它不持有 OS 线程。这与阻塞平台线程（昂贵，因为白白占着稀缺线程）形成鲜明对比。

默认调度器：一个工作窃取池

事实说明
默认 Scheduler一个私有的 ForkJoinPool（工作窃取），并行度默认等于可用 CPU 核数
并行度可调系统属性 jdk.virtualThreadScheduler.parallelism
调度模型M:N：M 个虚拟线程映射到 N 条 OS 线程
历史对照Java 早期的「绿色线程」是 M:1（全共享一条 OS 线程），后被 1:1 的平台线程淘汰；虚拟线程回到 M:N 并由运行时负责阻塞挂起

为什么能提升吞吐：Little's Law

服务端可扩展性受 Little's Law 支配，它关联延迟、并发与吞吐：给定请求处理时长（延迟），应用同时处理的请求数（并发）必须与到达速率（吞吐）成比例增长。例如平均延迟 50ms、并发 10 个请求时吞吐 200 req/s；要扩到 2000 req/s，就必须并发处理 100 个请求。线程数必须随吞吐增长。

  • thread-per-request 风格：一个请求从始至终占用一个线程。易写、易调试（平台的并发单元 = 应用的并发单元），但 OS 线程昂贵，线程数往往在 CPU / 网络打满之前就先成了瓶颈；池化只省了启动开销，并不增加线程总数。
  • 异步风格：等待时把线程还给池子，换取高并发，却要放弃顺序组合（循环、try/catch），把逻辑拆成回调 / CompletableFuture 管道；栈追踪无上下文、调试器无法单步、profiler 无法关联成本到调用方。
  • 虚拟线程：保留 thread-per-request 风格，让每个请求全程跑在一个虚拟线程上，但它只在 CPU 计算时占用 OS 线程——透明地获得异步风格的可扩展性与近满硬件利用率。

L3 · API 层：创建与运行虚拟线程

Thread 与 Thread.Builder API 可创建两种线程；java.util.concurrent.Executors 也定义了为每个任务启动一个新虚拟线程的 ExecutorService。

方式 1：Thread.ofVirtual() + start/join

// 创建并启动一个打印消息的虚拟线程，再 join 等待它结束
Thread thread = Thread.ofVirtual().start(() -> System.out.println("Hello"));
thread.join();

Thread.Builder 接口让你用线程名等公共属性来创建线程：子接口 Thread.Builder.OfPlatform 建平台线程，Thread.Builder.OfVirtual 建虚拟线程。

// 具名单个线程
Thread.Builder builder = Thread.ofVirtual().name("MyThread");
Runnable task = () -> System.out.println("Running thread");
Thread t = builder.start(task);
System.out.println("Thread t name: " + t.getName());
t.join();

// 前缀 + 起始序号：批量自动命名 worker-0, worker-1 ...
Thread.Builder workers = Thread.ofVirtual().name("worker-", 0);
Runnable id = () -> System.out.println("Thread ID: " + Thread.currentThread().threadId());
Thread t1 = workers.start(id);   // worker-0
t1.join();
Thread t2 = workers.start(id);   // worker-1
t2.join();

方式 2：newVirtualThreadPerTaskExecutor()（推荐的服务端入口）

Executor 把线程的管理与创建从应用其余部分分离出来。每次调用 submit 都会创建并启动一个新虚拟线程来跑任务。

try (ExecutorService myExecutor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<?> future = myExecutor.submit(() -> System.out.println("Running thread"));
    future.get();                 // 等待该任务完成
    System.out.println("Task completed");
}   // close()：隐式等待所有任务结束

下面这个程序提交 10 000 个「睡 1 秒」的任务——本机实测约 1.1 秒全部跑完，背后只用了极少数 OS 线程（甚至少到一条）：

public class ManyVT {
  public static void main(String[] args) {
    long st = System.currentTimeMillis();
    try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
      IntStream.range(0, 10_000).forEach(i -> {
        executor.submit(() -> { Thread.sleep(Duration.ofSeconds(1)); return i; });
      });
    }
    System.out.println("10k tasks in " + (System.currentTimeMillis() - st) + "ms");
  }
}
// 本机实测输出（openjdk-25.0.1）：
// 10k tasks in 1090ms
换成平台线程会怎样
  • 用 Executors.newCachedThreadPool()：会试图创建 10 000 条平台线程（= 10 000 条 OS 线程），程序可能直接崩。
  • 用 Executors.newFixedThreadPool(200)：只有 200 条线程被 10 000 个任务共享，大量任务排队、跑很久（吞吐上限 200 task/s，而虚拟线程约 10 000 task/s）。
  • 把 10_000 改成 1_000_000：虚拟线程版会创建百万个并发虚拟线程，达到约百万 task/s（充分热身之后）。

toString() 还能看到载体信息，这是判断「代码正跑在哪个 carrier 上」的直接证据：

Thread t = Thread.ofVirtual().name("vt-hello").start(() -> {});
t.join();
System.out.println(t.isVirtual() + " / " + t);
// 实测（运行中 toString）：VirtualThread[#26,vt-hello]/runnable@ForkJoinPool-1-worker-1
//                                    斜杠后就是它当时挂载的 carrier 线程

方式 3：每连接一个虚拟线程的 Echo Server

服务端每接受一条连接就启动一个虚拟线程处理，于是可以同时服务大量客户端，代码仍是顺序阻塞写法：

public class EchoServer {
  public static void main(String[] args) throws IOException {
    int port = Integer.parseInt(args[0]);
    try (ServerSocket serverSocket = new ServerSocket(port)) {
      while (true) {
        Socket clientSocket = serverSocket.accept();        // 接受连接
        Thread.ofVirtual().start(() -> {                    // 每连接一个虚拟线程
          try (PrintWriter out = new PrintWriter(clientSocket.getOutputStream(), true);
               BufferedReader in = new BufferedReader(
                   new InputStreamReader(clientSocket.getInputStream()))) {
            String inputLine;
            while ((inputLine = in.readLine()) != null) {
              System.out.println(inputLine);
              out.println(inputLine);                       // 原样回显
            }
          } catch (IOException e) { e.printStackTrace(); }
        });
      }
    }
  }
}

L4 · 边界层：钉住、池化与限流

Pinning：虚拟线程无法卸载的两种情况

当虚拟线程被钉（pinned）在载体上时，阻塞操作期间它无法卸载。JDK 21 上钉住发生在：

  1. 虚拟线程在 synchronized 块或方法内运行代码；
  2. 虚拟线程运行 native 方法或外部函数（Foreign Function，见 FFM API）。

钉住不会让程序出错，但会损害可扩展性。官方建议：改写频繁执行的 synchronized 块/方法，并用 java.util.concurrent.locks.ReentrantLock 守护可能很长的 I/O 操作，以避免频繁且长寿的钉住。

版本实测对照：synchronized 钉住（JDK 21） vs 不钉住（JDK 24+）

100 个虚拟线程，各自在自己的、零竞争的 monitor 上 synchronized 后睡 300ms：

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
  for (int i = 0; i < 100; i++) {
    final Object ownLock = new Object();        // 每个任务自己的锁：无竞争
    exec.submit(() -> {
      synchronized (ownLock) { Thread.sleep(Duration.ofMillis(300)); }
      return null;
    });
  }
}
版本预期 / 实测耗时原因
JDK 21≈ ⌈100 / carrier 数⌉ × 300ms（约 2.7s@12 carriers）synchronized 内阻塞 → 钉住 carrier，carrier 被睡占无法复用
JDK 25 实测303ms（JFR 中 jdk.VirtualThreadPinned 事件 0 条）JEP 491（JDK 24）让 synchronized 阻塞也能卸载

注意 native 方法 / 外部函数的钉住在 25 上仍然存在（JEP 491 只解决 synchronized）。判断线上是否发生钉住，直接看 JFR 的 jdk.VirtualThreadPinned 事件。

JDK 21 上的改写：synchronized → ReentrantLock
// JDK 21：synchronized 内做阻塞 I/O 会钉住 carrier
synchronized (guard) {
    socket.read(buf);
}

// 改写：j.u.c.l.ReentrantLock 在虚拟线程上阻塞不会钉住
guardLock.lock();
try {
    socket.read(buf);
} finally {
    guardLock.unlock();
}

前提是这段 synchronized 只是为了互斥、不依赖 monitor 的 wait/notify 语义；改写后临界区行为不变。

不要池化虚拟线程

虚拟线程便宜又海量，因此永远不该被池化：每个应用任务都应创建一个新虚拟线程。大多数虚拟线程短命、栈浅；池化是过去为应对平台线程高成本而生的习惯，用在虚拟线程上适得其反。平台线程才重、才需要池化。

用 Semaphore 限制并发，而不是靠线程数

虚拟线程可以无限开，但下游外部资源（如数据库连接、对端 API）往往有硬上限。此时用 Semaphore 在业务层显式限流：

static final Semaphore DB_PERMITS = new Semaphore(16);   // DB 连接上限

void handle() throws InterruptedException {
  DB_PERMITS.acquire();                                  // 拿不到许可就等
  try {
    query();                                             // 阻塞 JDBC 调用
  } finally {
    DB_PERMITS.release();
  }
}

不要用「固定大小的虚拟线程池」来限流——那等于把平台线程时代的做法硬套回来；池化虚拟线程没有意义，限流应表达为对资源许可的获取。

ThreadLocal 的百万级成本

虚拟线程支持 ThreadLocal 与 InheritableThreadLocal，这保证大量现有库可以原样使用。但单 JVM 可能有百万虚拟线程：每个线程都为线程局部变量维护独立映射，内存与继承开销会被放大百万倍。JDK 21 起虚拟线程总是支持线程局部变量（预览期曾可创建不支持的虚拟线程，转正后取消）。更优替代是 ScopedValue，详见 0026 线程局部变量。

CPU 密集型任务：线程数超过核数没有收益

若任务做的是 1 秒的计算（如给大数组排序）而非睡 1 秒，那么无论虚拟线程还是平台线程，线程数超过处理器核数都无济于事。大数据集并行仍优先用 Stream API（JEP 444 明确不提供新的数据并行构造）。

观测虚拟线程：JFR 与 jcmd

虚拟线程仍然是线程，调试器可以像平台线程一样单步调试。JFR 与 jcmd 还提供额外观测能力。

JFR 事件

事件含义默认状态
jdk.VirtualThreadStart / jdk.VirtualThreadEnd虚拟线程启动 / 终止默认关闭

L5 · 面试层：追问链

Q1: 虚拟线程是什么？它和平台线程的本质区别？

虚拟线程是 JDK 21（JEP 444）引入的轻量级 java.lang.Thread 实现，由 Java 运行时而非 OS 实现。平台线程 1:1 封装 OS 线程、一生独占、数量受限；虚拟线程是 M:N，不绑定特定 OS 线程，阻塞 I/O 时挂起并释放载体线程，同一 JVM 可承载百万级。

本质区别：谁实现线程（OS vs 运行时），以及阻塞时是否释放 OS 线程。
Q2: 追问 — 虚拟线程能让接口变快吗？什么情况下才能提升吞吐？

不能。虚拟线程不是更快的线程，不降低延迟，只提供规模。它提升吞吐需要两个条件：① 并发任务数很高（几千以上）；② 工作负载不是 CPU 密集型（线程数远超核数对计算任务无收益）。典型服务端大量任务阻塞等待 I/O，正符合。

提供 scale（吞吐）而非 speed（延迟）；CPU 密集用 Stream 并行，别用虚拟线程。
Q3: 追问 — 什么是 carrier？什么是 pinning？JDK 21 上哪些情况会钉住？

Carrier 是承载虚拟线程运行的平台线程；虚拟线程 mount 上去执行、阻塞 I/O 时 unmount 让出 carrier。Pinning 指虚拟线程被钉在 carrier 上、阻塞时无法卸载。JDK 21 上两种情形：① 在 synchronized 块/方法内；② 运行 native 方法或外部函数。钉住不错误但损害扩展性。

JDK 24 的 JEP 491 已消除 synchronized 钉住；native/FFI 仍会钉住。排查看 JFR jdk.VirtualThreadPinned（默认阈值 20ms）。
Q4: 代码审查 — 这段「用固定大小虚拟线程池做限流」的代码有什么问题？
var pool = Executors.newFixedThreadPool(200);   // 想「限制」虚拟线程并发
pool.submit(() -> query());
  1. newFixedThreadPool 建的是平台线程，根本不是虚拟线程——既没拿到虚拟线程的规模，又把 200 条重线程变成瓶颈；
  2. 虚拟线程永远不该池化：每个任务应 Thread.ofVirtual() 新建或走 newVirtualThreadPerTaskExecutor()；
  3. 限流要表达为对下游资源的许可：用 Semaphore（如 DB 连接数），拿许可再调用。
池化是应对平台线程昂贵的旧习惯，对虚拟线程适得其反；限限流用 Semaphore。
Q5: 架构师 — 现有异步 / 响应式服务要不要迁到虚拟线程？怎么迁成本最小？

若异步管道已稳定运行、且团队能接受其调试与推理成本，不急于迁。虚拟线程的最大价值在保留 thread-per-request 风格：迁回简单的顺序阻塞代码（循环、try/catch 都能正常用），由框架为每个请求启动虚拟线程。最小改动路径：① 请求入口改用 newVirtualThreadPerTaskExecutor()；② 业务代码改写为同步阻塞 I/O；③ 排查 synchronized 内长 I/O（21 上改 ReentrantLock）；④ 对外部资源加 Semaphore。异步风格的 CompletableFuture 链路不会从虚拟线程获益多少。

迁移的核心是「回到同步代码」，而不是给旧回调链套虚拟线程。
Q6: 故障排查 — 上线虚拟线程后吞吐没提升、CPU 也不高，先查什么？
  1. 先取 jcmd <pid> Thread.dump_to_file -format=text：确认请求是否真跑在虚拟线程上（标签 virtual），大量线程是否卡在同一阻塞点；
  2. 开 JFR 看 jdk.VirtualThreadPinned：JDK 21 上常因 synchronized 守护了 I/O（如老版连接池 / 老 JDBC），carrier 被钉占——改用 ReentrantLock 或升级驱动 / JDK；
  3. 查下游是否成瓶颈：DB 连接池打满会让虚拟线程全部 park 在等连接，此时用 Semaphore 限并发而非盲目加线程；
  4. 确认负载不是 CPU 密集型。
排查顺序：thread dump 定性 → JFR pinning 事件 → 下游资源 → CPU 密集度。
