本课怎么读 · 版本口径（重要）

结构化并发在 JDK 21 是第一次预览（JEP 453），主角是 java.util.concurrent.StructuredTaskScope（含 ShutdownOnSuccess / ShutdownOnFailure 两个内置策略）。预览特性编译运行都要加开关：javac 用 --enable-preview --release 21，运行 java --enable-preview。
本课以 21 的 API 为主线（忠于 Oracle Java 21 文档）；本机用 openjdk-25.0.1 实测时，该特性已演进到 JEP 505（第五次预览）且 API 重新设计（open(Joiner) 模型，不再有两个嵌套子类）——L4 层专门给出 21 → 25 演进与实测对照。

L1 · 概念层：什么是结构化并发

结构化并发把在不同线程中运行的一组相关任务当作单一工作单元，从而简化错误处理与取消、提升可靠性、增强可观测性。

核心类是 java.util.concurrent.StructuredTaskScope：用它把一组并发子任务作为一个整体协调——fork 每个子任务（各自在独立线程中运行），然后把它们作为整体 join。scope 保证主任务继续之前子任务都已结束；也可以指定「某个子任务成功就继续」。

非结构化并发的三个老问题

传统写法用 ExecutorService + Future：

Response handle() throws Exception {
  Future<String> user  = exec.submit(this::findUser);
  Future<Integer> order = exec.submit(this::fetchOrder);
  String u = user.get();          // 任一失败 / 请求被取消时……
  int o = order.get();
  return new Response(u, o);
}
问题表现
线程泄漏findUser 失败了，fetchOrder 仍在自己的线程里跑——它的结果已无人需要，却要手动取消；忘了就泄漏成「孤儿线程」
取消传播困难请求超时 / 被中断时，需要把取消信号逐个传给子线程；异常从 Future.get() 里以 ExecutionException 包装抛出，处理啰嗦且易漏
无可观测结构thread dump 里子任务与父任务是一堆平级线程，看不出谁属于谁、谁在等谁
「结构化」的含义

类比结构化编程里 { ... } 代码块：进入块、块内语句、退出块——控制流嵌套、寿命有界。结构化并发让线程的寿命也嵌套在语法结构里：子任务在 scope 内 fork，scope 关闭（退出 try 块）时所有子任务必然已结束。于是「父任务活着时子任务必活着，父任务结束前子任务必结束」成为可由代码结构保证的不变式。

L2 · 原理层：scope 的生命周期

六步流程

  1. 创建 StructuredTaskScope，并用 try-with-resources 管理；
  2. 把子任务定义为 Callable；
  3. 在 try 块内用 StructuredTaskScope::fork 让每个子任务在自己的线程运行；
  4. 调用 StructuredTaskScope::join；
  5. 处理子任务的结果；
  6. 确保 scope 被关闭（try-with-resources 自动完成）。

关闭、短路与取消传播

机制语义
shutdown()不关闭 scope 而停止接收新任务：中断线程以取消所有未完成子任务；子类用它实现「不必等全部完成」的策略
close()（try 退出）关闭 scope，并等待运行未完成子任务的线程结束——保证 try 之后无孤儿线程
短路（short-circuiting）主任务在结果已定时中断/取消不再需要的子任务，促使它们尽快结束
owner创建并 fork/join 的那个线程；结果访问与关闭都受 owner 约束

L3 · API 层：内置的两种关闭策略（JDK 21）

基本骨架

Callable<String> task1 = ...
Callable<Integer> task2 = ...

try (var scope = new StructuredTaskScope<Object>()) {

    Subtask<String> subtask1 = scope.fork(task1);
    Subtask<Integer> subtask2 = scope.fork(task2);

    scope.join();

    // ... 处理结果 / 异常 ...

} // close：等待任何未完成子任务结束

策略 1：ShutdownOnFailure — 一个失败就全部取消

经典的「聚合多个下游服务」场景：任一下游失败，请求就无法成功，立即取消其余子任务。

record User(String name, int order, String tag) {}

User handle() throws ExecutionException, InterruptedException {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        Subtask<String> name  = scope.fork(this::findName);
        Subtask<Integer> order = scope.fork(this::fetchOrder);
        Subtask<String> tag   = scope.fork(this::fetchTag);

        scope.join()
             .throwIfFailed();          // 有失败 → 原样抛出捕获的异常；全部成功 → 继续

        return new User(name.get(), order.get(), tag.get());
    }
}
  • ShutdownOnFailure 捕获第一个子任务抛出的异常，然后调用 shutdown：阻止新子任务启动、中断其余未完成线程，让应用得以继续。
  • 访问捕获的异常用 exception()；想重新抛出用 throwIfFailed()（本例用法）。
  • join 之后、全部成功时，Subtask.get() 才能安全取到结果。

策略 2：ShutdownOnSuccess — 谁先成功用谁的结果

适合「多个等价来源取最快的一个」（如多副本 / 多地域）：捕获第一个成功完成的子任务结果，然后 shutdown 取消其余。

String fastest() throws ExecutionException, InterruptedException {
    try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
        scope.fork(() -> fetchFrom("region-a"));
        scope.fork(() -> fetchFrom("region-b"));
        scope.fork(() -> fetchFrom("region-c"));
        scope.join();
        return scope.result();          // 第一个成功子任务的结果
    }
}

官方示例 SCRandomTasks 同时演示两者：fork 5 个随机时长的任务，超阈值就抛 TooSlowException——ShutdownOnFailure 在无异常时打印总时长，ShutdownOnSuccess 打印最先完成者：

// ShutdownOnFailure：无异常 → 汇总；有异常 → throwIfFailed 抛出
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var subtasks = IntStream.range(0, 5)
        .mapToObj(i -> scope.fork(() -> randomTask(1000, 850)))
        .toList();
    scope.join().throwIfFailed();
    var total = subtasks.stream().map(Subtask::get).reduce(0, Integer::sum);
    System.out.println("Total duration: " + total);
}

// ShutdownOnSuccess：最先完成者
try (var scope = new StructuredTaskScope.ShutdownOnSuccess<Integer>()) {
    IntStream.range(0, 5)
        .mapToObj(i -> scope.fork(() -> randomTask(1000, 850)))
        .toList();
    scope.join();
    System.out.println("First: " + scope.result());
}
// 实测输出片段：
// Total duration: 2263
// First task to finish: 40

L4 · 边界层：自定义策略、预览开关与版本演进

自定义 StructuredTaskScope 策略

继承 StructuredTaskScope 可实现不同于内置两者的策略——核心是重写 handleComplete，在每个子任务完成时按状态分流。下例 CollectingScope 把成功与失败子任务分别收入两个队列：

public class CollectingScope<T> extends StructuredTaskScope<T> {
    private final Queue<Subtask<? extends T>> successSubtasks = new LinkedTransferQueue<>();
    private final Queue<Subtask<? extends T>> failedSubtasks  = new LinkedTransferQueue<>();

    @Override
    protected void handleComplete(Subtask<? extends T> subtask) {
        if (subtask.state() == Subtask.State.SUCCESS) {
            successSubtasks.add(subtask);
        } else if (subtask.state() == Subtask.State.FAILED) {
            failedSubtasks.add(subtask);
        }
    }

    @Override
    public CollectingScope<T> join() throws InterruptedException {
        super.join();
        return this;
    }

    public Stream<Subtask<? extends T>> successfulTasks() {
        super.ensureOwnerAndJoined();          // 仅 owner、且已 join 才可访问
        return successSubtasks.stream();
    }

    public Stream<Subtask<? extends T>> failedTasks() {
        super.ensureOwnerAndJoined();
        return failedSubtasks.stream();
    }
}

三个关键保护：① Subtask.state() 取值 SUCCESS / FAILED（另有未完成态）；② get() / exception() 分别取结果与异常；③ ensureOwnerAndJoined() 强制「当前线程是 owner、且 fork 之后已 join」，防止在任务未完成时读到半成品。

与 ScopedValue 配合：上下文安全地传给子任务

fork 出的子线程可以配合 ScopedValue（21 预览 JEP 446）继承上下文，而不必用 InheritableThreadLocal：绑定在父任务的动态作用域内、scope 关闭即失效。详见 0026 线程局部变量。

版本演进与 JDK 25 实测（API 已重新设计）

结构化并发经历了多次预览：21 JEP 453（一）→ 22 JEP 462（二）→ 23 JEP 480（三）→ 24 JEP 499（四）→ 25 JEP 505（五）。在 25 上：

  • StructuredTaskScope<T,R> 变成接口，不再 new，而用静态工厂 StructuredTaskScope.open(Joiner)；
  • ShutdownOnFailure / ShutdownOnSuccess 两个嵌套子类被移除，改由 Joiner 工厂表达策略；
  • join() 直接返回结果 R（21 上 join 返回 scope、结果靠 Subtask.get() 取）。
21（JEP 453）25（JEP 505，实测）
new StructuredTaskScope.ShutdownOnFailure() + join().throwIfFailed()open(Joiner.awaitAllSuccessfulOrThrow())；任一失败 join 抛 FailedException
new StructuredTaskScope.ShutdownOnSuccess<T>() + result()open(Joiner.<T>anySuccessfulResultOrThrow())；join 返回首个成功结果
new StructuredTaskScope<T>()（等全部，含失败）open(Joiner.awaitAll())
// 本机 JDK 25 实测：javac --enable-preview --release 25
User handle() throws Throwable {
  try (var scope = StructuredTaskScope.<Object, Stream<Subtask<Object>>>
           open(Joiner.<Object>allSuccessfulOrThrow())) {
    Subtask<String> name  = scope.fork(this::findName);
    Subtask<Integer> order = scope.fork(this::fetchOrder);
    Subtask<String> tag   = scope.fork(this::fetchTag);
    scope.join();
    return new User(name.get(), order.get(), tag.get());
  }
}
// 实测输出：User[name=Alice, order=42, tag=VIP]

失败短路实测：一个子任务抛 boom，join 抛 FailedException: java.lang.IllegalStateException: boom，并行的慢任务被中断取消（未跑完）。因此查 21 资料时以 ShutdownOnXxx 为准，在 25 上写代码以 open(Joiner) 为准，两者不要混用。

L5 · 面试层：追问链

Q1: 什么是结构化并发？它解决了传统 ExecutorService + Future 的什么痛点？

结构化并发把在不同线程运行的一组相关任务当作单一工作单元（JDK 21 JEP 453 预览，核心 StructuredTaskScope）。它解决：① 线程泄漏——一个子任务失败后其余仍在跑、结果已无人需要；② 取消传播困难——超时/中断要逐个处理、异常包装繁琐；③ 无可观测结构——thread dump 里看不出子任务属于谁。try-with-resources 保证 scope 关闭时所有子任务必然结束。

核心不变式：父任务结束前，所有子任务必已结束——由语法结构而非手工约定保证。
Q2: 追问 — 描述 StructuredTaskScope 的使用步骤；fork 和 join 分别做什么？

① try-with-resources 创建 scope；② 子任务写成 Callable；③ fork 让每个子任务在自己的线程启动；④ join 等待；⑤ 处理结果；⑥ close 自动收尾。fork = 启动独立子线程并返回 Subtask 句柄；join = 把所有子任务作为整体等待完成（或等待策略短路）。

close 会等待未完成子任务结束；shutdown 则中断取消未完成子任务。
Q3: ShutdownOnFailure 和 ShutdownOnSuccess 的区别？各举一个使用场景。

ShutdownOnFailure：捕获第一个异常并 shutdown 取消其余——用于「聚合多个必需的下游服务」，任一下游失败请求即失败，用 join().throwIfFailed()。ShutdownOnSuccess：捕获第一个成功结果并 shutdown——用于「多个等价来源取最快」，用 scope.result()。两者都是短路模式。

一个对「首个失败」短路，一个对「首个成功」短路。
Q4: 代码审查 — 为什么在 JDK 25 上这段 JDK 21 代码编译不过？怎么改？
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    scope.fork(this::findName);
    scope.join().throwIfFailed();
}

因为 JDK 25 已演进到 JEP 505（第五次预览）：ShutdownOnFailure 嵌套子类被移除，StructuredTaskScope 改为接口、用 open(Joiner) 创建，join() 直接返回结果。等价写法：

try (var scope = StructuredTaskScope.open(Joiner.awaitAllSuccessfulOrThrow())) {
    scope.fork(this::findName);
    scope.join();
}
21 与 25 是两套 API 形态：ShutdownOnXxx（21） vs open(Joiner)（25），且都需 --enable-preview。
Q5: 架构师 — 结构化并发和虚拟线程是什么关系？上线要注意什么？

两者同属 Project Loom 但正交：虚拟线程提供廉价海量线程；结构化并发提供「把一组线程当单元管理」的纪律。fork 出的子任务默认就跑在虚拟线程上。上线注意：① 21 上结构化并发是预览特性，需 --enable-preview --release 21，API 未来可能变（25 已重设计），不宜暴露到长期 API；② 用 jcmd JSON 转储确认父子结构与 owner；③ 子任务上下文优先用 ScopedValue 而非 InheritableThreadLocal；④ 子任务要正确响应中断以便短路取消能及时生效。

虚拟线程解决「线程贵」，结构化并发解决「线程散」；组合使用，但 21 上后者仍是预览。
Q6: 故障排查 — jcmd JSON 转储里怎么看出一个卡住请求的子任务结构？

① 在 threadContainers 里找到 container 名为 StructuredTaskScope$... 的容器；② 看它的 owner（父任务 tid）与 parent，重建归属；③ 容器内 threads 数组即该 scope fork 的全部子任务，逐个看 stack 定位卡点（如全部 park 在等下游连接）；④ 父线程栈通常停在 ThreadFlock.awaitAll / StructuredTaskScope.join，说明它在等子任务。

container + owner + parent 三字段是从转储重建父子结构的钥匙。
