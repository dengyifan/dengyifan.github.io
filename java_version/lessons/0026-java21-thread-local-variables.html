线程局部变量 — ThreadLocal、InheritableThreadLocal 与三大设计缺陷

首页 / Java 21 / 线程局部变量
本课怎么读 · 版本口径

本课基于 Oracle Java 21 Core 文档「Thread-Local Variables」。ThreadLocal 自 Java 1.0 就存在、非新特性，但它在 JDK 21 因百万虚拟线程而重新成为焦点（JEP 444 保证虚拟线程总是支持它）。文档同时指出继任者：ScopedValue——21 预览（JEP 446），本机 JDK 25 已转正（JEP 506），实测免开关。

L1 · 概念层：什么是线程局部变量

线程局部变量是类型为 ThreadLocal 的变量：每个访问它的线程都拥有自己独立初始化的副本。读写分别调用 set / get。它通常声明为 final static 字段，以便许多组件都能方便地访问。

一个完整例子：把「当前用户」藏进线程

下例中 TLDBConn 表示数据库连接，TLServer 表示数据库（fetchOrder 无参数，直接读线程局部变量），TLApplication 在各自线程里创建多个连接：

public class User {
    public String name;
    public User(String n) { name = n; }
}

public class TLDBConn {
    final static ThreadLocal<User> TLUSER = new ThreadLocal<>();

    public static String open(String info) {
        System.out.println(info + ": " + TLUSER.get().name);
        return info + ": " + TLUSER.get().name;
    }
}

public class TLServer {
    public static String fetchOrder() {
        return "Fetching order for " + TLDBConn.TLUSER.get().name;
    }
}
public class TLApplication {
    public void testConnection(User u) {
        Runnable r = () -> {
            TLDBConn.TLUSER.set(u);
            TLDBConn.open("Thread " + Thread.currentThread().getName() + ", testConnection");
            System.out.println(TLServer.fetchOrder());

            try { Thread.sleep(new Random().nextInt(1000)); }
            catch (InterruptedException e) { e.printStackTrace(); }

            TLDBConn.TLUSER.set(new User(u.name + " renamed"));
            TLDBConn.open("Thread " + Thread.currentThread().getName() + ", testConnection");
        };
        Thread t = new Thread(r, u.name);
        t.start();
    }

    public static void main(String[] args) throws Exception {
        TLApplication app = new TLApplication();
        for (int i = 0; i < 5; i++) {
            app.testConnection(new User("user" + i));
            Thread.sleep(new Random().nextInt(1000));
        }
    }
}

输出（各线程交错，但每个线程读到的都是自己的用户）：

Thread user0, testConnection: user0
Fetching order for user0
Thread user1, testConnection: user1
Fetching order for user1
...
Thread user0, testConnection: user0 renamed
Thread user1, testConnection: user1 renamed
两个要点
  • 尽管 TLUSER 声明为 final static（全 JVM 只有一个 ThreadLocal 对象），它的值对每个线程都是唯一的——共享的是「变量的定位器」，独立的是「每线程的值」。
  • TLServer.fetchOrder() 无参数，调用方不必把 User 层层透传，它直接读「运行它的那个线程」对应的副本。因此线程局部变量可以隐藏方法参数。

L2 · 原理层：每线程副本是怎么存的

机制说明
值存在线程身上，而非 ThreadLocal 对象身上每个 Thread 内部持有一个线程局部映射（Thread.threadLocals）；ThreadLocal 对象只是键
set(v)取当前线程的映射，以「这个 ThreadLocal」为键写入 v
get()以该 ThreadLocal 为键查当前线程映射；没有则调用 initialValue() 初始化（默认 null）
remove()从当前线程映射删除该键——线程结束前主动清理的唯一入口
为什么用 staticThreadLocal 对象本身无状态、只作键；static 保证全应用用同一个键，避免每实例一个键造成映射膨胀

心智模型一句话：不是「一个变量，每线程一份值」，而是「每个线程有一张 Map，ThreadLocal 当 key」。所以 N 个线程 × M 个 ThreadLocal = N 张各含 M 个条目的映射，内存成本是 N×M。

InheritableThreadLocal：子线程继承父线程的值

父线程启动子线程时，普通 ThreadLocal 的值不会被继承。若希望子线程继承，改用 InheritableThreadLocal：

public class TLDBConn {
    final static ThreadLocal<User> TLUSER = new ThreadLocal<>();
    final static InheritableThreadLocal<User> TLADMIN = new InheritableThreadLocal<>();
}
Thread childThread = new Thread(() -> {
    System.out.println("TLADMIN: " + TLDBConn.TLADMIN.get().name);   // 继承到
    try {
        System.out.println("TLUSER: " + TLDBConn.TLUSER.get().name); // 未继承 → NPE
    } catch (NullPointerException e) {
        System.out.println("NullPointerException: TLUSER not set");
    }
});
childThread.start();
// 输出：
// TLADMIN: Admin
// NullPointerException: TLUSER not set
继承的两个实现细节（实测确认）
  • 拷贝发生在 new Thread(...) 构造时，不是 start() 时：Thread 构造函数会快照父线程的可继承映射。因此「先构造子线程、再 set 父值、后 start」子线程拿不到新值；必须先 set 再构造。
  • 浅拷贝、传引用：子线程拿到的是父值的同一个对象引用（实测 child.get() == parent.get() 为 true），不是克隆——父子对该对象的修改互相可见。

L3 · 边界层：ThreadLocal 的三大设计缺陷

Oracle 文档明确指出线程局部变量有若干设计缺陷，而 ScopedValue 正是为解决这些问题而生。

缺陷 1：无约束的可变性（Unconstrained Mutability）

每个线程局部变量都是可变的。这让你很难分辨应用中哪些组件更新了共享状态、以什么顺序更新——任何能拿到 TLUSER 的代码都能 set，如例子里同一任务后半段把它改成了「renamed」：

TLDBConn.TLUSER.set(u);
// ... 中途任意深度的代码都可能再 set ...
TLDBConn.TLUSER.set(new User(u.name + " renamed"));

后果：行为依赖「调用时序」而非显式数据流，重构和排查都困难。

缺陷 2：无界的生命周期（Unbounded Lifetime）

Java 运行时会保留线程的某个线程局部副本，直到线程结束或线程内代码显式调用 remove()。

场景风险
忘记 remove()线程数据被保留超过必要时间，造成长期内存泄漏；多次 set 之后往往没有明确的安全 remove 点
线程池线程被复用：上一个任务 set 的值会泄漏到下一个任务——上一个用户的身份 / 事务上下文被下一个请求意外读到，这是最危险的一类生产事故
// 线程池里的正确纪律：每个任务结束必须 remove
pool.submit(() -> {
    TLUSER.set(user);
    try {
        handle();
    } finally {
        TLUSER.remove();        // 不写就泄漏给同线程的下一个任务
    }
});

缺陷 3：昂贵的继承（Expensive Inheritance）

使用大量线程时开销会恶化：父线程的可继承线程局部变量会被子线程继承——每生一个子线程，都要复制父映射里的相关条目。在线程数达百万级的虚拟线程场景，该成本与 ThreadLocal 占用的内存被急剧放大。

L4 · 继任者：ScopedValue

ScopedValue 用「不可变值 + 有界作用域」重写这套机制，专为海量虚拟线程设计：写一次，只在 where(...).run(...) / .call(...) 的动态作用域内可读，出作用域自动失效、不可再改。

public class SVDemo {
    static final ScopedValue<String> WHO = ScopedValue.newInstance();

    public static void main(String[] a) throws Exception {
        // call：执行并返回结果
        String v = ScopedValue.where(WHO, "bob").call(() -> "inside=" + WHO.get());
        System.out.println(v);

        // run：执行不求值
        ScopedValue.where(WHO, "alice").run(() -> System.out.println(WHO.get()));

        // 出作用域：不再绑定
        System.out.println("bound=" + WHO.isBound());
    }
}
// 实测输出（JDK 25，免预览）：
// inside=bob
// alice
// bound=false
维度ThreadLocalScopedValue
可变性可变，任何代码可 set不可变，绑定时写一次，之后只读
生命周期无界：直到线程结束或手动 remove有界：where 的动态作用域结束即失效
跨线程传递InheritableThreadLocal：构造子线程时复制映射（昂贵）无继承机制；配合 StructuredTaskScope 时，fork 的子任务自动共享绑定，无需复制
线程池风险任务间值泄漏作用域随任务结束而关闭，无泄漏
状态Java 1.0 起正式21 预览 JEP 446 → JDK 25 转正 JEP 506

实测 ScopedValue 与结构化并发配合：父任务绑定后，fork 的子任务能直接读到，作用域关闭即失效：

ScopedValue.where(USER, "alice").run(() -> {
    try (var scope = StructuredTaskScope.open(Joiner.<String>allSuccessfulOrThrow())) {
        scope.fork(() -> "subtask sees: " + USER.get());
        scope.fork(() -> "subtask sees: " + USER.get());
        scope.join().forEach(s -> System.out.println(s.get()));
    }
});
System.out.println("after, bound=" + USER.isBound());
// 实测输出：
// subtask sees: alice
// subtask sees: alice
// after, bound=false
选型建议
  • 需要「贯穿整个线程寿命、且确实要被中途修改」的状态（如某些遗留库契约）→ 仍只能用 ThreadLocal，但务必在 finally 里 remove。
  • 只是「把一个上下文（用户 / 租户 / 事务 / 追踪 ID）传给一段计算及其子任务」→ 新代码优先 ScopedValue：不可变、有界、与虚拟线程和结构化并发天然契合。

L5 · 面试层：追问链

Q1: ThreadLocal 是什么？为什么声明为 final static 还能让每个线程有不同的值？

ThreadLocal 让每个访问线程拥有独立副本。值并不存在 ThreadLocal 对象上，而存在每个 Thread 内部的映射里，ThreadLocal 只是键；set/get 操作的是「当前线程的映射」。static 共享的是同一个键（定位器），每线程映射里的值各自独立，所以一个 final static 字段就能承载全应用的线程隔离值。

心智模型：每线程一张 Map，ThreadLocal 当 key——成本是 N 线程 × M 个 ThreadLocal。
Q2: ThreadLocal 在线程池里最危险的问题是什么？怎么防？

任务间值泄漏：线程被复用，上一个任务 set 的上下文（用户身份、事务）会被下一个任务意外读到，且无报错。防护：任务体用 try/finally，finally 里必须 remove()；不要依赖线程结束清理（池化线程不结束）。

ThreadLocal + 线程池：每个任务 finally remove，是不可省略的纪律。
Q3: 追问 — InheritableThreadLocal 的继承发生在什么时候？是深拷贝吗？

发生在 new Thread(...) 构造时（构造函数快照父线程的可继承映射），不是 start() 时；先构造后 set 的值子线程拿不到。且是浅拷贝、传同一引用，父子对该对象的修改互相可见，不是克隆。

构造时拷贝 + 引用共享——两个顺序/别名陷阱都源于此。
Q4: Oracle 文档说 ThreadLocal 有哪三个设计缺陷？

① 无约束可变性：任何代码可 set，难追踪谁在何时改了状态；② 无界生命周期：保留到线程结束或手动 remove，线程池中任务间泄漏；③ 昂贵继承：每生一个子线程都复制父映射，百万虚拟线程下成本被急剧放大。

三个缺陷正好对应 ScopedValue 的三个设计：不可变、有界作用域、无继承复制。
Q5: ScopedValue 是什么？它和 ThreadLocal 的关键区别？JDK 21 能用吗？

ScopedValue 用「不可变 + 有界作用域」替代 ThreadLocal：where(KEY,value).run/call 绑定，只在动态作用域内可读，出作用域即失效；配合 StructuredTaskScope 时 fork 的子任务自动共享绑定、无需复制映射。JDK 21 上是预览特性 JEP 446（需 --enable-preview --release 21），JDK 25 由 JEP 506 转正免开关。

ThreadLocal 可变/无界/靠继承复制；ScopedValue 不可变/有界/结构化共享。
Q6: 架构师 — 百万虚拟线程下为什么要重新审视 ThreadLocal？怎么定迁移策略？

平台线程时代线程只有几百，N×M 的映射内存与继承复制尚可接受；虚拟线程可达百万，每个线程的 ThreadLocalMap 与 InheritableThreadLocal 的复制成本被放大百万倍，还可能因线程寿命极短而频繁初始化。策略：① 审计现有 ThreadLocal 用途，区分「真·线程寿命可变状态」与「请求上下文传递」；② 后者在 21 预览/25 转正后逐步迁 ScopedValue；③ 结构化并发内的父子上下文一律走 ScopedValue 共享绑定；④ 迁移期保留的 ThreadLocal 仍要 finally remove，并避免在虚拟线程里用 InheritableThreadLocal 做扇出。

迁移分界线：是否「需要可变且贯穿线程寿命」——不需要就用 ScopedValue。
