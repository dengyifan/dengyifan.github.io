12.1 Switch 表达式（JEP 325 · 预览）

版本忠实写法（Java 12 预览：箭头标签 + break 值; 产值）：

// ❌ 未实测：JDK 12 预览写法（javac --enable-preview --release 12）
// JDK 13(JEP 354) 改成 yield，JDK 14(JEP 361) 转正——25 上此写法编译不过
int numLetters = switch (day) {
    case MONDAY, FRIDAY, SUNDAY -> 6;

    case WEDNESDAY              -> 9;
};
String out = switch (kind) {
    case LIGHT -> {
        String result = "L" + lumens;
        break result;                 // ← Java 12 的产值写法
    }
    case HEAVY -> {
        if (lumens > 1000) throw new IllegalArgumentException("too bright");
        break "H" + lumens;
    }
};

JDK 25 等价写法（同一特性现行形态，正式特性）：

public class SwitchYield {
  enum Day { MONDAY, TUESDAY, WEDNESDAY }
  public static void main(String[] a) {
    int n = switch (Day.TUESDAY) {
      case MONDAY    -> 6;
      case TUESDAY   -> 7;
      case WEDNESDAY -> 9;
    };
    String s = switch (n) {
      case 7 -> "seven";
      default -> { yield "other"; }   // 13 起：yield 替代 12 的 break 值
    };
    System.out.println(n + " " + s);
  }
}
// 运行输出：7 seven

✅ 实测通过（JDK 25）。⚠️ 12→13→14 的产值关键字演进：break 值;（12）→ yield 值;（13 预览）→ 正式（14）。

12.2 Collectors.teeing()

把同一份流分别喂给两个下游收集器，再用 merger 合并两个结果——内部是一个 PairBox（左、右两个容器）。

import java.util.List;
import java.util.stream.Collectors;
record Order(String item, int qty, int price) {}
public class TeeingD {
  public static void main(String[] a) {
    var orders = List.of(new Order("pen", 3, 5), new Order("book", 1, 40), new Order("bag", 2, 15));
    var stats = orders.stream().collect(Collectors.teeing(
        Collectors.summingInt(o -> o.qty() * o.price()),
        Collectors.counting(),
        (sum, cnt) -> "sum=" + sum + ", orders=" + cnt));
    System.out.println(stats);
  }
}
// 运行输出：sum=85, orders=3

✅ 实测通过（JDK 25）。并行流下 PairBox 按容器两两 combine，merger 需满足交换律。

本机实测踩到的一个初始化顺序坑（openjdk-25.0.1）

在全新 JVM 里直接调用 ClassDesc.ofDescriptor("I")（原始类型描述符）或 MethodTypeDesc.ofDescriptor(...)，本机会抛 ExceptionInInitializerError：PrimitiveClassDescImpl 与 java.lang.constant.ConstantDescs 存在循环类初始化（后者 <clinit> 中 ofConstantBootstrap 收到 null）。先执行 Class.forName("java.lang.constant.ConstantDescs") 即可规避。引用类型描述符（如 12.5 的 ClassDesc.of）不受影响。若你的 JDK 版本复现不了，以自身环境为准。

12.6 Files.mismatch()

import java.nio.file.Files;
public class MismatchD {
  public static void main(String[] a) throws Exception {
    var p1 = Files.createTempFile("t1", ".txt");
    var p2 = Files.createTempFile("t2", ".txt");
    Files.writeString(p1, "hello");
    Files.writeString(p2, "hellp");
    System.out.println("mismatch@" + Files.mismatch(p1, p2));
    Files.writeString(p2, "hello");
    System.out.println("same=" + (Files.mismatch(p1, p2) == -1));
    Files.deleteIfExists(p1);
    Files.deleteIfExists(p2);
  }
}
// 运行输出：
// mismatch@4
// same=true

✅ 实测通过（JDK 25）。static long mismatch(Path, Path) throws IOException（@since 12）：按字节级字典序比较两个文件的内容，返回值语义如下：

  • 返回首个不同字节的偏移量（从 0 起，本例 "hello" 与 "hellp" 第 5 个字节不同 → 4）；
  • 两文件内容完全相同 → 返回 -1；
  • 长度不同、且较短文件是较长文件的前缀 → 返回较短文件的大小（实测："hello" vs "hello!" → 5；"hello" vs 空文件 → 0）；
  • 任一文件不存在 → 抛 NoSuchFileException（是异常，不是返回值——实测确认，注意与「返回 -1」区分）。

实现是分块流式读取（固定缓冲区 + Arrays.mismatch 逐块比较），不会把整个文件读进内存，比「读两个 byte[] 再手写 diff」省一次全量拷贝；与其它文件系统操作之间不保证原子性，文件保持静态时满足自反性（mismatch(f, f) 恒为 -1）与对称性。

解决什么问题：JDK 12 之前标准库没有「按内容比较文件」的 API，常见替代各有硬伤——Files.readAllBytes 全量读入再比，大文件有 OOM 风险且多一次全量拷贝；引第三方 Commons IO 的 FileUtils.contentEquals，为一个小功能加依赖；拿时间戳 Files.getLastModifiedTime 凑合，mtime 相同内容也可能不同（拷贝、版本控制、云同步场景下并不可靠）。Files.mismatch 把「两个文件是否一致、第一处差异在哪」变成一次无依赖的标准库调用。

正确使用场景：

  • 等价性快速判定（早停优势）：配置文件/部署产物与预期是否一致、缓存是否失效、上传下载是否损坏。差异靠前时，读到第一个不同字节就返回，不必扫完全文件——这是它相对 SHA-256 等散列（必须读完整个文件才能出结果）的核心优势；两者在内容完全相同时都要全量读。
  • 增量同步/备份的「跳过」判断：源文件与副本是否一致，一致则跳过拷贝——时间戳判断不可靠时的内容级兜底。
  • 回归测试 / golden 文件比对：生成产物 vs 基线文件是否一致，并用返回的偏移量直接定位第一处偏差，再决定是否需要拉起行级 diff 工具深挖。
  • 大文件首错定位：日志、数据导出的完整性校验，先拿到偏移量（配合可估算出大致行/位置）再做结构化 diff。
不该用它做什么
需要多处差异的完整对比报告（行级/并排 diff）——它只回答「第一处差异在哪」，那是 diff 工具的活；比较期间文件可能被并发修改——结果不保证原子性，先固定快照（拷贝或加锁）再比；两个完全相同的大文件仍需全量读两遍，海量小文件场景可先比大小（Files.size）短路，再调 mismatch 精确比内容。

12.7 紧凑数字格式（Compact Number Formatting）

import java.text.NumberFormat;
import java.util.Locale;
public class CompactNum {
  public static void main(String[] a) {
    var en = NumberFormat.getCompactNumberInstance(Locale.ENGLISH, NumberFormat.Style.SHORT);
    var enL = NumberFormat.getCompactNumberInstance(Locale.ENGLISH, NumberFormat.Style.LONG);
    var zh = NumberFormat.getCompactNumberInstance(Locale.CHINA, NumberFormat.Style.SHORT);
    System.out.println(en.format(1234567) + " / " + enL.format(1234567));
    System.out.println(zh.format(1234567) + " / " + zh.format(100000000));
  }
}
// 运行输出：
// 1M / 1 million
// 123万 / 1亿

✅ 实测通过（JDK 25）。注意：中文 SHORT 与 LONG 输出相同（都用「万/亿」）；999000 在中文 SHORT 下进位为 100万——这是格式化取整，不是四舍五入错误。

13.3 Socket API 重构（JEP 353）

import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;
public class Sock13 {
  public static void main(String[] a) throws Exception {
    try (var server = new ServerSocket(0)) {
      int port = server.getLocalPort();
      var t = new Thread(() -> {
        try (var s = server.accept()) {
          s.getInputStream().readNBytes(5);
          s.getOutputStream().write("pong".getBytes(StandardCharsets.UTF_8));
        } catch (Exception e) { throw new RuntimeException(e); }
      });
      t.start();
      try (var c = new Socket("127.0.0.1", port)) {
        c.getOutputStream().write("ping!".getBytes(StandardCharsets.UTF_8));
        System.out.println(new String(c.getInputStream().readNBytes(4), StandardCharsets.UTF_8));
      }
      t.join();
      System.out.println("localPort=" + (port > 0));
    }
  }
}
// 运行输出：
// pong
// localPort=true

✅ 实测通过（JDK 25）。JEP 353 只是把 Socket/ServerSocket 底层实现换成 NIO 通道版（更好调试、共享同一套实现），公开 API 一个签名都没变——示例即按老 API 写，12 及以前同样能跑。

13.5 String.stripIndent() / translateEscapes()

两个方法各解决一个问题：

  • stripIndent() —— 文本块在编译期自动剥掉「为了和源码对齐而加的公共缩进」，但运行时才拿到的多行字符串（读文件/配置、字符串拼接、模板、代码生成）没有这个待遇。stripIndent() 把编译器同一套「偶然缩进剥离算法」搬到运行时。Oracle 官方定位：程序把文本当输入数据读进来、想按文本块同样的方式剥缩进时用它。
  • translateEscapes() —— 有些字符串里的 \t、\n 不是控制字符，而是反斜杠+t 两个普通字符（来自配置文件、JSON、网络或别的程序）。它按 Java 字符串字面量的规则把这些反斜杠序列还原成真实字符。
public class Str13 {
  public static void main(String[] a) {
    // 1) 拼出来的多行串带公共缩进 → 剥掉，相对缩进保留
    String sql = "    SELECT *\n" +
                 "    FROM t\n" +
                 "      WHERE id = 1";
    System.out.println("[" + sql.stripIndent().replace("\n", "|") + "]");
    // 2) 以换行结尾 → 末尾空行以 0 计入 → 不剥（见下方 warning）
    String nl = "    x\n";
    System.out.println("[" + nl.stripIndent().replace("\n", "|") + "]");
    // 3) 配置里存的字面 \t \n → 真实控制字符
    String cfg = "col1\\tcol2\\nnext";
    String real = cfg.translateEscapes();
    System.out.println("tab=" + real.contains("\t") + " nl=" + real.contains("\n"));
  }
}
// 运行输出：
// [SELECT *|FROM t|  WHERE id = 1]
// [    x|]
// tab=true nl=true

✅ 实测通过（JDK 25）。

stripIndent() 算法规则（原 CSR JDK-8223776 / javadoc）：

  1. 按行终止符切行；最后一行即使全空白也参与「最小公共缩进」计算（原文称 significant trailing line 政策，本意是让文本块闭合定界符行的缩进也算数）。
  2. 取计入行前导空白的最小值 min：每个非空行剥掉 min 个前导空白（相对缩进保留），行尾「隐藏空白」一并去掉，全空白行变空串。
  3. 行终止符归一为 LF；输入以换行结尾，输出也以换行结尾。
反直觉：以换行结尾的字符串不会被剥缩进

规则 1 的直接后果：字符串以 \n 结尾 → 末尾空行按「0 个空白」计入 → min=0 → 前导缩进完全不剥（行尾空白仍清理）。JDK 25 源码对此有显式特判（String.java stripIndent()：boolean optOut = lastChar == '\n' || lastChar == '\r' → outdent = 0；JDK 17/21 源码同款，非新行为）。实测：" a\n b\n" 原样返回，" a\n b" 才被剥离。想剥带尾换行的文本：先 s.stripTrailing().stripIndent()（已实测）。另注意：文本块的值编译期已剥过缩进，再调 stripIndent() 无效果。

translateEscapes() 的边界：

  • 支持的转义：\b \f \n \r \s \t \' \" \\、八进制 \0–\377、行继续（反斜杠+真实换行 → 丢弃）。
  • \uXXXX 直接抛 IllegalArgumentException——javadoc 明说 Unicode 转义由编译器处理、不属于字符串字面量规范；其他未知转义（如 \q）同样抛。
  • 它复刻的是「Java 字面量」转义集，与 JSON、.properties 的转义集并不相同——别拿它当通用 unescape。
与相近 API 的分工

strip() 只去整串首尾；stripIndent() 按行去公共前缀并清行尾空白。文本块字面量编译期已剥缩进；stripIndent() 服务运行时字符串。还原转义时，translateEscapes() 按字面量规则一次处理全部种类，比手写 replaceAll("\\\\n", "\n") 全面且不易错。

版本沿革：13 诞生（预览绑定），15 转正

素材把 stripIndent() / translateEscapes() / formatted() 列在 Java 13——有历史依据：三者确实随 JEP 355（Text Blocks 第二次预览）在 13 出生，当时源码标注为 @since 13 + @Deprecated(forRemoval=true, since="13")（原文注明「与预览特性 text blocks 关联」，可编译运行但带弃用警告），14 仍标注与预览绑定；15 随 JEP 378（Text Blocks 正式）解除弃用，现行 JDK 源码对三者统一标 @since 15（JDK 25 实测）。引用时区分「诞生版本（13）」与「转正版本（15）」。formatted() 示例见 15.7。

14.6 JFR 事件流（JEP 349）

import java.util.concurrent.atomic.AtomicLong;
import jdk.jfr.consumer.RecordingStream;
public class JFRStream {
  public static void main(String[] a) throws Exception {
    var count = new AtomicLong();
    try (var rs = new RecordingStream()) {
      rs.onEvent("jdk.ThreadStart", e -> count.incrementAndGet());
      rs.startAsync();
      for (int i = 0; i < 3; i++) {
        Thread t = new Thread(() -> {});
        t.start();
        t.join();

      rs.close();
    }

}

现代等价（JDK 22 起 FFM 的 Arena 版 mmap，JDK 25 可运行）：

import java.lang.foreign.Arena;
import java.lang.foreign.ValueLayout;
import java.nio.channels.FileChannel;
import java.nio.file.Files;
import java.nio.file.Path;
import java.nio.file.StandardOpenOption;
public class ArenaMap {
  public static void main(String[] a) throws Exception {
    Path p = Files.createTempFile("m", ".bin");
    Files.write(p, new byte[64]);
    try (var ch = FileChannel.open(p, StandardOpenOption.READ, StandardOpenOption.WRITE);
         var arena = Arena.ofConfined()) {
      var seg = ch.map(FileChannel.MapMode.READ_WRITE, 0, 64, arena);
      seg.set(ValueLayout.JAVA_INT, 0, 0x1234_5678);
      System.out.println(Integer.toHexString(seg.get(ValueLayout.JAVA_INT, 0)));
    }
    Files.deleteIfExists(p);
  }
}
// 运行输出：12345678

✅ 实测通过（JDK 25）。JEP 352 的 isSync 语义（映射到易失性存储设备）在 14–21 可用，JDK 22 起随 FFM 重构被移除；存取非易失内存的新写法是 Arena/Segment 一族。

15.2 Sealed Classes（预览）

含义：sealed 修饰类/接口后，只有 permits 子句列出的直接子类型才可以继承/实现它；每个被许可的子类型必须恰好声明为三态之一——final（叶子，不再往下继承）、sealed（这一支继续受限封闭）、non-sealed（显式重新开放，Java 第一个带连字符的关键字）。

解决什么问题（为什么提出）：

  • 继承默认全开放，缺一个中间态：Java 里只要一个类能被继承，就能被任何人无限继承——库作者无法声明「我的类型只有这几种」。原有手段只有两档：final（一个子类都不许，连复用都不行）或包私有（用户根本摸不到这个抽象、没法 switch，如 JDK 的 AbstractStringBuilder）。JEP 409 要的正是中间态：父类型对所有人可见（重要抽象），但只对作者指定的子类可扩展——「widely accessible but not widely extensible」。
  • 枚举封闭的是「实例个数」，sealed 封闭的是「值的种类」：枚举能穷尽 switch 是因为常量集合固定；但要建模「一组有状态、可多实例的类型种类」（图形库只有 Circle/Square、表达式树只有 Plus/Times/Const），枚举做不到，普通类层次又拦不住外来子类。
  • 为模式匹配的穷尽性检查打地基（JEP 409 三大目标之一）：if-else instanceof 链漏写一个分支，编译器毫无感知；父类型一旦封闭，编译器就知道全集——17 的 switch 模式匹配（JEP 406，21 转正）漏一个 case 直接编译报错，且可安心省略 default。
public class Sealed15 {
  public sealed interface Shape permits Circle, Square {}
  public record Circle(double r) implements Shape {}
  public record Square(double s) implements Shape {}
  public static void main(String[] a) {
    Shape sh = new Circle(2.0);
    String d = switch (sh) {
      case Circle c -> "circle " + c.r();
      case Square s2 -> "square " + s2.s();
    };
    System.out.println(d);
  }
}
// 运行输出：circle 2.0

✅ 实测通过（JDK 25）。switch 不写 default 能编译通过，正因为 permits 把子类集合钉死了——这正是模式匹配 switch 省略 default 的前提。

规则要点：

  • permits 约束：被许可子类必须与父类型同模块（父类型在命名模块时）或同包（未命名模块/classpath）；子类与父类型互相可见；必须有规范名（匿名类、局部类不行）。
  • 子类与 sealed 父类在同一源文件时可省略 permits，编译器从同文件声明自动推断。
  • non-sealed 分支虽重新开放，不破坏 sealed 顶层的穷尽性：该分支的任何子类实例也算「这一种」，穷尽检查仍成立于直接子类集合。
  • JVM 层强制执行：sealed 类的 class 文件带 PermittedSubclasses 属性，装载未授权的子类直接抛 IncompatibleClassChangeError。
与 record 组合 = 代数数据类型（ADT）

record 隐式 final，天生是「积类型」（一组字段的组合）；sealed 封闭可选种类，是「和类型」（N 选一）。两者合写就是 Haskell 风格 ADT 的 Java 表达——JEP 409 官方原话：Record classes allow us to express product types, and sealed classes allow us to express sum types。上面示例的 Shape = Circle | Square 就是最小 ADT。JEP 409 还以 java.lang.constant.ConstantDesc 层次作官方示例（见 0020 课），本机 JDK 25 源码中它确为 sealed。

版本线：15（JEP 360 首次预览）→ 16（JEP 397 第二次预览，含细化）→ 17（JEP 409 转正，与 16 版本零改动）。反射 API Class.isSealed() / getPermittedSubclasses() 随 17 正式版提供，故本例不演示反射。

15.5 Hidden Classes（JEP 371 · 正式）

import java.lang.invoke.MethodHandles;
public class HID {
  public static void main(String[] a) throws Throwable {
    byte[] bytes;
    try (var in = HID.class.getResourceAsStream("HID.class")) { bytes = in.readAllBytes(); }
    var hidden = MethodHandles.lookup().defineHiddenClass(bytes, true,
        MethodHandles.Lookup.ClassOption.NESTMATE).lookupClass();
    System.out.println(hidden.getName() + " hidden=" + hidden.isHidden());
    System.out.println(hidden.getDeclaredMethod("hi").invoke(null));
  }
  public static String hi() { return "hello from hidden"; }
}
// 运行输出（0x 后缀随运行变化）：
// HID/0x0000000130040c00 hidden=true
// hello from hidden

✅ 实测通过（JDK 25）。要点：类名形如 HID/0x…（不可从类加载器反查）、isHidden()=true、不进 metaspace 的弱引用命名空间——动态代理/框架字节码（cglib、lambda 的 inner-class 元风格）就靠它省 classloader 泄漏。

15.10 DatagramSocket API 重构（JEP 373）

import java.net.DatagramPacket;
import java.net.DatagramSocket;
import java.net.InetAddress;
public class Dgram15 {
  public static void main(String[] a) throws Exception {
    try (var ds = new DatagramSocket(0)) {
      int port = ds.getLocalPort();
      var t = new Thread(() -> {
        try {
          var buf = new byte[64];
          var pkt = new DatagramPacket(buf, buf.length);
          ds.receive(pkt);
          ds.send(new DatagramPacket(pkt.getData(), pkt.getLength(), pkt.getAddress(), pkt.getPort()));
        } catch (Exception e) { throw new RuntimeException(e); }
      });
      t.start();
      try (var c = new DatagramSocket()) {
        var data = "ping".getBytes();
        c.send(new DatagramPacket(data, data.length, InetAddress.getLoopbackAddress(), port));
        var buf = new byte[64];
        var rp = new DatagramPacket(buf, buf.length);
        c.receive(rp);
        System.out.println(new String(rp.getData(), 0, rp.getLength()));
      }
      t.join();
    }
  }
}
// 运行输出：ping

✅ 实测通过（JDK 25）。与 13.3 的 Socket 重构同思路：DatagramSocket/DatagramPacket 实现从 PlainDatagramSocketImpl 换成 NIO 通道版，API 不变、诊断信息更透明。
