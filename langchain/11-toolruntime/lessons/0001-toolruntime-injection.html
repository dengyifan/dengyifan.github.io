📖 本课回答三个问题 ⏱ 预计 30 分钟 🎯 L1+L2

本课回答三个问题：ToolRuntime 是什么？它为什么对模型"隐藏"？它是怎么被自动注入到工具里的？这是理解后续「读写记忆」的基础。

1.1 ToolRuntime 是什么

ToolRuntime 是 LangGraph 在工具执行时自动注入到工具函数里的一个运行时上下文对象。它让你在工具内部访问到 Agent 运行时的各种信息，而不需要显式地通过函数参数层层传递。

先看一个最小例子：

from langchain.tools import tool, ToolRuntime

@tool
def get_user_info(runtime: ToolRuntime) -> str:
    """look up user info"""
    user_id = runtime.state["user_id"]   # 读取状态
    return "User is John Smith" if user_id == "user_123" else "User is unknown"

注意关键点：工具函数只声明了 runtime: ToolRuntime 一个参数，但调用时你并没有手动传这个参数——是系统在背后帮你填进去的。这就是"自动注入"。

ToolRuntime 里装了什么

字段类型作用
stateStateT当前图的状态对象（含 messages 等运行数据）
contextContextT运行时上下文（由 context_schema 定义）

server_infoServerInfo | None部署服务器信息

1.2 为什么对模型"隐藏"？

这是 ToolRuntime 最核心的设计动机。工具函数签名里声明了 runtime 参数，但模型（LLM）看不到这个参数——它只看到工具真正需要模型提供的参数。

# 模型的视角：只看到 x 这个参数
@tool
def my_tool(x: int, runtime: ToolRuntime) -> str:
    """Tool that accesses runtime context."""
    ...

为什么必须隐藏？三个原因：

1. 防止模型伪造注入参数（安全）：如果 runtime 暴露给模型，恶意或错误的模型可能在 ToolCall.args 里塞一个假的 runtime 值，污染状态或越权访问。隐藏后，系统会强制剥离模型提供的注入参数，只保留系统注入的受信任值。
2. 职责分离（设计）：state、store、context 这些是框架内部状态，不该由模型控制。模型只该负责"业务参数"（比如查谁的信息），框架负责"上下文注入"。
3. 简化模型决策（效率）：模型不需要理解"当前有哪些上下文可以拿"，它只需要按工具文档（docstring）声明业务参数即可。降低了模型的认知负担和出错率。

1.3 自动注入机制（源码级）

注入机制的核心在 langgraph/prebuilt/tool_node.py（langgraph 1.2.5）。完整调用链如下：

sequenceDiagram participant Model as LLM 模型 participant TN as ToolNode._func participant R1 as _run_one participant Inj as _inject_tool_args participant Tool as 工具函数 Model->>TN: 返回 ToolCall(含 name/args/id) TN->>TN: 构造 ToolRuntime(state, context, ...) TN->>R1: 传入 tool_call + tool_runtime R1->>Inj: 注入参数 Inj->>Inj: 剥离模型提供的注入键 Inj->>Inj: 填入受信任的 runtime/state/store Inj->>Tool: 调用工具(带注入参数) Tool-->>TN: 返回结果

关键源码片段 1：构造 ToolRuntime

每次工具调用前，ToolNode._func 会为每个 tool call 构造一个独立的 ToolRuntime 实例：

# tool_node.py L806-816
tool_runtime = ToolRuntime(
    state=state,                          # 从当前图状态提取
    tool_call_id=call["id"],              # 当前调用的 ID
    config=cfg,                           # 当前执行的 RunnableConfig
    context=runtime.context,              # 继承自外层 Runtime
    store=runtime.store,                  # 继承自外层 Runtime
    stream_writer=runtime.stream_writer,  # 继承自外层 Runtime
    tools=list(self.tools_by_name.values()),
    execution_info=runtime.execution_info,
    server_info=runtime.server_info,
)

关键洞察：ToolRuntime 的 context、store、stream_writer 三个字段直接继承自外层 Runtime（图节点级别的运行时）。而 state、tool_call_id、tools 是工具特有的新字段。这正是第 4 课要讲的「ToolRuntime vs Runtime」的区别来源。

关键源码片段 2：剥离伪造参数

注入参数时，系统会先剥离模型提供的所有注入键，再填回受信任的值。这是「防伪造」的落地实现：

# tool_node.py L1421-1429
# Strip any caller-supplied values for injected args, then add
# back only trusted values. This prevents an LLM from forging
# hidden InjectedToolArg fields via ToolCall.args.
stripped_args = {
    k: v
    for k, v in tool_call_copy["args"].items()
    if k not in injected.all_injected_keys     # 剥离所有注入键
}
tool_call_copy["args"] = {**stripped_args, **injected_args}  # 填回受信任值
return tool_call_copy

这段注释直接点明了设计意图：prevents an LLM from forging hidden InjectedToolArg fields——防止 LLM 通过 ToolCall.args 伪造隐藏的注入字段。

关键源码片段 3：识别注入参数

系统怎么知道一个参数需要注入？_get_all_injected_args 在 ToolNode 初始化时扫描工具签名，识别出三类注入参数：

# tool_node.py L1997-2021（简化）
for name, type_ in all_annotations.items():
    # 1. 参数名为 "runtime" → 注入 ToolRuntime
    if name == "runtime":
        runtime_arg = name
    # 2. 标注了 InjectedState → 注入 state
    if state_inj := _get_injection_from_type(type_, InjectedState):
        state_args[name] = state_inj.field
    # 3. 标注了 InjectedStore → 注入 store
    if _get_injection_from_type(type_, InjectedStore):
        store_arg = name
    # 4. 标注了 ToolRuntime → 注入 ToolRuntime
    if _get_injection_from_type(type_, ToolRuntime):
        ...
重点：识别注入参数靠的是类型标注（type annotation），而不是参数位置或命名约定（除了 runtime 这个特殊名字）。这就是为什么你必须写 runtime: ToolRuntime 而不能只写 runtime。

1.4 从 Java 视角看

Java 视角对照

这个「自动注入」机制，Java 开发者最熟悉的对应物是 Spring 的依赖注入（DI）+ 框架的「隐藏参数」：

  • 类比 Spring DI：ToolRuntime 类似 Spring 容器自动注入的 ApplicationContext 或 HttpServletRequest。你声明了类型，框架帮你填值，不需要手动 new。
  • 关键差异：Spring 的 DI 是对象图组装期注入的（应用启动时），而 ToolRuntime 是每次工具调用时动态构造的，因为 state/context 每次调用都不同。
  • 防伪造：Java 里类似「不让调用方伪造注入参数」的机制是 final 字段 + 构造器私有化，或者 Servlet 容器的 HttpServletRequest 无法由客户端直接构造。LangGraph 用「剥离 + 填回」的方式实现同一目的。

1.5 生产环境视角

生产环境要点

并发安全：注意 _func 里用了 executor.map(self._run_one, ...) 并行执行多个 tool call，每个 tool call 有独立的 ToolRuntime 实例，所以多个工具并行读写状态时互不串扰。但如果多个工具同时写同一个 state 字段，合并顺序是不确定的——这正是第 3 课「写入记忆」要展开的陷阱。
