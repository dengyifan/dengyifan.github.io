第3课：写入记忆 — Command + update 机制

📖 前置：第2课 读取记忆 ⏱ 预计 35 分钟 🎯 L2+L3

前两课讲了 ToolRuntime 的注入和读取。本课讲最核心的操作：工具如何修改 state？这是面试中最容易出追问链的地方。

3.1 为什么不能直接修改 state？

看一个「错误示范」：

@tool
def bad_tool(runtime: ToolRuntime) -> str:
    # ❌ 错误：直接修改 runtime.state 不会生效
    runtime.state["user_name"] = "John"
    return "done"

为什么不行？三个原因：

1. state 是不可变快照：ToolRuntime 构造时（第 1 课的 ToolNode._func），state 是从当前图状态拷贝出来的快照，修改它不会影响图的实际状态。
2. 并发安全：多个工具可能并行执行（executor.map），如果都直接修改同一个 state 对象，会导致竞态条件。
3. 溯源：Graph 框架通过检查每个节点/Tool 的返回值来确定状态变更，而不是通过副作用检测。这保证了状态变更的可追溯性。

3.2 正确的写入方式：Command + update

from langgraph.types import Command
from langchain.messages import ToolMessage

class CustomState(AgentState):
    user_name: str

@tool
def update_user_info(runtime: ToolRuntime[CustomContext, CustomState]) -> Command:
    """look up and update user info."""
    user_id = runtime.context.user_id
    user_name = "John Smith" if user_id == "user_123" else "Unknown"

    return Command(update={
        "user_name": user_name,      # 更新自定义状态字段
        "messages": [                # 必须附带 ToolMessage
            ToolMessage(
                "Successfully looked up user information",
                tool_call_id=runtime.tool_call_id
            )
        ]
    })

关键点：

  • 返回 Command 对象，而不是直接返回字符串
  • update 字典里指定要修改的 state 字段
  • 必须附带 ToolMessage——这是 LangGraph 的硬约束：每次工具调用必须有对应的 ToolMessage 作为执行记录
  • tool_call_id 必须与当前工具调用匹配，否则系统无法关联

3.3 写入的完整流程

关键源码：_normalize_tool_response

# tool_node.py L1432-1453
def _normalize_tool_response(self, response, tool_call, input_type):
    if isinstance(response, Command):
        return self._validate_tool_command(response, tool_call, input_type)
    if isinstance(response, ToolMessage):
        response.content = msg_content_output(response.content)
        return response
    if isinstance(response, list):
        if all(isinstance(r, (Command, ToolMessage)) for r in response):
            return self._validate_tool_command_list(response, tool_call, input_type)
    raise TypeError(...)

这个函数是工具返回值的「安检门」。合法的返回值只有三种：Command、ToolMessage、或它们的列表。任何其他类型直接抛异常。

3.4 写入后立即读取：工具间协作的核心

同一个 agent 中，前一个工具写入的状态，后一个工具可以立即读取：

@tool
def update_user_info(runtime: ToolRuntime[CustomContext, CustomState]) -> Command:
    user_name = "John Smith" if runtime.context.user_id == "user_123" else "Unknown"
    return Command(update={
        "user_name": user_name,
        "messages": [ToolMessage("Successfully looked up", tool_call_id=runtime.tool_call_id)]
    })

@tool
def greet(runtime: ToolRuntime[CustomContext, CustomState]) -> str:
    user_name = runtime.state["user_name"]   # 读取 update_user_info 写入的字段
    return f"Hello, {user_name}"

这正是「工具间通过 state 通信」的完整演示。注意：greet 工具不需要返回 Command——它只是读取 state，不修改它。

3.5 三种返回值对比

返回值类型用途何时用示例
str只返回文本给模型纯查询工具，不修改状态return "The weather is sunny"
ToolMessage结构化消息，通常含 tool_call_id需要精确控制消息格式ToolMessage("done", tool_call_id=...)
Command(update={...})修改 state + 返回消息需要写入状态字段Command(update={"user_name": "John", "messages": [...]})
常见陷阱：如果工具返回 Command 但 update 里忘了加 messages，系统会报错。因为 ToolMessage 是 LangGraph 追踪工具执行的必要记录，缺少它会导致消息链断裂。

3.6 并行执行的写入冲突

生产环境要点

当模型一次返回多个 ToolCall 时，ToolNode 会用 executor.map 并行执行它们。如果两个工具同时修改同一个 state 字段，谁先谁后是不确定的。

解决方式：

  1. 避免冲突：让每个工具只写自己负责的字段，不交叉。
  2. 使用 reducer：在 state 定义时声明字段的合并策略（如 operator.add 用于 list 追加），由框架自动合并。
  3. 顺序执行：如果确实有依赖，通过图结构设计让工具串行执行，而不是让模型一次性返回所有 ToolCall。

3.7 从 Java 视角看

Java 视角对照

Command.update ↔ 类似 Spring 的 ModelAndView：既返回数据（ToolMessage），又指定状态变更（update）。但关键区别是：Spring 的 ModelAndView 是表示层概念，修改的只是当前请求的 Model；而 LangGraph 的 Command.update 是图状态变更，会被持久化到 Checkpointer，影响后续所有节点。

不可变快照 ↔ 类似 Java 的 Collections.unmodifiableMap()：给你一个只读视图，但 LangGraph 更进一步——它直接拷贝一份，完全隔离。

ToolMessage 必须附带 ↔ 类似数据库事务的 WAL：每次工具调用必须留下记录（ToolMessage），就像数据库的 Write-Ahead Log 保证可恢复性。
