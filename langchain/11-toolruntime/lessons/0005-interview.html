面试题库：ToolRuntime 深度掌握

📖 前置：第4课 ⏱ 预计 40 分钟 🎯 L5

以下题目对齐 deep-grill 的五个考察角度，每题带完整参考答案。学完前 4 课后，用这些题目去 deep-grill 检验掌握度。

面试官角度

Q1: LangGraph 中 ToolRuntime 是什么？它和普通函数参数有什么区别？

参考答案：

ToolRuntime 是 LangGraph 在工具执行时自动注入的运行时上下文对象。区别在于：

  • 普通参数由模型在 ToolCall.args 中提供（如 "x": 5），对模型可见
  • ToolRuntime 对模型隐藏——参数签名中声明了，但模型看不到它，系统在工具执行时自动注入
  • 它承载了 state（图状态）、context（运行时上下文）、config（执行配置）、tool_call_id（调用 ID）、store（持久化存储）等框架内部信息
关键得分点：自动注入 + 对模型隐藏 + 承载框架内部状态
Q2: 为什么 ToolRuntime 要对模型隐藏？如果暴露给模型会有什么问题？

参考答案：

三个原因：

  1. 安全：防止模型通过 ToolCall.args 伪造注入参数。如果 runtime 暴露给模型，恶意模型可以篡改 state、伪造 tool_call_id。源码中 _inject_tool_args 的 stripped_args 逻辑专门剥离模型提供的注入键，然后再填回受信任值。
  2. 职责分离：state、store、context 是框架内部状态，模型只该负责业务参数。这符合「关注点分离」原则。
  3. 简化模型决策：模型不需要理解「当前有哪些上下文可拿」，降低认知负担和出错率。
关键得分点：安全（防伪造）+ 职责分离 + 简化模型决策，能引用源码 stripped_args 逻辑加分
Q3: 追问 — 你能说出 ToolRuntime 里有哪几个字段？哪些是从 Runtime 继承的，哪些是工具特有的？

参考答案：

继承自 Runtime 的：context、store、stream_writer、execution_info、server_info

工具特有的：state、tool_call_id、config、tools

记忆口诀：state（当前状态）、tool_call_id（调用 ID）、config（执行配置）、tools（可用工具列表）——这四个是工具专属的。

关键得分点：能区分继承和特有，能说出四个特有字段的名称和作用

架构师角度

Q1: 在设计一个多 Agent 系统时，state 和 context 分别该放什么信息？为什么？

参考答案：

  • state 放「对话内变化的信息」：对话历史、工具执行结果、中间状态（如"已查到的用户信息"）、跨轮次共享的上下文。
  • context 放「对话外不变的配置」：用户身份、租户 ID、API 密钥、权限级别。

核心原因：state 需要持久化（多轮对话恢复），context 不需要。如果 context 混入 state 并被持久化，修改一个用户 ID 需要清理所有历史 checkpoint，这是灾难性的。同时 context 可能含敏感信息（API key），不应出现在持久化的 state 中，增加泄露风险。

关键得分点：区分「对话内动态」vs「对话外静态」+ 持久化策略差异 + 安全性考量
Q2: 如果两个工具并行执行，同时修改同一个 state 字段，会发生什么？你怎么解决？

参考答案：

当模型一次返回多个 ToolCall 时，ToolNode 用 executor.map 并行执行，写入顺序不确定。三种解决方式：

  1. 字段隔离：每个工具只写自己负责的字段，不交叉（最简单）
  2. 使用 reducer：在 state 定义时声明合并策略，如 Annotated[list, operator.add] 用于追加，由框架自动合并
  3. 串行执行：通过图结构设计让工具按序执行，而非让模型一次性返回所有 ToolCall
关键得分点：能说出三种方案 + 知道 executor.map 是并行执行 + 能给出具体场景的推荐方案

代码审查者角度

Q1: 以下代码有什么问题？
@tool
def update_user_info(runtime: ToolRuntime) -> str:
    runtime.state["user_name"] = "John"
    return "done"

参考答案：

三个问题：

  1. 无法生效：runtime.state 是不可变快照，直接修改它不会影响图的实际状态。
  2. 缺少 ToolMessage：正确写法应返回 Command(update={"user_name": "John", "messages": [ToolMessage("done", tool_call_id=runtime.tool_call_id)]})。ToolMessage 是 LangGraph 追踪工具执行的必要记录。
  3. 并发不安全：如果多个工具并行执行且都尝试直接修改 state，会导致竞态条件。
关键得分点：不可变快照 + 缺少 ToolMessage + 并发安全
Q2: 以下代码有什么问题？
@tool
def my_tool(x: int, runtime: str) -> str:
    context = runtime  # 类型标注错误
    return f"done {x}"

参考答案：

类型标注错误：runtime 参数应该标注为 runtime: ToolRuntime，而不是 runtime: str。系统在 _get_all_injected_args 中通过类型标注来识别注入参数——如果类型不是 ToolRuntime，系统不会注入，runtime 会被当作普通参数暴露给模型。结果就是模型需要在 ToolCall 中提供一个 runtime 字符串值，而不是框架自动注入。

关键得分点：类型标注决定注入行为 + 错误的类型标注会导致注入失效

故障排查者角度

Q1: 生产环境 Agent 报错 KeyError: 'user_id'，发生在 runtime.state["user_id"] 处。怎么排查？

参考答案：

排查步骤：

  1. 确认 state_schema 定义：检查 create_agent 中是否通过 state_schema 定义了 user_id 字段。如果 CustomState(AgentState) 里没有 user_id，这里必然报 KeyError。
  2. 确认 invoke 时传入：检查 agent.invoke({"messages": ..., "user_id": "user_123"}) 中是否传入了 user_id。如果没传，state 里就没有这个字段。
  3. 检查是否被其他工具覆盖：如果前面有工具返回了 Command(update={"user_id": ...}) 但覆盖错误，也可能导致字段丢失。
  4. 检查 Checkpointer 脏数据：如果使用了 Checkpointer 且 thread_id 复用，之前对话的 state 可能不含 user_id。清理旧 checkpoint 或用新 thread_id。
关键得分点：按"定义 → 传入 → 覆盖 → 持久化"的顺序排查，不是胡乱猜测
Q2: 工具正常返回了 Command，但后续工具读不到写入的 state 字段。可能的原因？

参考答案：

  1. update 的 key 拼写错误：Command(update={"user_name": ...}) 中 key 拼写与 state 定义不一致
  2. Graph 未正确处理 Command：检查 _normalize_tool_response 是否被绕过（极少发生，但自定义 ToolNode 时可能）
  3. 后续工具在同一个 ToolNode 批次中执行：如果模型一次返回了多个 ToolCall（并行执行），后续工具拿到的 state 是批次开始时的快照，看不到同批次其他工具的写入。这是设计行为，不是 bug——需要用 reducer 或串行执行解决。
关键得分点：能识别"同批次并行执行"是 root cause，而不是以为是 bug

技术讲师角度

Q1: 请用大白话向一个新人解释 ToolRuntime 是什么。

参考答案：

想象你是一个餐厅的服务员（工具），客人（模型）点了菜（ToolCall），厨房（框架）在你开始做菜之前，偷偷塞给你一张小纸条（ToolRuntime），上面写着：

  • 这桌客人之前点过什么（state）——帮你了解上下文
  • 这桌客人的会员卡号（context）——帮你确认身份
  • 这道菜的订单编号（tool_call_id）——帮你追踪

客人看不到这张纸条（对模型隐藏），但你可以用纸条上的信息来更好地服务。

关键得分点：服务员/小纸条的类比 + 强调「客人看不到」这个核心特征
