Interviewer Angle (Concept + Principle + Deep Dive)

Q1: What is middleware in LangChain, and why does it exist?

Q1: What is middleware in LangChain, and why does it exist?

Middleware is a configurable interception layer that hooks into the agent execution loop at specific points (before/after model calls, around tool calls, at agent start/end). It exists to solve four problems that are inherent to production agent systems:

  1. Reliability: retries, fallbacks, error recovery — you can't have an agent in production that crashes on the first transient API error.
  2. Safety: PII detection, human approval, guardrails — agents need guardrails that run inside the execution loop, not just at the edges.
  3. Cost control: model call limits, tool call limits, summarization — agents can loop forever, and you need a way to bound them.
  4. Observability: logging, tracing, custom events — you need to see what the agent is doing at each step.

Without middleware, you'd have to bake all of this logic into the agent's core loop directly, which couples it to your specific business logic and makes it unmaintainable.

Key point: Middleware is not a separate runtime — it compiles directly into the agent's LangGraph graph as nodes and edges. This means every middleware hook runs with full access to AgentState and Runtime.

Q2: What's the difference between node-style hooks and wrap-style hooks?

Q2: What's the difference between node-style hooks and wrap-style hooks? When would you use each?

Node-style hooks (before_agent, before_model, after_model, after_agent) run sequentially at fixed points in the graph. They receive (state, runtime) and return a dict of state updates (or None). They are observers — they see the state but don't control whether the core operation happens.

Wrap-style hooks (wrap_model_call, wrap_tool_call) receive a handler callback and decide whether to call it and how many times. They are interceptors — they control the execution flow.

Use node-style for: logging, validation, state inspection, emitting events. Use wrap-style for: retries, fallbacks, short-circuiting, caching, request/response transformation.

Key point: If you need to call the handler 0, 1, or N times, you MUST use wrap-style. Node-style hooks cannot control execution flow — they can only observe and optionally redirect via jump_to.

Q3: Explain the execution order when you have three middleware in the list.

Q3: With middleware=[m1, m2, m3], describe the execution order of all hooks.

before_* hooks: m1 → m2 → m3 (list order).

wrap_* hooks: m1 wraps m2 wraps m3 wraps handler. So m1 is the outermost layer — it sees the final result after all inner middleware have processed.

after_* hooks: m3 → m2 → m1 (reverse order).

This follows the standard middleware pattern (Express.js, Django, etc.): before runs forward, after runs backward like a stack unwinding. The outermost middleware (first in the list) has the most power — it can short-circuit the entire chain.

Key point: The "outer wins" rule for state updates: when multiple middleware return ExtendedModelResponse with the same key, the outermost (first in the list) value wins. Messages are an exception — they're additive via the add_messages reducer.

Q4: What is jump_to and why does it need can_jump_to?

Q4: What is jump_to and why does it need can_jump_to?

jump_to is a state key in AgentState that redirects the agent to a different graph node: 'tools', 'model', or 'end'. It's how middleware terminates the agent early (model call limits), blocks content (guardrails), or forces a tool call.

can_jump_to must be declared on the hook because the compiled LangGraph needs conditional edges built at compile time. Without can_jump_to=["end"], the graph has no edge from the hook's node to the end node, so the jump_to value is silently ignored — no error, no warning.

jump_to is also EphemeralValue — it resets after each superstep. You must set it each time you want a jump; it doesn't persist.

Key point: The compile-time declaration + runtime trigger split is unique to LangGraph's design. It's a trade-off: the graph topology is fixed at compile time for safety, but the routing decision is dynamic at runtime.

Q5: Write the pseudocode for the agent loop routing function.

Q5: Write the pseudocode for the agent loop routing function. What does it check?
def should_continue(state: AgentState) -> str:
    # 1. Check if middleware requested a jump
    if state.get("jump_to") == "end":
        return "end"
    if state.get("jump_to") == "tools":
        return "tools"
    if state.get("jump_to") == "model":
        return "model"

    # 2. Default: check if the last message has tool calls
    last_message = state["messages"][-1]
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "tools"
    else:
        return "end"

The routing function checks exactly two things: (1) jump_to (middleware override), (2) messages[-1].tool_calls (normal loop logic). There is no next_node field and no explicit state machine — the routing is purely data-driven from the last message.

Key point: The loop iteration is per model response, not per tool call. If the model returns 3 tool_calls in one response, all 3 run in parallel, then a new model call happens.

Architect Angle (System Design + Trade-offs)

Q6: Why is ModelRequest immutable? What's the trade-off?

Q6: Why is ModelRequest immutable? What's the alternative design and its trade-off?

ModelRequest is immutable because middleware compose by nesting. If middleware A modifies the request object in place, middleware B (which runs after A) sees A's modifications. This creates a hidden coupling: B's behavior depends on A's side effects, and the order of middleware becomes critical in ways that are hard to debug.

With immutability (via request.override()), each middleware creates a new request with its changes. The original request is unchanged. When B runs, it sees the request as A left it, but if A's override had a bug, it doesn't corrupt the original request for other purposes.

Trade-off: Immutability means every modification allocates a new object. For large message histories, this is a shallow copy via dataclasses.replace() — the message list itself is not deep-copied, so the overhead is O(1) per field change, not O(n) for the message list. The real cost is mental: developers must switch from "mutate in place" to "create and pass forward" thinking.

Key point: Direct attribute assignment on ModelRequest emits a DeprecationWarning — the framework is actively pushing everyone toward immutability.

Q7: Compare the two middleware creation approaches: decorator-based vs class-based.

Q7: You can create middleware with @before_model decorators or by subclassing AgentMiddleware. When do you choose which?

Decorator-based: Quick, single-hook. The decorator uses Python's type() to dynamically create an AgentMiddleware subclass at runtime. The function name becomes the class name. Ideal for quick prototyping, simple logging, or one-off hooks.

Class-based: Powerful, multi-hook, configurable. You subclass AgentMiddleware directly and implement multiple hook methods. You can add __init__ parameters, share state between hooks, and declare state_schema, tools, and transformers as class attributes.

Choose decorator for: single hook, no configuration, throwaway middleware. Choose class for: multiple hooks, shared state, complex configuration, reuse across projects, both sync and async implementations.

Key point: Decorators don't give you less power — they just build a class for you. The type() call creates a real AgentMiddleware subclass. But for anything beyond a single hook, the class approach is more readable and maintainable.

Q8: How would you design a middleware that needs to share state across multiple hooks?

Q8: Design a middleware that tracks the number of model calls and terminates the agent after 10 calls. How does it share state between before_model and after_model?

Use a custom state schema with a class-based middleware:

from langchain.agents.middleware import AgentState, AgentMiddleware
from typing_extensions import NotRequired

class CounterState(AgentState):
    model_call_count: NotRequired[int]

class CallLimitMiddleware(AgentMiddleware[CounterState]):
    state_schema = CounterState

    def before_model(self, state, runtime):
        if state.get("model_call_count", 0) >= 10:
            return {"jump_to": "end"}  # terminate early
        return None

    def after_model(self, state, runtime):
        return {"model_call_count": state.get("model_call_count", 0) + 1}

agent = create_agent(
    model="gpt-5.5",
    middleware=[CallLimitMiddleware()],
    tools=[],
)

The before_model hook reads the count and decides to terminate. The after_model hook increments it. The state is persisted in AgentState and flows through the graph's reducers — so before_model always sees the latest count from after_model of the previous iteration.

Key point: This is exactly how ModelCallLimitMiddleware works internally. The state schema replaces instance variables — middleware instances are stateless; all persistent data lives in the graph state.

Code Reviewer Angle (Bug Detection + Best Practices)

Q9: Find the bug in this middleware code.

Q9: The following middleware is supposed to prevent the agent from responding to blocked content. What's wrong?
@after_model
def block_content(state, runtime):
    last_msg = state["messages"][-1]
    if "BLOCKED" in last_msg.content:
        return {
            "messages": [AIMessage("I cannot respond.")],
            "jump_to": "end"
        }
    return None

Bug: can_jump_to is not declared. The jump_to value will be silently ignored — the agent will continue executing as if nothing happened. The fix:

@after_model(can_jump_to=["end"])  # ← add this
def block_content(state, runtime):
    last_msg = state["messages"][-1]
    if "BLOCKED" in last_msg.content:
        return {
            "messages": [AIMessage("I cannot respond.")],
            "jump_to": "end"
        }
    return None

Additional bug: The code appends an AIMessage via jump_to with can_jump_to=["end"]. But the messages key uses add_messages reducer, so the new AIMessage will be appended to the existing messages, not replace them. The original blocked message is still in the history. This might be intentional (for audit trail) or a bug (the blocked content leaks).

Key point: Silent failure of jump_to is the #1 custom middleware bug. There's no compiler warning, no lint, no runtime error — it just doesn't work. Always declare can_jump_to when you use jump_to.

Q10: Find the bug — exception handling.

Q10: This middleware catches all exceptions from tool calls. What's the subtle bug?
@wrap_tool_call
def safe_tool_handler(request, handler):
    try:
        return handler(request)
    except Exception as e:
        return ToolMessage(
            content=f"Tool failed: {e}",
            tool_call_id=request.tool_call["id"],
            status="error",
        )

Bug: This catches GraphBubbleUp — LangGraph's control-flow signal for interrupts and parent Commands. If you're using HumanInTheLoopMiddleware, the interrupt signal will be swallowed by this handler, and the agent will not pause for human approval. The fix:

from langgraph.errors import GraphBubbleUp

@wrap_tool_call
def safe_tool_handler(request, handler):
    try:
        return handler(request)
    except GraphBubbleUp:       # ← always propagate control-flow
        raise
    except Exception as e:
        return ToolMessage(
            content=f"Tool failed: {type(e).__name__}",
            tool_call_id=request.tool_call["id"],
            status="error",
        )

Additional improvement: Use type(e).__name__ instead of {e} in the error message. The raw exception message may contain sensitive internal details (API keys, file paths, stack traces).

Key point: Any except Exception in a wrap-style hook must explicitly re-raise GraphBubbleUp. This is a hard requirement documented in ToolErrorMiddleware's source code.

Incident Responder Angle (Troubleshooting + Debugging)

Q11: Your agent is silently ignoring jump_to. What's your troubleshooting path?

Q11: You've written custom middleware that returns {"jump_to": "end"}, but the agent continues executing. Walk through your troubleshooting steps.
  1. Check can_jump_to: Is the hook decorated with can_jump_to=["end"] (or @hook_config(can_jump_to=["end"]))? Without it, the graph has no edge to "end" from this hook's node.
  2. Check the return value: Is the jump_to value spelled correctly? It must be 'end', 'tools', or 'model' — case-sensitive, no typos.
  3. Check if the hook is actually running: Add a print() or logging statement to verify the hook is being called. If the hook isn't running, the middleware isn't being passed to create_agent correctly.
  4. Check EphemeralValue semantics: jump_to resets after each superstep. If your hook returns jump_to but the routing logic runs before the hook's state update is applied, the jump might be consumed by the previous superstep's routing.
  5. Check middleware order: If another middleware after yours returns None (no state update), does it overwrite your jump_to? Node-style hooks return dicts — the last hook's return value wins for non-reducer fields.
Key point: Step 1 catches 90% of cases. The can_jump_to requirement is the most common root cause of silent jump failures.

Q12: Your agent works fine with ainvoke() but crashes with invoke().

Q12: Your custom middleware uses async def awrap_model_call and works with agent.ainvoke(). When you call agent.invoke(), it raises NotImplementedError. Why?

The base AgentMiddleware.wrap_model_call method raises NotImplementedError by default. When you only define awrap_model_call (async), the sync path has no implementation — it falls through to the base class's NotImplementedError.

Fix: Either (1) define both wrap_model_call (sync) and awrap_model_call (async), or (2) always use the async invocation path (ainvoke, astream).

The reverse is also true: if you only define wrap_model_call (sync) and call ainvoke, the async base method raises NotImplementedError.

Key point: The error message from the base class is actually helpful — it tells you exactly what's wrong: "You defined only the async version and invoked synchronously."

Instructor Angle (Feynman Explanation + Teaching)

Q13: Explain middleware to a junior developer using an analogy.

Q13: Explain LangChain middleware to a junior developer who's never heard of the concept. Use an analogy, not technical terms.

Airport security analogy:

Imagine an agent is a passenger trying to fly from A to B. The agent loop is the flight path: board → fly → land. Middleware is like the security checkpoints along the way:

  • Check-in (before_agent): Verify the passenger has a ticket. If not, turn them away.
  • Security screening (before_model): Check the passenger's bags. If something dangerous is found, block the flight.
  • Gate agent (after_model): After the passenger passes through, log that they boarded.
  • Re-routing (wrap_model_call): If the flight is cancelled, the gate agent can rebook the passenger on a different flight (fallback) or try the same flight again (retry).
  • Customs (after_agent): After arrival, check the passenger's final state.

The key insight: the passenger (agent) doesn't know about the checkpoints. They just move through the process. The checkpoints (middleware) observe and control the flow without the passenger needing to be aware of them.

Key point: A good analogy emphasizes that middleware is transparent to the agent — the agent doesn't know it's being intercepted, and the middleware doesn't change the agent's core behavior, only the environment around it.

Q14: What's the single most important thing to understand about middleware?

Q14: If you could only teach one thing about LangChain middleware, what would it be?

Middleware hooks are compiled into LangGraph nodes and edges — they are not a separate runtime.

Every other concept flows from this: execution order mirrors the graph topology, jump_to needs can_jump_to because the graph needs edges built at compile time, state updates use graph reducers, and the entire agent (middleware included) can be dropped into a larger graph as a subgraph.

If you understand that middleware is graph-native, you understand why it's not just a "plugin system" — it's a structural part of the agent's execution graph.

Key point: Many people think of middleware as "interceptors that run before/after the agent." The reality is more fundamental: middleware is the agent's graph structure. The hooks are the nodes; the hooks' edges are the graph's edges.
