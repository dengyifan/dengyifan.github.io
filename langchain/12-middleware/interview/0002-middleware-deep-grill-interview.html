🎯 一、面试官角度 概念定义 + 原理追问 · Q1-Q7
Q1
什么是 LangChain Middleware？它解决了什么问题？
用户回答 middleware 是中间件；存在的原因是用于在 agent 调用前后、模型调用前后、工具调用前后以增加自定义逻辑来完善业务流程和增加 langchain 的可扩展性。例如在调用模型前需要对用户输入的内容进行特殊处理，模型输出时对于其中涉及敏感信息增加脱敏，工具调用失败在问题排查时增加日志。agent 前、后，模型调用前后、工具调用前后触发运行。
参考答案

Middleware 是可配置的拦截层，在 Agent 执行流程的特定点位（模型调用前后、工具调用前后、Agent 开始/结束）插入自定义逻辑。它解决四大生产问题：

  1. 可靠性（Reliability）：重试、降级、错误恢复 — ModelRetryMiddleware、ToolRetryMiddleware、ModelFallbackMiddleware
  2. 安全性（Safety）：PII 检测、人工审批、护栏 — PIIMiddleware、HumanInTheLoopMiddleware
  3. 成本控制（Cost Control）：模型/工具调用限制、自动摘要 — ModelCallLimitMiddleware、ToolCallLimitMiddleware、SummarizationMiddleware
  4. 可观测性（Observability）：日志、追踪、自定义事件 — runtime.stream_writer + trace_policy

无中间件时，这些逻辑只能硬编码进 Agent 核心循环，与业务逻辑耦合、不可维护。中间件即 Agent 版 AOP（切面编程），把横切关注点从核心逻辑剥离。

核心 insight：中间件是 graph-native 的——hook 被编译成 LangGraph 的节点和边，不是独立的运行时层。每个 hook 都能访问 AgentState 与 Runtime。
Q2
追问工具层面有哪些 hook？有 before_tool_call 和 after_tool_call 吗？
用户回答 不存在，对应的是 wrap_tool_call，属于包裹式。
参考答案

没有 before_tool_call / after_tool_call 这类 node-style hook。工具层面只有一个 wrap-style hook：wrap_tool_call（异步为 awrap_tool_call）。

风格Hook数量
Node-style（观察者）before_agent、before_model、after_model、after_agent4 个
Wrap-style（拦截器）wrap_model_call、wrap_tool_call2 个
易错点：很多人误以为工具调用也有 before/after hook，但源码 types.py 中只有 6 个 hook 方法签名。
Q3
Node-style 和 Wrap-style hook 的本质区别是什么？
用户回答（首次，不准确） 「最根本的区别是 node-style 只关注某一侧，要么调用前面，要么调用后；而 wrap-style 是调用前调用后都能处理。例如工具有时会调用超时，需要用 wrap_tool_call 增加重试逻辑。」

追问：缓存命中场景 handler 调用次数？ 「对应 1。」

用户回答（重考后，正确） 「wrap-style 里有 handler，可以决定 handler 是否调用、调用几次；而 node-style 里没有。」
参考答案

Node-style = 观察者（Observer）：签名 (state, runtime)，只能看状态、改状态，不能控制核心操作是否发生、发生几次。

Wrap-style = 拦截器（Interceptor）：签名 (request, handler)，多了一个 handler 回调。可以决定调用 handler 0 次、1 次、N 次。

判断标准：你是否需要控制 handler 被调用几次？

易错点：缓存命中场景对应"0 次或 1 次"，不是单纯 1 次。缓存命中时不调用模型（handler 调 0 次），这才是必须用 wrap-style 的原因。
Q4
middleware=[m1, m2, m3] 时，所有 hook 的执行顺序是什么？
用户回答 before 按列表出现顺序执行；洋葱模型；after 按出现顺序逆序执行，原因是调用栈天然是 LIFO。m1 { m2 { m3 }}，m1 是最外层；最外层可以决定后面的中间件是否能被触发。
参考答案

最外层（m1）的三大特权：

  1. 短路：可在调用 handler 前决定不触发内层，m2/m3 完全不执行
  2. 看到最终结果：m1 的 handler(request) 返回整个内层链处理完的结果
  3. outer wins：多个中间件返回同一非 reducer 字段时，最外层值胜出
顺序很关键：日志中间件必须放重试中间件外面，才能记录到每次重试。
Q5
jump_to 是什么？为什么必须配合 can_jump_to？
用户回答 jump_to 合法目标值有：end 跳转到结束节点、tools 跳转到工具调用、model 跳转到模型调用。必须配合 can_jump_to 的原因是编译时根据 can_jump_to 来生成相应节点的边。忘记声明 can_jump_to 时不会抛异常，是静默的，在编译时也不会生成相应的边。
参考答案

jump_to 是 AgentState 中的一个 key，可以重定向 agent 到：'tools'（工具节点）、'model'（模型节点）、'end'（结束）。

can_jump_to 必须在编译时声明，因为 LangGraph 需要在编译时建好条件边。没有声明 → 图里无边 → jump_to 静默失效。

jump_to 是 EphemeralValue（临时值），每次 superstep 结束后自动重置为 None。

#1 自定义中间件 bug：静默失效是最高频的自定义中间件问题——无编译器警告、无 lint、无运行时错误，只是不生效。
Q6
写出 Agent Loop 路由函数 should_continue 的伪代码
用户回答 从 state 获取 jump_to 值：若 a==end 返回 "end"；若 a==tools 返回 "tools"；若 a==model 返回 "model"。然后获取最近一条消息，判断是否有 tool_calls 属性，有且不为空则返回 "tools" 触发工具调用，否则跳转结束节点。误以为有 next_node 是因为自然想到执行完一步后通过 next_node 明确下一步节点。
参考答案
def should_continue(state: AgentState) -> str:
    if state.get("jump_to") == "end":
        return "end"
    if state.get("jump_to") == "tools":
        return "tools"
    if state.get("jump_to") == "model":
        return "model"

    last_message = state["messages"][-1]
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "tools"
    else:
        return "end"

路由只检查两个条件：(1) jump_to（中间件覆盖），(2) messages[-1].tool_calls（正常循环）。没有显式状态机、没有 next_node 字段。

循环迭代粒度：是"每次模型响应"而非"每个工具调用"。模型一次返回 3 个 tool_calls 会并行执行。
Q7
为什么 ModelRequest 是不可变的？override() 性能开销是多少？
用户回答（首次，不准确） 如果模型一次返回了多个 tool 它们是并发调用的，为此对于 ModelRequest 需要是不可变的，防止并发误写；override() 对于属性很多时是会存在很大的开销，根据属性的多少。赋值之后不会起作用，因为它是不可变的。

用户回答（重考后，正确） 中间件是可以组合的，特别是嵌套 m1{m2{m3}}，如果 ModelRequest 是可变的，那么嵌套到内部变更后，外层之前获取的 ModelRequest 就不一致。开销是 O(1)。在 python 语言的角度可以进行设值，但会有一个 warning 日志输出提示。
参考答案

不可变性的首要原因不是并发安全，而是中间件组合（nesting）的可预测性。如果可变，内层 m3 修改 request 会污染 m2 和 m1 看到的请求，造成隐藏耦合。

性能开销：O(1)。底层用 dataclasses.replace()（源码第 267 行），只做浅拷贝——messages 列表共享引用不被深拷贝。

直接赋值会怎样？ModelRequest 没用 frozen=True，所以赋值会生效。但 __setattr__ 会先发出 DeprecationWarning，然后照样执行。这是"约定优于配置"，不是语言层面强制不可变。

易错点：很多人把原因说成"并发安全"、把性能开销说成 O(n)，都错了。并发安全只是附带收益。
🏗️ 二、架构师角度 系统设计 + 选型对比 · Q8-Q9
Q8
Decorator-based vs Class-based 创建方式：底层怎么工作？
用户回答（首次） 不知道。

用户回答（重考后） 底层将装饰器所对应的方法动态地创建一个类。如果需要多个场景处理如 before_model + after_model，例如想限制调用模型次数，node-style 只能处理单场景。装饰器方式一个函数对应一个 hook，不能支持多场景，另外没有构造参数，只能获取全局和闭包内部的参数。
参考答案

装饰器方式真的创建了一个类。@before_model 装饰器调用 type() 动态创建 AgentMiddleware 子类并立即实例化。装饰器不是魔法，只是帮你写了一个类。

必须用类方式的场景：多个 hook 协同、需要 __init__ 构造参数、多 hook 共享状态、同时实现 sync+async。

选择原则：装饰器 → 单 hook、无配置、一次性使用；类 → 多 hook、共享状态、复杂配置、跨项目复用。
Q9
设计一个中间件：计算模型调用次数，超过 10 次时终止 Agent。
用户回答（首次，有四个错误） State 未继承 AgentState；return 返回的是 str 而非 dict；after_model 原地修改了 state；用两个装饰器当多 hook 协同。

用户回答（重考后，正确） 
class CallLimitState(AgentState):
    call_model_count: NotRequired[int]

class CallLimitMiddleware(AgentMiddleware[CallLimitState]):
    state_schema = CallLimitState

    @hook_config(can_jump_to=["end"])
    def before_model(self, state, runtime):
        if state.get("call_model_count", 0) >= 10:
            return {"jump_to": "end"}
        return None

    def after_model(self, state, runtime):
        return {"call_model_count": state.get("call_model_count", 0) + 1}
「在自定义的 State 里通过 call_model_count 来更新的，在流转时会将最新的 state 传递到下一次的 before_model 中；中间件实例自身不会存储这个 count。」
参考答案

状态传递：中间件实例无状态，所有持久数据在 Graph State 中。after_model 返回 dict → 框架 merge 入 AgentState → 下一次 before_model 看到最新值。

常见错误：State 未继承 AgentState、返回值类型错误（返回 str 而非 dict）、原地修改 state（state["xxx"] += 1）、两个装饰器当多 hook 协同用。
🔍 三、代码审查者角度 Bug 检测 + 最佳实践 · Q10-Q12
Q10
以下中间件想阻止 agent 回复敏感内容，找 bug：
用户回答 函数签名没有返回类型的定义；jump_to 应该在上面通过装饰器指定，并且缺少 can_jump_to。
参考答案
@after_model
def block_content(state, runtime):
    last_msg = state["messages"][-1]
    if "BLOCKED" in last_msg.content:
        return {"messages": [AIMessage("I cannot respond.")], "jump_to": "end"}
    return None

Bug 1：缺少 can_jump_to 声明。必须 @after_model(can_jump_to=["end"])。

Bug 2：messages 是追加而非替换。add_messages reducer 是追加语义，原敏感消息仍在历史中，用户会看到两条消息。

修复：添加 can_jump_to=["end"]，并意识到 messages 的追加语义。
Q11
以下中间件想安全捕获工具异常，找 bug：
用户回答 不能直接全量捕获 Exception，而应该先捕获 GraphBubbleUp。
参考答案
@wrap_tool_call
def safe_tool_handler(request, handler):
    try:
        return handler(request)
    except Exception as e:
        return ToolMessage(content=f"Tool failed: {e}",
                           tool_call_id=request.tool_call["id"], status="error")

Bug 1：吞掉 GraphBubbleUp。except Exception 会吞掉 LangGraph 的控制流信号。

Bug 2：错误信息泄露敏感数据。{e} 直接拼接原始异常消息，应改用 type(e).__name__。

from langgraph.errors import GraphBubbleUp

@wrap_tool_call
def safe_tool_handler(request, handler):
    try:
        return handler(request)
    except GraphBubbleUp:       # 先放行控制流信号
        raise
    except Exception as e:
        return ToolMessage(
            content=f"Tool failed: {type(e).__name__}",
            tool_call_id=request.tool_call["id"],
            status="error",
        )
硬性要求：任何 wrap-style hook 中的 except Exception 必须显式 re-raise GraphBubbleUp。
Q12
追问messages 用 add_messages reducer，替换 vs 追加？
追问：jump_to 生效了但消息是追加不是替换，用户会看到什么？ 「用户会看到敏感的内容。」
参考答案
字段类型规则
非 reducer 字段outer wins — 最外层覆盖内层
messages（add_messages reducer）追加 — 所有层都保留
安全影响：返回 {"messages": [AIMessage("blocked")]} 想替换敏感内容，但 add_messages 是追加语义，敏感消息仍在历史中。
🚨 四、故障排查者角度 排查 + 调试 · Q13-Q14
Q13
只有 async awrap_model_call，ainvoke() 正常，invoke() 报 NotImplementedError？
用户回答 agent.invoke 默认调用 sync 同步方法，因为前面只实现了 async 异步的，没有 sync 实现，所以报 NotImplementedError；增加同步的实现方式。
参考答案

基类 AgentMiddleware.wrap_model_call 默认抛 NotImplementedError。当只定义了 awrap_model_call（async）时，sync 路径无实现。

三种修复：(1) 同时实现 sync+async；(2) 始终用异步路径；(3) 始终用同步路径。

诊断技巧：基类错误消息非常友好，会明确告诉你"你只定义了 async 版本却同步调用了"。
Q14
返回 {"jump_to": "end"} 但 agent 继续执行。完整排障路径？
用户回答（首次，不完整） 检查代码涉及 jump_to 的地方有无配置 can_jump_to 属性。

用户回答（重考后，仍不完整） 检查代码针对于有返回 jump_to 的地方是否有 can_jump_to 的属性配置；在对应的中间件里补充日志；检查 jump_to 的取值是否为 end, model, tools 三个中的一个。
参考答案

5 步排障路径，按优先级：

  1. can_jump_to 是否声明（90% 案例）
  2. jump_to 值拼写是否正确（静态检查，零成本）
  3. hook 是否真的在运行（加 print/日志）
  4. EphemeralValue 语义（jump_to 每次 superstep 后重置为 None）
  5. 中间件顺序（后面 hook 可能覆盖你的 jump_to）
排障思维：先零成本静态检查（can_jump_to、拼写），再加日志验证运行时，最后考虑运行时语义陷阱（EphemeralValue、顺序覆盖）。
📖 五、技术讲师角度 费曼讲解 + 本质洞察 · Q15
Q15
用生活类比向新手解释中间件；如果只能教一个道理，教什么？
用户回答 坐火车时的安检。安检对应 before_agent；查票有点像 before_model；晚点改签 after_model；出站 after_agent。

最核心 insight 追问 「如果不改变执行流程就用 node-style；如果需要改变执行流程就用 wrap-style。」
参考答案

火车出行类比：

生活场景对应 hook类型
进站安检before_agent观察者
上车查票before_model观察者
晚点改签/换乘wrap_model_call拦截器
乘务员巡查after_model观察者
到站出站after_agent观察者

最核心 insight：中间件是 graph-native 的。Hook 被编译成 LangGraph 的节点和边，不是独立的运行时层。所有其他概念都是这个本质的推论。

易错点：很多人把"改签"归到 after_model（观察者），但改签本质是控制执行，只有 wrap-style 拦截器能做到。很多人误以为中间件是"在 agent 外部运行的插件系统"。
