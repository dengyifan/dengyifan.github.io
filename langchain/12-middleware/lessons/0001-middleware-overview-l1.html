What Is Middleware?

Middleware is a configurable interception layer that lets you control and customize agent execution at every step. Think of it as an "aspect-oriented" layer for the agent loop — you can inject logic before/after model calls, around tool calls, or at the start/end of the entire agent run.

The official docs list four broad use cases:

  1. Tracking — logging, analytics, debugging
  2. Transforming — prompts, tool selection, output formatting
  3. Resilience — retries, fallbacks, early termination
  4. Safety — rate limits, guardrails, PII detection

You add middleware when calling create_agent:

from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware, HumanInTheLoopMiddleware

agent = create_agent(
    model="gpt-5.5",
    tools=[...],
    middleware=[
        SummarizationMiddleware(...),
        HumanInTheLoopMiddleware(...)
    ],
)
From a Java perspective

Middleware is conceptually similar to Servlet Filters or Spring Interceptors — they sit in front of the core processing and can modify the request, the response, or short-circuit entirely. The key difference is that LangChain middleware is stateful (it has access to the full agent AgentState) and can jump between nodes in the compiled graph, not just pass/fail the request.

The Agent Loop

To understand where middleware hooks fire, you must first understand the agent loop — the core cycle that every agent built with create_agent follows:

graph TD A[Start] --> B[Call Model] B --> C{Has tool_calls?} C -->|Yes| D[Execute Tools] D --> B C -->|No| E[End] style A fill:#e8f5e9,stroke:#42c02e style E fill:#fdf2f2,stroke:#e74c3c style B fill:#f0f7fd,stroke:#3194d0 style D fill:#fef0f0,stroke:#ea6f5a

This loop is simple but fundamental:

  1. Call Model — send the current messages (history + system prompt) to the LLM.
  2. Check tool_calls — did the model request any tool calls?
  3. If yes: Execute Tools one by one, collect the results, feed them back to step 1.
  4. If no: End — the agent is done.
Production reality

The loop is bounded by the model's single response — if the model returns 3 tool_calls in one response, all 3 are executed in parallel (within a single LangGraph superstep). The loop does NOT iterate one tool at a time internally; it only iterates across model calls. This is a common deep-grill trap — people think "loop" means "one tool per iteration" but it's actually "one model response per iteration."

Where Hooks Run in the Loop

Middleware exposes hooks before and after each step of the loop:

sequenceDiagram participant User participant Agent as Agent (Graph) participant MW as Middleware participant Model as LLM participant Tools User->>Agent: invoke(messages) Agent->>MW: before_agent() 🔵 once loop Agent Loop Agent->>MW: before_model() 🔵 Agent->>MW: wrap_model_call() 🟠 around Agent->>Model: call() Model-->>Agent: response Agent->>MW: wrap_model_call() returns Agent->>MW: after_model() 🔵 alt has tool_calls Agent->>MW: wrap_tool_call() 🟠 around each Agent->>Tools: execute() Tools-->>Agent: result Agent->>MW: wrap_tool_call() returns end end Agent->>MW: after_agent() 🔵 once Agent-->>User: result

The two styles are:

StyleHooksWhen they runBehavior
Node-style 🔵 before_agent, before_model, after_model, after_agent At specific points in the graph Run sequentially; return state updates or None
Wrap-style 🟠 wrap_model_call, wrap_tool_call Around each model/tool call Receive a handler callback; can call it 0, 1, or N times
Key insight

Node-style hooks are observers — they see the state before/after each step. Wrap-style hooks are interceptors — they control whether the step happens at all, and can modify the request/response.

Node-Style Hooks

Node-style hooks run at fixed points in the execution graph. They receive (state, runtime) and return a dict of state updates (or None for no change).

before_agent — once per invocation

Fires once at the very start of agent execution. Use it for initialization, logging, or injecting setup messages.

from langchain.agents.middleware import before_agent, AgentState
from langgraph.runtime import Runtime

@before_agent
def init_session(state: AgentState, runtime: Runtime) -> dict | None:
    print(f"Agent starting with {len(state['messages'])} messages")
    return None  # no state change

before_model — before each LLM call

Fires before every model call in the loop. This is the most commonly used node-style hook. Use it to check message limits, inject context, or decide to exit early.

from langchain.agents.middleware import before_model, AgentState
from langchain.messages import AIMessage

@before_model(can_jump_to=["end"])
def check_message_limit(state: AgentState, runtime) -> dict | None:
    if len(state["messages"]) >= 50:
        return {
            "messages": [AIMessage("Conversation limit reached.")],
            "jump_to": "end"
        }
    return None
Critical detail

To use jump_to in a node-style hook, you MUST declare can_jump_to=["end"] (or ["tools"] / ["model"]). Without this declaration, the compiled graph won't have the conditional edges needed to redirect execution. The jump will be silently ignored.

after_model — after each LLM response

Fires after every model response. Use it to inspect the output, validate content, or log the response.

from langchain.agents.middleware import after_model, AgentState

@after_model
def log_response(state: AgentState, runtime) -> dict | None:
    last_msg = state["messages"][-1]
    print(f"Model returned: {last_msg.content[:100]}...")
    return None

after_agent — once per invocation

Fires once when the agent loop ends. Use it for cleanup, final logging, or emitting completion events.

Wrap-Style Hooks

Wrap-style hooks are fundamentally different: they receive a handler callback and decide if and how many times to call it.

# Signature pattern
def wrap_model_call(
    request: ModelRequest,
    handler: Callable[[ModelRequest], ModelResponse],
) -> ModelResponse:
    # You control: call handler()? once? many times?
    return handler(request)  # normal flow
    # OR: skip handler() entirely (short-circuit)
    # OR: call handler() multiple times (retry logic)

wrap_model_call — around each model call

The most powerful hook. Use it for retries, fallbacks, dynamic prompt/model/tool selection, caching, and response rewriting.

from langchain.agents.middleware import wrap_model_call, ModelRequest, ModelResponse

@wrap_model_call
def retry_model(request, handler):
    for attempt in range(3):
        try:
            return handler(request)
        except Exception as e:
            if attempt == 2:
                raise
            print(f"Retry {attempt + 1}/3 after error: {e}")

wrap_tool_call — around each tool call

Same pattern but for tools. Use it for tool-level retries, monitoring, result caching, or argument rewriting.

from langchain.agents.middleware import wrap_tool_call

@wrap_tool_call
def monitor_tool(request, handler):
    print(f"Executing tool: {request.tool_call['name']}")
    result = handler(request)
    print("Tool completed successfully")
    return result
From a Java perspective

Wrap-style hooks are very similar to Spring AOP's @Around advice or JAX-RS ContainerRequestFilter. The handler callback is equivalent to ProceedingJoinPoint.proceed() — you can call it zero, one, or many times, and you can modify the arguments before calling it or the result after.

Middleware Inside a LangGraph Workflow

Middleware is not a separate runtime. When you call create_agent, the middleware hooks are compiled into the resulting LangGraph StateGraph as nodes and edges. This means you can drop the entire agent (middleware and all) into a larger graph as a subgraph:

from langchain.agents import create_agent, AgentState
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.graph import START, StateGraph

email_agent = create_agent(
    model="claude-sonnet-4-6",
    tools=[read_email, send_email],
    middleware=[HumanInTheLoopMiddleware(interrupt_on={"send_email": True})],
)

graph = (
    StateGraph(AgentState)
    .add_node("classify", classify_node)
    .add_node("email_agent", email_agent)  # agent as a subgraph
    .add_edge(START, "classify")
    .add_conditional_edges("classify", route)
    .compile()
)

Every middleware hook (HITL interrupts, summarization, PII, retries, custom hooks) travels with the agent node. This is a key design decision: middleware is not a global interceptor; it's scoped to the agent it's attached to.

Basic Usage Pattern

The simplest complete example with custom middleware:

from langchain.agents import create_agent
from langchain.agents.middleware import before_model, after_model, AgentState

@before_model
def log_before(state: AgentState, runtime) -> None:
    print(f"About to call model with {len(state['messages'])} messages")

@after_model
def log_after(state: AgentState, runtime) -> None:
    print(f"Model returned: {state['messages'][-1].content}")

agent = create_agent(
    model="gpt-5.5",
    middleware=[log_before, log_after],
    tools=[...],
)

# The middleware runs automatically on every agent invocation
result = agent.invoke({"messages": [{"role": "user", "content": "Hello"}]})
Mind the list order

The order of middleware in the list matters. before_* hooks run in list order (first to last). after_* hooks run in reverse (last to first). wrap_* hooks nest with the first middleware as the outermost layer. We'll explore this in detail in the L2 Principles lesson.

The Role of the Checkpointer

Some middleware (HumanInTheLoopMiddleware, ModelCallLimitMiddleware with thread_limit, ToolCallLimitMiddleware with thread_limit) require a checkpointer to persist state across invocations:

from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model="gpt-5.5",
    checkpointer=InMemorySaver(),  # required for HITL and thread limits
    middleware=[HumanInTheLoopMiddleware(...)],
)

Without a checkpointer, interrupt-based middleware cannot resume after a pause, and thread-level counters cannot persist across calls with the same thread_id.
