Execution Order: The Critical Rule

When you pass multiple middleware to create_agent, they execute in a specific, predictable order that is fundamental to understanding middleware behavior:

agent = create_agent(
    model="gpt-5.5",
    middleware=[middleware1, middleware2, middleware3],
    tools=[...],
)
sequenceDiagram participant A as Agent Start participant M1 as middleware1 participant M2 as middleware2 participant M3 as middleware3 participant M as Model participant T as Tools Note over A,T: === BEFORE hooks run in order === A->>M1: before_agent() A->>M2: before_agent() A->>M3: before_agent() Note over A,T: === Agent Loop === A->>M1: before_model() A->>M2: before_model() A->>M3: before_model() Note over A,T: === WRAP hooks nest (first = outermost) === M1->>M2: wrap_model_call() M2->>M3: wrap_model_call() M3->>M: call model M-->>M3: response M3-->>M2: M2-->>M1: Note over A,T: === AFTER hooks run in REVERSE === M3->>A: after_model() M2->>A: after_model() M1->>A: after_model() Note over A,T: === Tool calls (if any) === M3->>A: wrap_tool_call() (nested) M2->>A: wrap_tool_call() (nested) M1->>A: wrap_tool_call() (outermost) Note over A,T: === Agent ends === M3->>A: after_agent() M2->>A: after_agent() M1->>A: after_agent()

The three rules are:

RuleDirectionRationale
before_* hooks First → Last Earliest middleware gets to prepare state first
after_* hooks Last → First (reverse) Like a call stack unwinding — the last to be called returns first
wrap_* hooks Nested: first middleware is outermost Like function composition: m1(m2(m3(handler)))
Why reverse for after-hooks?

This follows the same pattern as middleware in Express.js, Django, and virtually every middleware framework. The "after" is the unwinding of the "before" — like a stack. If you think of middleware as wrappers around a core operation, the outermost wrapper (first in list) naturally wraps the entire chain, so its "after" runs last.

Why This Design? (Design Principle Analysis)

Q1: Why two hook styles instead of just one?

The two styles serve fundamentally different purposes:

NeedBest styleWhy
Logging / monitoringNode-styleJust observe; no need to control execution
Retry logicWrap-styleMust call handler multiple times
Short-circuit (skip model)Wrap-styleMust decide whether to call handler at all
State validationNode-styleRuns after the model; can jump if invalid
Request/response transformationWrap-styleMust modify request before calling handler

A single hook style would force either unnecessary complexity (node-style trying to express retry) or lack of clarity (wrap-style for simple logging).

Q2: What's the trade-off of the nesting model?

Cost: The outermost middleware (first in list) has the most power — it can short-circuit the entire chain. This means order matters and you must think carefully about which middleware goes first. A middleware that logs must come before one that retries, or the retry won't be logged.

Benefit: The nesting model creates a clear "chain of responsibility" where each middleware only sees the request/response after all inner middleware have processed it. This is exactly what you want for patterns like retry-around-fallback: the outer middleware retries the entire inner chain, including the fallback logic.

Q3: If you were to redesign this, what would you change?

The current design has two pain points:

  1. Silent failure of jump_to without can_jump_to — a compile-time check would be safer.
  2. No explicit priority system — order is purely positional. A middleware that "must run last" has no way to enforce that; it just documents the requirement.

Pseudocode: How the Agent Loop Routes

This is the routing logic that the compiled LangGraph uses to decide whether to continue the loop:

def should_continue(state: AgentState) -> str:
    """Route after each model call: continue or end?"""
    last_message = state["messages"][-1]

    # Check if middleware requested a jump
    if state.get("jump_to") == "end":
        return "end"
    if state.get("jump_to") == "tools":
        return "tools"
    if state.get("jump_to") == "model":
        return "model"

    # Default: check if model has tool calls
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "tools"
    else:
        return "end"
Common deep-grill trap

The loop does NOT check for a dedicated "next_node" field. It checks messages[-1].tool_calls and jump_to. Many people wrongly assume AgentState has a next_node field like some graph frameworks do — it doesn't. The routing is purely data-driven from the last message.

Agent Jumps: Redirecting Execution

The jump_to mechanism lets middleware redirect the agent to a different node in the graph. It's how ModelCallLimitMiddleware terminates the agent, how guardrails block execution, and how custom middleware exits early.

Available jump targets

TargetMeaningUse case
'end'Jump to end of agent (or first after_agent hook)Terminate early, block content
'tools'Jump to the tools nodeForce tool execution
'model'Jump to the model node (or first before_model hook)Force another model call

How can_jump_to works

When you declare can_jump_to=["end"] on a hook, the agent factory adds a conditional edge from that hook's node to the specified target. Without this declaration, the graph has no edge for the jump, and the jump_to value is silently ignored.

# Decorator-based: pass can_jump_to as parameter
@before_model(can_jump_to=["end"])
def my_guard(state, runtime):
    if should_block(state):
        return {"jump_to": "end", "messages": [AIMessage("Blocked")]}
    return None

# Class-based: use @hook_config decorator
class GuardMiddleware(AgentMiddleware):
    @hook_config(can_jump_to=["end"])
    def before_model(self, state, runtime):
        if should_block(state):
            return {"jump_to": "end", "messages": [AIMessage("Blocked")]}
        return None
From a Java perspective

jump_to is analogous to Spring WebFlux's WebFilter chain short-circuiting or Apache Camel's ControlBus pattern. The key difference is that LangChain's jump is declared at graph build time (via can_jump_to) and triggered at runtime (via jump_to return value). This compile-time declaration + runtime trigger split is unique to LangGraph's design.

State Updates: How Middleware Modifies State

Both hook styles can update agent state, but the mechanism differs:

Node-style: Return a dict

Node-style hooks return a dict[str, Any] that is merged into the agent state using the graph's reducers. The most important reducer is add_messages, which appends messages rather than replacing them.

@after_model
def count_calls(state, runtime):
    return {"model_call_count": state.get("model_call_count", 0) + 1}
    # Simple dict merge: overwrites 'model_call_count'

Wrap-style: Return ExtendedModelResponse with Command

For wrap_model_call, return ExtendedModelResponse with a Command to inject state updates alongside the model response:

from langchain.agents.middleware import (
    wrap_model_call, ModelRequest, ModelResponse, ExtendedModelResponse
)
from langgraph.types import Command

@wrap_model_call
def track_usage(request, handler):
    response = handler(request)
    return ExtendedModelResponse(
        model_response=response,
        command=Command(update={"last_model_call_tokens": 150}),
    )
Production: Composition with multiple middleware

When multiple middleware layers return ExtendedModelResponse:

  • Messages are additive (via add_messages reducer) — they append, not replace.
  • Non-reducer fields use outer wins — the outermost middleware's value takes precedence on conflicting keys.
  • Retry-safe: If the outer middleware calls handler() multiple times (retry), commands from earlier calls are discarded.

Custom State Schema

Middleware can extend the agent's state with custom properties by declaring a state_schema:

from langchain.agents.middleware import AgentState, AgentMiddleware
from typing_extensions import NotRequired

class CustomState(AgentState):
    model_call_count: NotRequired[int]
    user_id: NotRequired[str]

class CallCounterMiddleware(AgentMiddleware[CustomState]):
    state_schema = CustomState

    def before_model(self, state, runtime):
        if state.get("model_call_count", 0) > 10:
            return {"jump_to": "end"}
        return None

    def after_model(self, state, runtime):
        return {"model_call_count": state.get("model_call_count", 0) + 1}

# Invoke with custom state
agent = create_agent(
    model="gpt-5.5",
    middleware=[CallCounterMiddleware()],
    tools=[],
)

result = agent.invoke({
    "messages": [HumanMessage("Hello")],
    "model_call_count": 0,
    "user_id": "user-123",
})

This is how built-in middleware like ModelCallLimitMiddleware tracks its internal counters — it declares a custom state field that the middleware reads/writes across hooks.

Summary: The Five Principles

  1. Middleware is graph-native — hooks are compiled into LangGraph nodes/edges, not a separate runtime.
  2. Node-style = observer, Wrap-style = interceptor — choose based on whether you need to control execution.
  3. Order matters — before-hooks run first→last, after-hooks run reverse, wrap-hooks nest.
  4. jump_to requires can_jump_to — the graph must have edges built at compile time.
  5. State updates use reducers — messages are additive, non-reducer fields use outer-wins.
