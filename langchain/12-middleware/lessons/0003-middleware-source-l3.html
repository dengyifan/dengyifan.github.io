Core Call Chain: How Hooks Become Graph Nodes

When create_agent is called, the middleware list is compiled into a LangGraph StateGraph. The decorator functions (@before_model, @wrap_model_call, etc.) use Python's type() to dynamically create AgentMiddleware subclasses at runtime:

AgentState — The Default State Schema

Source: langchain/agents/middleware/types.py, lines 347-352

class AgentState(TypedDict, Generic[ResponseT]):
    """State schema for the agent."""

    messages: Required[Annotated[list[AnyMessage], add_messages]]
    jump_to: NotRequired[Annotated[JumpTo | None, EphemeralValue, PrivateStateAttr]]
    structured_response: NotRequired[Annotated[ResponseT, OmitFromInput]]

Analysis:

  • messages uses the add_messages reducer — updates append, not replace. This is the most important annotation in the entire middleware system.
  • jump_to is EphemeralValue — it resets after each superstep. You cannot set it once and have it persist; you must set it each time you want a jump.
  • jump_to is also PrivateStateAttr — it's hidden from input/output schemas. Users never see it; it's purely internal routing.
  • structured_response is OmitFromInput — the user can't provide it; only the agent can set it.
Why EphemeralValue for jump_to?

If jump_to persisted, a single "jump to end" would permanently route all subsequent invocations to the end. The reset ensures that each invocation starts fresh. The middleware must explicitly set jump_to each time it wants to redirect.

ModelRequest — Immutable Request Pattern

Source: langchain/agents/middleware/types.py, lines 85-267

The ModelRequest is a @dataclass(init=False) — the __init__ is custom-written, not auto-generated. This allows it to handle the deprecated system_prompt parameter gracefully:

@dataclass(init=False)
class ModelRequest(Generic[ContextT]):
    model: BaseChatModel
    messages: list[AnyMessage]  # excluding system message
    system_message: SystemMessage | None
    tool_choice: Any | None
    tools: list[BaseTool | dict[str, Any]]
    response_format: ResponseFormat[Any] | None
    state: AgentState[Any]
    runtime: Runtime[ContextT]
    model_settings: dict[str, Any] = field(default_factory=dict)

Key design: override() method (lines 201-267):

def override(self, **overrides: Unpack[_ModelRequestOverrides]) -> ModelRequest[ContextT]:
    """Replace the request with a new request with the given overrides.

    Returns a new `ModelRequest` instance with the specified attributes replaced.
    This follows an immutable pattern, leaving the original request unchanged.
    """
    if "system_prompt" in overrides and "system_message" in overrides:
        msg = "Cannot specify both system_prompt and system_message"
        raise ValueError(msg)

    if "system_prompt" in overrides:
        system_prompt = cast("str | None", overrides.pop("system_prompt"))
        if system_prompt is None:
            overrides["system_message"] = None
        else:
            overrides["system_message"] = SystemMessage(content=system_prompt)

    return replace(self, **overrides)

Analysis:

  • ModelRequest is immutable — you never modify it in place. Instead, call .override() to get a new instance. This is critical for middleware composition: one middleware's modifications don't leak into another's.
  • Direct attribute assignment is deprecated (lines 167-199) — __setattr__ emits a DeprecationWarning. This is a strong signal: "never mutate, always create."
  • Backward compatibility with system_prompt (string) is handled by converting it to SystemMessage internally.
  • Uses dataclasses.replace() — a shallow copy with field overrides. Efficient because it doesn't deep-copy the message list.
From a Java perspective

This is conceptually identical to Java 17 Records or Lombok's @With annotation — the object is immutable, and you create a new instance with specific fields changed. The difference is Python uses dataclasses.replace() instead of a withX() method.

ModelRetryMiddleware — Retry with Exponential Backoff

Source: langchain/agents/middleware/model_retry.py, lines 31-312

The wrap_model_call implementation

def wrap_model_call(
    self,
    request: ModelRequest[ContextT],
    handler: Callable[[ModelRequest[ContextT]], ModelResponse[ResponseT]],
) -> ModelResponse[ResponseT] | AIMessage:
    # Initial attempt + retries
    for attempt in range(self.max_retries + 1):          # Line 232
        try:
            return handler(request)                       # Line 234
        except Exception as exc:
            attempts_made = attempt + 1                   # Line 236

            # Check if we should retry this exception
            if not should_retry_exception(exc, self.retry_on):  # Line 239
                # Exception is not retryable, handle failure immediately
                return self._handle_failure(exc, attempts_made) # Line 241

            # Check if we have more retries left
            if attempt < self.max_retries:                # Line 244
                # Calculate and apply backoff delay
                delay = calculate_delay(
                    attempt,
                    backoff_factor=self.backoff_factor,
                    initial_delay=self.initial_delay,
                    max_delay=self.max_delay,
                    jitter=self.jitter,
                )                                         # Lines 246-251
                if delay > 0:
                    time.sleep(delay)                     # Line 254
                # Continue to next retry
            else:
                # No more retries, handle failure
                return self._handle_failure(exc, attempts_made) # Line 258

Analysis:

  • Line 232: The loop runs max_retries + 1 times (initial attempt + retries). With default max_retries=2, that's 3 total attempts.
  • Line 239: should_retry_exception checks if the exception is retryable before checking if retries remain. If the exception is not retryable, it fails immediately — even if retries are available.
  • Line 244-254: Only sleeps if retries remain. The delay calculation uses calculate_delay from the shared _retry.py module.
  • Early-return pattern: The loop follows the "fail fast" style — each branch returns immediately. No deep nesting of if/else.

Failure handling

def _handle_failure(self, exc: Exception, attempts_made: int) -> ModelResponse[ResponseT]:
    if self.on_failure == "error":           # Line 203
        raise exc                            # Re-raise, stopping agent

    if callable(self.on_failure):            # Line 206
        content = self.on_failure(exc)       # Custom message from callable
        ai_msg = AIMessage(content=content)
    else:
        ai_msg = self._format_failure_message(exc, attempts_made)  # Line 210

    return ModelResponse(result=[ai_msg])    # Line 212

Analysis:

  • Three failure modes: re-raise ("error"), custom message (callable), default message ("continue").
  • When on_failure="continue", the agent receives an AIMessage with the error — it can decide to retry differently or give up. This is the "graceful degradation" path.
  • The default message format reveals the exception type name but NOT the full traceback. This is deliberate — you don't want to leak internal details to the model.

Shared Retry Utilities: calculate_delay

Source: langchain/agents/middleware/_retry.py, lines 87-125

def calculate_delay(
    retry_number: int,
    *,
    backoff_factor: float,
    initial_delay: float,
    max_delay: float,
    jitter: bool,
) -> float:
    if backoff_factor == 0.0:                          # Line 111
        delay = initial_delay                          # Constant delay
    else:
        delay = initial_delay * (backoff_factor ** retry_number)  # Line 114

    # Cap at max_delay
    delay = min(delay, max_delay)                      # Line 117

    if jitter and delay > 0:                           # Line 119
        jitter_amount = delay * 0.25                   # ±25% jitter
        delay += random.uniform(-jitter_amount, jitter_amount)  # Line 121
        # Ensure delay is not negative after jitter
        delay = max(0, delay)                          # Line 123

    return delay

Analysis:

  • Line 111: backoff_factor=0.0 gives constant delay. This is the "retry with fixed wait" mode.
  • Line 114: Standard exponential backoff: delay = initial_delay * (backoff_factor ^ retry_number). With defaults (1.0 * 2.0^0 = 1s, 1.0 * 2.0^1 = 2s, 1.0 * 2.0^2 = 4s).
  • Line 117: Capped at max_delay=60.0 — prevents unbounded growth for high retry counts.
  • Line 121: ±25% jitter — critical for production. Without jitter, many clients retrying simultaneously create a "thundering herd" problem. The jitter spreads retries across a 50% window.
  • Line 123: Safety clamp — jitter cannot make delay negative (though with 25% of a positive value, this is a defensive check).

ToolErrorMiddleware — Exception-to-ToolMessage Conversion

Source: langchain/agents/middleware/tool_error.py, lines 30-200

The wrap_tool_call implementation

def wrap_tool_call(
    self,
    request: ToolCallRequest,
    handler: Callable[[ToolCallRequest], ToolMessage | Command[Any]],
) -> ToolMessage | Command[Any]:
    tool_name = request.tool.name if request.tool else request.tool_call["name"]  # Line 138

    if not self._should_handle_tool(tool_name):          # Line 140
        return handler(request)                          # Pass through for excluded tools

    try:
        return handler(request)                          # Line 144
    except GraphBubbleUp:                                # Line 145
        # Control-flow signals (interrupts, parent commands) must propagate.
        raise
    except Exception as exc:                             # Line 148
        if self.on_error is None:                        # Line 149
            msg = ("ToolErrorMiddleware has no sync `on_error`; run async "
                   "(ainvoke/astream) or provide `on_error`.")
            raise RuntimeError(msg) from exc             # Line 155
        content = self.on_error(exc, request)            # Line 156
        if content is None:                              # Line 157
            raise                                        # Propagate: handler chose not to handle
        return ToolMessage(
            content=cast("str | list[str | dict[Any, Any]]", content),
            tool_call_id=request.tool_call["id"],        # Line 161
            name=tool_name,
            status="error",                              # Line 163
        )

Analysis:

  • Line 145: GraphBubbleUp is a special exception that carries LangGraph control-flow signals (interrupts, parent Commands). It must propagate — catching it would break the graph's control flow.
  • Line 140: The _should_handle_tool filter lets you scope error handling to specific tools. Tools not in the filter pass through unchanged.
  • Line 157: Opt-in handling. If on_error returns None, the exception propagates. This means you only handle the exceptions you want to handle — unhandled exceptions crash the agent as normal.
  • Line 161: The tool_call_id must match the original tool call. This is how the model associates the error message with the right tool call — without it, the model can't correct its mistake.
  • Line 163: status="error" is the signal that tells the model this ToolMessage represents an error, not a normal result.
Production: ToolError + ToolRetry composition

The docs emphasize: "Place retry inner (earlier in the list) with on_failure="error" so exceptions reach ToolErrorMiddleware after retries are exhausted."

middleware=[
    ToolRetryMiddleware(max_retries=3, on_failure="error"),  # inner: retries first
    ToolErrorMiddleware(on_error=on_error),                    # outer: converts errors
]

The retry middleware runs first (inner), and when it exhausts retries, it re-raises (on_failure="error"). The exception then reaches ToolErrorMiddleware, which converts it to a ToolMessage the model can see.

ModelFallbackMiddleware — Sequential Fallback

Source: langchain/agents/middleware/model_fallback.py, lines 278-408

def wrap_model_call(
    self,
    request: ModelRequest[ContextT],
    handler: Callable[[ModelRequest[ContextT]], ModelResponse[ResponseT]],
) -> ModelResponse[ResponseT] | AIMessage:
    # Try primary model first
    last_exception: Exception
    try:
        return handler(request)                          # Line 346
    except Exception as e:
        last_exception = e                               # Line 348

    # Try fallback models
    for fallback_model in self.models:                   # Line 354
        fallback_request = (
            request
            if _supports_anthropic_cache_control(fallback_model)
            else _sanitize_request_for_fallback(request) # Line 358
        )
        try:
            return handler(fallback_request.override(model=fallback_model))  # Line 361
        except Exception as e:
            last_exception = e                           # Line 363
            continue

    raise last_exception                                 # Line 366

Analysis:

  • Lines 355-358: The cache control sanitization is a subtle but important detail. When an outer middleware (like AnthropicPromptCachingMiddleware) adds cache_control markers to the request, those markers are Anthropic-specific. If the fallback model is non-Anthropic (e.g., OpenAI), the markers would cause an API error. The middleware detects this via _llm_type and strips them.
  • Line 361: Uses request.override(model=fallback_model) — the immutable pattern again. The original request is unchanged; only the model field changes.
  • Line 366: If all fallbacks fail, re-raises the last exception. This means you see the failure from the last model tried, not the first.

How Decorators Create Middleware Classes at Runtime

Source: langchain/agents/middleware/types.py, lines 1026-1100

The @before_model decorator doesn't just wrap a function — it creates a new AgentMiddleware subclass at runtime using type():

# From @before_model decorator (simplified)
def decorator(func):
    is_async = iscoroutinefunction(func)

    if is_async:
        async def async_wrapped(_self, state, runtime):
            return await func(state, runtime)

        return type(
            middleware_name,          # e.g., "log_before_model"
            (AgentMiddleware,),       # parent class
            {
                "state_schema": AgentState,
                "tools": [],
                "abefore_model": async_wrapped,  # async hook
            },
        )()                           # instantiate!
    else:
        def wrapped(_self, state, runtime):
            return func(state, runtime)

        return type(
            middleware_name,
            (AgentMiddleware,),
            {
                "state_schema": AgentState,
                "tools": [],
                "before_model": wrapped,  # sync hook
            },
        )()

Analysis:

  • This is Python metaprogramming — creating classes at runtime with type(). The decorator function's name becomes the class name.
  • The sync/async detection (iscoroutinefunction) determines which hook method to set. If the function is async, abefore_model is set; if sync, before_model.
  • The instantiation happens immediately — type()(...) calls the constructor. The returned object is an AgentMiddleware instance, ready to pass to create_agent.
  • can_jump_to is stored as __can_jump_to__ on the function object (func.__can_jump_to__), then read by the agent factory when building the graph.
From a Java perspective

Java has nothing directly equivalent to Python's type() for creating classes at runtime. The closest analogue is dynamic proxies (java.lang.reflect.Proxy) or CGLIB — both create proxy classes at runtime but are far more limited than Python's runtime class creation. In Java, you'd typically use a Builder pattern or annotation processor to achieve similar middleware registration.

Key Design Decisions

DecisionWhyCost
ModelRequest is immutable Prevents middleware from leaking state into each other; enables safe composition Every change requires a new object allocation; dataclasses.replace() is shallow
Decorators create classes with type() Zero boilerplate for single-hook middleware; decorator name becomes class name Opaque class names; hard to debug; no static type checking for dynamically created classes
jump_to is EphemeralValue Prevents stale jump values from persisting across invocations Middleware must explicitly set jump_to every time; easy to forget and have jump silently ignored
GraphBubbleUp always propagates Protects LangGraph control-flow from being swallowed by error handlers Every middleware's except clause must handle it; easy to forget
Cache control sanitization in fallback Provider cache markers (Anthropic) cause API errors on non-Anthropic models Knowledge of cache_control is duplicated here; fragile if new providers add similar markers
