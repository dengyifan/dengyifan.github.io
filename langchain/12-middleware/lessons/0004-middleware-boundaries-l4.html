Production Dimensions: The Four Mandatory Checks

This lesson systematically examines each production dimension that deep-grill probes. These are the areas where demo-level understanding breaks down in real systems.

1. Concurrency Semantics

ScenarioSerial or Parallel?Deciding factor
Multiple tool_calls in one model response Parallel The LLM returns N tool_calls in a single response; LangGraph executes them concurrently in one superstep
Multiple model responses (agent loop iterations) Serial Each model call is sequential; the loop waits for tool results before the next model call
Multiple wrap_tool_call hooks on parallel tools Per-call Each tool call gets its own wrapped execution; middleware instances are shared but stateless per call
Fallback chain in ModelFallbackMiddleware Serial Models tried one after another, only advancing on failure
Critical insight

The agent loop is not "one tool per iteration." It's "one model response per iteration." If the model returns 3 tool_calls, all 3 run in parallel in the same superstep. The loop only iterates again after those results come back and trigger a new model call. This is the #1 concurrency misconception.

2. Exception Tolerance

Failure pointDefault behaviorTolerance mechanism
Tool execution raises exception Exception halts the agent ToolErrorMiddleware converts to ToolMessage(status="error")
Tool call fails transiently Same as above ToolRetryMiddleware retries with backoff
Model call fails transiently Exception halts the agent ModelRetryMiddleware retries with backoff
Model unavailable entirely Exception halts the agent ModelFallbackMiddleware tries alternative models
Argument-binding error (tool input validation) ToolNode converts to error ToolMessage before tool runs Handled upstream — does NOT reach ToolErrorMiddleware
Exception detail: GraphBubbleUp

GraphBubbleUp (LangGraph control-flow signals like interrupts and parent Commands) must ALWAYS propagate. If your wrap_tool_call or wrap_model_call catches Exception broadly, you must explicitly re-raise GraphBubbleUp — otherwise you'll silently swallow interrupts and break human-in-the-loop.

3. Boundary Judgment

How does the agent know when a model "turn" ends?

  • A model response ends when the LLM returns — the boundary is the single AIMessage (or AIMessageChunk in streaming) in the response.
  • The loop termination is decided by: does the last AIMessage have non-empty tool_calls? If yes → continue; if no → end.
  • Streaming detection: when streaming, you cannot rely on metadata token counts to detect the end. You detect it via the finish_reason on the final chunk, or via the model node completing.
  • jump_to boundary: jump_to is EphemeralValue — it resets after each superstep. A jump only affects the next routing decision, not future ones.

4. Performance Overhead

PatternOverheadMitigation
Many wrap_model_call layers nested Each layer adds a Python function call frame; deep nesting slows each model call Consolidate into fewer, well-designed middleware
SummarizationMiddleware on every turn Extra LLM call to generate summary + token counting on every turn Tune trigger threshold; use cheap model for summaries
Stream transformers on every event Every stream event passes through transformer factories Register transformers only when needed; keep them lightweight
ModelRequest.override() in a hot loop Shallow copy per override — cheap, but repeated copies of large message lists add up Override only what changed; avoid copying entire message history

Pitfalls & Edge Cases

Pitfall 1: jump_to silently ignored

If you return {"jump_to": "end"} but forget can_jump_to=["end"], the jump is silently ignored — no error, no warning. The agent just continues normally.

# ❌ WRONG: jump_to will be silently ignored
@before_model
def broken_guard(state, runtime):
    if should_stop(state):
        return {"jump_to": "end"}  # never declared can_jump_to!
    return None

# ✅ CORRECT: declare can_jump_to
@before_model(can_jump_to=["end"])
def fixed_guard(state, runtime):
    if should_stop(state):
        return {"jump_to": "end"}
    return None

Pitfall 2: Sync/async mismatch

The base AgentMiddleware methods raise NotImplementedError with a helpful message if you only define one variant. If you define only awrap_model_call (async) but invoke with stream() (sync), you get a runtime error.

class MyMiddleware(AgentMiddleware):
    async def awrap_model_call(self, request, handler):  # only async defined
        return await handler(request)

# ❌ This fails: sync invoke() can't use the async-only middleware
agent.invoke({"messages": [...]})  # NotImplementedError

# ✅ This works: async invoke
await agent.ainvoke({"messages": [...]})

Pitfall 3: Forgetting tool_call_id in error ToolMessages

When converting an exception to a ToolMessage, you must set tool_call_id=request.tool_call["id"]. Without it, the model can't associate the error with the correct tool call, and it can't correct its mistake.

Pitfall 4: Mutating ModelRequest directly

Direct attribute assignment on ModelRequest is deprecated. Always use .override(). Mutating in place breaks the immutability guarantee and can leak state across middleware.

# ❌ WRONG: deprecated, emits DeprecationWarning
request.system_prompt = "new prompt"

# ✅ CORRECT: immutable override
request = request.override(system_message=SystemMessage(content="new prompt"))

Pitfall 5: Broad exception catching swallows control flow

# ❌ WRONG: swallows GraphBubbleUp, breaks HITL
@wrap_tool_call
def bad_handler(request, handler):
    try:
        return handler(request)
    except Exception as e:
        return ToolMessage(content=f"error: {e}", tool_call_id=request.tool_call["id"])

# ✅ CORRECT: explicitly propagate control-flow
from langgraph.errors import GraphBubbleUp

@wrap_tool_call
def good_handler(request, handler):
    try:
        return handler(request)
    except GraphBubbleUp:
        raise
    except Exception as e:
        return ToolMessage(content=f"error: {e}", tool_call_id=request.tool_call["id"])

Core vs Deep Agents

Most middleware lives in langchain.agents.middleware. But FilesystemMiddleware, SubAgentMiddleware, and RubricMiddleware live in the separate deepagents package. They are not in this project's venv (documented from official docs only).

Custom vs Built-in: When to Use Which
