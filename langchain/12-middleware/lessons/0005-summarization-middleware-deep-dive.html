关键区别先记住：

  • before_model / after_model —— 能改 state（返回 RemoveMessage、新消息）
  • wrap_model_call / wrap_tool_call —— 不改 state，只包裹调用（重试、降级、捕获异常）

这解释了为什么 SummarizationMiddleware 用 before_model（它要改消息列表），而 Retry / Fallback / Error 用 wrap_*（它们只改调用的行为，不改数据）。这是本课最重要的一个判断依据。

1. SummarizationMiddleware

摘要压缩中间件

钩子：before_model 类别：上下文治理
① 概念层② 原理层③ 源码层 ④ 完整代码⑤ 流程图
① 概念层它是什么
SummarizationMiddleware 是 LangChain 内置的 Agent 中间件，挂载在 before_model 生命周期钩子上。它监控消息列表的 token 数量，当达到触发阈值时，自动调用一个 LLM 把较早的对话压缩成摘要文本，用摘要替换旧消息，同时保留最近的消息，并确保 AI/Tool 消息对不被切断。它是 LangChain 短期记忆管理三种策略（修剪、删除、摘要）中唯一保留语义信息的方案。

反常识现象

❌ 无摘要

对话 100 轮后，token 超出窗口，直接报错

agent = create_agent(model, checkpointer=...)

✅ 有摘要

对话 100 轮后仍然正常工作，还能记住早期信息

agent = create_agent(model,
  middleware=[SummarizationMiddleware(...)]
)

反常识之处：它明明在内部调用了 RemoveMessage(id=REMOVE_ALL_MESSAGES) 把消息全删了，但 Agent 没失忆——它还能记住用户名字、之前的决策、已完成任务。

答案：它不是删除，而是「先总结、再替换」——删之前先调 LLM 把旧消息压成摘要，删之后立即把摘要塞回去。

常见误解

误解 1：摘要会把所有消息都替换掉，Agent 就失忆了
看似合理：代码里明明有 RemoveMessage(id=REMOVE_ALL_MESSAGES)。
真相：删掉后立即追加摘要 + 保留的最近消息。最终 state 是「摘要 + 最近消息」，不是空的。
误解 2：摘要是免费的、无损的
看似合理：「总结」听起来比「删除」高级。
真相：摘要是有损压缩——精确数字、工具调用参数、微妙语气会在压缩中丢失。且每次摘要是额外一次 LLM 调用，有成本和延迟。
误解 3：trigger 和 keep 是同一个东西
看似合理：两个参数都接受 ("tokens", N) 这种 tuple。
真相：trigger 决定何时触发，keep 决定触发后保留多少。当 keep 用 tokens 且值接近 trigger 时，摘要空间极小，几乎没价值。

Why Chain（追问到根因）

Q: 为什么需要 SummarizationMiddleware？
A: 因为 Agent 对话历史会无限增长，迟早超出模型上下文窗口。
↓ 追问
Q: 为什么对话历史会无限增长？
A: 因为 checkpointer 每轮都持久化，add_messages reducer 只追加不删除。
↓ 追问
Q: 为什么不能直接用 RemoveMessage 删旧消息？
A: 直接删除会永久丢失信息——用户名字、关键决策、已完成任务都没了。
↓ 追问
Q: 为什么丢失信息会导致问题？
A: 因为 Agent 任务跨多轮，早期上下文是后续推理的必要输入。
↓ 追问到根因
根因 有限上下文窗口 vs 无限增长记忆，两者存在根本矛盾。
SummarizationMiddleware 用「语义压缩」解这个矛盾：牺牲细节精度，换取信息保留 + 空间释放。

两个独立子算法

算法 A：何时触发（_should_summarize）

  • trigger 支持三种形态：tuple（单条件）、dict（AND）、list（OR of AND）
  • 还支持 ("fraction", 0.8) 形态——按模型窗口的百分比触发，需要模型有 profile（窗口大小已知），否则构造时直接抛 ValueError

算法 B：切在哪（_determine_cutoff_index + _find_safe_cutoff_point）

这是整个中间件最精妙的部分。核心约束是：不能把 AIMessage 和它对应的 ToolMessage 拆开。因为 OpenAI/Anthropic 的 API 会校验：每个 tool_call_id 必须有对应的 ToolMessage 回应，否则报错。

# 伪代码：找安全切割点
def find_safe_cutoff(messages, cutoff_index):
    # 1. 先按消息数算出候选切割点
    candidate = cutoff_index

    # 2. 如果候选点落在 ToolMessage 上 → 危险！
    #    孤立的 ToolMessage 前面没有 AIMessage.tool_calls 会 API 报错
    while candidate < len(messages) and is_tool_message(messages[candidate]):
        candidate -= 1        # 前移，把这个 ToolMessage 划入「保留区」

    # 3. 如果候选点落在 AIMessage 且有 tool_calls → 同样危险
    #    孤立的 AIMessage.tool_calls 后面没有 ToolMessage 回应会 API 报错
    while candidate > 0 and has_tool_calls(messages[candidate - 1]):
        candidate -= 1

    return candidate
关键洞察：切割点只能落在「用户消息」或「无 tool_calls 的 AI 消息」之前。AI/Tool 对是一个原子单元——就像数据库事务，要么整个进摘要区，要么整个进保留区，不能切开。

# langchain/agents/middleware/summarization.py（结构摘录）

class SummarizationMiddleware(AgentMiddleware):
    def __init__(self, *, model, trigger=None, keep=("messages", 20),
                 token_counter=count_tokens_approximately,
                 summary_prompt=DEFAULT_SUMMARY_PROMPT,
                 trim_tokens_to_summarize=4000):
        super().__init__()
        self.model = model
        self.trigger = trigger
        self.keep = keep
        self.token_counter = token_counter
        self.summary_prompt = summary_prompt
        self.trim_tokens_to_summarize = trim_tokens_to_summarize

    def before_model(self, state, runtime):
        messages = state["messages"]

        # ① 补 id：reducer 需要 id 才能正确去重
        messages = self._ensure_message_ids(messages)

        # ② 判断是否达阈值；未达则 return None 表示"我不干预"
        if not self._should_summarize(messages):
            return None

        # ③ 算候选切割点 + 回溯到安全点
        cutoff = self._determine_cutoff_index(messages)
        if cutoff <= 0:
            return None                      # 没有可摘要的部分

        # ④ 切两段
        to_summarize, preserved = self._partition_messages(messages, cutoff)
        if not to_summarize:
            return None

        # ⑤ 调 LLM 摘要（内部捕获异常 → 降级为错误字符串）
        summary = self._create_summary(to_summarize)

        # ⑥ 构造新消息列表 —— 顺序至关重要！
        return {"messages": [
            RemoveMessage(id=REMOVE_ALL_MESSAGES),   # 先清空
            *self._build_new_messages(summary),      # 再放摘要
            *preserved,                              # 再放保留的最近消息
        ]}
为什么是 RemoveMessage(ALL) 而不是逐个删？
两个原因：
① 性能：一条指令比 N 条 RemoveMessage(id=...) 便宜，且 reducer 处理更快。
② 原子性：清空 + 重建是一次 state 更新，不存在「删到一半失败」导致消息列表处于中间状态的风险。
代价：如果 preserved 计算错了，你会一次性丢掉全部历史——所以安全切割点的回溯逻辑是必须的。

异常降级设计

# _create_summary 内部的容错（结构摘录）
def _create_summary(self, messages):
    try:
        trimmed = self._trim_messages_for_summary(messages)
        response = self.model.invoke(
            self.summary_prompt.format(messages=format_messages(trimmed))
        )
        return response.content
    except Exception as e:
        # 关键设计：不抛异常，返回错误字符串
        return f"Error generating summary: {e}"

这是「降级」而非「中断」：摘要失败时 Agent 依然能继续跑（只是丢了一段历史），而不是整个请求 500。代价是失败会被静默吞掉——你必须主动监控 content 是否以 "Error generating summary" 开头。

"""
SummarizationMiddleware 完整示例
依赖：pip install langchain langchain-openai langgraph
"""
from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware
from langchain_openai import ChatOpenAI

# 主模型（贵、能力强）
model = ChatOpenAI(model="gpt-4o")

# 摘要模型（便宜、够用）—— 省钱的关键
summary_model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# 自定义摘要 prompt（保留默认契约： 标记 + {messages} 占位符）
CUSTOM_PROMPT = """请总结以下对话，必须保留：
1. 用户提供的所有精确数字（预算、日期、数量）
2. 用户的明确偏好和限制条件
3. 已完成的决策和未完成的待办


{messages}


输出格式：
- SESSION INTENT: 用户的总体目标
- KEY FACTS: 精确事实（数字、名称、日期）
- DECISIONS: 已达成的决策
- NEXT STEPS: 下一步要做什么
"""

agent = create_agent(
    model,
    checkpointer=InMemorySaver(),
    middleware=[
        SummarizationMiddleware(
            model=summary_model,              # 用便宜模型做摘要
            trigger=("tokens", 4000),         # 总 token 超 4000 触发
            keep=("messages", 20),            # 保留最近 20 条
            summary_prompt=CUSTOM_PROMPT,     # 自定义，但保留契约
            trim_tokens_to_summarize=4000,    # 摘要输入先裁剪
        )
    ],
)

config = {"configurable": {"thread_id": "user-42"}}

agent.invoke({"messages": "你好，我叫 Bob，预算 5000 元"}, config)
agent.invoke({"messages": "写一首关于猫的短诗"}, config)
agent.invoke({"messages": "现在换成关于狗的"}, config)

# 即使前三轮被摘要，仍能答对
result = agent.invoke({"messages": "我的名字和预算是多少？"}, config)
print(result["messages"][-1].content)
# 期望输出包含 "Bob" 和 "5000"

# ---- 生产排查：检查摘要是否真的生成成功 ----
state = agent.get_state(config)
for msg in state.values["messages"]:
    if msg.additional_kwargs.get("lc_source") == "summarization":
        if msg.content.startswith("Error generating summary"):
            print("⚠️ 摘要生成失败，需告警：", msg.content)
        else:

❌ 反模式 vs ✅ 正确配置

❌ 错误：keep 用 tokens 且值接近 trigger

SummarizationMiddleware(
    model=model,
    trigger=("tokens", 4000),
    keep=("tokens", 3500),
)

为什么错：真正被摘要的只有 500 token，摘要空间太小，几乎没价值，却额外消耗一次 LLM 调用。

✅ 正确：trigger 用 token，keep 用消息条数

SummarizationMiddleware(
    model=model,
    trigger=("tokens", 4000),
    keep=("messages", 20),
)

为什么对：摘要空间充足，摘要质量有保障。trigger 和 keep 的语义各自独立。

2. ToolErrorMiddleware

工具异常兜底中间件

钩子：wrap_tool_call 类别：工具韧性
① 概念层② 原理层③ 源码层 ④ 完整代码⑤ 流程图
① 概念层它是什么
ToolErrorMiddleware 拦截工具执行过程中抛出的异常，把异常转换成一条 ToolMessage（status="error"）返回给模型，而不是让异常向上冒泡中断整个 Agent 运行。它让模型有机会「看到错误并自我纠正」——比如换个参数重试、换个工具、或告诉用户失败了。

它解决什么问题

假设你有一个查天气的工具，API 临时挂了：

❌ 无 ToolErrorMiddleware

# 工具抛异常
raise HTTPError("503 Service Unavailable")

# 结果：整个 Agent.invoke() 抛出异常
# 用户看到 500 错误，对话彻底中断
# 模型根本没机会知道"刚才失败了"

✅ 有 ToolErrorMiddleware

# 异常被捕获，转成 ToolMessage
ToolMessage(
  content="Error: 503 Service Unavailable",
  tool_call_id="call_abc",
  status="error"
)

# 结果：模型收到这条消息后可以：
#   - 换个城市名重试
#   - 用备用的天气 API
#   - 告诉用户"暂时查不到"

常见误解

误解 1：ToolErrorMiddleware 会「重试」失败的工具
看似合理：都是处理失败的中间件。
真相：它只捕获、不重试。重试是 ToolRetryMiddleware 的职责。两者是正交的——错误兜底管「失败后怎么让流程活下去」，重试管「失败后要不要再试一次」。
误解 2：它会把异常吞掉，出问题也发现不了
看似合理：异常被 catch 了，日志里没有 traceback。
真相：错误信息被写进了 ToolMessage.content，模型能看到，你也能通过 status="error" 筛出来做监控。不是静默吞掉，而是「转成了模型可消费的形式」。

② 原理层内部机制

挂在 wrap_tool_call 上——为什么不是 before_model？

回到 0.5 节的核心判断依据：

  • 它不修改 state.messages（它产生的那条错误 ToolMessage 是正常流的一部分）
  • 它只是包裹一次调用，在调用外层加 try/except

所以它属于 wrap_tool_call 家族。这是一个可以推广到所有中间件的判断方法：要改数据 → before_model；要改行为 → wrap_*。

数据结构：错误 ToolMessage 的三个必要字段

字段值为什么必须
content格式化后的错误文本模型要读它才知道发生了什么
tool_call_id对应 request.tool_call["id"]API 强校验：每个 tool_call 必须有匹配的 ToolMessage，否则下一次模型调用直接 400

on_error 回调的设计

默认行为是把异常 str(e) 塞进 content。但生产环境通常需要更精细的控制：

# 伪代码：错误处理策略
def on_error(exc: Exception, request: ToolCallRequest) -> str:
    if isinstance(exc, TimeoutError):
        return "工具调用超时，请稍后重试或换用其他工具"
    if isinstance(exc, ValidationError):
        return f"参数校验失败：{exc}。请检查参数格式后重试"
    if isinstance(exc, PermissionError):
        return "没有权限执行此操作，请勿再次尝试"
    # 兜底
    return f"工具执行失败：{type(exc).__name__}: {exc}"

设计意图：错误信息是给模型读的，不是给人读的。所以要写成「模型能据此决策」的形式——告诉它「能不能重试」「要不要换工具」，而不是甩一个 Python traceback。

class ToolErrorMiddleware(AgentMiddleware):
    """把工具异常转换成 ToolMessage 返回给模型。"""

    def __init__(
        self,
        *,
        on_error: Callable[[Exception, ToolCallRequest], str] | None = None,
        tools: list[str] | None = None,     # 只对指定工具生效；None = 全部
    ):
        super().__init__()
        self.on_error = on_error or self._default_on_error
        self.tools = tools

    # ---------- 同步版本 ----------
    def wrap_tool_call(self, request, handler):
        if not self._applies_to(request):
            return handler(request)          # 不适用 → 直接透传

        try:
            return handler(request)          # 执行真正的工具
        except Exception as exc:
            return self._build_error_message(exc, request)

    # ---------- 异步版本 ----------
    async def awrap_tool_call(self, request, handler):
        if not self._applies_to(request):
            return await handler(request)
        try:
            return await handler(request)
        except Exception as exc:
            return self._build_error_message(exc, request)

    # ---------- 构造错误 ToolMessage ----------
    def _build_error_message(self, exc, request):
        return ToolMessage(
            content=self.on_error(exc, request),
            tool_call_id=request.tool_call["id"],   # ← 绝对不能漏
            status="error",                          # ← 让模型/监控能区分
        )

3. ToolRetryMiddleware

工具自动重试中间件

钩子：wrap_tool_call 类别：工具韧性
① 概念层② 原理层③ 源码层 ④ 完整代码⑤ 流程图
① 概念层它是什么
ToolRetryMiddleware 在工具执行失败时，按配置的退避策略（指数退避 + 抖动）自动重试同一工具调用。它只对指定的异常类型触发重试，达到最大重试次数后按 on_failure 策略决定是抛出异常还是返回错误 ToolMessage。

它解决什么问题

生产环境中，工具失败绝大多数是瞬时故障：网络抖动、第三方 API 限流（429）、数据库连接池暂时耗尽、DNS 解析超时。这类故障重试一次大概率就好了。

没有重试中间件时，你只能在每个工具函数里手写 try/except + sleep，重复且难维护。ToolRetryMiddleware 把这套逻辑抽成了可复用的声明式配置。

⚠️ 最重要的一条警告：幂等性

误解：重试是安全的，失败就重试呗
看似合理：重试不是标准的容错手段吗？
真相：重试非幂等工具会造成重复副作用。假设 create_order(商品, 数量) 已经成功创建了订单，但在返回响应时网络超时——重试会再创建一个订单。用户被扣两次钱。
正确做法：只对读操作和幂等写操作（带幂等键的）开启重试。对下单、转账、发邮件这类工具，要么禁用重试，要么在工具内部实现幂等键。

② 原理层退避算法与参数语义

指数退避 + 抖动（Exponential Backoff with Jitter）

为什么不能「失败后立刻重试」？因为如果失败原因是服务端过载，立刻重试会加剧过载（重试风暴 / thundering herd）。正确的做法是：

  1. 延迟递增：第 1 次等 1s，第 2 次等 2s，第 3 次等 4s...（乘 backoff_factor）
  2. 设上限：延迟不超过 max_delay（比如 60s），否则重试间隔会长到没意义
  3. 加抖动：在延迟上叠加随机量，避免所有客户端在同一时刻齐刷刷重试
# 退避延迟计算公式（伪代码）
delay_n = min(initial_delay * (backoff_factor ** n), max_delay)
if jitter:
    delay_n = random.uniform(0, delay_n)     # 全抖动（full jitter）
sleep(delay_n)

举例（initial_delay=1.0, backoff_factor=2.0, max_delay=60.0, jitter=True）：

重试次数理论延迟加抖动后的实际范围
第 1 次1.0s0 ~ 1.0s
第 2 次2.0s0 ~ 2.0s
第 3 次4.0s0 ~ 4.0s
第 4 次8.0s0 ~ 8.0s
第 5 次16.0s0 ~ 16.0s
为什么用「全抖动」而不是「固定抖动」？
全抖动（random.uniform(0, delay)）会把请求打散到整个区间，削峰效果最好。AWS 的经典论文 *Exponential Backoff and Jitter* 实测表明，全抖动在多客户端并发场景下总完成时间最优。代价是「可能第一次就立刻重试」，但这恰恰是削峰想要的效果。

# langchain/agents/middleware/tool_retry.py（结构摘录）

class ToolRetryMiddleware(AgentMiddleware):
    """工具失败时按退避策略自动重试。"""

    def __init__(
        self,
        *,
        max_retries: int = 2,
        retry_on: tuple[type[Exception], ...] | Callable = (Exception,),
        on_failure: Literal["continue", "error"] = "continue",
        backoff_factor: float = 2.0,
        initial_delay: float = 1.0,
        max_delay: float = 60.0,
        jitter: bool = True,
        tools: list[str] | None = None,
    ):
        super().__init__()
        self.max_retries = max_retries
        self.retry_on = retry_on
        self.on_failure = on_failure
        self.backoff_factor = backoff_factor
        self.initial_delay = initial_delay
        self.max_delay = max_delay
        self.jitter = jitter
        self.tools = tools

    # ---------- 退避延迟计算 ----------
    def _calculate_delay(self, attempt: int) -> float:
        delay = self.initial_delay * (self.backoff_factor ** attempt)
        delay = min(delay, self.max_delay)
        if self.jitter:
            delay = random.uniform(0, delay)     # 全抖动
        return delay

    # ---------- 同步包裹 ----------
    def wrap_tool_call(self, request, handler):
        if not self._applies_to(request):
            return handler(request)

        last_exc = None
        for attempt in range(self.max_retries + 1):
            try:
                return handler(request)
            except self.retry_on as exc:
                last_exc = exc
                if attempt == self.max_retries:
                    break                       # 重试耗尽
                time.sleep(self._calculate_delay(attempt))

        return self._handle_failure(last_exc, request)

    # ---------- 重试耗尽后的处理 ----------
    def _handle_failure(self, exc, request):
        if self.on_failure == "error":
            raise exc                            # 抛出，中断 Agent
        return ToolMessage(
            content=f"工具在 {self.max_retries} 次重试后仍失败：{exc}",
            tool_call_id=request.tool_call["id"],
            status="error",
        )

4. ToolCallLimitMiddleware

工具调用次数限制中间件

钩子：before_model / wrap_tool_call 类别：工具韧性
① 概念层② 原理层③ 源码层 ④ 完整代码⑤ 流程图
① 概念层它是什么
ToolCallLimitMiddleware 限制某个工具（或全部工具）在一次 run 或一个 thread 内被调用的最大次数。当计数达到上限时，按 exit_behavior 决定是返回提示消息让模型停止、直接结束，还是抛出异常。

它解决什么问题：Agent 的「工具调用死循环」

这是生产环境最烧钱、最常见的失控模式：

模型: 我要搜索 "Python 教程"
工具: 返回 10 条结果
模型: 结果不够好，我要再搜 "Python 教程 入门"
工具: 返回 10 条结果
模型: 还是不够好，我要再搜 "Python 教程 入门 2024"
工具: ...
（无限循环，每次循环都是一次模型调用 + 一次搜索 API 调用）

模型陷入了「搜索 → 不满意 → 再搜索」的循环。没有限制时，这个循环会一直跑到耗尽 token 预算或触发 API 限额为止。

run_limit vs thread_limit：两个维度的限制

限制类型计数范围典型用途
run_limit单次 invoke() 内防止单次请求陷入死循环（应急刹车）
thread_limit整个会话（thread） 内，跨多轮成本控制：限制用户在整个会话中的工具预算

举例：thread_limit=50, run_limit=10 意味着：

  • 用户每次提问，最多触发 10 次工具调用（防死循环）
  • 整个会话累计最多 50 次（防成本失控）

常见误解

误解：limit 到了就直接报错中断
看似合理：「限制」听起来就是硬性拦截。
真相：默认 exit_behavior="continue"——返回一条 ToolMessage 告诉模型「这个工具已经调用 N 次了，请用其他方式回答」。模型还有机会完成任务，而不是直接把用户的请求打回。只有 "error" 才真的中断。
② 原理层计数状态如何跨轮持久化

核心难点：计数必须持久化到 state

中间件实例是无状态的单例——所有 thread 共享同一个 middleware 对象。如果你在 self.count 上计数，会发生灾难性的串号：用户 A 的调用次数会算到用户 B 头上。

所以计数必须存在 LangGraph state 里，按 thread_id 隔离。这就是为什么这个中间件需要扩展 state schema（定义自己的私有字段）。

这是本中间件最容易被面试官追问的点：
「run_limit 是怎么在每次 invoke() 开始时重置的？」
答案的思路：中间件需要能感知「run 的边界」。在 LangGraph 中，一次 invoke() 有明确的生命周期，thread_limit 的计数存在 checkpointer 持久化的 state 中（跨 run 保留），而 run_limit 的计数需要与 run 生命周期绑定。这也是为什么这个中间件同时挂在 before_model 和 wrap_tool_call 两个位置——前者负责判断和拦截，后者负责计数。

exit_behavior 三档语义

值行为模型能否继续适用场景
"continue"返回 ToolMessage：「该工具已达调用上限 N 次，请用其他方式」✅ 能，模型可换方案推荐默认
"error"抛出 ToolCallLimitExceededError❌ 直接中断安全关键场景，超限必须人工介入
"end"用 goto 直接跳转到图终止节点❌ 但优雅结束已达成本预算上限，正常收尾

约束：thread_limit 和 run_limit 至少要填一个。两个都不填的中间件没有意义（也通常会在构造时报错）。

# langchain/agents/middleware/tool_call_limit.py（结构摘录）

class ToolCallLimitMiddleware(AgentMiddleware):
    """限制工具调用次数。"""

    # 声明本中间件需要扩展 state
    state_schema = ToolCallLimitState

    def __init__(
        self,
        *,
        tool_name: str | None = None,
        thread_limit: int | None = None,
        run_limit: int | None = None,
        exit_behavior: Literal["continue", "error", "end"] = "continue",
    ):
        super().__init__()
        if thread_limit is None and run_limit is None:
            raise ValueError("必须至少指定 thread_limit 或 run_limit 之一")
        self.tool_name = tool_name
        self.thread_limit = thread_limit
        self.run_limit = run_limit
        self.exit_behavior = exit_behavior

    # ---------- 计数键：区分"特定工具"和"所有工具" ----------
    def _count_key(self) -> str:
        return self.tool_name if self.tool_name else "__all_tools__"

    # ---------- 超限判断 ----------
    def _is_limit_exceeded(self, state) -> bool:
        key = self._count_key()
        thread_count = state.get("tool_call_counts", {}).get(key, 0)
        run_count = state.get("run_tool_call_counts", {}).get(key, 0)

        if self.thread_limit is not None and thread_count >= self.thread_limit:
            return True
        if self.run_limit is not None and run_count >= self.run_limit:
            return True
        return False

    # ---------- 钩子 1：模型调用前拦截 ----------
    def before_model(self, state, runtime):
        if not self._is_limit_exceeded(state):
            return None                      # 未超限，放行

        # 超限 → 按 exit_behavior 处理
        if self.exit_behavior == "error":
            raise ToolCallLimitExceededError(...)
        if self.exit_behavior == "end":
            return {"jump_to": "__end__"}    # 概念示意：跳到终止
        # "continue"：注入一条提示消息，让模型换方案
        return {"messages": [
            ToolMessage(
                content=f"工具 {self.tool_name or 'ALL'} 已达调用上限，"
                        f"请使用其他方式完成任务。",
                tool_call_id=..., status="error",
            )
        ]}

    # ---------- 钩子 2：工具调用时计数 ----------
    def wrap_tool_call(self, request, handler):
        result = handler(request)
        # 计数 +1，写回 state（通过 return 的 state 更新）
        # 实际实现依赖 LangGraph 的 state 更新机制
        return result

5. ModelRetryMiddleware

模型调用自动重试中间件

钩子：wrap_model_call 类别：模型韧性
① 概念层② 原理层③ 源码层 ④ 完整代码⑤ 流程图
① 概念层它是什么
ModelRetryMiddleware 在模型调用失败时（限流 429、超时、5xx 服务端错误），按退避策略自动重试同一个模型。它与 ToolRetryMiddleware 共享同一套退避算法，区别只在于作用点是「模型调用」而不是「工具调用」。

它解决什么问题

LLM API 的失败率远比你想象的高。生产环境实测，OpenAI / Anthropic 在高负载时段的瞬时失败率可达 1%~5%，主要类型：

错误类型是否应该重试原因
429 Too Many Requests✅ 强烈建议重试限流是瞬时的，退避后大概率成功
500 / 502 / 503✅ 建议重试服务端瞬时故障
TimeoutError✅ 建议重试网络抖动或服务端慢
401 Unauthorized❌ 绝不重试API Key 错了，重试 100 次还是错
400 Bad Request❌ 绝不重试请求格式错（如消息顺序不对）
ContextLengthExceeded❌ 绝不重试上下文太长，重试还是太长——应该用 SummarizationMiddleware
误解：重试是「免费的」
看似合理：又没成功，凭什么收费？
真相：如果第一次调用实际上成功了、只是响应超时，服务端已经计费。重试会产生第二次计费。对长上下文、大模型的调用，这意味着成本翻倍。重试是成本与可靠性的权衡，不是免费的可靠性。

模型重试的特殊考量

① 流式响应下的重试语义

如果模型调用是流式的（stream()），重试的复杂度陡增：

  • 失败发生在建立连接阶段 → 干净重试即可
  • 失败发生在流式传输中途 → 前面已经吐出的 token 怎么办？已经计费了

生产建议：流式场景下，对「中途断开」重试要慎重——用户可能已经看到了半句话，重试会导致内容重复或跳变。

② 重试与 token 成本的叠加

# 成本估算
单次调用成本 = input_tokens × 输入单价 + output_tokens × 输出单价
最坏情况成本 = 单次成本 × (1 + max_retries)

# 例：max_retries=3 时，最坏成本是单次的 4 倍
# 长上下文（如 100K tokens）场景下这个数字非常可观

③ 重试会放大 Agent 循环的延迟

Agent 一次 invoke() 可能包含多轮模型调用（每轮工具调用后都要再调一次模型）。如果每轮都可能重试 3 次、每次退避 1+2+4=7 秒，最坏情况下一次 invoke() 的延迟会呈乘法式增长。

③ 源码层关键结构与调用链
源码标注：仓库 langchain-ai/langchain，路径 libs/langchain/langchain/agents/middleware/model_retry.py。以下为结构示意，以你所安装版本为准。 
# langchain/agents/middleware/model_retry.py（结构摘录）

class ModelRetryMiddleware(AgentMiddleware):
    """模型调用失败时按退避策略自动重试同一模型。"""

    def __init__(
        self,
        *,
        max_retries: int = 2,
        retry_on: tuple[type[Exception], ...] | Callable = (Exception,),
        on_failure: Literal["continue", "error"] = "error",
        backoff_factor: float = 2.0,
        initial_delay: float = 1.0,
        max_delay: float = 60.0,
        jitter: bool = True,
    ):
        super().__init__()
        self.max_retries = max_retries
        self.retry_on = retry_on
        self.on_failure = on_failure
        self.backoff_factor = backoff_factor
        self.initial_delay = initial_delay
        self.max_delay = max_delay
        self.jitter = jitter

    def _calculate_delay(self, attempt: int) -> float:
        delay = min(
            self.initial_delay * (self.backoff_factor ** attempt),
            self.max_delay,
        )
        return random.uniform(0, delay) if self.jitter else delay

    # ---------- 同步：包裹模型调用 ----------
    def wrap_model_call(self, request, handler):
        last_exc = None
        for attempt in range(self.max_retries + 1):
            try:
                return handler(request)          # handler 内部真正调 LLM
            except self.retry_on as exc:
                last_exc = exc
                if attempt == self.max_retries:
                    break
                time.sleep(self._calculate_delay(attempt))

        if self.on_failure == "error":
            raise last_exc
        # "continue"：返回一条 AIMessage 说明失败，让循环继续
        return AIMessage(content=f"模型调用失败：{last_exc}")

    # ---------- 异步：注意 handler 要 await ----------
    async def awrap_model_call(self, request, handler):
        last_exc = None
        for attempt in range(self.max_retries + 1):
            try:
                return await handler(request)
            except self.retry_on as exc:
                last_exc = exc
                if attempt == self.max_retries:
                    break
                await asyncio.sleep(self._calculate_delay(attempt))
        if self.on_failure == "error":
            raise last_exc
        return AIMessage(content=f"模型调用失败：{last_exc}")
注意 on_failure 的默认值差异：工具重试通常默认 "continue"（工具失败是局部问题，模型可以换方案）；模型重试通常默认 "error"（模型是核心依赖，调不通说明整个 Agent 不可用）。这个差异体现了「核心依赖 vs 局部依赖」的设计判断。

6. ModelFallbackMiddleware

模型降级中间件

钩子：wrap_model_call 类别：模型韧性
① 概念层② 原理层③ 源码层 ④ 完整代码⑤ 流程图
① 概念层它是什么
ModelFallbackMiddleware 按顺序维护一个模型列表（first_model + *additional_models）。当主模型调用失败时，自动尝试下一个模型，直到某个模型成功或全部失败。它解决的是模型可用性问题——不是「这次调用碰巧失败」，而是「这个模型现在整个不可用了」。

它解决什么问题

生产环境中的持续性故障，重试多少次都没用：

  • 区域故障：OpenAI 的 us-east-1 挂了，你的请求全打到这个区域
  • 配额耗尽：本月的 API 配额用完，429 会持续到配额重置
  • 模型下线：供应商废弃了某个模型版本（如 gpt-4-0314 被退役）
  • 合规限制：某些地区禁止调用特定供应商的模型

这些场景下，「换一个模型」是唯一有效的降级手段。

三重降级策略（生产必知）

层级策略触发条件实现
L1同模型重试瞬时故障（429 抖动、超时）ModelRetryMiddleware
L2换模型降级持续性故障ModelFallbackMiddleware
L3降能力 / 降精度所有模型都不可用返回缓存答案、简化版回答、提示用户稍后重试

常见误解

误解 1：Fallback 是「透明的」，用户感觉不到
看似合理：反正都是模型，回答出来就行。
真相：不同模型的能力、风格、输出格式差异很大。如果主模型是 gpt-4o、备用是 gpt-4o-mini，备用模型在复杂推理上会明显退化。如果你的 Agent 依赖结构化输出（JSON schema），备用模型必须支持同样的能力，否则会解析失败。降级是「可用性换质量」，不是无损的。
误解 2：模型列表可以随便排
看似合理：不就是一个优先顺序吗。
真相：列表顺序需要配合成本模型和能力模型。通常策略是「强 → 中 → 弱」，因为降级意味着「宁可弱一点也要有响应」。但如果你的场景是「高并发低成本」，可能是「便宜 → 贵」（平时用便宜的，扛不住时才用贵的）。
② 原理层链式尝试的实现机制

核心机制：把模型列表当成一条责任链

# 伪代码：链式尝试
def wrap_model_call(request, handler):
    # handler 内部已经绑定了"当前模型"
    # 我们要做的是：如果 handler 失败，用别的模型重建请求

    models = [self.first_model, *self.additional_models]

    for i, model in enumerate(models):
        try:
            # 关键：用当前的 model 覆盖请求中的模型
            return handler(request.override(model=model))
        except Exception as exc:
            if i == len(models) - 1:
                raise           # 最后一个也失败 → 抛出
            continue            # 否则试下一个

    # 理论上不可达
    raise RuntimeError("unreachable")
关键点：handler 是不可变的吗？
不是。request 对象支持覆盖（override）——可以替换模型、替换 prompt、替换工具列表，然后重新调用 handler。这是 LangChain middleware 设计的一个精巧之处：
同一个 handler 可以被用不同的参数调用多次，而不需要重新构建整条中间件链。
这就是为什么 Fallback 能实现「换模型重试」——它不是在重建 Agent，只是在重新调用 handler。

③ 源码层关键结构与调用链
源码标注：仓库 langchain-ai/langchain，路径 libs/langchain/langchain/agents/middleware/model_fallback.py。以下为结构示意，以你所安装版本为准。 
# langchain/agents/middleware/model_fallback.py（结构摘录）

class ModelFallbackMiddleware(AgentMiddleware):
    """主模型失败时按顺序切换到备用模型。"""

    def __init__(
        self,
        first_model: str | BaseChatModel,
        *additional_models: str | BaseChatModel,
    ):
        super().__init__()
        self.models = [first_model, *additional_models]

    def wrap_model_call(self, request, handler):
        last_exc = None

        for i, model in enumerate(self.models):
            try:
                # 用当前模型覆盖请求中的模型，再交给 handler
                return handler(request.override(model=model))
            except Exception as exc:
                last_exc = exc
                if i == len(self.models) - 1:
                    raise                  # 全部失败，抛出最后一个异常
                # 否则静默切换到下一个（可在此加日志/指标）

        raise last_exc      # 理论上不可达

    async def awrap_model_call(self, request, handler):
        last_exc = None
        for i, model in enumerate(self.models):
            try:
                return await handler(request.override(model=model))
            except Exception as exc:
                last_exc = exc
                if i == len(self.models) - 1:
                    raise
        raise last_exc
源码阅读要点：
① 没有任何退避/延迟逻辑——它假设「这个模型不行就立刻换下一个」，不做等待。
② request.override(model=...) 是核心 API。它返回一个新的请求对象，模型被替换，其他一切不变。
③ 异常处理极简：不区分异常类型，任何异常都触发降级。这是合理的——能走到 Fallback 这一层，说明内层的 Retry 已经放弃了。
④ 没有「记住哪个模型可用」的机制：每次调用都从 first_model 开始试。这可能导致「主模型已经挂了，但每次调用还是要先试一次主模型、等它超时」。这是可以改进的点（见下面的「如果是你，会怎么改进」）。

设计追问三连（L4 边界层）

Q1：为什么这样设计，而不是其他方案？

A：把「模型切换」做成一个独立的、无状态的中间件，而不是塞进 ModelRetryMiddleware 里。好处是：职责单一、可组合。你可以只用 Retry、只用 Fallback，或者两者叠加，顺序还能自定义。如果合并成一个「重试+降级」中间件，配置会变得极其复杂（重试几次后降级？降级后还重试吗？）。

Q2：这个设计有什么代价？

A：没有熔断机制。主模型持续不可用时，每次调用都要先试主模型（可能等到超时），再切备用。这会白白浪费一次超时时间。理想的设计应该引入熔断器（Circuit Breaker）：连续失败 N 次后，在一段时间内直接跳过主模型。

Q3：如果是你，会怎么改进？

# 改进思路：带熔断的 Fallback
class CircuitBreakerFallbackMiddleware(AgentMiddleware):
    """连续失败 N 次后，暂时跳过该模型。"""

    def __init__(self, *models, failure_threshold=5, recovery_timeout=60):
        self.models = models
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.failures = defaultdict(int)      # 每个模型的连续失败次数
        self.opened_at = {}                   # 熔断开启时间

    def _is_available(self, model) -> bool:
        if self.failures[model] < self.failure_threshold:
            return True
        # 熔断已开启，检查是否到了半开状态
        elapsed = time.time() - self.opened_at.get(model, 0)
        return elapsed > self.recovery_timeout

    def wrap_model_call(self, request, handler):
        for model in self.models:
            if not self._is_available(model):
                continue                        # 熔断中，直接跳过
            try:
                result = handler(request.override(model=model))
                self.failures[model] = 0        # 成功 → 重置计数
                return result
            except Exception:
                self.failures[model] += 1
                if self.failures[model] >= self.failure_threshold:
                    self.opened_at[model] = time.time()
                continue
        raise RuntimeError("所有模型均不可用")

① 概念层它是什么
ModelCallLimitMiddleware 限制在一次 run 或一个 thread 内，LLM 被调用的最大次数。它是 Agent 循环的总闸——不管是因为工具调用死循环、还是因为模型不收敛，只要模型调用次数超限，就强制终止。

它解决什么问题：Agent 的「循环失控」

Agent 的本质是一个 while 循环：调模型 → 有 tool_calls 就执行工具 → 再调模型 → ...。这个循环的终止条件是「模型返回的 AIMessage 里没有 tool_calls」。

但如果模型始终返回 tool_calls（陷入不收敛），这个循环永远不会退出：

轮次 1: 模型调 weather(北京)     → 工具返回
轮次 2: 模型调 weather(上海)     → 工具返回
轮次 3: 模型调 weather(广州)     → 工具返回
...（模型觉得信息不够，一直查下去）
轮次 N: 无限循环，每次都是一次模型调用（$$$）
误解：Recursion Limit 已经能防死循环了，不需要这个中间件
看似合理：LangGraph 有 recursion_limit 参数。
真相：recursion_limit 限制的是图的步数（super-steps），不是模型调用次数。而且它抛异常中断，用户会看到一个硬错误。ModelCallLimitMiddleware 提供的是更精确的语义控制（限制模型调用而非图步数）+ 更优雅的退出（exit_behavior="end" 可以正常收尾）。两者互补，不是替代。

关系ModelCallLimit 是外层总闸，ToolCallLimit 是内层细控。两者同时用最稳。

为什么两个都要有？

因为它们防的是不同的失控模式：

  • ToolCallLimit 能防的：某个工具被反复调用（如搜索 50 次）
  • ToolCallLimit 防不了的：模型调了很多不同的工具，每个都不超限，但总轮次爆炸
  • ModelCallLimit 能防的：无论调用什么工具，总轮次有上限

举例：如果只有 ToolCallLimit（每个工具 run_limit=5），模型可以依次调用 10 个不同工具各 5 次 = 50 次工具调用 = 50+ 轮模型调用。ModelCallLimit 才能兜住这个洞。

如何优雅地「终止」Agent 循环

这是这个中间件最有意思的设计点。Agent 循环的退出条件是「模型不再返回 tool_calls」。那么超限时怎么让它退出？三种手法：

手法实现退出方式
阻止模型调用超限时 before_model 直接返回一条不含 tool_calls 的 AIMessage模型"看到"这条消息后不再调工具，循环自然结束
跳转到终止节点exit_behavior="end" → 触发 goto("__end__")强制跳出图，直接返回
抛异常exit_behavior="error"硬中断，上层捕获
为什么默认是「阻止模型调用」而不是「抛异常」？
因为抛异常意味着用户拿不到任何回答——前面 N 轮模型调用白花了钱，用户还得看到一个报错。而「阻止模型调用」让 Agent 用现有的信息给出一个不完美但有用的回答。
这是典型的优雅降级（graceful degradation）思想：宁可给一个 80 分的答案，也不要给一个 500 错误。

run_limit 该设多少？

设太松没意义，设太紧会误杀正常任务。经验公式：

run_limit ≈ 3 × (预期最大工具调用轮次) + 2

# 举例：
# 一个"研究型" Agent，预期最多调 5 次搜索 + 2 次总结
# → 轮次约 7~8 → run_limit = 3 × 3 + 2 = 11 ~ 25
#
# 一个"客服" Agent，通常 1~2 轮就答完
# → run_limit = 5~8 足够
#
# 一个"编程" Agent（ReAct 风格，多轮调试）
# → run_limit = 25~40
③ 源码层关键结构与调用链
源码标注：仓库 langchain-ai/langchain，路径 libs/langchain/langchain/agents/middleware/model_call_limit.py。以下为结构示意，以你所安装版本为准。 
# langchain/agents/middleware/model_call_limit.py（结构摘录）

class ModelCallLimitMiddleware(AgentMiddleware):
    """限制模型调用次数。"""

    state_schema = ModelCallLimitState

    def __init__(
        self,
        *,
        thread_limit: int | None = None,
        run_limit: int | None = None,
        exit_behavior: Literal["continue", "error", "end"] = "continue",
    ):
        super().__init__()
        if thread_limit is None and run_limit is None:
            raise ValueError("必须至少指定 thread_limit 或 run_limit 之一")
        self.thread_limit = thread_limit
        self.run_limit = run_limit
        self.exit_behavior = exit_behavior

    # ---------- 钩子 1：模型调用前检查 ----------
    def before_model(self, state, runtime):
        run_count = state.get("model_call_count", 0)
        thread_count = state.get("thread_model_call_count", 0)

        exceeded = (
            (self.run_limit is not None and run_count >= self.run_limit)
            or (self.thread_limit is not None
                and thread_count >= self.thread_limit)
        )
        if not exceeded:
            return None                     # 放行

        # ---------- 超限处理 ----------
        if self.exit_behavior == "error":
            raise ModelCallLimitExceededError(
                f"模型调用超限：run={run_count}/{self.run_limit}, "
                f"thread={thread_count}/{self.thread_limit}"
            )

        if self.exit_behavior == "end":
            # 概念示意：请求跳转到图终止节点
            return {"jump_to": "__end__"}

        # "continue"：注入一条不含 tool_calls 的 AIMessage
        # 循环条件（有 tool_calls 才继续）因此不再满足 → 自然退出
        return {"messages": [
            AIMessage(
                content="已达模型调用次数上限，"
                        "请基于现有信息给出最终回答。"
            )
        ]}

    # ---------- 钩子 2：模型调用后计数 ----------
    def wrap_model_call(self, request, handler):
        result = handler(request)
        # 计数由 state 更新机制累加
        return result
核心洞察：exit_behavior="continue" 的实现非常巧妙——它注入的 AIMessage 不含 tool_calls。而 Agent 循环的退出条件正是「AIMessage 没有 tool_calls」。所以这条消息一注入，循环就自然结束了。
不需要任何强制跳转或异常，只是顺着循环本来的退出条件走。
这是一个很好的设计示范：与其和机制对抗，不如顺着机制走。

"""
ModelCallLimitMiddleware 完整示例：生产级 Agent 循环保护
"""
from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents import create_agent
from langchain.agents.middleware import (
    ModelCallLimitMiddleware,
    ToolCallLimitMiddleware,
    ToolErrorMiddleware,
    ModelRetryMiddleware,
    ToolRetryMiddleware,
)
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

@tool
def web_search(query: str) -> str:
    """搜索网页。"""
    return f"搜索结果（{query}）：共 10 条"

@tool
def read_page(url: str) -> str:
    """读取网页内容。"""
    return f"网页内容（{url}）：..."

agent = create_agent(
    ChatOpenAI(model="gpt-4o", max_retries=0),
    tools=[web_search, read_page],
    checkpointer=InMemorySaver(),
    middleware=[
        # ============ 韧性层（内层） ============
        ToolErrorMiddleware(),                 # 工具异常兜底
        ToolRetryMiddleware(                   # 工具瞬时故障重试
            max_retries=2,
            retry_on=(ConnectionError, TimeoutError),
            tools=["web_search", "read_page"],
        ),
        ModelRetryMiddleware(max_retries=2, on_failure="error"),

        # ============ 限制层（外层） ============
        # 细粒度：单个工具的次数上限
        ToolCallLimitMiddleware(
            tool_name="web_search",
            run_limit=5,
            thread_limit=30,
            exit_behavior="continue",
        ),
        ToolCallLimitMiddleware(
            tool_name="read_page",
            run_limit=3,
            thread_limit=15,
            exit_behavior="continue",
        ),
        # 粗粒度：模型调用总闸（防住"调了很多不同工具"的失控）
        ModelCallLimitMiddleware(
            run_limit=20,              # 单次提问最多 20 轮模型调用
            thread_limit=100,          # 整个会话最多 100 次
            exit_behavior="continue",  # 优雅收尾，而不是报错
        ),
    ],
)

config = {"configurable": {"thread_id": "research-1"}}

result = agent.invoke(
    {"messages": "帮我深入研究一下 LangChain 的中间件体系，尽可能找全资料"},
    config,
)
print(result["messages"][-1].content)
# 即使研究任务很发散，最多 20 轮后也会收尾并给出阶段性答案

# ---------- 生产监控：统计超限率 ----------
state = agent.get_state(config)
run_count = state.values.get("model_call_count", 0)
thread_count = state.values.get("thread_model_call_count", 0)
print(f"本次 run 模型调用 {run_count} 次，会话累计 {thread_count} 次")

if run_count >= 20:
    print("⚠️ 触发了 run_limit，说明该任务可能过于发散，"
          "建议优化 prompt 或放宽 limit")

中间件顺序的完整说明

顺序中间件层次为什么在这
1ToolErrorMiddleware最内离工具最近，最先捕获异常
2ToolRetryMiddleware内包住 Error，重试的是"整个执行（含错误捕获）"
3ModelRetryMiddleware中模型调用的重试，与工具链独立
4ToolCallLimitMiddleware外在重试之后判断——重试不计入 limit 更合理
5ModelCallLimitMiddleware最外总闸，最后兜底
顺序的一条判断原则：
「先让调用成功，再判断是否超限」。所以 Retry 在内、Limit 在外。
如果你把 Limit 放在 Retry 里面，会出现「重试 3 次被算作 3 次调用」——limit=5 时，两次失败的重试就用光了配额，但实际上只完成了 1 个逻辑任务。这显然不合理。
反过来说，如果你的 limit 就是想按"物理调用次数"计费，那顺序应该反过来。——顺序不是死规定，而是语义选择。

11. 深度练习

练习 1：故障模拟——「Agent 忘事」

场景：你部署了一个使用 trigger=("tokens", 8000), keep=("messages", 5) 的客服 Agent。上线后发现用户投诉「Agent 忘记了我前面说的需求」。请一步步排查。

参考思路
  1. 先查摘要文本内容：打印 state 中 lc_source="summarization" 的消息，看摘要是否遗漏了关键信息
  2. 检查 keep 值：keep=5 意味着只保留最近 5 条消息，如果用户需求在第 6 条之前说的，且摘要没覆盖到，就会丢失
  3. 检查默认 prompt：默认 prompt 提取「目标/结论/产物/下一步」，但不会提取精确需求细节。如果用户需求是「预算 5000 元内的产品」，这个数字可能被摘要丢失
  4. 缓解方案：调大 keep 到 20-30；自定义 summary_prompt 要求保留「用户的具体需求参数」；对关键信息做额外持久化到 state 的自定义字段

练习 2：故障模拟——「成本一夜暴涨 10 倍」

场景：某天早上你发现 LLM 账单比平时高了 10 倍。日志显示 Agent 的调用量没变。可能的根因有哪些？怎么排查？

参考思路
  1. 检查是否发生了「重试风暴」：某天供应商开始频繁限流（429），ModelRetryMiddleware 疯狂重试。查 trace 中单次请求的实际模型调用次数。
  2. 检查 SDK 重试是否与中间件叠加：max_retries=0 是否设了？如果 SDK 默认 2 次 × 中间件 3 次 = 最坏 6 次，成本直接 6 倍。
  3. 检查是否触发了 Fallback 到更贵的模型：如果 fallback 链是「便宜 → 贵」，主模型故障时全部降级到贵模型，成本反而暴涨。
  4. 检查是否发生了 Agent 循环失控：ModelCallLimitMiddleware 是否配置了？没配置时，某个不收敛的 prompt 可能导致 50 轮循环。
  5. 检查摘要频率：trigger 阈值是否被调低了？如果 keep 用 tokens 且接近 trigger，摘要会疯狂触发。
  6. 排查手段：在 trace 中按 run_id 统计「每次 invoke 的模型调用次数分布」，看长尾是否有异常值。

练习 3：设计一个「带熔断的 Fallback」

ModelFallbackMiddleware 没有熔断机制——主模型持续不可用时，每次调用都要先试主模型、等超时。请你设计一个改进版本。

参考思路
  1. 核心状态：每个模型的「连续失败次数」+「熔断开启时间」
  2. 三态熔断器：关闭（正常尝试）→ 连续失败 N 次 → 开启（直接跳过，不尝试）→ 等待 T 秒 → 半开（放一个请求试探）→ 成功则关闭、失败则重新开启
  3. 状态存哪：这里是关键权衡。如果存在中间件实例上，是「全局共享」的——所有用户共享同一个熔断状态（这通常是对的，因为模型故障是全局的）。如果存在 state 里，每个 thread 独立熔断（不合理）。这是少数应该存在实例上的状态——与 ToolCallLimit 相反。
  4. 并发安全：多线程/多协程下要加锁，否则计数会竞态。
  5. 可观测：熔断开启/关闭必须打日志 + 上报指标，否则你永远不知道降级发生了。

13. 间隔回顾

跨概念连接

  • RemoveMessage 从 Lesson 0001：SummarizationMiddleware 的 return 里用了 RemoveMessage(id=REMOVE_ALL_MESSAGES) 清空消息。今天讲清了「为什么是 ALL 而不是逐个删」——性能和原子性。
  • trim_messages 从之前课程：_trim_messages_for_summary 内部调用它防止摘要输入超长。
  • checkpointer 从之前课程：摘要后的 state 被持久化 → 摘要不可逆。同时，ToolCallLimit / ModelCallLimit 的跨轮计数必须依赖 checkpointer 才能生效。
  • tool_call_id 一致性：ToolErrorMiddleware 必须带正确的 tool_call_id，这与 Agent 消息协议强相关——每个 tool_call 必须有对应的 ToolMessage。

本课的统一心智模型

「改数据用 before_model，改行为用 wrap_*」
这一条把七个中间件全部串起来了：
· Summarization 改数据 → before_model
· ToolError / ToolRetry 改行为 → wrap_tool_call
· ModelRetry / ModelFallback 改行为 → wrap_model_call
· ToolCallLimit / ModelCallLimit 两个都占（判断用 before_model，计数用 wrap_*）
