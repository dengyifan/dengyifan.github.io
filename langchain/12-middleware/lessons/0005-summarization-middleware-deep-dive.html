0. 动机引爆

反常识现象

运行同一段 Agent 代码，唯一区别是有没有加 SummarizationMiddleware：

❌ 无摘要

对话 100 轮后，token 超出窗口，直接报错

agent = create_agent(model, checkpointer=...)

✅ 有摘要

对话 100 轮后仍然正常工作，还能记住早期信息

agent = create_agent(model,
  middleware=[SummarizationMiddleware(...)]
)

反常识之处：SummarizationMiddleware 明明在内部调用了 RemoveMessage(id=REMOVE_ALL_MESSAGES) 把消息全部删掉了，但 Agent 并没有失忆——它还能记住对话早期的关键信息（用户名字、之前的决策、已完成任务）。

这怎么可能？答案藏在它的核心设计里：它不是简单删除，而是"先总结、再替换"——在删除之前，先调用 LLM 把旧消息压缩成摘要。

最简可行场景

from langgraph.checkpoint.memory import InMemorySaver
from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="deepseek-v4-pro")

agent = create_agent(
    model,
    checkpointer=InMemorySaver(),
    middleware=[
        SummarizationMiddleware(
            model=model,              # 用于摘要的模型
            trigger=("tokens", 4000), # 总 token 超 4000 时触发
            keep=("messages", 20),    # 摘要后保留最近 20 条消息
        )
    ],
)

config = {"configurable": {"thread_id": "1"}}
agent.invoke({"messages": "hi, my name is bob"}, config)
agent.invoke({"messages": "write a short poem about cats"}, config)
agent.invoke({"messages": "now do the same but for dogs"}, config)
final_response = agent.invoke({"messages": "what's my name?"}, config)
# 即使前面三轮对话被摘要了，Agent 仍能回答 "Your name is Bob!"

0.5. 前置知识检查

开始之前，确认你理解以下概念：

  1. RemoveMessage — 它不是"聊天消息"，而是发给 add_messages reducer 的删除指令。如果记不清了，点这里回顾。
  2. trim_messages — 在调用模型前临时裁剪上下文，不修改 state。如果记不清了，点这里回顾。
  3. checkpointer — 负责持久化 Agent state，使对话历史跨轮次保持。如果记不清了，点这里回顾。

1. 概念层

精确定义

SummarizationMiddleware 是 LangChain 内置的 Agent 中间件，挂载在 before_model 生命周期钩子上。它监控消息列表的 token 数量，当达到触发阈值时，自动调用一个 LLM 把较早的对话压缩成摘要文本，用摘要替换旧消息，同时保留最近的消息，并确保 AI/Tool 消息对不被切断。它是 LangChain 短期记忆管理三种策略（修剪、删除、摘要）中唯一保留语义信息的方案。
— 基于 LangChain 官方文档

Why Chain

Q: 为什么需要 SummarizationMiddleware？
A: 因为 Agent 对话历史会无限增长，迟早超出模型上下文窗口。
↓ 追问
Q: 为什么对话历史会无限增长？
A: 因为 checkpointer 每轮都持久化，add_messages reducer 只追加不删除。
↓ 追问
Q: 为什么不能直接用 RemoveMessage 删旧消息？
A: 因为直接删除会永久丢失信息——用户名字、关键决策、已完成任务都没了。
↓ 追问
Q: 为什么丢失信息会导致问题？
A: 因为 Agent 任务跨多轮，早期上下文是后续推理的必要输入。
↓ 追问到根因
根因 有限上下文窗口 vs 无限增长记忆，两者之间存在根本矛盾。
SummarizationMiddleware 用"语义压缩"来解这个矛盾：牺牲细节精度，换取信息保留 + 空间释放。

常见误解

误解 1：摘要会把所有消息都替换掉，Agent 就失忆了
看似合理：代码里明明有 RemoveMessage(id=REMOVE_ALL_MESSAGES)。
真相：删掉所有消息后，立即追加摘要 + 保留的最近消息。最终 state 是"摘要 + 最近消息"，不是空的。
误解 2：摘要是免费的、无损的
看似合理："总结"听起来比"删除"高级。
真相：摘要有信息损耗——精确数字、工具调用参数、微妙语气可能在压缩中丢失。它是"有损压缩"，不是"无损保存"。每次摘要是额外一次 LLM 调用，有成本和延迟开销。
误解 3：trigger 和 keep 是同一个东西
看似合理：两个参数都接受 ("tokens", N) 这种 tuple。
真相：trigger 决定何时触发摘要，keep 决定触发后保留多少最近消息。是两个完全独立的概念。当 keep 用 tokens 且值接近 trigger 时，摘要空间极小，几乎没价值。

2. 系统层

上游依赖

  • create_agent + AgentMiddleware 机制：SummarizationMiddleware 继承自 AgentMiddleware，通过 before_model 钩子注入。
  • add_messages reducer：return 中的 RemoveMessage(id=REMOVE_ALL_MESSAGES) 依赖 state 的 messages 字段使用 reducer。
  • 一个用于摘要的 LLM：model 参数，可以是独立的模型（推荐用更便宜的小模型），也可以和 Agent 主模型是同一个。
  • trim_messages 工具：_trim_messages_for_summary 内部调用它，防止待摘要消息超过摘要模型的窗口。

下游消费者

  • Agent 的模型推理：摘要后的新消息列表（摘要 + 保留消息）作为模型输入。
  • checkpointer：摘要后的新 state 被持久化，后续用 thread_id 恢复时看到的是摘要后的状态。

可替换性

  • 什么情况下换掉它？：当任务需要精确记忆（法律、金融领域的精确数字），摘要的有损压缩不可接受时，应改用外部向量记忆 + RAG 检索。
  • 迁移路径：自定义 AgentMiddleware 子类，重写 before_model，做"摘要 + 检索 + 压缩"组合。
  • 设计模式：模板方法模式（AgentMiddleware 定义 before_model 钩子，SummarizationMiddleware 重写它）+ 装饰器模式（不改动 Agent 核心图结构，在模型调用前装饰一层摘要逻辑）。

反模式警告

❌ 错误：keep 用 tokens 且值接近 trigger

SummarizationMiddleware(
    model=model,
    trigger=("tokens", 4000),
    keep=("tokens", 3500),
)

为什么错：真正被摘要的只有 500 token，摘要空间太小，几乎没价值，却额外消耗一次 LLM 调用。

✅ 正确：trigger 用 token，keep 用消息条数

SummarizationMiddleware(
    model=model,
    trigger=("tokens", 4000),
    keep=("messages", 20),
)

为什么对：摘要空间充足，摘要质量有保障。trigger 和 keep 的语义各自独立。

可维护性陷阱

  • 摘要 prompt 的隐式契约：DEFAULT_SUMMARY_PROMPT 中的 <messages> 标记和 {messages} 占位符是下游（如 deep agents）的"公开契约"。自定义 prompt 时如果删掉这两个标记，会破坏下游消费者。预防：自定义时保留这些结构。
  • token 计数器不准确：默认使用 count_tokens_approximately（基于字符数估算），中文、代码、特殊 token 可能偏差大。Anthropic 模型自动调整到 3.3 chars/token 的近似值。生产环境建议用模型真实 tokenizer。

误导类比警示

流行类比："摘要就像给对话拍照存档，把照片收进相册，腾出桌面空间。"

为什么吸引人：它暗示"信息没丢，只是换了种形式存起来"，符合直觉。

哪里不准确：

  1. 拍照是无损的（像素级完整），但摘要是有损压缩——精确数字、微妙语气会丢失。
  2. 照片可以"原样恢复"，但摘要无法还原原始对话——它是单向的、不可逆的压缩。

更好的类比："摘要更像是榨汁——把一堆对话（水果）压成一杯浓缩汁（摘要）。你保住了营养（关键信息），但失去了果肉纤维（细节和原始结构），而且榨完就回不去了。"

4. 韧性层

失败场景 1：摘要后 Agent 仍然"失忆"

触发摘要把关键信息（如精确数字、完整列表）压缩时丢失了，或摘要质量太差
症状用户问"我之前的预算是多少？"Agent 答错；Agent 重复已完成的任务
诊断
  1. 检查触发后的 state 摘要文本内容
  2. 确认默认 prompt 的四个 section（SESSION INTENT / SUMMARY / ARTIFACTS / NEXT STEPS）是否覆盖了所需信息
根因默认 prompt 提取"目标、结论、产物、下一步"，但不提取精确数字、完整列表等细节
缓解自定义 summary_prompt 要求保留特定类型信息；或调大 keep 保留更多原始消息；或对关键信息做额外持久化

失败场景 2：摘要触发太频繁，成本暴涨

触发trigger 阈值太低，或 keep 用 tokens 且值接近 trigger
症状每次对话都触发一次摘要 LLM 调用，延迟增加、成本上升
诊断
  1. 观察日志中 lc_source="summarization" 的调用频率
  2. 计算 trigger 与 keep 的差值
根因摘要空间太小（trigger - keep 差值小），导致稍微累积就触发
缓解调高 trigger；或改用 keep=("messages", N) 保证摘要空间

失败场景 3：摘要模型调用失败导致 Agent 中断

触发摘要 LLM 不可用、超时、或返回格式异常
症状Agent 调用被中断，或摘要内容为 "Error generating summary: ..."
诊断
  1. 检查摘要消息的 content 是否以 "Error" 开头
  2. 确认摘要模型 API 可用性
根因_create_summary 捕获异常后返回错误字符串而非抛出，设计上是为了"降级"而非中断
缓解监控摘要异常率；考虑为摘要模型设置独立的超时和重试策略

监控信号

信号关注什么阈值动作
摘要触发频率lc_source="summarization" 消息数每轮对话 > 1 次检查 trigger/keep 配置

5. 费曼讲解

对 5 岁小孩

就像你有一个小本子，上面记满了你和朋友说的话。本子写满了写不下新的话了，这时候你拿出一个聪明的小帮手，让他把前面的话变成一句话的总结写在本子上，然后把前面的话擦掉。这样本子就有新的地方写了，而且你还记得前面说了什么重要的事。

更准确的类比

摘要不是"拍照存档"（拍照是像素级无损），而是"榨汁"：把一堆对话水果压成一杯浓缩汁。营养（关键信息）保住了，但果肉纤维（细节和原始结构）没了，而且榨完就回不去了。

对非技术同事

SummarizationMiddleware 是 LangChain 内置的记忆管理工具。当 Agent 的对话历史太长、超出模型的处理上限时，它会自动调用一个 AI 把旧对话压缩成一段总结，然后用这段总结替换掉旧消息，同时保留最近的消息。这样既控制了对话长度，又不会完全丢失之前的信息。代价是总结会丢失一些细节，而且每次总结需要额外调用一次 AI，有成本。

7. 深度练习

练习 1：故障模拟

场景：你部署了一个使用 trigger=("tokens", 8000), keep=("messages", 5) 的客服 Agent。上线后发现用户投诉"Agent 忘记了我前面说的需求"。请一步步排查：可能的原因有哪些？先查什么？怎么验证？

参考思路
  1. 先查摘要文本内容：打印 state 中 lc_source="summarization" 的消息，看摘要是否遗漏了关键信息
  2. 检查 keep 值：keep=5 意味着只保留最近 5 条消息，如果用户需求在第 6 条之前说的，且摘要没覆盖到，就会丢失
  3. 检查默认 prompt：默认 prompt 提取"目标/结论/产物/下一步"，但不会提取精确需求细节。如果用户需求是"预算 5000 元内的产品"，这个数字可能被摘要丢失
  4. 缓解方案：调大 keep 到 20-30；自定义 summary_prompt 要求保留"用户的具体需求参数"；对关键信息做额外持久化到 state 的自定义字段

练习 2：对比分析

对比三种记忆管理方案。针对以下场景，分别选哪个？为什么？

  1. 一个需要精确记录金额的财务 Agent
  2. 一个闲聊型客服 Agent（不关心历史细节）
  3. 一个需要删除用户敏感信息的合规 Agent
参考思路
  1. 财务 Agent：不适合 SummarizationMiddleware（有损压缩会丢精确数字）。推荐自定义 state 字段持久化金额 + trim_messages 控制对话长度，或外部数据库存储关键数据。
  2. 闲聊客服：最适合 SummarizationMiddleware。不关心精确细节，摘要保留"对话意图"即可。
  3. 合规 Agent：用 RemoveMessage 精确删除敏感消息。摘要是不可逆压缩，敏感信息可能残留在摘要中，不合规。

9. 间隔回顾

跨概念连接

  • RemoveMessage 从 Lesson 0001：SummarizationMiddleware 的 return 里直接用了 RemoveMessage(id=REMOVE_ALL_MESSAGES) 来清空消息。今天的摘要机制本质上是"先清空，再填充"——借用了 RemoveMessage 的 reducer 机制。
  • trim_messages 从之前课程：_trim_messages_for_summary 内部调用 trim_messages(strategy="last", allow_partial=True, include_system=True) 来防止摘要输入超长。这是 trim_messages 在摘要流程中的实际应用。
  • checkpointer 从之前课程：摘要后的新 state 被 checkpointer 持久化，后续用相同的 thread_id 恢复时看到的是摘要后的状态。这意味着摘要是不可逆的——一旦持久化，原始消息就永久丢失了。
