LangGraph Agent Streaming / 常见误区

常见误区知识库

LangGraph Agent Streaming 流式输出中最常见的 10 个误解。

误区 1: stream_mode="updates" 会输出每个 token
错误理解： 认为 updates 模式也会像 messages 一样逐 token 输出。
正确理解： updates 按 superstep 粒度输出，每个 superstep（如一次模型调用、一次工具调用）完成后才发出一个事件。只有 messages 模式才是逐 token 输出。
为什么容易犯： 名字 updates 暗示"更新"，容易让人联想到实时更新，但实际是步骤级别的批量更新。
如何避免： 记住 updates = 步骤粒度，messages = token 粒度。用"步骤"和"字符"作为记忆锚点。
误区 2: custom 模式需要额外的配置才能启用
错误理解： 需要在 create_agent 时传入特殊参数来启用 custom 模式。
正确理解： custom 模式的启用完全由 stream_mode 参数控制。只要在 agent.stream() 时传入 stream_mode="custom"（或包含 "custom" 的列表），工具内部的 get_stream_writer() 就能正常工作。
为什么容易犯： 其他框架（如 FastAPI 的 StreamingResponse）需要先配置再使用，形成了思维定式。
如何避免： get_stream_writer() 是一个被动接收者，它不决定流是否开启，只是从当前上下文中获取 writer。流是否开启由 stream_mode 决定。
误区 3: 多模式组合时，chunk 的顺序是固定的
错误理解： 当 stream_mode=["updates", "custom"] 时，认为会先输出所有 updates，再输出所有 custom。
正确理解： chunk 按实际发生的时间顺序输出。如果在工具执行过程中先调用了 writer()，那么 custom chunk 会在 updates 之前输出。
为什么容易犯： 数组的顺序暗示了优先级，但实际输出顺序由事件的发生时间决定。
如何避免： 理解 stream 是事件驱动的，不是模式驱动的。每种模式只是对同一事件流的不同"视角"。
误区 4: messages 模式下 metadata 只有 langgraph_node
错误理解： 认为 metadata 字典只有一个键。
正确理解： metadata 是一个字典，langgraph_node 是其中一个关键字段。不同版本的 LangGraph 可能包含更多字段（如 thread_id、checkpoint_id 等），但 langgraph_node 是最稳定和常用的。
如何避免： 不要假设 metadata 只有 langgraph_node，使用时按需取值，不要硬编码索引。
误区 5: tools 节点不出现在 messages 模式流中
错误理解： 认为 messages 模式只输出 LLM 生成的 token，tools 节点（工具执行）不会出现在 messages 流中。
正确理解： tools 节点会出现在 messages 模式流中，但输出形式不同——不是逐 token 流，而是工具执行完后 ToolMessage 作为一次性完整消息发出。messages 模式流的是状态中 messages 通道的所有增量，包含 LLM 消息和工具消息。
为什么容易犯： 把 "messages = LLM 生成" 想当然了，忽略了工具返回结果也是 messages 通道的一部分。
如何避免： 记住 messages 模式流的对象是 state 里的 messages 通道，而不仅是 LLM 的 token。工具结果（ToolMessage）也是 messages 通道的内容。
误区 6: 多工具调用时，定义顺序决定串行还是并发
错误理解： 认为 tools=[get_weather, get_air_quality] 中工具的先后顺序决定它们是串行执行还是并发执行。
正确理解： 多工具是并行还是串行，由 LLM 单次返回的 tool_calls 数量决定，与工具定义顺序无关。LLM 一次返回多个 tool_calls 时，tools 节点在同一个 superstep 内处理整个列表（并行）；LLM 分两次返回时，需要两轮 ReAct 循环（串行）。
为什么容易犯： 把工具的"定义顺序"（一个 Python list）误当成"执行顺序"。
如何避免： 区分"定义顺序"（代码里的列表）和"执行顺序"（图流转的轮次）。执行轮次由 LLM 的 tool_calls 返回决定。
误区 7: writer 的内容会进入 messages 并被 LLM 看到
错误理解： 认为 writer("进度提示") 会作为 ToolMessage 添加到 messages 列表，回传给 LLM。
正确理解： writer(...) 写入的是 custom 流式通道，直接推送给用户，不会进 messages、不会进状态、不会被 LLM 看到。只有 return 返回值才被包装成 ToolMessage 进入 messages。这是"通知通道"与"数据通道"的分离（CQRS 变体）。
为什么容易犯： 看到工具函数里既有 writer(...) 又有 return，以为它们都进 messages。
如何避免： 记住两条通道：writer → 用户（进度通知），return → LLM（数据传递）。两者职责不同，不可混用。
误区 8: 流式输出中断 = 后端状态也被截断
错误理解： 用户网络断开导致流式中断，认为后端 state 里的消息也被截断了。
正确理解： 网络断开不一定会截断后端状态。流式传输中断 ≠ 生成中断，后端 LLM 通常还在继续生成，最终 messages 里的 AIMessage 是完整的。真正的恢复机制是 checkpoint（每个 superstep 后保存状态快照），而不是 message_id。
为什么容易犯： 混淆了"传输中断"和"生成中断"，以及 message_id（流式拼接）和 checkpoint（状态恢复）的职责。
如何避免： 区分 message_id（帮助拼接 token 碎块）和 checkpoint（帮助断点续传）。生成中的半句话无法精确续写，但可以通过 checkpoint 恢复已完成的 superstep。
误区 9: 判断流式是否存活可以看 metadata 的 token 计数
错误理解： 认为 metadata 里有一个 token 计数字段，通过它是否变化来判断流是否还活着。
正确理解： metadata 里没有 token 计数字段。判断流是否存活应该用心跳检测（每次收到事件重置定时器）或 asyncio.wait_for 超时机制。
为什么容易犯： 把"逐 token 输出"误当成"metadata 有 token 计数"。
如何避免： 存活检测用事件心跳（收到事件 = 心跳），或用整体超时包装。不要依赖不存在的 metadata 字段。
误区 10: content 和 tool_calls 可以同时存在
错误理解： 认为一条消息可以既有文本 content，又有 tool_calls。
正确理解： 对于 tool_call 类型的消息，content 返回空字符串 ""。因为 content 是纯文本部分，tool_calls 是结构化函数调用指令，两者语义互斥——模型要么"说"（生成文本），要么"做"（调用工具），不会同时。
为什么容易犯： 把 content_blocks（可以同时包含 text 和 tool_call 块）和 content（纯文本）混为一谈。
如何避免： 记住 content_blocks 是结构化列表（可以混装），content 是纯文本（对 tool_call 为空）。
