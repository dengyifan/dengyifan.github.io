Agent 执行流程与 superstep 概念

L1 概念层 + L2 原理层 2026-08-24

1. 整体架构：Agent 是什么

在 LangGraph 中，一个 Agent 本质上是一个状态图（StateGraph）——由多个节点（node）和边（edge）组成的有限状态机。每个节点执行一个具体操作（如调用 LLM、执行工具），边定义了节点之间的流转规则。

flowchart TD A[用户输入] --> B[model 节点] B -->|需要工具| C[tools 节点] B -->|直接回答| D[结束] C --> B classDef model fill:#fef0f0,stroke:#ea6f5a classDef tools fill:#f0f7fd,stroke:#3194d0 class B model class C tools

这是一个典型的 ReAct Agent 循环：模型调用 → 工具调用 → 模型调用 → ... → 最终回答。每一次从「模型调用」到「工具调用」再回到「模型调用」的完整轮次，就是一个 superstep。

2. superstep：流式粒度的最小单位

superstep 是理解 LangGraph 流式输出的核心概念。它不是一个 API 参数，而是 Agent 执行流程中的天然步骤。

2.1 什么是 superstep？

一个 superstep 包含以下完整过程：

  1. 从当前 state 中读取输入
  2. 执行一个节点（如 model 或 tools）
  3. 将输出写回 state
  4. 触发 checkpoint（如果配置了 checkpointer）

换句话说，一个 superstep = 一个节点的完整执行周期。

关键洞察

superstep 是 LangGraph 执行模型中的原子单位。每个 superstep 执行完毕后，state 被更新，checkpoint 被保存。这也是为什么 stream_mode="updates" 会按 superstep 粒度输出事件——因为每个 superstep 完成后，state 才真正发生变化。

2.2 用代码理解 superstep

from langchain.agents import create_agent
from langchain_openai import ChatOpenAI
import os

def get_weather(city: str) -> str:
    """Get the weather for a city."""
    return f"The weather in {city} is sunny."

model = ChatOpenAI(
    base_url=os.getenv("LOCAL_AI_API_URL"),
    api_key=os.getenv("LOCAL_AI_API_KEY"),
    temperature=0.0,
    model="deepseek-v4-pro",
)

agent = create_agent(model, tools=[get_weather])

# stream_mode="updates" 按 superstep 输出
for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "What is the weather in SF?"}]},
    stream_mode="updates"
):
    for step, data in chunk.items():
        print(f"Step {step}")
        print(f"content: {data['messages'][-1].content}")

当你运行这段代码，你会看到两个 superstep：

  1. Step model — 模型决定调用工具 get_weather
  2. Step tools — 工具执行并返回天气结果
  3. Step model — 模型基于工具结果生成最终回答

每个 Step model 或 Step tools 就是一个 superstep 的输出。

3. Agent 执行流程详解

3.1 时序图

3.2 条件边的判断逻辑

条件边决定 Agent 下一步去向。它的判断逻辑非常简洁：

def route_after_agent(state):
    """条件边路由函数：根据最后一条消息是否有 tool_calls 决定去向"""
    last_message = state["messages"][-1]
    if hasattr(last_message, "tool_calls") and last_message.tool_calls:
        return "tools"       # 有工具调用 → 去 tools 节点
    else:
        return "__end__"     # 无工具调用 → 结束

核心判断：messages[-1].tool_calls 是否非空。这是整个 ReAct 循环的"方向盘"——它决定了 Agent 是继续调用工具还是直接结束。

与 deep-grill 的对照

在 deep-grill 追问中，学习者能复述图结构（"有 tool_calls → tools 节点，无 tool_calls → END"），但被要求写伪代码时遗漏了具体判断逻辑。关键是：条件边是一条边，由路由函数动态决定去向，两个分支不算独立边。

3.3 图结构总结：节点、边与 State

create_agent 生成的完整 LangGraph 图包含：

元素数量说明
节点2 个agent 节点（调用 LLM）和 tools 节点（执行工具）
边3 条START→agent（入口边）、agent→tools→agent（条件边+循环边）、agent→END（条件边，条件边是一条边，两个分支不算独立边）
State 关键字段messages消息列表，是 State 中最重要的（也是最稳定）字段。没有"下一个步骤节点"字段——下一步由条件边的路由函数实时计算
常见误区

很多人会误以为 State 中有"下一个步骤节点"字段（如 next_node），实际上没有。Agent 的下一步去向由条件边的路由函数根据 state 内容实时计算，而不是预先存储在 state 中。这是 LangGraph 的"无状态路由"设计。

3.4 多工具调用的并发与串行语义

如果 LLM 一次返回多个 tool_calls（如 [get_weather, get_air_quality]），tools 节点如何处理？

场景LLM 返回图流转工具执行方式
一次返回多个工具[weather, aq]agent→tools→agent（1 轮）并行（同一节点内执行所有工具）
分两次返回先 [weather] 再 [aq]agent→tools→agent→tools→agent（2 轮）串行（需两次经过 agent 节点）

关键理解：多工具是并行还是串行，不由工具定义顺序决定，而是由 LLM 单次返回的 tool_calls 数量决定。ToolNode 收到 AIMessage 后遍历 tool_calls 列表，对每个 tool_call 执行工具并包装成 ToolMessage。tools 节点只执行一次，处理整个列表。

与 deep-grill 的对照

在 deep-grill 中，学习者认为"定义顺序决定串行/并发"，这是错误理解。真正的决定因素是：LLM 在一次推理中返回了几个 tool_calls。如果 LLM 需要先执行一个工具、看到结果后再决定是否执行下一个，那就是两轮 ReAct 循环（串行）。

3.5 每个 superstep 内部发生了什么

阶段操作说明
1. 读取 state从 checkpointer 或初始 state 读取确保节点拿到最新状态
2. 执行节点调用 node 函数（如 LLM 推理）节点可能是同步或异步的
3. 更新 state通过 reducer 合并输出到 statemessages 的 reducer 是 add_messages
4. 保存 checkpoint将新 state 写入 checkpointer仅在配置了 checkpointer 时执行
5. 发出事件通知 stream 消费者具体内容取决于 stream_mode

4. stream 方法的调用方式

4.1 同步 vs 异步

方法类型适用场景
agent.stream()同步生成器脚本、CLI 工具、简单 Web 应用
agent.astream()异步生成器FastAPI、异步 Web 框架
 
# 同步版本
for chunk in agent.stream(input, stream_mode="updates"):
    process(chunk)

# 异步版本
async for chunk in agent.astream(input, stream_mode="updates"):
    await process(chunk)
从 Java 视角看

Java 中的 Stream<T> 是惰性求值的管道，而 Python 的 agent.stream() 返回的是 生成器（generator）。两者的核心区别：

  • Java Stream：数据源已存在，只是延迟计算
  • Python Generator：数据按需产生，每次 yield 后才会有下一个值

这意味着 LangGraph 的 stream 是真正的实时流式——Agent 一边执行，一边产出结果。不是等全部执行完再一次性返回。

// Java 等价思维：Spring WebFlux 的 Flux<T>
Flux<String> stream = Flux.create(sink -> {
    // 每个 superstep 调用 sink.next(data)
    sink.next("superstep 1 output");
    sink.next("superstep 2 output");
    sink.complete();
});

4.2 stream_mode 参数

stream_mode 决定了流式输出的粒度和内容。它支持以下值：

模式粒度输出内容典型场景
"updates"superstep 级别每个步骤的完整 state 更新显示 Agent 执行步骤
"messages"token 级别每个 LLM token + metadata打字机效果
"custom"自定义工具内部通过 writer 输出进度提示、中间状态
"values"superstep 级别每个步骤后的完整 state状态快照监控
"debug"细粒度完整执行图追踪开发调试
最佳实践

生产环境最常见的选择：stream_mode=["updates", "custom"] 组合。updates 提供步骤级别的结构化输出，custom 提供工具内部的实时进度反馈。

5. 设计原理追问

5.1 为什么 LangGraph 选择按 superstep 粒度输出，而不是更细或更粗？

superstep 是 state 变更的最小单位。在 LangGraph 的设计中，state 只在 superstep 完成后才更新——这意味着：

  • 更细（如每次函数调用）：没有意义，因为 state 没变
  • 更粗（如整个 Agent 执行完）：失去了流式的意义，用户还是要等

所以 superstep 是自然的粒度选择——它恰好对应 state 的变更点。

5.2 这个设计有什么代价？

代价是：用户无法在 superstep 内部看到进度。比如 LLM 正在生成 token 的过程中，updates 模式不会输出任何内容，直到整个生成完成。这也是为什么需要 `messages` 模式——它在 token 级别做补充。

5.3 如果是你，会怎么改进？

一个可能的改进方向是支持 progress 回调——在 superstep 内部（如 LLM 生成过程中）定期回调一个进度函数，不需要等到整个 superstep 结束。这本质上是 `messages` 模式的另一种表达方式，但更灵活。

6. 费曼自检：用大白话讲一遍

想象一个餐厅厨房。顾客点了一道菜（用户输入），厨师（Agent）开始工作：

  • 第一步：看菜单决定做什么菜（model 节点）
  • 第二步：切菜炒菜（tools 节点）
  • 第三步：装盘点缀（model 节点）

每完成一步，厨师就喊一声"好了！"——这就是 superstep。`stream_mode="updates"` 就是在厨房门口装了个喇叭，每次厨师喊"好了"的时候就广播出去。

而 `stream_mode="messages"` 则是把摄像头对准厨师的手，每切一刀、每翻一下锅都直播出去——这就是 token 级别的流式。
