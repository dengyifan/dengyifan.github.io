四种 stream_mode 详解

L2 原理层 + L3 源码层 2026-08-24

1. 总览：四种模式的对比

LangGraph 的 agent.stream() 通过 stream_mode 参数控制输出粒度。本课深入讲解最常用的四种模式。

2. updates 模式：按步骤流式输出

2.1 原理

updates 是最常用的模式。每个 superstep 完成后，它发出一个事件，内容是该步骤对 state 的更新。

关键点：每次迭代返回一个 字典，键是节点名称（如 "model" 或 "tools"），值是该节点对 state 的更新内容。

2.2 示例代码

# stream_mode="updates" — 按步骤流式输出
import os
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI

def get_weather(city: str) -> str:
    """Get the weather for a city."""
    return f"The weather in {city} is sunny."

model = ChatOpenAI(
    base_url=os.getenv("LOCAL_AI_API_URL"),
    api_key=os.getenv("LOCAL_AI_API_KEY"),
    temperature=0.0,
    model="deepseek-v4-pro",
)

agent = create_agent(model, tools=[get_weather])

for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "What is the weather in SF?"}]},
    stream_mode="updates"
):
    for step, data in chunk.items():
        print(f"Step {step}")
        print(f"content: {data['messages'][-1].content}")

2.3 输出结构分析

每个 chunk 的结构是：

# chunk 是 dict，键为节点名
{
    "model": {
        "messages": [AIMessage(...)]  # 模型新增的消息
    }
}
# 或
{
    "tools": {
        "messages": [ToolMessage(...)]  # 工具新增的消息
    }
}
关键点

chunk.items() 遍历的是节点名，data['messages'][-1] 取的是该节点新增的最后一条消息。因为一个 superstep 中，节点的输出会通过 add_messages reducer 追加到 state。

2.4 两种 content 取法：content vs content_blocks

在示例代码中，你可能会看到两种取内容的方式：

# 方式一：直接取 content（字符串）
print(f"content: {data['messages'][-1].content}")

# 方式二：取 content_blocks（结构化列表）
print(f"content: {data['messages'][-1].content_blocks}")

它们的区别：

属性类型内容适用场景
.contentstr纯文本内容只需要文本时
.content_blockslist结构化块（文本块 + 工具调用块）需要区分文本和工具调用时

2.5 为什么 tool_call 时 content 返回空字符串？

这是一个经常被追问的设计细节。当消息包含 tool_call 时：

# content_blocks 包含结构化信息
[
    {"type": "tool_call", "name": "get_weather", "args": {"city": "SF"}, "id": "call_xxx"}
]

# content 返回空字符串 ""
""

原因：content 是消息的纯文本部分，而 tool_call 不是文本——它是结构化的函数调用指令。两者在语义上互斥：

  • content = 模型想"说"的文本（自然语言）
  • tool_calls = 模型想"做"的动作（函数调用）

当模型决定调用工具时，它不会同时生成文本——所以 content 为空。这就是为什么在 ex-stream-6-1-agent-process.py 中，用 .content 取 model 节点的输出时，step:model 打印为空——因为此时模型返回的是 tool_call，不是文本。

与 deep-grill 的对照

在 deep-grill 追问中，学习者能复述 content_blocks 的内容结构，但被问"content 会返回什么"时，回答的是 content_blocks 的内容而非 content 的值。关键是理解 content 和 tool_calls 是互斥的——一条消息要么有文本内容，要么有工具调用，不会同时有。

3. messages 模式：按 Token 流式输出

3.1 原理

messages 模式实现了打字机效果——在 LLM 逐 token 生成时实时输出。这是流式体验最强的模式。

关键点：每次迭代返回一个 (token, metadata) 元组。token 是 AIMessageChunk 或 ToolMessageChunk，metadata 包含 langgraph_node 等字段。

3.2 示例代码

# stream_mode="messages" — 按 Token 流式输出
import os
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI

def get_weather(city: str) -> str:
    """Get the weather for a city."""
    return f"The weather in {city} is sunny."

model = ChatOpenAI(
    base_url=os.getenv("LOCAL_AI_API_URL"),
    api_key=os.getenv("LOCAL_AI_API_KEY"),
    temperature=0.0,
    model="deepseek-v4-pro",
)

agent = create_agent(model, tools=[get_weather])

for token, metadata in agent.stream(
    {"messages": [{"role": "user", "content": "What is the weather in SF?"}]},
    stream_mode="messages"
):
    print(f"node: {metadata['langgraph_node']}")
    print(f"content: {token.content_blocks}")
    print("\n")

3.3 metadata["langgraph_node"] 的来源

langgraph_node 是 LangGraph 在发出每个 token 事件时自动附加的元数据，用于标识当前 token 来自哪个节点。

langgraph_node 值含义
"model"来自 LLM 模型节点的 token
"tools"来自工具执行节点的 token

这个字段的核心价值：在多节点 Agent 中，你需要知道每个 token 是模型生成的，还是工具返回的。例如，在 UI 上，模型生成的 token 显示在对话框左侧，工具返回的内容显示在右侧。

源码位置

metadata["langgraph_node"] 由 LangGraph 的 Pregel 执行引擎在 _emit 或类似方法中注入。具体在 langgraph/pregel/main.py 中，当 stream_mode 包含 "messages" 时，节点执行过程中产生的每个 chunk 都会被包装并附加上节点名。

3.4 tools 节点在 messages 模式中的输出

一个常见误区是认为"tools 节点不出现在 messages 模式流中"。实际上 tools 节点会出现，但输出形式不同：

节点输出形式说明
model逐 token 流（AIMessageChunk）打字机效果，每次输出一个 token 增量
tools一次性完整 ToolMessage工具执行完后，整个结果作为一条完整消息发出

messages 模式流的是状态中 messages 通道的所有增量，包含 LLM 消息和工具消息。区别在于：model 节点内部是流式生成（逐 token），tools 节点是执行完成后一次性输出。

updates 与 messages 在工具节点输出上的本质区别

维度updatesmessages
tools 节点是否出现✅ 是✅ 是
工具结果切分粒度整个节点更新（dict 结构）一条完整 ToolMessage
返回结构{节点名: {messages:[...]}}(消息对象, metadata) 元组
model 节点输出整步文本（一次性）逐 token

简单说：updates 把整个 superstep 的输出打包成一个 dict，messages 把每条消息（包括工具消息）都单独拆出来流式输出。

3.5 从 messages 流中判断消息边界

messages 模式输出的是 token 碎块，如何判断一条消息何时结束？有以下三种方式：

方式依据可靠性
AIMessageChunk.id（message_id）同一轮 LLM 调用拆出的所有 token 碎块共享同一个 id，id 变化说明新消息开始⭐ 最可靠
metadata["langgraph_node"] 变化model→tools→model 的节点切换标志消息边界⭐⭐ 辅助判断
finish_reason 标记LLM 流式最后 chunk 的 response_metadata 含 finish_reason⭐⭐ 补充验证
 
# 通过 message_id 变化判断消息边界
current_msg_id = None
full_message = ""

for token, metadata in agent.stream(input, stream_mode="messages"):
    if metadata["langgraph_node"] != "model":
        continue  # 只处理 model 节点的输出

    msg_id = token.id  # 同一条消息的所有 token 共享同一个 id
    if msg_id != current_msg_id:
        if current_msg_id is not None:
            print(f"【完整消息】{full_message}")
        current_msg_id = msg_id
        full_message = ""

    full_message += token.content  # 拼接 token
与 deep-grill 的对照

在 deep-grill 追问中，学习者不清楚如何从 token 碎块中判断消息边界。关键是理解 AIMessageChunk.id 是 message_id——同一条消息的所有 token 碎块共享同一个 id，id 变化=新消息开始。推荐方式 1（message_id）+ 方式 3（finish_reason）结合使用。

4. custom 模式：自定义流式输出

4.1 原理

custom 模式允许你在工具函数内部通过 get_stream_writer() 获取一个 writer，手动往流中写入任意内容。这适合输出进度提示、中间状态等工具执行过程中的信息。

关键点：get_stream_writer() 返回的是一个可调用对象，你直接调用它就能写入流。

4.2 示例代码

# stream_mode="custom" — 自定义流式输出
import os
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI
from langgraph.config import get_stream_writer

def get_weather(city: str) -> str:
    """Get the weather for a city."""
    writer = get_stream_writer()
    writer(f"Looking up data for city: {city}")
    writer(f"Acquired data for city: {city}")
    return f"It's always sunny in {city}."

model = ChatOpenAI(
    base_url=os.getenv("LOCAL_AI_API_URL"),
    api_key=os.getenv("LOCAL_AI_API_KEY"),
    temperature=0.0,
    model="deepseek-v4-pro",
)

agent = create_agent(model, tools=[get_weather])

for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "what is the weather in SF?"}]},
    stream_mode="custom"
):
    print(chunk)

4.3 get_stream_writer() 的工作机制

get_stream_writer() 是理解 custom 模式的核心。它的工作方式：

  1. 工具函数在执行时，LangGraph 会在当前上下文中设置一个 StreamWriter
  2. get_stream_writer() 从这个上下文中取出 writer
  3. 调用 writer(content) 时，内容被写入 custom 流
  4. 消费者通过 stream_mode="custom" 收到这些内容
sequenceDiagram participant Consumer participant Agent participant Tool participant Context Consumer->>Agent: stream 请求 Agent->>Context: 设置 StreamWriter Agent->>Tool: 执行工具函数 Tool->>Context: get_stream_writer Context-->>Tool: 返回 writer Tool->>Agent: 写入进度提示 Agent-->>Consumer: custom 事件 Tool->>Agent: 写入中间状态 Agent-->>Consumer: custom 事件 Tool-->>Agent: 返回工具结果
线程安全

get_stream_writer() 基于 Python 的 contextvars 实现，这意味着它是线程安全和异步安全的。即使多个工具并行执行，每个工具拿到的 writer 也指向正确的流。这是 Python 中处理"隐式上下文"的标准方案。

4.4 writer 与 return 的职责分离（关键设计原则）

这是 custom 模式最容易混淆的核心概念。writer(...) 和 return 是两条完全不同的通道，职责不能混用：

内容去向是否进 messages是否被 LLM 看到
writer("...")custom 流通道 → 用户❌ 否❌ 否
return 返回值包装成 ToolMessage → messages✅ 是✅ 是

核心理解：

  • writer(...) 写入的是流式输出通道，直接作为 stream_mode="custom" 的 chunk 实时推送给用户。它不会进状态、不会进 messages、不会被 LLM 看到。它的唯一目的是让用户了解执行进度。
  • return 返回值才被包装成 ToolMessage 添加到 messages 列表，回传给 LLM 用于后续推理。
两个方向的错误后果

错误方向 1（把 writer 当 return）：如果只 writer("结果") 而不 return，LLM 就收不到工具返回信息，无法进行后续推理，Agent 会退化。

错误方向 2（把 return 当 writer）：如果只 return 不 writer，用户看不到进度提示，但功能正常。

正确做法：两者各司其职——writer 通知进度，return 传递数据。

为什么设计者要让 writer 不进状态？

这是"关注点分离"设计原则的体现（CQRS 变体——写操作与通知操作走不同通道）：

  • 避免污染状态：进度提示与推理无关，进状态会污染推理上下文
  • 控制成本：进 messages 会增加上下文窗口长度 → token 成本增加
  • 保证输出质量：无关信息可能误导 LLM → 输出质量下降

类似的架构模式：Redux/Vuex 的 action dispatch vs devtools 监听；Kafka 的消息写入 vs webhook 推送；数据库 trigger 的数据变更 vs 审计日志。

从 Java 视角看

get_stream_writer() 的机制类似于 Java 的 ThreadLocal，但更优雅：

  • Java ThreadLocal：线程级隔离，但异步场景（CompletableFuture、虚拟线程）容易串
  • Python contextvars：上下文级隔离，自动在 async/await 和线程间正确传递

这是 Python 生态在处理"隐式上下文传递"上的一个优势——Java 中要做到同样效果，通常需要显式传参或使用 Reactor Context（WebFlux）这样的机制。

5. values 模式：整个状态快照

5.1 原理

values 模式在每个 superstep 后，输出完整的 state 快照，而不是仅输出增量。

与 updates 的区别：

  • updates：只输出本次变更（增量）
  • values：输出完整状态（全量）
# values 模式
for state in agent.stream(
    {"messages": [...]},
    stream_mode="values"
):
    # state 是完整的消息列表快照
    print(state["messages"])
注意

values 模式输出全量状态，在消息历史很长时会显著增加传输量。生产环境通常用 updates 代替，除非确实需要监控完整状态。

6. debug 模式：完整执行追踪

debug 模式输出最细粒度的执行信息，包括每个任务的开始、结束、状态变化等。它主要用于开发调试，因为输出量大且格式不稳定。

# debug 模式（开发调试用）
for event in agent.stream(
    {"messages": [...]},
    stream_mode="debug"
):
    print(event)

7. 流式中的异常处理

7.1 tools 节点异常：handle_tool_errors

如果 tools 节点执行过程中抛出异常，默认行为是：异常向上传播，Agent 流程中断。但 LangGraph 提供了两级容错机制：

策略行为适用场景
默认抛异常，流程中断快速失败
handle_tool_errors=True捕获异常 → 包装成 ToolMessage → 回传给 LLM 恢复LLM 感知并处理失败
retry_policy节点级自动重试 N 次网络抖动等临时故障

handle_tool_errors=True 的精确行为

当工具抛出异常时，异常信息会被包装成以下格式的 ToolMessage：

ToolMessage(
    content="Error: ValueError('city not found')",
    tool_call_id="call_xxx",  # 与原始 tool_call.id 匹配
    name="get_weather"
)

关键点：

  • tool_call_id 与原始 tool_call.id 匹配，让 LLM 知道对应哪个工具调用
  • content 是完整错误信息
  • LLM 看到错误后可以尝试重试、换参数、或向用户道歉

7.2 静默失败：空字符串的风险

如果工具内 API 调用没有抛异常，但返回了空字符串 ""，LLM 看到 ToolMessage(content="") 是一个模糊信号：

  • 高概率：LLM 可能编造结果（幻觉）
  • 中概率：LLM 说"信息暂时不可用"
  • 低概率：LLM 说"获取失败"

这是静默失败的典型场景。正确设计：工具返回空时显式返回 "ERROR: 天气数据查询失败"，让 LLM 明确知道是失败。

与 deep-grill 的对照

在 deep-grill 追问中，学习者对 handle_tool_errors 的具体格式和静默失败的风险有认识缺口。关键补充：tool_call_id 匹配是让 LLM 理解"哪个工具失败了"的核心机制；空字符串返回是"静默失败"的典型场景，需要显式标记错误。

8. 设计原理追问

8.1 为什么要有 5 种模式，而不是一种万能模式？

因为不同消费者需要不同粒度的数据：

  • UI 打字机效果需要 token 级（messages）
  • 步骤进度条需要 superstep 级（updates）
  • 工具内部进度需要自定义（custom）
  • 调试需要完整追踪（debug）

如果只有一种万能模式（如全部输出 token 级），那么步骤进度条消费者就必须自己聚合 token，增加复杂度。分离粒度是关注点分离原则的体现。

8.2 这个设计有什么代价？

代价是学习成本和模式选择困惑。新手容易选错模式。但 LangGraph 通过多模式组合（下一步讲解）部分缓解了这个问题——你可以同时订阅多种模式，按需消费。

8.3 如果是你，会怎么改进？

一个可能的改进是提供声明式的模式组合——例如用 StreamSpec 对象代替字符串，支持更细粒度的过滤（如只订阅某个节点的 messages）。目前 LangGraph 已经支持列表形式的组合，但过滤能力还需要消费者自己处理。

9. 费曼自检

用大白话说四种模式：

  • updates：厨师每做完一道菜，把这道菜端出来给你看
  • messages：直播厨师切菜，每一刀都能看到
  • custom：厨师自己拿对讲机，想说什么说什么
  • values：每做完一道菜，把整桌菜都拍张照发给你
