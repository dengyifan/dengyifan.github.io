1. 多模式组合：同时订阅多种流

1.1 原理

当 stream_mode 被设为一个列表时，LangGraph 会同时启用多种模式。每次迭代返回一个 (stream_mode, chunk) 元组，第一个元素标识当前 chunk 属于哪种模式。

关键区别：单一模式 vs 列表模式

参数形式返回值示例
stream_mode="updates"（字符串）裸 chunk（直接是 dict）{"model": {...}}
stream_mode=["updates", "custom"]（列表）(mode, chunk) 元组("updates", {"model": {...}})

这就是为什么多模式消费端必须用 for stream_mode, chunk in agent.stream(...) 解包——因为返回值从裸 chunk 变成了元组。如果忘了这个区别，直接用单一模式的写法消费多模式流，会得到 TypeError。

常见错误

当 stream_mode 是列表时，chunk 是 (mode, chunk) 元组。如果对 custom 模式的 chunk（字符串）做 chunk["messages"] 操作，会抛出 TypeError: string indices must be integers, not 'str'。必须先按 stream_mode 分支，再按各自类型处理。

1.2 示例代码

# stream_mode=["updates", "custom"] — 多模式组合
import os
from langchain.agents import create_agent
from langchain_openai import ChatOpenAI
from langgraph.config import get_stream_writer

def get_weather(city: str) -> str:
    """Get the weather for a city."""
    writer = get_stream_writer()
    writer(f"Looking up data for city: {city}")
    writer(f"Acquired data for city: {city}")
    return f"It's always sunny in {city}."

model = ChatOpenAI(
    base_url=os.getenv("LOCAL_AI_API_URL"),
    api_key=os.getenv("LOCAL_AI_API_KEY"),
    temperature=0.0,
    model="deepseek-v4-pro",
)

agent = create_agent(model, tools=[get_weather])

for stream_mode, chunk in agent.stream(
    {"messages": [{"role": "user", "content": "what is the weather in SF?"}]},
    stream_mode=["updates", "custom"]
):
    print(f"stream_mode: {stream_mode}")
    print(f"content: {chunk}")
    print("\n")

1.3 输出序列分析

假设 Agent 执行：model → tools → model，则输出顺序为：

# 输出顺序（按事件发生时间）
("updates", {"model": {...}})     # superstep 1: 模型决定调用工具
("custom", "Looking up data...")  # 工具执行中：自定义进度
("custom", "Acquired data...")    # 工具执行中：自定义进度
("updates", {"tools": {...}})     # superstep 2: 工具执行完成
("updates", {"model": {...}})     # superstep 3: 模型生成最终回答
关键点

chunk 按事件发生的时间顺序输出，不是按模式的顺序。custom 模式的 chunk 可以在 updates 之间任意位置出现，取决于工具何时调用 writer()。

1.4 消费端代码模式

# 推荐：按模式分发处理
for stream_mode, chunk in agent.stream(
    input,
    stream_mode=["updates", "custom"]
):
    if stream_mode == "updates":
        handle_updates(chunk)
    elif stream_mode == "custom":
        handle_custom(chunk)
从 Java 视角看

多模式组合的 (mode, chunk) 元组类似于 Java 的 Union type 或 sealed class 模式：

// Java 等价思维
sealed interface StreamEvent {
    record Updates(Map<String, StateUpdate> data) implements StreamEvent {}
    record Custom(String data) implements StreamEvent {}
}

// 消费
for (StreamEvent event : stream) {
    switch (event) {
        case Updates(var data) -> handleUpdates(data);
        case Custom(var data) -> handleCustom(data);
    }
}

Python 的选择是结构化的（用元组 + 字符串标签），Java 的选择是类型化的（用 sealed class）。各有优劣：Python 更灵活但缺乏编译期检查，Java 更安全但更啰嗦。

2. 生产环境最佳实践

2.1 常见组合方案

组合适用场景说明
["updates"]简单步骤展示最常用，适合不需要实时 token 的场景
["messages"]打字机效果适合需要实时显示 LLM 输出的场景
["updates", "custom"]步骤 + 工具进度生产环境最推荐：兼顾结构化和实时性
["updates", "messages"]全功能同时展示步骤和 token，但输出量大
["updates", "messages", "custom"]极致体验所有模式全部开启，需注意消费端复杂度
生产环境推荐

stream_mode=["updates", "custom"] 是生产环境的最佳平衡点：

  • updates 提供步骤级别的结构化输出（用于 UI 步骤展示）
  • custom 提供工具内部的实时进度反馈（用于 loading 动画）
  • 不需要 messages 如果你不需要打字机效果

2.2 生产环境注意事项

生产环境关注点
  • 输出量控制：不要同时订阅 3 种以上的模式，输出量会急剧膨胀
  • 前端消费：通过 SSE（Server-Sent Events）将 stream 转发到前端，每个 chunk 作为一个 SSE 事件
  • 错误处理：工具内部的 writer 调用如果异常，默认不会中断 Agent 执行，但流会中断
  • 超时管理：长时间无输出的流需要前端做超时处理（如 30 秒无输出则显示"处理中..."）
  • checkpointer 选择：流式输出 + checkpointer 会增加延迟，PostgresSaver 的写入延迟高于 MemorySaver

2.3 多模式性能开销

同时开启 messages + updates 会产生以下问题：

开销类型说明
内容重复同一段文本在 messages 中逐 token 流一次，在 updates 中完整输出一次——用户看到两次相同内容
内存开销每种模式需要独立缓冲，三模式全开时内存占用翻倍
序列化开销同一文本被序列化两次（messages 和 updates），CPU 浪费
网络传输双倍数据量通过 SSE 传输
前端渲染复杂度需要去重逻辑，避免重复渲染

优化方案：如果既需要打字机效果（messages），又需要后端审计（需要记录完整步骤），推荐"后端聚合"方案：

# 方案：前端用 messages + custom，后端从 messages 流拼接完整消息写日志
# 不开启 updates 模式，避免重复传输

full_message = ""
current_msg_id = None

for stream_mode, chunk in agent.stream(input, stream_mode=["messages", "custom"]):
    if stream_mode == "messages":
        msg_id = chunk.id
        if msg_id != current_msg_id:
            if current_msg_id is not None:
                log_to_audit(full_message)  # 完整消息写入审计日志
            current_msg_id = msg_id
            full_message = ""
        full_message += chunk.content
        yield chunk  # 透传给前端打字机
    elif stream_mode == "custom":
        yield chunk  # 透传给前端进度提示
与 deep-grill 的对照

在 deep-grill 追问中，学习者对多模式性能开销认识不足，也不清楚如何在既要打字机又要审计的场景下优化。关键是：审计用 updates 虽然方便但浪费，更好的做法是从 messages 流中通过 message_id 拼接完整消息，一举两得。

2.4 流式可观测性：心跳与超时

生产环境中如何知道流式输出是否还活着？

import asyncio

async def stream_with_timeout(agent, input, timeout=30):
    """带超时检测的流式消费"""
    async for chunk in agent.astream(input, stream_mode=["updates", "custom"]):
        yield chunk  # 每次收到事件 = 心跳，重置超时

# 或使用 asyncio.wait_for 包装整个流
try:
    async for chunk in asyncio.wait_for(
        agent.astream(input, stream_mode=["updates", "custom"]),
        timeout=60
    ).__aiter__():
        yield chunk
except asyncio.TimeoutError:
    yield ("custom", "请求超时，请稍后重试")

关键点：

  • metadata 里没有 token 计数字段——不能用它来检测存活
  • 正确做法：每次收到事件重置定时器（心跳模式），或使用 asyncio.wait_for 整体超时
  • 如果工具执行了 60 秒还没返回，writer("Looking up...") 在阻塞前已发出，前端会收到这个 custom 事件然后卡住

2.5 流式中断与恢复

用户通过 stream_mode="messages" 看到打字机效果，在 LLM 生成到一半时网络断开：

问题答案
后端状态里的消息是截断的还是完整的？通常是完整的。流式传输中断 ≠ 生成中断，后端 LLM 通常还在继续生成，最终 messages 里的 AIMessage 是完整的
能否从断点继续？不能从 token 级别断点续写。可以通过 checkpointer 恢复整个 superstep 的状态，但生成中的那半句话无法精确续写
如何避免 token 浪费？设置 max_tokens 限制；心跳+断线检测 → 立即 cancel LLM 调用；缓存相同问题；检查点+重放避免从头重新生成

message_id 和 checkpoint 的本质区别：

概念作用持久化
AIMessageChunk.id（message_id）流式识别符，帮助拼接同一条消息的 token 碎块❌ 不持久化
checkpoint状态恢复点，每个 superstep 后保存完整 state 快照✅ 持久化

两者职责完全不同：id 是流式拼接的"胶水"，checkpoint 是断点续传的"存档"。不能互相替代。

与 deep-grill 的对照

在 deep-grill 追问中，学习者混淆了 message_id 和 checkpoint 机制，错误认为"可以通过 message_id 从断点输出"。正确理解：网络断开不一定会截断后端状态；message_id 只用于拼接，不能用于恢复；checkpoint 在每个 superstep 后保存，但生成中的半句话无法精确续写。

3. 边界条件与坑

3.1 坑 1：custom 模式下忘记 stream_mode 参数

# 错误：工具内调用了 writer，但 stream_mode 没包含 "custom"
for chunk in agent.stream(input, stream_mode="updates"):
    # 永远不会收到 custom 内容！
    pass

# 正确：stream_mode 必须包含 "custom"
for chunk in agent.stream(input, stream_mode=["updates", "custom"]):
    pass

3.2 坑 2：get_stream_writer() 在工具外调用

# 错误：在工具外调用 get_stream_writer()
writer = get_stream_writer()  # RuntimeError: 没有活跃的流上下文

# 正确：只在工具函数内调用
def my_tool(x: str) -> str:
    writer = get_stream_writer()  # OK
    writer("progress")
    return "result"

3.3 坑 3：messages 模式下 metadata 的不稳定字段

# 不推荐：直接访问 metadata 的其他字段
for token, metadata in agent.stream(input, stream_mode="messages"):
    node = metadata["langgraph_node"]  # ✅ 稳定字段
    # thread_id = metadata["thread_id"]  # ❌ 可能不存在

# 推荐：使用 .get() 防御性访问
for token, metadata in agent.stream(input, stream_mode="messages"):
    node = metadata.get("langgraph_node")

3.4 坑 4：多模式组合时消费端未区分模式

# 错误：未区分模式，直接处理 chunk
for stream_mode, chunk in agent.stream(input, stream_mode=["updates", "custom"]):
    print(chunk["messages"])  # custom 的 chunk 不是 dict，会报错！

# 正确：按模式分发
for stream_mode, chunk in agent.stream(input, stream_mode=["updates", "custom"]):
    if stream_mode == "updates":
        print(chunk["messages"])
    elif stream_mode == "custom":
        print(chunk)

4. 设计原理追问

4.1 为什么选择 (mode, chunk) 元组而不是按 mode 分组输出？

如果按 mode 分组输出（如先输出所有 updates，再输出所有 custom），那么：

  • 所有 custom 内容会延迟到 Agent 执行完后才输出，失去了"实时进度"的意义
  • 前端无法交错展示步骤和进度

按时间顺序输出保证了时序正确性——用户看到的内容顺序就是实际发生的顺序。

4.2 这个设计有什么代价？

代价是消费端需要显式分发。每次迭代都要检查 mode 字符串，增加了消费端代码复杂度。如果 LangGraph 未来能提供类型安全的 stream 消费 API（如 typed stream），可以降低这个代价。

4.3 如果是你，会怎么改进？

一个方向是提供 回调式 API 作为生成器 API 的补充：

# 理想 API（回调式）
agent.stream(
    input,
    on_updates=lambda chunk: handle_updates(chunk),
    on_custom=lambda chunk: handle_custom(chunk),
    on_messages=lambda token, meta: handle_messages(token, meta),
)

这样消费端不需要自己做分发，每种模式有独立的回调。但生成器模式更符合 Python 生态习惯，两种 API 可以共存。

5. 费曼自检

多模式组合就像同时开了多个监控摄像头：

  • updates = 厨房门口监控（看到厨师进进出出）
  • custom = 厨师身上的 GoPro（看到厨师视角）
  • 组合 = 同时看两个画面，但画面是实时交错的，不是先放完一个再放另一个

本课 Deep-Grill 就绪度

  • 能解释 (mode, chunk) 元组的输出顺序规则（对应 interviewer 角度）
  • 能区分单一模式（裸 chunk）和多模式（元组）的返回结构差异（对应 interviewer 角度）
  • 能说出多种组合方案的适用场景（对应 architect 角度）
  • 能分析多模式组合的性能开销，并给出"后端聚合"优化方案（对应 architect 角度）
  • 能解释流式存活检测（心跳/超时）而非依赖 metadata 的 token 计数（对应 incident responder 角度）
  • 能区分 message_id（流式拼接）和 checkpoint（断点续传）的职责（对应 incident responder 角度）
  • 能识别 4 个常见坑并给出修复方案（对应 code reviewer 角度）
  • 能解释为什么多模式组合要按时间顺序输出而非按模式分组（对应 architect 角度）
  • 能用大白话讲清多模式组合（对应 instructor 角度）
  • 能排查 custom 模式不生效的根因（对应 incident responder 角度）
