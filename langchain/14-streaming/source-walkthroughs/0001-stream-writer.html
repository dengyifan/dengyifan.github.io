3. 逐段分析

3.1 get_stream_writer() — langgraph/config.py

# 伪代码重构（基于 contextvars 实现原理）
import contextvars

# 全局 contextvar，存储 StreamWriter 实例
STREAM_WRITER_KEY: contextvars.ContextVar = contextvars.ContextVar(
    "stream_writer", default=None
)

def get_stream_writer() -> callable:
    """获取当前上下文的 StreamWriter。

    工具函数内部调用此函数，获取 writer 可调用对象。
    通过 writer(content) 将自定义内容写入流。

    Returns:
        callable: 一个可调用对象，调用它即可写入流。

    Raises:
        RuntimeError: 如果当前没有活跃的流上下文。
    """
    # L1: 从 contextvars 中取出 writer
    writer = STREAM_WRITER_KEY.get()
    if writer is None:
        raise RuntimeError(
            "No stream writer found in current context. "
            "get_stream_writer() must be called from within a tool "
            "running inside an agent with stream_mode='custom'."
        )
    return writer

分析：

  • contextvars 选择：Python 的 contextvars 模块在 3.7 引入，专门解决"隐式上下文传递"问题。与 threading.local 不同，它在 async/await 切换时能正确传递上下文。
  • 为什么不是全局变量：如果 writer 是全局变量，多个并发请求会互相覆盖。contextvars 确保了每个请求的 writer 是隔离的。
  • RuntimeError 设计：在工具外部调用 get_stream_writer() 会抛出异常，这是一个好的防御性设计——明确告诉开发者"你用错了"，而不是静默失败。

3.2 StreamWriter 的写入机制

# 伪代码：StreamWriter 如何在 Pregel.stream() 中设置
class Pregel:
    def stream(self, input, stream_mode):
        modes = stream_mode if isinstance(stream_mode, list) else [stream_mode]

        # L1: 创建 StreamWriter 回调
        def _custom_writer(data):
            """Writer 内部回调：将数据作为 custom 事件发出"""
            self._emit("custom", data)

        # L2: 将 writer 设置到 contextvars 上下文
        token = STREAM_WRITER_KEY.set(_custom_writer)

        try:
            # L3: 执行 Agent
            for step_output in self._execute(input):
                if "updates" in modes:
                    self._emit("updates", step_output)
                if "messages" in modes:
                    for token_chunk in step_output.tokens:
                        self._emit("messages", token_chunk)
                # custom 不在循环中 emit，因为由 _custom_writer 回调驱动
        finally:
            # L4: 恢复上下文
            STREAM_WRITER_KEY.reset(token)

分析：

  • 回调模式：StreamWriter 本质上是一个回调函数。当工具调用 writer(data) 时，实际上是触发了 _custom_writer(data)，进而调用 _emit("custom", data)。
  • 上下文的设置与恢复：使用 contextvars.ContextVar.set() 的返回值 token 在 finally 块中恢复，确保即使 Agent 执行异常，上下文也不会泄漏。
  • custom 不在主循环中 emit：custom 事件由工具内部的 writer 调用驱动，而不是由 Pregel 的 step 循环驱动。这是它与 updates/messages 的本质区别。

3.3 _emit() — 事件分发

# 伪代码：_emit 如何产生生成器的输出
def _emit(self, mode, data):
    """根据 stream_mode 产生对应的 yield 输出。

    Args:
        mode: 事件类型 ("updates" | "custom" | "messages" | "values" | "debug")
        data: 事件数据
    """
    # L1: 如果 stream_mode 是单个字符串，直接 yield data
    if len(self._modes) == 1:
        yield data
        return

    # L2: 如果 stream_mode 是列表，yield (mode, data) 元组
    yield (mode, data)

分析：

  • 单个模式 vs 列表模式：当 stream_mode 是字符串时，直接 yield data（不需要元组包装）；当是列表时，yield (mode, data) 元组。这是消费者端需要区分处理的根本原因。
  • 设计意图：单个模式是简化版 API，列表模式是全功能版。这种"渐进式复杂度"的设计在 Python 生态中很常见（如 asyncio 的 API）。

4. 关键设计决策

决策为什么代价
使用 contextvars 而非全局变量 保证并发安全，每个请求/协程独立 增加了 API 的隐式性，对新手不直观
custom 事件由回调驱动而非主循环 custom 事件的发生时机完全由工具控制 如果工具不调用 writer，custom 流永远为空
单模式 yield data，多模式 yield (mode, data) 简化常见场景（单模式），同时支持复杂场景 消费者需要根据 stream_mode 参数类型做不同处理
RuntimeError 在无上下文时抛出 明确告知开发者使用错误，而非静默失败 要求开发者在工具外捕获异常（但通常不需要）
